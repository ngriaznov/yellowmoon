For Mykyta, 2026-10-30. Research only: this file and one row in `research/README.md` are the only changes, nothing was built into the app and no dependency was added. You asked on 2026-10-30: "Research windows specifically. No need to migrate to any new framework, just a research for now." No new framework is proposed. Where the stack has two Windows routes (DirectX 12 or Vulkan in wgpu, MSI or NSIS in Tauri) both are compared.

## 0. Short answer

1. **The core is closer to Windows than the shell is.** `cargo check --target x86_64-pc-windows-msvc` passes for `ym-raw`, `ym-color`, `ym-gpu`, `ym-core`, `ym-cli`, `ym-agents` and `ym-apple` (its stub), with no warning, and for `yellowmoon-app` (`src-tauri`) with one `dead_code` warning once two stand-ins were supplied (a C compiler for `ring`, and an `icon.ico` the repository does not have). The test targets fail in 2 files with 5 errors, all code that assumes Unix. Nothing proves it runs: a type check says nothing about libm, drivers or the webview (section 9).
2. **The blockers, in order of cost.** (a) The native viewport exists only for macOS and refuses to start without Display P3, which DirectX 12 never offers; Windows needs its own viewport and its own idea of colour (sections 3 and 5). (b) A WebView2 page and a native surface can share a window only in certain ways, and wry 0.57 hosts WebView2 only as a child window (section 3). (c) Nobody has run a kernel on Direct3D 12 or on a Windows Vulkan driver; the offline HLSL translation test is the only check of that path today (section 2). (d) Signing: an unsigned installer meets SmartScreen and, on some machines, Smart App Control (section 7). (e) A tail of 20 or so portability faults, each small (section 1).
3. **GPU, by reading wgpu.** With our `backends: None` wgpu enables every backend it was built with (Vulkan, DX12, GL on Windows) and, for one GPU exposed twice, lists the Vulkan adapter first (section 2.1). DX12 gets no pipeline cache from wgpu (Vulkan does; DX12's `create_pipeline_cache` is an empty stub), so every launch would recompile the kernels it uses (43 WGSL files in all) through FXC or DXC. Native f16 on DX12 needs DXC and shader model 6.2; the shipped path is f32 and does not need it. DX12 reports no Display P3.
4. **Viewport route.** The route with the best evidence is the one wry's own `wgpu` example uses: the wgpu surface on the top-level window and a transparent WebView2 child above it. tao 0.37.1 already leaves out `WS_CLIPCHILDREN`, which that pattern needs. It keeps the core's device (zero copies), but Tauri's Windows runtime puts a second presenter (a `softbuffer` surface) on a transparent window and ties the webview's transparency to the window's, so nothing in the evidence shows it working inside a Tauri window as configured today. DirectComposition visual hosting is the route Microsoft itself recommends against the "airspace" problem, and wgpu 30 can target a visual, but wry would have to be forked (section 3). The existing PNG-to-webview viewport already runs on Windows as it is.
5. **Colour.** Windows has no tag-the-layer equivalent of macOS. The honest choices are an sRGB viewport (the default export colour), conversion to the display's own profile or primaries in the core, or an scRGB fp16 surface. Section 5.
6. **Auto.** Default Auto, Claude Code and Antigravity have Windows installers and the crate already has Windows process code that has never run. Apple Auto stays Mac-only; the stub and the hidden row exist.
7. **Distribution.** Tauri builds NSIS on Windows, MSI (WiX v3) only on Windows. Our updater needs no `zip` feature for plain installers. Signing costs from about 10 USD a month (Azure Artifact Signing, whose eligibility for you depends on where you live) to a certificate of 150 to 300 USD a year; EV no longer gives instant reputation. CI on this public repository is free; the Windows minute multiplier of 2 would matter only for a private one.
8. **Licences.** No blocker found. `cargo deny` already sees every Windows-only crate in `Cargo.lock` (`deny.toml` has no `targets` filter). Two open items: `tools/licences/about.toml` names only the macOS targets, and a static DXC build would add a University of Illinois licence that is not on the allow list. Questions are in section 11.
9. **Size.** About 44 agent-days (range 34 to 54) for everything: a signed x64 and ARM64 app with a zero-copy viewport and display colour; 9 to 14 agent-days to a Windows `ym.exe` with CPU and GPU in CI; 21 to 32 to a signed app on the PNG viewport. The range is wide because the first run on real Windows hardware will find things this study cannot (section 10).

## 2. The GPU on Windows through wgpu

### 2.1 DirectX 12 or Vulkan: what wgpu would pick

- **Built in.** The workspace takes `wgpu = "30"` with default features (`Cargo.toml`), and wgpu's defaults are `dx12`, `metal`, `gles`, `vulkan`, `wgsl`, `webgpu` (`wgpu-30.0.1/Cargo.toml`, features) [L]. On Windows that is DX12, Vulkan and GL. `static-dxc` is a separate, off-by-default feature (same file).
- **Which is tried.** `GpuConfig::default().backends` is `None` (`ym-gpu/src/device.rs:221-222`, `:574-583`), which reads `WGPU_BACKEND` and otherwise enables all backends (`Backends::default()` is `all()`, `wgpu-types-30.0.1/src/backend.rs:140-143` [L]). `request_adapter` sorts by device type (discrete before integrated for high performance, `Other` after, `Cpu` last) with a stable sort (`wgpu-core-30.0.1/src/instance.rs:571-603` [L]), and the backends are added in the order Vulkan, Metal, DX12, GL (`instance.rs:83-90` [L]). So for one GPU that both Vulkan and DX12 expose with the same device type, **the Vulkan adapter comes first**. Whether a given Windows machine has a Vulkan driver for its GPU I could not confirm here; GPU vendors' Windows drivers normally include one (stated from general knowledge, not checked).
- **What each needs on the machine.** DX12: Windows 10 or later (`wgpu-types` backend.rs docs [L]), a driver with resource binding tier 2 or better (adapters at tier 1 are not exposed, `wgpu-hal-30.0.1/src/dx12/adapter.rs:243-250` [L]), and, if DXC compiles the shaders, shader model 6 (an adapter below it is not exposed under DXC, `adapter.rs:412-421` [L]). Dynamic DXC also needs "WDDM 2.1 (Windows 10 version 1607)" and DXC 1.8.2502 or newer (`wgpu-types` `Dx12Compiler` docs [L]). Vulkan: the vendor's ICD. A machine with neither has WARP (DX12, `DeviceType::Cpu`) and nothing else; under `GpuPolicy::Auto` that is the CPU path (`docs/17` section 1).
- **Differences that matter to us.**

  | | DX12 | Vulkan |
  |---|---|---|
  | Pipeline cache (`PIPELINE_CACHE`, K6) | not offered (the feature appears in `vulkan/adapter.rs:677` and not in `dx12/adapter.rs`) [L] | offered |
  | Shader compiler | FXC (SM 5.1) or DXC (SM up to 6.7+), see 2.2 | the driver's, from naga's SPIR-V |
  | `max_buffer_size` / `max_storage_buffer_binding_size` | `i32::MAX` / `2^31 - 1` (`dx12/adapter.rs:916-917`, `auxil/mod.rs:59`) | the driver's, also capped at `2^31 - 1` (`vulkan/adapter.rs:1723-1726`) |
  | Workgroup memory | 32,768 bytes (`dx12/adapter.rs:947`) | the driver's |
  | Display P3 on the surface | never reported (`wgpu-types` `SurfaceColorSpace::DisplayP3` docs: "Not reported on DX12") | "where the driver exposes it" |
  | `SHADER_F16` | SM 6.2 and native 16-bit ops (`dx12/adapter.rs:568-591`) | with the driver's 16-bit storage and arithmetic |
  | DirectComposition surface | yes (`SurfaceTargetUnsafe::CompositionVisual`, `Dx12SwapchainKind::DxgiFromVisual`) | no |
  | RenderDoc / PIX | PIX; RenderDoc "better support" with `DxgiFromHwnd` | RenderDoc |
  | Storage-buffer budget | per stage up to 16 for tier 2 (`dx12/adapter.rs:817-825`) | far more | 

  Our design limits fit both: 128 MiB bindings (`docs/17` section 4) against 2 GiB, 16 KiB workgroup memory (K2) against 32 KiB, at most 8 storage buffers plus 1 uniform (K3) against 16. The 4 GiB buffer the device asks for (`device.rs:635`, `min(adapter.max_buffer_size, 1 << 32)`) is clamped to 2 GiB − 1 on DX12; no kernel binds more than 128 MiB, and the pool holds many buffers.
- **Recompilation on every launch.** The 43 WGSL files (9,943 lines) are translated and compiled when first used. On Metal the same is true and `docs/17` section 15 already lists "first-launch compile time" as a Mac check. On DX12 the cost is FXC or DXC, and wgpu offers no cache. Vulkan has one, and `default_pipeline_cache_dir` (`device.rs:279-291`) would need the `HOME` fix first. I found no number for either.
- **Recommendation to test, not a decision.** Restrict the backends on Windows to `VULKAN | DX12` (GL gives an `Other`-typed adapter that sorts after real GPUs but is the worst place to land), leave Vulkan first because that is what wgpu does anyway, and keep DX12 as the fallback and the second CI leg. Let `YELLOWMOON_GPU` and `WGPU_BACKEND` stay the switches (`docs/17` section 1).

### 2.2 How naga's HLSL is compiled: FXC, DXC, and static DXC

- **How wgpu 30 chooses.** `Dx12Compiler` is `Fxc`, `DynamicDxc { dxc_path }`, `StaticDxc` or `Auto` (the default). `Auto` uses static DXC if the crate was built with `static-dxc`; otherwise it tries to load `dxcompiler.dll` (by that bare name, so the normal DLL search order); if that fails it loads FXC (`d3dcompiler_47.dll`, part of Windows). `WGPU_DX12_COMPILER=fxc|dxc|staticdxc` overrides (`wgpu-hal-30.0.1/src/dx12/instance.rs:53-96`, `wgpu-types` `backend.rs:777-840` [L]; the doc comment on `Fxc` that calls it "the default" is stale, `Auto` has `#[default]`). Whether a stock Windows 10 or 11 installation has a `dxcompiler.dll` on that search path I could not confirm; if not, `Auto` means FXC.
- **What the two are given.** FXC: `D3DCOMPILE_ENABLE_STRICTNESS` only, and the HLSL is written for SM 5.1 (`shader_compilation.rs:222-240`, `adapter.rs:391-437` [L]). DXC: `-HV 2018 -no-warnings` and `DXC_ARG_ENABLE_STRICTNESS`, plus `-enable-16bit-types` when `SHADER_F16` or `SHADER_I16` is on; default optimisation (`O3`); no `-Gis`; no `-denorm` (`shader_compilation.rs:365-420` [L]; DXC's defaults are `O3` and `-denorm any`, from DXC's `HLSLOptions.td` [read], https://github.com/microsoft/DirectXShaderCompiler/blob/main/include/dxc/Support/HLSLOptions.td). naga's HLSL writer emits `precise` only for an invariant vertex position (`naga-30.0.1/src/back/hlsl/writer.rs:581`) and writes `fma()` as `mad` (`writer.rs:3168`) [L]; our kernels never call `fma()` (D6).
- **The static option and its licence.** `static-dxc` pulls `mach-dxcompiler-rs` 0.1.4 on `cfg(all(windows, not(target_arch = "aarch64"), target_env = "msvc"))` (`wgpu-hal` `Cargo.toml:299-302`), so it does not exist on Windows ARM64 (the `StaticDxc` docs say so too) and assumes shader model 6.7 (`shader_compilation.rs:76-92`) [L]. `mach-dxcompiler` is a Zig build of DXC, marked experimental, in an organisation named "hexops-graveyard", licensed Apache-2.0 and MIT, and says it has "zero dependency on proprietary dxil.dll code-signing blob" [read], https://github.com/hexops/mach-dxcompiler. DXC itself is under the University of Illinois Open Source License [read], https://github.com/microsoft/DirectXShaderCompiler, a licence that `deny.toml` does not allow (it is "NCSA" in SPDX terms; whether the embedded library would show up in `cargo deny` at all depends on how the crate declares it, which I did not check). I did not check whether `mach-dxcompiler-rs` builds DXC or downloads a prebuilt library. The dynamic route ships two Microsoft DLLs next to the exe: DXC's README calls `dxil.dll` "a DLL providing the DXIL validation and hashing support" and "the dxil.dll signing binary" and lists the Windows SDK and the GitHub release as sources [read], same URL. Redistribution terms of `dxil.dll` are not on that page; they are a question for you (section 11). The latest DXC release at the time of writing is v1.9.2609 of September 2026, with a Linux archive [read], https://github.com/microsoft/DirectXShaderCompiler/releases/latest.

### 2.3 DXC's floating point against K8

K8 (`docs/17` section 6) asks that a kernel hold under strict IEEE and under a compiler that fuses, re-associates, uses reciprocal division and approximate square roots. `docs/17` section 13 models Metal with clang and replays the dispatches a lavapipe run records.

- **What D3D12 compilers do by default.** HLSL gives the compiler leave to reorder and fuse anything not marked `precise`; Microsoft's HLSL team describes `/Gis` as "marks everything as precise" and `precise` as meaning "computations should behave as spelled by the program, without any optimizations that might reorder them, and that denorms, NaNs and INFs should be honored strictly", with an example where a `mul` and an `add` are not fused under `precise` [search], https://learn.microsoft.com/en-us/archive/blogs/marcelolr/precise-and-ieee-strictness-in-hlsl. DXC offers `-Gis` ("Force IEEE strictness"), `-denorm` ("any is the default") and `-ffinite-math-only` (opt in); its `-ffp-contract=` option is commented out in the options table [read], `HLSLOptions.td` above. wgpu passes none of them. So both FXC and DXC, as wgpu calls them, are in the "fast" family: `mad` fusion and reordering are allowed, denormals may be flushed (`-denorm any`), and the GPU driver's own compiler then does what Metal's does. That is the situation K8 was written for.
- **Would the OR barrier hold?** The barrier is `bitcast<f32>(bitcast<u32>(x) | zero)` with `zero` a uniform word (`docs/17` K8). In HLSL it becomes `asfloat(asuint(x) | z)`. A compiler cannot fold an integer OR with a run-time value it does not know, whether the compiler is FXC, DXC (LLVM) or a driver's backend, and the product that feeds it cannot be fused into the sum after it, because an integer operation sits between. The reason it held on Metal (an OR is idempotent where an XOR pair cancels) is independent of the backend. The exact division and square root are integer arithmetic (`ar_div`, `sharpen_sqrt`, `fc_sqrt`, `bm_sqrt`) and the logarithm and exponential are the kernels' own (`lg_log2`, `bm_exp2`), so no `/`, `sqrt`, `log2` or `exp2` of the device enters a pinned result. I expect them to hold; that is a prediction from the construction, not a result.
- **What is not covered.** Kernels that deliberately avoid the barrier (the cine rendering, `docs/17` section 13 "Cine rendering") rely on the stated fact that the compiler does not distribute a product over a difference; the same assumption is untested for DXC. Built-in `pow`, `exp`, `sin` and friends in non-pinned kernels have vendor-specific accuracy on D3D12 as on Vulkan; they are inside the stated tolerances because those tolerances were set against lavapipe and Metal, not because anyone measured D3D12. `-denorm any` lets a driver flush denormal results; the kernels' arithmetic on values near 1e-38 is not something the parity suites target.
- **How to check without a Windows GPU.** The same method as for Metal, in two steps. (1) A test that is already there: `crates/ym-gpu/tests/shaders_naga.rs:56-68` translates every kernel to HLSL at SM 5.1 and 6.2 against `Capabilities::empty()`. (2) New, offline and cheap: compile that HLSL with DXC from its Linux release (the release page lists a Linux archive; I did not download it) with `-T cs_6_2` at `-O3`, and read the DXIL disassembly (`-Fc`) for the pinned kernels: the products that meet sums must not appear fused (no `fmad` / `dx.op.tertiary` form) and the barrier must survive. Do the same with `-Gis` as the strict twin and replay the dispatches a lavapipe run records through a DXIL interpreter if one exists; I know of none, so the modelling stops at "the compiler did not fuse". That checks DXC's front half. Neither FXC (Windows only) nor any vendor's backend can be checked this way, so the final test is the parity suites on real D3D12 and Windows Vulkan hardware (section 10, stage 1).

### 2.4 `shader-f16` on DX12

In wgpu 30 `SHADER_F16` is exposed on DX12 only when the shader model is at least 6.2 **and** `D3D12_FEATURE_DATA_D3D12_OPTIONS4.Native16BitShaderOpsSupported` is true (`dx12/adapter.rs:566-591` [L]). The shader model is above 5.1 only when DXC is in use (`adapter.rs:391-437` [L]), so with FXC (the fallback of `Auto`) there is no native f16 at all. Microsoft's documentation says native 16-bit operations need shader model 6.2 and that drivers are not required to implement them [search], https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_d3d12_options4 and [read] https://github.com/microsoft/DirectXShaderCompiler/wiki/Shader-Model-6.2. **I found no published share of Windows GPUs with the flag**, and the Steam survey does not report it; I will not guess one. What matters for us: `StoragePreference::Auto` resolves to f32 on every device (`device.rs:596`; `docs/17` section 2), the f16 modes are `Force`-only for legacy kernels and their tests, and `pack2x16float` packing is a downlevel capability that every DX12 adapter has. A Windows machine without native f16 loses only the legacy-mode tests, which already skip (`docs/13`).

### 2.5 The watchdog (TDR)

Windows resets a GPU that does not answer the scheduler's preempt request in time. `TdrDelay` defaults to 2 seconds [search], https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys, https://www.pugetsystems.com/labs/hpc/working-around-tdr-in-windows-for-a-better-gpu-computing-experience-777/; Intel's guidance for compute says the same, and Microsoft says end users should not edit the keys. `docs/17` K5 designs every job for it ("about 30 ms on an M1 is the design figure"). What we have: the Mac figure is the design figure and nothing was measured on any GPU; on lavapipe, a CPU emulation, a chain tile takes 2.2 s on average and 4.3 s at the longest, and one step of the reduced group (the σ plane) 5.9 s (`docs/05` "Measured on Mesa lavapipe"), which says nothing about a GPU. A GPU job is a tile times a stage group, but the watchdog counts a single submission's non-response, and a job may be several dispatches; the heaviest single dispatches are the block-matching/3-D DCT passes (one workgroup of 256 threads per reference block, `docs/17` section 11) and the 289-tap lens gather. On a recent GPU the margin is wide. On a slow integrated GPU I cannot tell: if such a part is 10 times slower than an M1 the design figure becomes 300 ms, still far from 2 s. The failure mode is covered: a reset loses the device, `set_device_lost_callback` marks it (`device.rs:665`), the context is rebuilt at most twice and then the GPU is off with one note (`docs/17` section 9). **The check to ask for:** `ym doctor --bench` with `TIMESTAMP_QUERY` (offered on DX12 and Vulkan hardware) on the cheapest Windows machine you can borrow, and read the longest pass of each kernel.

### 2.6 Discrete GPUs against the unified-memory rule

`MemoryBudget::for_unified_memory` applies to `DeviceType::IntegratedGpu` (`scheduler.rs:120-136`; `docs/17` section 8). On DX12 that type is set from `D3D12_FEATURE_DATA_ARCHITECTURE.UMA` (`dx12/adapter.rs:196-203` [L]); Vulkan reports its own. So an Intel or AMD integrated GPU gets `clamp(RAM/4, 512 MiB, 4 GiB)` and the 0.6 × RAM ceiling, as Apple silicon does. A discrete GPU keeps 4 GiB and 6 GiB, whatever its VRAM: a card with 4 GB or less gets a 4 GiB budget it cannot hold. On Windows an allocation beyond dedicated memory does not necessarily fail; it can be paged to system memory, with a large slowdown. wgpu 30 has the tool for this: `InstanceDescriptor::memory_budget_thresholds` with `for_resource_creation` and `for_device_loss` as a percent of the budget the OS reports, "currently only the D3D12 and (optionally) Vulkan backends" (`wgpu-types-30.0.1/src/instance.rs:337-351` [L]). Using it would turn paging into the existing `OutOfBudget` path (retry once, then the CPU, `docs/17` section 9). Hybrid laptops add a second effect: the high-performance GPU renders and the integrated GPU drives the display, so a zero-copy present crosses adapters inside the driver; that cost is not ours to remove.

### 2.7 WARP, lavapipe and SwiftShader in CI

Two Microsoft posts disagree on its shader model: the inbox WARP supports "only up to shader model 6.2", and a downloadable preview adds 6.7 [search], https://devblogs.microsoft.com/directx/announcing-warp-preview-with-shader-model-6-7-support/. wgpu's own CI installs WARP with a composite action, and also installs Mesa, the Vulkan SDK, DXC and the Agility SDK on `windows-2022` [read], https://github.com/gfx-rs/wgpu/blob/trunk/.github/workflows/ci.yml, which sets `WGPU_DX12_COMPILER: dxc`; the page does not show how an adapter is chosen. wgpu can select WARP: `force_fallback_adapter` filters to `DeviceType::Cpu` (`wgpu-core` `instance.rs:511-525` [L]), and our `pick_adapter` tries it second. The Linux `gpu-lavapipe` job has a 100-minute limit and was measured at about 55 minutes before its last step (`ci.yml:152`, comment); a hosted Windows runner with two or four vCPUs running Mesa's llvmpipe should be of the same order, and WARP's kernels are not what lavapipe's are, so a first run would need its own timeout.
- **Mesa on Windows.** wgpu's CI proves it can be installed on a Windows runner (above). I did not look for the build it uses.
- **ARM64.** Windows ARM64 hosted runners exist and are free for public repositories (`windows-11-arm`, 4 vCPU; generally available since 2025-08-07) [search], https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/. I found no wgpu issue about Adreno. An x64 `ym.exe` also runs under Windows' emulation, but a GPU kernel under emulation goes through the driver as usual and the CPU path is slower; the ARM64 build is the proper one (Tauri builds it with `--target aarch64-pc-windows-msvc`, and its NSIS installer stays x86 under emulation) [read], https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/distribute/windows-installer.mdx.

## 3. The native viewport on Windows

Today (`docs/01` "Native viewport"; `native.rs`): a plain `NSView` behind a transparent webview, a surface made from the core's own `wgpu::Instance`, the core's RGBA8 buffer drawn by a full-screen triangle (zero copies), Display P3, the page transparent where the photo is. HTML overlays (look chip, camera line, Before label, ⌥ readout, crop frame, pick crosshair, zoom menu) sit **above** the photo. That last fact is the constraint everything below must meet.

**What Tauri 2, wry and WebView2 give us** (tao 0.37.1, wry 0.57.0, tauri 2.12.3 [L]):
- wry hosts WebView2 in **windowed** mode: a container `HWND` with `WS_CHILD | WS_CLIPCHILDREN` under the top-level window (`wry-0.57.0/src/webview2/mod.rs:230`), created through the HWND controller. There is no `CompositionController` anywhere in the module (1,938 lines); a search of wry's issue tracker for "composition" found no issue asking for it [read], https://github.com/tauri-apps/wry/issues?q=is%3Aissue+composition (a title search only).
- Transparency: with `transparent`, wry sets the WebView2 `DefaultBackgroundColor` to alpha 0 (`mod.rs:127,464-466`). Microsoft: with a fully transparent default colour "WebView will render hosting app content as the background", only alpha 0 and 255 are accepted, and a page that paints an opaque background hides it [search], https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller2. tao makes a transparent top-level window with `DwmEnableBlurBehindWindow` and an empty region (`tao-0.37.1/src/platform_impl/windows/window.rs:1203-1215`), and a Tauri project reported that this costs performance on Windows (per-pixel alpha composition) [search], https://github.com/athasdev/athas/pull/728.
- tao leaves `WS_CLIPCHILDREN` off the top-level window: its style is `WS_CAPTION | WS_CLIPSIBLINGS | WS_SYSMENU` (`window_state.rs:241`) after the change "fix(windows): remove `WS_CLIPCHILDREN` from window style" (tao PR #839, November 2023: "when setting the webview to be transparent, the portion of the parent behind it doesn't render properly") [read], https://github.com/tauri-apps/tao/pull/839.
- Input: windowed hosting gets mouse and keyboard from the OS; visual hosting leaves them to the host [search], https://learn.microsoft.com/ja-jp/microsoft-edge/webview2/concepts/windowed-vs-visual-hosting.
- Our config: `transparent: true`, `backgroundColor: #0f0f10` (`tauri.conf.json:24-25`). Two facts from Tauri's source matter for a native surface on the main window. (1) `WebviewWindowBuilder::transparent` sets the window's and the webview's transparency together (`tauri-2.12.3/src/webview/webview_window.rs:1146-1151` [L]), so "opaque window, transparent webview" is not a setting of the config file; it would take the window and webview builders used apart, and I did not find that Tauri 2 offers this outside its `unstable` multi-webview API. (2) On Windows, a transparent Tauri window gets a `softbuffer` surface on the same `HWND`, painted with `backgroundColor` on every `RedrawRequested` (`tauri-runtime-wry-2.12.1/src/lib.rs:4005-4012,4140-4148` [L]); that is how the paper colour shows behind the page. It is a second presenter on the window, and a wgpu swapchain on that `HWND` would collide with it unless the window stops being transparent.

**How others do it.** Microsoft's answer to native content and web content overlapping is visual hosting: "WebView2 is always displayed on top, hiding any WPF elements" in the HWND control, and `WebView2CompositionControl` is the replacement that stops it being topmost [search], https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/wpf and https://learn.microsoft.com/en-us/answers/questions/1182308/webview2-overlap-other-wpf-controls (the WPF feedback item #286 is named there; I did not open it). wry's own `examples/wgpu.rs` puts a wgpu surface on a transparent winit window with clip-children off and a 200 × 200 transparent webview above it, clearing to `Color::TRANSPARENT` (`wry-0.57.0/examples/wgpu.rs:160-185` [L]). I found no Tauri 2 sample that renders wgpu behind a transparent webview on Windows [search].

### The routes

| Route | What it is | Zero copies? | Overlays above the photo? | Cost and risk |
|---|---|---|---|---|
| **A. Surface on the top-level window, transparent WebView2 above** | `SurfaceTargetUnsafe::RawHandle` with a `Win32WindowHandle` of the Tauri main window, made from the core's instance as `surface_for` does for the `NSView`; the sink draws paper everywhere and the photo in the cell; the page is transparent over the cell | yes, on the core's device (the device frame is bound as a storage buffer exactly as in `native.rs`) | yes, they are page elements above a transparent region | Medium to high. Evidence: wry's example, tao's `WS_CLIPCHILDREN` change. Against it: a DXGI swapchain on the HWND is opaque (`Dx12SwapchainKind::DxgiFromHwnd` "does not support transparency", `wgpu-types` `backend.rs:675-692` [L]); a Tauri window with `transparent: true` is composed through DWM's blur-behind trick and carries a `softbuffer` presenter (section 3, "Our config"); and Tauri ties the webview's transparency to the window's. So the spike must find out whether a Tauri window can be opaque with a transparent WebView2 at all, or whether the window has to be created another way (a `tao` window of our own, or wry's example pattern outside Tauri's runtime, which is a large change). The whole client area is presented at every frame (about 20 MB of BGRA8 at 2880 × 1800, on the GPU); resize must keep the swapchain and the webview in step; `desired_maximum_frame_latency` as today. DX12 and Vulkan differ in how they present into a window with child windows; both need a try. |
| **B. DirectComposition visual hosting** | WebView2 as a composition controller in a visual tree we own, the wgpu surface as `SurfaceTargetUnsafe::CompositionVisual(IDCompositionVisual)` below it; premultiplied alpha is real (`SurfaceTarget::Visual` reports `PreMultiplied` and `PostMultiplied` alpha modes, `dx12/adapter.rs:1364-1380` [L]) | yes | yes, with true alpha | High. wry 0.57 has no composition controller, so wry's `webview2` module (1,938 lines: controller creation, resize, DPI, focus, input forwarding, drag and drop, IME, accessibility) would be forked or replaced, and Tauri's runtime sits on top of it. DX12 only; Vulkan cannot target a visual (the variant is `#[cfg(dx12)]`, `wgpu-30.0.1/src/api/surface.rs:438-444`). Closest to what Microsoft recommends. Mac keeps its own code, so two viewport worlds |
| **C. Frames to the webview (exists)** | `FallbackSink`: each frame read back, encoded as PNG with a P3 profile, served as `http://ym-frame.localhost/…` | no: a 24 MB readback (3000 × 2000 cell, `docs/17` section 16) plus encode and decode per frame | yes, it is an `<img>` | None to build: it is what Linux development builds use today. Slowest of the three, and it is the route whose speed `docs/01` already names as the thing to measure (M0-H4). It could be made cheaper (raw RGBA into a canvas, or WebView2 shared buffers through `with_webview`) without leaving Tauri; I did not check the shared-buffer API |
| **D. Child HWND for the cell, under the page** | a second HWND sibling beneath the WebView2 container | yes | only if the transparent page composes over it | Not recommended. I found no evidence it works: the sources are about a parent surface (A) or visual hosting (B). The sibling case is the "airspace" problem |

**Which route keeps zero copies?** A and B, on the core's device. **Which I would try first:** A, as a spike of a few days, because the pieces are in the versions we already ship and the macOS sink's drawing code carries over; the spike's first question is the one above (an opaque window with a transparent WebView2 inside Tauri), its stop condition is one afternoon on a real machine showing the page and the photo composing cleanly through a window resize and a move between monitors. If A fails, B is the principled route and the largest piece of work in this study; C is the floor. **Windows without the zero-copy path is not a regression:** the product works on route C today in the sense that the code runs; its frame rate on Windows is unmeasured.

The macOS parts that depend on `NSView`: the colour check at `native.rs:535-545` must go (section 5); the `data-native-viewport` rules and `PAPER_SRGB` logic in the page are platform-neutral and carry over; `viewport_info` already tells the page which backend draws.

Terms: the **SDK** (`Microsoft.Web.WebView2`) is under a BSD-style licence [search], https://www.nuget.org/packages/Microsoft.Web.WebView2/1.0.1243-prerelease/license; the **Runtime** has its own Microsoft Software License Terms, and I could not confirm what they allow for redistribution [search], https://open.windriver.com/info/uni-license-list/licenses/ms-edge-webview2.html. - **The dark glass look.** The look is CSS `backdrop-filter` (31 uses in `src/styles/glass.css:504-553` and `glass-c2.css:625`). Chromium has supported it since version 76 [search], https://web-platform-dx.github.io/web-features-explorer/features/backdrop-filter, and WebView2 tracks Chromium, so the effect exists. Whether 12 to 28 px blurs over a still aurora are cheap in WebView2 on integrated GPUs is not something I could find a source for; it is a spot-check on the lowest-end machine. Mica and Acrylic would blur the **desktop**, not our aurora; the glass design blurs the aurora (`docs/11`), so no window effect is needed, and the screenshots in `design/screenshots-c2/` are of that. If you ever wanted one: Mica is Windows 11 only, Acrylic and Blur work on Windows 10 1809 and later but "lag when resizing or dragging" on Windows 10 1903+ and Windows 11 22000, and the crate is `window-vibrancy` 0.8.1 (Apache-2.0 OR MIT, already in the lock through Tauri) [search], https://docs.rs/window-vibrancy/latest/src/window_vibrancy/lib.rs.html and https://docs.rs/tauri-utils/2.9.3/tauri_utils/enum.WindowEffect.html; the interactive-glass note in `tauri-utils` says it affects Blur and Acrylic only on Windows 10 1903+ (`config.rs:1882-1885` [L]).
- **Title bar.** `titleBarStyle: Overlay` and `hiddenTitle` are Mac options; on Windows the window gets the system frame with its light or dark caption and a title, over a 1440 × 900 layout that assumes no title bar (`docs/11:26`). The choice: keep the system frame (cheap, native snap behaviour, a visible seam against the dark glass), or `decorations: false` with minimise, maximise and close buttons drawn in the page and `data-tauri-drag-region` (already on the header, `Header.tsx:45`; `core:window:allow-start-dragging` is granted). tao offers `set_undecorated_shadow` for the frameless case (`tao/src/platform/windows.rs:183`) [L]. The 84 px of left padding for traffic lights (`app.css:23-30`) must be conditional. Windows 11's snap-layout flyout on the maximise button belongs to the native caption; with page-drawn buttons it is lost (stated from general knowledge, not checked).
- **Shortcuts and menus.** Section 1. muda draws a menu bar under the title bar on Windows, 20 px or so that `docs/11`'s layout does not have; the options are to keep it, to hide it and show it on Alt, or to drop it on Windows and use the page's own controls. The "Yellowmoon" app menu (About, Preferences, Quit) has no Windows equivalent.
- **HiDPI and per-monitor DPI.** tao sets the process DPI awareness through `SetProcessDpiAwarenessContext` when available (`tao-0.37.1/src/platform_impl/windows/util.rs:305-309` [L]); `viewport_set_rect` already carries `scale` (`docs/01`). The case to test is a window dragged between monitors of different scale: the cell's device size changes and the core must be told (ResizeObserver does it for size, not for a scale-only change; check).
- **Full screen, dialogs, drop.** `set_fullscreen` is cross-platform and its capability is granted (`capabilities/default.json`). File dialogs: `tauri-plugin-dialog` 2.8.2 with `rfd` 0.16.0 (`Cargo.lock`), which uses the system dialogs on Windows (not verified here). - **Paths and locking against rule 5.** Rust's standard library adds the `\\?\` prefix itself when an absolute path reaches the legacy 260-unit limit [search], https://rust.googlesource.com/rust/+/HEAD/library/std/src/sys/path/windows.rs, so our file I/O is not limited; Explorer, the dialogs and some tools are. Paths compare case-insensitively on NTFS; the exporter's file identity falls back to `canonicalize` off Unix (`ym-core/src/export.rs:589-606`), which returns the on-disk spelling. Reading an original never writes (rule 5). Rust opens files with all three share modes by default (stated from the standard library's documentation, not re-fetched), so reading a file another program has open is allowed and an editor that holds it without sharing is not our problem; the export side is: a "Replace" over a file open in a viewer fails and should say so. Photos on OneDrive "files on demand", cards and MTP devices are the places a read may stall or fail; no code of ours is specific to them. Device names (`CON`, `NUL`) and trailing dots were covered in section 1.

## 5. Colour on the display

**What exists.** Viewport frames are Display P3 (`OutputTarget::Viewport`, `ym-color/src/display.rs:100-109`), tagged on a Metal layer; the fallback viewport ships PNGs with a P3 profile; `WarpPlane.tsx:75-83` already asks the canvas for `display-p3` and falls back to sRGB. The default export is sRGB (`docs/16`: "An sRGB-only photo view is acceptable if a toolkit cannot show Display P3, because the default export is sRGB").

**What Windows does.**
- **Default.** Windows composes SDR content as sRGB unless the app says otherwise. On a wide-gamut monitor an unmanaged sRGB app is shown with the monitor's native primaries (oversaturated). Windows 11's *Auto Color Management* manages SDR apps for such displays: "ACM prevents SDR apps from looking unnaturally vivid on wide-gamut monitors", and apps that manage colour themselves can keep targeting the native gamut; it began on selected displays in the 2022 update and was widened later, with a switch "Automatically manage color for apps" in the advanced display settings [search], https://devblogs.microsoft.com/directx/auto-color-management and https://pureinfotech.com/enable-new-auto-color-management-acm-windows-11/. I could not confirm whether it is on by default, or how it treats ICC profiles.
- **The display's profile.** The Windows Color System keeps a default profile per display. The routes I know are `GetICMProfile` and `WcsGetDefaultColorProfile`; I did not find a documentation page for them in this session [not confirmed]. An independent source of the display's primaries is `IDXGIOutput6::GetDesc1`, whose `DXGI_OUTPUT_DESC1` carries `RedPrimary`, `GreenPrimary`, `BluePrimary`, `WhitePoint`, luminance and `ColorSpace` ("usually from the EDID of the corresponding display or sometimes from an override") [search], https://learn.microsoft.com/en-us/windows/desktop/api/dxgi1_6/ns-dxgi1_6-dxgi_output_desc1. wgpu-hal itself reads it to classify gamut (`wgpu-hal` `auxil/dxgi/hdr.rs`, quoted in the same search). Our code only writes ICC profiles; reading one is new code (a matrix and curve profile is a few hundred lines; the `moxcms` crate that `image` already pulls in, MIT or Apache-2.0, is the alternative).
- **HDR and Advanced Color.** In HDR mode Windows composes in scRGB; an app presents either an fp16 swapchain in scRGB or a 10-bit one in BT.2100 PQ. The wgpu surface formats on DX12 are `Bgra8UnormSrgb`, `Bgra8Unorm`, `Rgba8UnormSrgb`, `Rgba8Unorm` (sRGB), `Rgb10a2Unorm` (sRGB or BT.2100 PQ) and `Rgba16Float` (extended sRGB linear, i.e. scRGB); never Display P3, HLG, encoded extended sRGB or extended P3 (`dx12/adapter.rs:1322-1362`, `wgpu-types/src/surface.rs:242-420` [L]). Vulkan offers sRGB, Display P3, PQ, HLG and the extended spaces "where the driver exposes" them. `Auto` never resolves to a wide-gamut or HDR space, except linear scRGB for `Rgba16Float` (`SurfaceColorSpace::Auto` docs [L]). "HDR/EDR is V2" (`docs/01`) stays out of scope.
- **The webview.** Chromium converts content to the display's colour space; on Windows that uses the monitor profile by default according to forum reports, and the `--force-color-profile` switch overrides it [search], https://chromium.googlesource.com/chromium/src/+/ceb8727d80e9ddd671577494ddeb1c182645833e%5E%21. Nothing I found says how WebView2 treats it; if Chromium converts and a native swapchain does not, the photo and its thumbnails would not agree on a profiled wide-gamut monitor. That is a visible risk, not a measured one.

**What the viewport would do in place of Display P3** (decision for you; costs, not a recommendation):

| Option | What it does | Cost |
|---|---|---|
| 1. sRGB frames (`OutputTarget::Srgb`, which thumbnails and exports use) | Right on sRGB monitors and under ACM; oversaturated on a wide-gamut monitor without ACM | One line in the sink's configuration plus the check at `native.rs:535-545`; `docs/01` Native viewport point 4 changes |
| 2. Frames converted to the display's profile or primaries in the core | Correct on any profiled or EDID-described display, and agrees with the page if Chromium converts too | A new output target with a 3×3 and curves per display, a kernel parameter, a profile reader, a monitor-change listener; 4 to 7 agent-days |
| 3. scRGB fp16 surface (`ExtendedSrgbLinear`) with P3 content expressed as scRGB | Windows maps it to the display, with wide gamut when Advanced Color is on | Doubles the surface bandwidth and adds a pass; behaviour on an SDR display outside HDR mode is something I could not confirm |

The honest default is option 1 first, since the core already makes sRGB, with option 2 as a later stage once a wide-gamut Windows monitor can be put in front of you. Gamut mapping to sRGB loses the part of P3 outside it; the macOS app shows that part.

- **`PATH` and shells.** `docs/22` already specifies the Windows rules: known folders first (`%USERPROFILE%\.local\bin\claude.exe`, WinGet links, `%APPDATA%\npm`), then `PATH` through `which` with `PATHEXT`, and **no login-shell probe on Windows** (that step is Unix only); a `.cmd`, `.bat` or `.ps1` is never started and `cmd /C` never used (CVE-2024-24576), the real `claude.exe` is looked for next to a `claude.cmd` (`docs/22` section 4, "The login shell, macOS and Linux only"). A GUI app started from Explorer gets the user's environment, so the Finder problem that made the known-folder step necessary on Mac matters less.
- **Processes.** `process-wrap` with `JobObject` and `CREATE_NO_WINDOW`, `TerminateJobObject` on cancel (`docs/22` section 15.7; `process.rs:905`). The limit `docs/22` records: the crate's job is made without `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so **a Windows process that ends without cancelling leaves the child running**; Ctrl-C and quit go through `cancel()`, a crash or Task Manager does not. Setting the flag needs a job object of our own, nested over the crate's. `ym`'s Ctrl-C uses the `ctrlc` crate (`runtime.rs:87`), which handles console control events on Windows. Closing a console window or logging off are other events (`CTRL_CLOSE_EVENT`) that I did not check the crate for.
- **Never run on Windows.** The test doubles, the job-object code and the `.cmd` rule have been type-checked for Windows (`docs/22` section 15.7: `ym-agents` and `ym-cli` on 2026-10-26; this study repeated it, section 9) and executed nowhere. `agents.yml` has no Windows leg since 2026-10-29 ("no windows for now", STATUS Question 31). Re-adding it is one line and needs no hardware.
- **On-device Windows options (facts only, not a proposal).** The Windows AI APIs, including Phi Silica, need a Copilot+ PC (an NPU rated 40+ TOPS, 16 GB+ RAM; Snapdragon X, Intel Core Ultra 200V, AMD Ryzen AI 300), though Phi Silica on a GPU also runs on some non-Copilot+ Windows 11 PCs with a supported NVIDIA or AMD GPU; the app must be packaged (MSIX or sparse identity) [search], https://learn.microsoft.com/windows/ai/windows-ai-comparison. Windows ML is the ONNX Runtime-based runtime for your own models on CPU, GPU or NPU (same page). I did not find whether Phi Silica works fully offline, its redistribution licence, or whether it needs a network at first use. A packaged-identity requirement would not fit an NSIS installer.

[read], https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/distribute/windows-installer.mdx. For a free app with an in-app updater and no administrator, **NSIS per-user** is the natural pick; MSI matters for managed fleets and Group Policy. The `ym` sidecar is a target-triple-suffixed file in `src-tauri/binaries/` (`ym-x86_64-pc-windows-msvc.exe`), per the sidecar page [read], https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/develop/sidecar.mdx; where it lands in the install folder the page does not say.

### 7.2 The updater

- **Platforms and files.** `latest.json` keys are `OS-ARCH` (`windows-x86_64`, `windows-aarch64`); with `createUpdaterArtifacts: true` the NSIS and MSI installers themselves are the artefacts, each with a `.sig`; `"v1Compatible"` makes `.zip` archives and "will be removed in v3"; `installMode` is `passive` (default), `basicUi` or `quiet`; signing "cannot be disabled" and uses `TAURI_SIGNING_PRIVATE_KEY` [read], https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/updater.mdx. **The minisign key we have works as it is**: the same key pair signs every platform's artefact.
- **No `zip` feature needed.** `Cargo.toml` builds the updater without its `zip` feature, with a comment that it "serves only Windows installers". In `tauri-plugin-updater` 2.13.3 the Windows path extracts a zip only under `feature = "zip"`; otherwise `extract_exe` accepts an `.exe` or an `.msi` as it is (`src/updater.rs:1049-1105` [L]). So the plain installers need no change; only a `v1Compatible` zip would.
- **What the release workflow lacks.** Step 7 of `release.yml` writes `darwin-aarch64` and `darwin-x86_64` only, in a macOS job (`docs/12`). Windows needs its own job (or a final job that merges), and `latest.json` must carry the new keys with signatures before any Windows build can update itself. The update restart is the app's own `restart_app` command (`docs/12`), cross-platform.
- **Windows replaces a running exe's installer in a separate process**, with the app closing while the NSIS installer runs; the "an update never interrupts an export" rule (`docs/12`) holds because the shell refuses the restart.

### 7.3 Code signing

- **The Mac comparison.** The Mac app is signed ad hoc with no Developer ID; macOS asks once before the first open, and the README explains it (`docs/12` Signing). Windows has an equivalent first-run prompt, SmartScreen, but also a stricter one:
- **SmartScreen.** "EV certificates no longer bypass SmartScreen"; reputation is per file hash, so every new build starts from zero, and an OV certificate is "just as effective" as EV for it; Store distribution avoids the warning [search], https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation, https://knowledge.digicert.com/alerts/ev-signed-application-showing-microsoft-defender-smartscreen-warnings, https://www.todesktop.com/blog/posts/windows-apps-psa-ev-certs-do-not-grant-immediate-reputation-anymore, https://textslashplain.com/2024/11/15/best-practices-for-smartscreen-apprep/. **Smart App Control** (Windows 11) "will block execution of unsigned files unless the file has a positive reputation" and checks signatures of code loaded by the OS loader, and does not support ECC signatures [search], same sources. An unsigned Yellowmoon may therefore be blocked outright on a machine where Smart App Control is on, with no "Run anyway". That is a harder wall than macOS's Open Anyway.
- **Options.**

  | Option | Cost | Notes |
  |---|---|---|
  | Unsigned | 0 | SmartScreen warning on every new build; Smart App Control may block. The updater's own check (minisign) is unaffected |
  | OV certificate (a CA of your choice) | I saw "$150 to $300 a year" in an AI-generated forum answer [search], https://learn.microsoft.com/en-us/answers/questions/5810735/cant-create-a-new-trusted-signing-individual-ident; unconfirmed | A hardware token or a cloud HSM is normally required for new code-signing certificates (stated from general knowledge); identity validation takes days; Tauri supports `certificateThumbprint` or a `signCommand` [search], https://v2.tauri.app/distribute/sign/windows/ |
  | EV certificate | more than OV; no price found | No reputation advantage any more (above) |
  | Azure Artifact Signing (formerly Trusted Signing) | Basic plan 9.99 USD a month for 5,000 signatures, 0.005 USD per extra [search], https://azure.microsoft.com/pricing/details/artifact-signing/ (the page shows placeholder prices; the figure is from the search summary) | **Individuals: "currently limited to the USA and Canada"**, and a March 2026 Q&A says onboarding was narrowed further during the public preview; organisations' eligibility I could not confirm [search], https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options. Needs an Azure subscription. Signs through a `signCommand` (`trusted-signing-cli`), which the official Tauri page does not cover (it documents OV and Azure Key Vault with `relic`) |
  | Microsoft Store (MSIX) | a developer account fee I did not look up | Avoids SmartScreen; needs a packaged app and Microsoft's review; the on-device Windows AI APIs need package identity; changes the updater story completely |

- **The sidecar and DLLs.** Every `.exe` and `.dll` we ship should be signed (`Yellowmoon.exe`, `ym.exe`, the installer); a signed installer around unsigned binaries still draws Defender attention.

### 7.4 CI cost

The repository is public (`gh api repos/ngriaznov/yellowmoon`: `private: false`, owner type `User`), and "the use of standard GitHub-hosted runners is free in public repositories"; the minute multipliers are Windows 2 and macOS 10 against Linux 1, and larger runners are always charged [search], https://docs.github.com/en/billing/concepts/product-billing/github-actions. Hosted-runner prices fell by up to 39 % on 2026-01-01; a 2-core price list I saw gives 0.006, 0.010 and 0.062 USD a minute for Linux, Windows and macOS [search], https://resources.github.com/actions/2026-pricing-changes-for-github-actions/ (`github.blog` and `resources.github.com` did not resolve here; the figures are from a search summary and one source gave a lower Linux price). **The "twice the Linux minutes" holds for the multiplier; for this account it does not matter** while the repository is public. It would if it went private (the figures above), and a GPU runner for real D3D12 is a larger runner and always charged. The hosted Windows image has no GPU (WARP and Mesa only, section 2.7).

### 7.5 `ym` on the `PATH`

On Windows the app folder is `%LOCALAPPDATA%\Yellowmoon` (NSIS per-user) and `ym.exe` is inside it. The ways to reach it: an installer step that appends the folder to the user's `PATH` (NSIS hook or WiX `Environment`); a menu item that does the same (`cli_link.rs` becomes "Add Yellowmoon to PATH", an `HKCU\Environment` write and a `WM_SETTINGCHANGE` broadcast); a separate `ym` zip for people who want only the tool; or a package manager (WinGet or Scoop manifest pointing at the GitHub release), which also gives the CLI users a way to update without the app. A symbolic link needs a privilege on Windows, so the Mac approach does not carry over. The Homebrew cask has no Windows twin; `latest.json` is not a package manager.

## 11. What this means for Yellowmoon

**The main blockers.**
1. The viewport. No Windows version exists; the Mac one cannot be reused because it tags a layer with Display P3, and DirectX 12 has no such thing. The sRGB frame (core already makes it) and the PNG route (already built) make a Windows app possible from day one, slowly; zero-copy is a spike away from a known pattern (route A) or a wry fork (route B).
2. No evidence yet from D3D12 or Windows-Vulkan hardware. Every promise of `docs/17` (parity bounds, K5 under the TDR, K8 under DXC or FXC, tile equals whole, determinism) was checked on lavapipe and Metal only. The prediction that the OR barrier holds on any compiler is sound by construction and unproven.
3. Signing. Smart App Control can refuse an unsigned installer outright, so unsigned is not a long-term answer for Windows the way it is for macOS. A route costs money (about 10 USD a month) or paperwork, and which route you can use depends on where you live.
4. A tail of small portability faults (`HOME`, `data/`, wording, shortcuts, tests); cheap and findable by a Linux job.

**The cheapest first step.** Stage 0 together with the Linux `windows-check` job: about 3 to 4 agent-days, no Windows machine, no money, and from then on a regression in Windows portability fails a pull request. The next cheapest step that teaches something is stage 1's CI leg: a free `windows-latest` run of the CPU path and of the GPU suites on WARP and Mesa Vulkan, which would show within a day whether the kernels compile through FXC and DXC and how far parity is.

**Questions for you** (not decided here):
1. **Do you want Windows at all, and which minimum?** `docs/00` says "Windows and Linux, if there's demand". Windows 10 is past Microsoft's support date (stated from general knowledge); WebView2, wgpu DX12 and Claude Code all run on 10 1809 or later. 2. **x64 only, or ARM64 too?** The free `windows-11-arm` runner makes the build cheap; a device to look at is the open part.
3. **Viewport: spike route A first, accept route C for a first release, or both in that order?** And if A fails, are you willing to fork wry (route B), a long-lived maintenance cost?
4. **Colour on the display:** sRGB first (option 1), a display-profile conversion (option 2), or scRGB (option 3)? Do you have a wide-gamut Windows monitor to look at?
5. **Signing:** where do you live, and do you want an OV certificate, Azure Artifact Signing (if you are eligible), or to start unsigned and say so in the README? Is a monthly cost of about 10 USD acceptable?
6. **Backends and compiler:** Vulkan first with DX12 as the fallback (what wgpu does by default), DX12 first, or restrict to one?
