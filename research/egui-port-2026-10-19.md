# What it takes to move the Yellowmoon interface to egui

For Mykyta, 2026-10-19. Research only: this file and one row in `research/README.md` are the only changes, nothing was built into the app. It follows `research/gui-toolkit-2026-10-16.md`, which studied Slint and named egui as the licence-clean fallback; you refused Slint's licence the same day (`docs/16`). Everything external was read on 2026-10-19; sources are tagged `[E1]`, `[E2]` and listed at the end. "Repo:" paths are files in this repository. There is no Mac here: every statement about how something looks or feels on macOS comes from source code, documentation and issue threads, not from running it. Licence remarks are my reading of the texts, not legal advice.

## 0. Short answer

1. **It can be done, licence-clean, on the wgpu we already use.** egui, eframe, egui-wgpu, egui-winit and egui_kittest 0.37.0 (2026-10-15, MIT OR Apache-2.0) are on wgpu 30 and winit 0.30.13 [E1]. A throwaway crate with eframe, muda, rfd, egui_extras, minisign-verify and wgpu 30 resolves to the same `wgpu 30.0.1` our `Cargo.lock` has, and every one of its 204 macOS crates (normal and build dependencies) has a licence on the `deny.toml` allow list; 65 crates would be new to the lock file (section 7.1).
2. **What is rewritten: the whole web front end.** 25.4k lines of TypeScript and TSX (no tests), 4.1k lines of CSS, 18.3k lines of Vitest (1,378 cases) and 5.6k lines of Playwright (250 tests), plus the Tauri IPC layer of `src-tauri` (about 4k lines). **What carries over: all of `crates/*` (259k lines) and about 6k lines of `src-tauri`**: `AppApi`, the `Viewport` controller, the wizard, the CLI link, logging and About already have no Tauri type in them, and the `FrameSink` and `Emitter` traits are exactly the seams an egui shell plugs into (section 2).
3. **Three things egui does not do, and how to get them.**
   - *Display P3.* eframe always configures the surface as sRGB and gives no way to choose `SurfaceColorSpace`; tagging the `CAMetalLayer` by hand does not stick because wgpu resets it on every reconfigure, and egui-wgpu reconfigures on every resize. You accepted an sRGB-only photo view on 2026-10-16, which needs nothing. P3 needs a ten-line patch of egui-wgpu (vendored, or upstreamed) or our own event loop (section 3.1).
   - *Backdrop blur.* egui has none and cannot sample its own framebuffer. Our aurora is still and grey, so the panes can be drawn from a blurred copy of it rendered once per window size: the same picture as CSS `backdrop-filter` wherever only the aurora is behind a pane, which is every pane but the dialogs and menus (section 3.2).
   - *Tabular figures.* egui shapes text with harfrust but passes it no OpenType features, so the value boxes cannot ask for `tnum`. Figtree has `tnum` (checked: the Latin face's default digits are 410 to 638 units wide), so a build step can bake tabular digits into a second face (section 3.3).
4. **Decisions only you can make before any of it starts** (section 9): reopening two settled decisions (the Tauri 2 shell in `docs/00`, and glasscn as the component framework in `docs/16` and the Frontend line of `AGENTS.md`: in egui every control is ours by definition); P3 or sRGB for the photo; how the test suites are replaced (screenshot references retaken from the egui app); and how packaging and the updater move off the Tauri CLI.
5. **Size.** About 19 agent-days to parity (range 14 to 28), plus 6 to 10 round trips with your Mac that are not in that number (section 8). The 2026-10-16 report put egui at 12 to 20 days; the interface has grown since (the dark glass components, Colour warp, Copy and Paste, from 18.7k to 25.4k lines).
6. **Will it fix "sluggish"?** Partly. In-process, a wheel or pinch reaches `Viewport` without IPC, there is no page that can rubber-band or select, and the cheap trick `docs/01` names as the next step ("show the last frame offset by the input delta at once") becomes a texture drawn with a transform, a few lines in egui. The render itself (849 ms for a warm fit frame on this Linux machine's CPU path) is the core's and does not change with the toolkit. `docs/16` says Tauri stays until the M3-16 to M3-20 fixes have been tried on your Mac, and those checks (M0-H4) are still open in `docs/STATUS.md`.

## 2. How an egui Yellowmoon would be put together

### 2.1 Crates

1. **Split `src-tauri` first, with Tauri still in place.** Move the toolkit-free modules into a library crate (say `crates/ym-app`, or `app/core` if it should stay out of `crates/`): `AppApi`, `Viewport` with `FrameSink`, the `Emitter` trait, `wire` types without `specta`, the wizard, the CLI link, logging, About text, the menu `spec()`, perf counters. `src-tauri` keeps working on top of it, and its 150 tests move with the code. This is a day of work, it is useful whatever the toolkit, and it lets the two shells live side by side during the port.
2. **A new app crate** (`app/egui`, package `yellowmoon-app` once Tauri is gone, binary `Yellowmoon`) with eframe, muda, rfd and the updater module. It depends on the library crate, never the other way round, so `docs/01`'s dependency rules hold: no crate under `crates/` knows the toolkit.
3. **The CLI is untouched**, and so is the bit-identical parity of app and `ym` (hard rule 6): exports never go through the UI, and `app_cli_parity.rs` drives `AppApi`.

### 2.2 Threads and state

- eframe runs the UI on the main thread and calls `App::update` only when something happens (input, `request_repaint`, a timer) [E3]. **No call into `AppApi` may block that thread**: today every Tauri command runs on a worker (`commands.rs`), and some calls wait for the core (`snapshot_synced` up to 1.5 s, `export_estimate`, looks import). The UI model keeps that shape: it sends commands to a small worker pool and reads answers from a channel at the start of each frame. `AppApi` is `Send + Sync`, so this is a thin layer.
- **Events.** An `EguiEmitter` implements `Emitter` by pushing `AppEvent`s into a channel and calling `ctx.request_repaint()`. The 30 Hz throttle of `events.rs` existed because each event cost the main thread an `evaluateJavaScript`; with a channel drained once per frame it is not needed.
- **`store.ts` (1,944 lines) shrinks to a UI model**: the parts that are window state (screen, tab, undo history of 100 steps, the Apply-to scope, picks in flight, zoom mirror, crop session, wizard model, copied settings) move to Rust; the mirror of the core's state mostly goes, because the UI can read the session through `AppApi` (cheap reads under the session lock, cached per frame). The patch coalescing of slider drags (one patch per frame, a final one on release) stays, since a render still takes longer than a frame.
- **Input over the photo** goes straight to `Viewport` (`viewport_input` without serialising, queueing or a round trip). `viewportInputQueue.ts` becomes a few lines: one frame's wheel and pinch deltas summed, sent once per frame.

### 2.3 The photo

- Today a frame is RGBA8 in CPU memory (`RenderedFrame.rgba`), and `native.rs` uploads it to its own wgpu device and draws one triangle into a `CAMetalLayer` behind the webview. In egui the photo is a texture drawn inside the window like anything else: an `EguiSink` implementing `FrameSink` keeps the newest frame and wakes the UI; the UI uploads it into a persistent texture registered with `egui_wgpu::Renderer::register_native_texture` (or `TextureHandle::set`, which is the same one copy) and draws it at the photo cell [E4]. The page transparency, the aurora mask cut out of the photo cell, `data-native-viewport`, the `!important` paper rules and the viewport job's "does the page paint over the cell" check all go away, because nothing composites through a hole any more.
- **Device.** eframe can be given a device (`WgpuSetup::Existing`) or make one we then hand to `ym-gpu` [E4]. Sharing one device is what a zero-copy path needs, but it puts egui's frame and the core's compute (an export tile can run for seconds) on one command queue. Keep two devices, as today, until a Mac measurement says the copy matters: on Apple silicon the 5.5 to 22 MB copy per frame is a memory-to-memory move, and the second queue keeps the interface drawing while an export runs.
- **Exact pixels.** At 100 % one image pixel must land on one device pixel (`docs/01`). egui lays out in points, so the cell's rectangle is rounded to physical pixels (`pixels_per_point`) and the texture is sampled with `TextureOptions::NEAREST`; the core already renders at the cell's device size.
- **A fast pan and zoom on top.** With the photo a texture, the UI can draw the last frame shifted and scaled by the input that arrived since (UV transform of the image), every display frame, while the core renders the sharp one. That is the follow-up `docs/01` names under *Which request stops which render*; in the webview it needed a native view, here it is part of drawing the image.

## 3. Rendering: colour, glass, text, widgets

### 3.1 Colour

- **What egui does.** egui-wgpu takes the first `Rgba8Unorm` or `Bgra8Unorm` surface format (`Bgra8Unorm` on Metal), blends premultiplied gamma-encoded colours, and builds the surface configuration from `get_default_config`, which leaves `SurfaceColorSpace` at `Auto`, which wgpu resolves to sRGB; its `SurfaceConfig` exposes present mode and frame latency only (`egui-wgpu-0.37.0/src/lib.rs` line 421, `src/winit.rs` line 134; `wgpu-30.0.1/src/api/surface.rs` line 93) [E4, E5]. `Color32` is gamma-encoded sRGB, premultiplied [E4].
- **What wgpu 30 can do.** `SurfaceColorSpace` exists (sRGB, Display P3, and the extended spaces), and on Metal a `Bgra8Unorm` surface offers sRGB and Display P3 (`wgpu-hal-30.0.1/src/metal/adapter.rs` lines 405 to 436) [E5]. That is what `native.rs` uses today.
- **Tagging the layer by hand does not work under eframe.** wgpu-hal's Metal `configure` sets the layer's colour space on every call (nil for sRGB), and egui-wgpu reconfigures on every resize, at the start and end of a live resize and on a suboptimal or outdated frame, with no hook to tag it again (`wgpu-hal-30.0.1/src/metal/surface.rs` lines 286 to 327) [E5].
- **Three ways, cheapest first.**
  1. *sRGB photo view* (your answer of 2026-10-16): render viewport frames with `OutputTarget::Srgb`, which the colour chain and its GPU pass already have for thumbnails (`crates/ym-core/src/pipeline/frame.rs` renders the viewport with `OutputTarget::Viewport`, Display P3, today). The photo then matches the default export exactly and loses the part of P3 outside sRGB. The header's status text would say sRGB. `docs/01` Native viewport point 4 changes.
  2. *P3 through a patched egui-wgpu*: pass `color_space: DisplayP3` into the surface configuration (about ten lines), vendored under `[patch.crates-io]` as a path dependency (`deny.toml` forbids git sources, not paths) and offered upstream; convert the colour tokens to P3 values once (the greys do not change; the yellow and the tab colours do). Open upstream issues on wide gamut: #2712, #1207; an open PR adds an HDR preference for scRGB only (#8703) [E6].
  3. *Our own loop* with egui-winit and `egui_wgpu::Renderer` (no eframe): full control of the surface, and of the raw winit events (section 4). About 500 to 800 lines that eframe would otherwise own: window, event loop, AccessKit adapter, repaint scheduling, multi-window if wanted.
- The 8-bit dither of the core's frames survives either way, because the texture is drawn 1:1 and the surface is 8-bit.

### 3.2 The glass

What `docs/11` asks for: translucent dark panes with a thin light rim, a soft shadow and backdrop blur (28 px in `glass.css`, 12 px for the "liquid" controls, with `saturate` and `brightness`), over a still aurora of three grey blobs on near-black; the filmstrip near-opaque with no blur; the yellow only on buttons; tab accents on what belongs to the tab.

- **Works in egui as it ships:** rounded rectangles with a radius per corner, strokes inside, centred or outside, `Shadow { offset, blur, spread, color }` (a linear ramp, not a Gaussian; close enough for a soft shadow, to be checked against the screenshots), rectangles filled with a texture, tinting [E4].
- **Gradients** need a `Mesh` with colours per vertex (the aurora's radial blobs, the wheels' hue), or a small WGSL callback where exactness matters.
- **No rounded clipping:** clip rectangles are square. A scroll area inside a rounded pane must stop short of the corners, or the corners are painted over afterwards.
- **No backdrop blur** (issue #1758, open; the author says blur needs a post-processing pass), and a paint callback cannot read the framebuffer [E4, E6]. The options:
  1. *Pre-blurred still aurora (recommended).* Render the aurora and a blurred, saturated copy into two textures once per window size and scale; draw each pane as a rounded rectangle filled with the blurred copy at the pane's screen position, then the dark tint, the rim and the shadow. Wherever only the aurora is behind a pane (the header, the tool panel, the Export panel, the Start blocks, the wizard), this is the same picture as CSS backdrop blur, and it costs one textured rectangle per pane per frame. It works because you chose a still ground (`animate={false}`, `docs/11`).
  2. *Panes over content* (a dialog over the tool panel, the zoom menu and the look chip over the photo) get either no blur (a stronger tint; the cheapest), or a real blur pass, which in eframe means drawing the UI twice or running our own loop. Two small crates do it on egui 0.34 and 0.35 with wgpu 29 (`egui_glass` 0.1.5, MIT; `backdrop-blur-egui` 0.2.0, MIT OR Apache-2.0); both are behind 0.37 and barely used, so they are references, not dependencies [E7].
  3. *`NSVisualEffectView`* (`window-vibrancy` 0.8.1, Apache-2.0 OR MIT) blurs the desktop behind a transparent window, not our aurora; egui draws into one layer, so a native view cannot sit between the aurora and the panes. Not what C2 is.
- **Reduced motion** is trivial: nothing animates under the glass.

### 3.3 Text

- egui 0.34 (2026-03-26) replaced ab_glyph with skrifa and the vello_cpu rasteriser and turned on hinting; 0.35 (2026-06-25) added shaping with harfrust; variable-font axes are settable per font or per run (`FontTweak.coords`, `RichText::variation("wght", 600.0)`) [E4, E8]. So Figtree's weights 400 to 800 are one variable font, not five families.
- **woff2 is not read** (TTF and OTF only) [E4]. Ship Figtree as TTF: the upstream variable TTF, or a build-time conversion of our woff2 (OFL 1.1 allows it; Figtree declares no Reserved Font Name, `design/fonts/OFL.txt`). `THIRD-PARTY.md` already carries the OFL text.
- **Tabular figures are missing**: egui calls `shaper.shape(buffer, ShapeOptions::new())` with no features (`epaint-0.37.0/src/text/text_layout.rs` line 1605) [E4]. Figtree has `tnum` and `pnum` and proportional default digits (checked with fontTools on `design/fonts/figtree-latin-wght-normal.woff2`: features `ccmp dnom frac locl numr pnum rvrn tnum`, axis `wght` 300 to 900, default digit advances 410 to 638). Ways: (a) a build step (a `tools/` script, not shipped code) writes a second face whose `cmap` points the digits at their `tnum` glyphs, used by the value boxes and the numbers of the queues; (b) a patch to epaint passing features through, offered upstream; (c) digits laid out in fixed-width cells. (a) is the least code and touches no dependency.
- Letter-spacing (`extra_letter_spacing`) covers the caps labels. Labels are not selectable once `style.interaction.selectable_labels = false`, and the few selectable texts of `docs/11` (error text, the command line, About) are `Label::selectable(true)` or a read-only `TextEdit` [E4]. That replaces the whole selection rule set of M3-16.
- Text will not be pixel-identical to WebKit's (different rasteriser and hinting). That matters for the screenshot comparisons (section 6), not for the look.
- Turn off the system-font fallback (`system_fonts` feature) so text renders the same on every Mac and in CI.

### 3.4 Our drawn widgets and lists

| Widget | In egui |
|---|---|
| Colour wheels (conic hue, chroma to the centre, 10 px puck) | a `Mesh` triangle fan of 256 to 360 slices, or a generated texture once per size; `ui.interact` with `Sense::click_and_drag` for the puck; double click resets |
| Curve plot (320 × 220, up to 16 points, drag off to delete, histogram behind) | `Painter` polyline of the monotone spline, computed by the Rust spline the core bakes (the TypeScript port `curve.ts` goes); `egui_plot` 0.38 is licence-clean but its axes, pan and zoom get in the way [E4] |
| Histogram | a filled `Mesh` per channel from the 64 bins of `histogram` |
| Colour warp plane (hue field, rings, scatter, pins, keyboard focus per pin) | the hue field as a texture (it is drawn once per size today on a canvas), the scatter as small circles, pins as shapes with an `id` each so they take keyboard focus; `warpMath.ts` goes, the UI calls `ym_color::warp` directly |
| Look grid (~600 tiles, lazy) | `ScrollArea::show_rows` over rows of N tiles; only visible rows ask for a tile; thumbnails arrive as RGBA from the core (no PNG encode, no `ym-frame` scheme, no address cache); keep our own LRU of `TextureHandle`s (dropping the last handle frees the texture) [E4] |
| Filmstrip (hundreds of 3:2 thumbnails, horizontal) | `ScrollArea::horizontal().show_viewport` with the visible range computed from the offset [E4] |
| Thumbnails in general | egui-wgpu makes no mipmaps, so a thumbnail must be uploaded at the size it is shown times the display scale; the core renders them at most 240 px on the long edge, a little under the 248 px a 124 px filmstrip thumbnail needs on a 2× display, so the size goes up a step or the slight enlargement is accepted [E4] |
| Crop frame, pick layer, ⌥ readout, look chip, camera line | shapes and labels painted over the photo texture in the same pass |
| The ~20 glasscn controls | each a small widget of ours drawn to the C2 tokens (section 5) |

### 3.5 Repaint and cost

- eframe sleeps until input, `request_repaint` or a timer; animations repaint until they end [E3]. Each repaint rebuilds the whole interface (immediate mode); the README claims 1 to 2 ms a frame for typical interfaces [E9], and our Photos screen is denser than typical, so the spike measures it.
- Known issues to watch: #7059 (open: high CPU on macOS when launched from Finder or partly covered, 120 fps in the background), #7761 (open: wgpu about three frames behind input on Windows against two for glow, slow start), #5037 (reopened 2026-04: input latency with vsync); since 0.35 the wgpu backend asks for a frame latency of 1 by default, adjustable at run time (#8203, #8442) [E6]. Live resize on macOS uses `presentsWithTransaction` with three drawables by default [E4].
