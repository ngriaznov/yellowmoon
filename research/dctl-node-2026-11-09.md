# A clean-room compiler lets Yellowmoon run DCTL

Yes. Yellowmoon can legally and technically add a node that runs users' plain-text `.dctl` files, but the honest promise is narrower than "runs your DCTLs". It would write its own clean-room compiler, support the per-pixel form first, and say plainly what it will never do: open encrypted `.dctle` files, match Resolve bit for bit, or run DCTLs that depend on Resolve itself (transitions, parametric ACES templates). DCTL is a C subset with CUDA-style vectors, about forty underscore-prefixed maths functions and a macro layer for controls and LUTs. Blackmagic publishes only a README and some sample files, with no grammar. Resolve compiles each file from source through CUDA, OpenCL or Metal with float modes it does not document ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)). No trademark on "DCTL" and no patent turned up. "DaVinci" is registered, so the node needs a generic name and a factual line such as "Opens DCTL files". The one permissive precedent, the MIT-licensed dctl-workbench, already turns DCTL into naga IR and WGSL in about 18.7k lines of Rust, which proves the GPU half ([dctl-workbench](https://github.com/nordsound/dctl-workbench/tree/main/rust/dctl-compiler)). The CPU half, a deterministic f32 evaluator built on `libm`, has no permissive precedent and must be written from scratch. Determinism holds on Yellowmoon's existing terms. The CPU evaluator gives the same bits on every machine. The app and `ym` agree byte for byte on one machine. The GPU agrees with the CPU only within a tolerance, because Metal's fast-math cannot be switched off and code Yellowmoon did not write cannot be made to meet rule K8. The hardest frictions are Yellowmoon's own. Nodes work in LogC4/AWG4, but DCTL authors expect other encodings. The persistence list must grow to keep imported files. Texture-form DCTLs that read any pixel collide with the tile-invariance rule. A per-pixel node built the way the Film node was (CPU first, then a separate GPU pass, then the panel) is roughly 14 to 22 engineer-weeks, an unmeasured estimate. Texture form, LUTs and more colour spaces add about 6 to 8. Nothing starts until the owner reverses the "DCTL (for now)" drop, whose reason was never written down, and answers the twelve decisions at the end.

## DCTL is a C-subset pixel shader defined by a README, not a grammar

### What a DCTL file is

Blackmagic describes DCTL as "C-like with additional definitions" and says such an effect "serves as a 'pixel shader' program", one that "defines a process to generate one pixel of data at a time". It "uses base C types - int, float, char*, pointer etc." ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)). **There is no formal specification.** Resolve's developer folder holds a plain-text README and a dozen sample files. The README tells authors to copy the entry signatures "exactly as-is - including parameter types and names", and it gives no operator table and no conversion rules. It also contradicts itself in small ways. It says there are "5 types" of UI element but lists six. It calls the `p_ToTex*` textures the "From" clip's image. It declares `_frexp(float x, int exp)` while describing it as updating `exp` (same source). A copy of the Resolve 17-era README is reformatted on CommandPost's ResolveCafe page, the link in the brief ([ResolveCafe](https://github.com/CommandPost/ResolveCafe/blob/main/docs/developers/dctl.md)). The newest copy found has a changelog to Resolve 20.1. Secondary guides say DCTL runs only in Resolve **Studio**, not the free edition ([PixelTools guide](https://pixeltoolspost.com/blogs/resolve/dctls-for-davinci-resolve)). So the people who write and collect DCTLs are paying Resolve users. In practice the de facto specification is three things together: the README, Blackmagic's samples and the public corpus of community DCTLs.

### Five entry points, chosen by exact signature

A file has exactly one entry function, picked by exact signature. The common case is `__DEVICE__ float3 transform(int p_Width, int p_Height, int p_X, int p_Y, float p_R, float p_G, float p_B)`: one pixel in, one pixel out. The **texture form** replaces the three floats with `__TEXTURE__ p_TexR, p_TexG, p_TexB` and lets the code read "the RGBA values for any pixel from the image by calling `_tex2D([textureVariable], [posX], [posY])`", one channel per call. Two `float4` variants add alpha. They work only through the ResolveFX DCTL plugin, starting with Resolve 19.1, and default to premultiplied alpha. A fifth signature, `transition`, takes From and To textures and a `TRANSITION_PROGRESS` value between 0 and 1. It "can only be used in the OpenFX DCTL Transition Plugin" ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)). The README does not say where the origin is. Thatcher Freeman's Fusion re-host flips Y (`p_Y = (p_Height - 1) - Y`) against Fusion's bottom-left origin, which implies row 0 is the top ([DCTL Interpreter.fuse](https://github.com/thatcherfreeman/utility-dctls/blob/main/Fuses/DCTL%20Interpreter.fuse)). The README also does not say what `_tex2D` returns outside the image, or whether it accepts fractional coordinates.

### Types, qualifiers and built-ins

The type system is C plus CUDA-style `float2/3/4` vectors with `.x/.y/.z/.w` access and arithmetic operators, built with `make_floatN`. Qualifiers mark functions (`__DEVICE__`), constant tables (`__CONSTANT__`), constant-table pointers passed to functions (`__CONSTANTREF__`) and textures (`__TEXTURE__`). Float literals "must have 'f' character at the end". The documented library is about forty `_`-prefixed float functions (`_powf`, `_logf`, `_exp10f`, `_sinpif`, `_atan2f`, `_fmaf`, `_mix`, `_frexp` and the rest), plus `isinf`, `isnan` and `signbit` and integer `abs`, `min` and `max`. It has no `_atanf`, `_fractf`, `_smoothstepf` and no vector `dot` ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)). Real code steps outside this list all the time. Blackmagic's own samples call `trunc`, `to_float3` and `->` on a `__CONSTANTREF__` struct pointer ([BMD examples](https://github.com/jdanna/Resolve_Tools_Public/tree/main/docs/DaVinciCTL)). Community DCTLs that run in Resolve use an undocumented `__PRIVATE__` qualifier on pointer parameters ([Quantize.dctl](https://github.com/thatcherfreeman/utility-dctls/blob/main/Utilities/Quantize.dctl)). dctl-workbench's symbol table is a third-party guess at the real surface. It is a superset that includes `_atanf`, `_fractf`, `_tex2DVec4`, `int2..4`, `half` and ACES-CTL helpers, and it is not confirmed against Resolve ([dctlTypes.ts](https://github.com/nordsound/dctl-workbench/blob/main/packages/core/src/parser/dctlTypes.ts)).

### Controls, LUTs and predefined keys

The non-C layer matters most for Yellowmoon's panel. `DEFINE_UI_PARAMS(name, label, kind, …)` declares a float slider, int slider, value box, check box, combo box or (since 19.1) colour picker. The limit is "up to 64 UI controls for each type", and tooltips have their own `DEFINE_UI_TOOLTIP` macro. Labels are bare unquoted text with spaces. `DEFINE_LUT(name, path)` takes an unquoted path that can contain spaces, and `DEFINE_CUBE_LUT(name) { … }` embeds a `.cube` body. None of this is valid C, so Resolve must run a DCTL-specific pre-pass before any C compiler sees the file. A reimplementation needs the same pre-pass. Published DCTLs put emoji in labels ([FadedBalancerDCTL](https://github.com/fabiocolor/Faded-Balancer-DCTL/blob/HEAD/FadedBalancerDCTL.dctl)). `APPLY_LUT` interpolates 1D LUTs linearly and 3D LUTs by the *project's* trilinear or tetrahedral setting, a host choice outside the file. The predefined keys are `__RESOLVE_VER_MAJOR__/_MINOR__`, `DEVICE_IS_CUDA/OPENCL/METAL`, `TIMELINE_FRAME_INDEX` ("1 as default value" when a DCTL is applied as a LUT) and, since 19.1, `RAND(uint seed)`, whose algorithm is unpublished. `DEFINE_ACES_PARAM` and `DEFINE_ACES_V2_PARAM` expand into calls to Resolve's internal ACES output transforms ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)).

### How Resolve compiles and runs a DCTL

Resolve compiles a DCTL from source, at load or rebuild, for whichever GPU backend is active. The `DEVICE_IS_*` keys exist so that authors can branch per backend. A "DCTL Build Error" dialog (19.1) and log files report compiler output ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt); [thatcherfreeman README](https://github.com/thatcherfreeman/utility-dctls/blob/main/README.md)). The same source really does pass through different vendor compilers. In Resolve 15 on macOS, ACES DCTL headers failed on the OpenCL backend with "conflicting types", and the suggested fix was to make the DCTL compile under Metal instead ([ACEScentral](https://community.acescentral.com/t/problems-loading-aces-dctl-files-in-resolve-15-macos/1409)). The qualifier set reads like a macro layer over CUDA C++, OpenCL C and the Metal Shading Language. Fusion's sibling dialect needs shims such as `#define POINTERPARAMETER thread` under `DEVICE_IS_METAL` (an inference from the Fuse shims, not a Blackmagic statement). **Blackmagic publishes nothing on precision, fast-math, pixel range or colour space.** The backends' defaults differ. Metal compiles with fast-math by default ([slang #13689](https://github.com/shader-slang/slang/issues/13689)). NVCC keeps precise transcendentals but contracts multiply-adds into FMA ([NVIDIA forum](https://forums.developer.nvidia.com/t/cuda-math-produces-a-slightly-different-result-to-c-math/226488/3)). The practical conclusion is that **Resolve does not promise identical DCTL output across its own backends**, so "compatible with Resolve" can only ever mean "within a tolerance". Nobody has measured that gap.

## Blackmagic owns the names and the lock, not the language

### Trademarks, the EULA and a clean-room build

Blackmagic Design holds US registrations for **DA VINCI** (Reg. 3989906), **DAVINCI** (renewed 2025) and **DAVINCI RESOLVE** (Reg. 5659269), per trademark aggregators that should be checked against the USPTO's own TSDR ([markinton](https://markinton.com/trademark/da-vinci-85191249); [trademarkdir DAVINCI](https://trademarkdir.com/trademark/davinci-77967187); [trademarkdir DAVINCI RESOLVE](https://trademarkdir.com/trademark/davinci-resolve-87732717)). **No registration for "DCTL" was found**, and neither was any patent or published licence covering the language. Resolve's licence forbids licensees to "reverse engineer, decompile, disassemble, or create derivative works based on the Software". That binds people who install Resolve, and it concerns Resolve, not independent implementations of the language it reads. The quote comes from a search-engine extraction of a third-party copy whose version was not confirmed ([Resolve licence PDF](https://d7umqicpi7263.cloudfront.net/eula/product/926e6a7e-46f0-465c-8182-ad56050c9094/d4d34663-7069-48ce-b0fa-57d3ddc00b6d.pdf)). Two things Blackmagic does own by copyright are the README's prose and its sample files.

The ResolveCafe page the brief points to sits in an archived MIT-licensed repository ("Copyright (c) 2023 LateNite Films") ([LICENSE](https://raw.githubusercontent.com/CommandPost/ResolveCafe/main/LICENSE)). The page itself names no author or source, keeps an editing note ("double check folders again") and reads like an edited copy of Blackmagic's README. LateNite's MIT grant therefore cannot relicense it. **The safe path is a clean-room implementation.** Developers read the README, ResolveCafe and the samples to learn facts, syntax and function names, which copyright does not protect. They then write `docs/` in Yellowmoon's own words, ship no Blackmagic sample or header, and never decompile Resolve. Naming follows the pattern hard rule 3 already sets for ARRI ("Imports ARRI Look Library files") and the Film node's practice of generic names plus data with a disclaimer ([AGENTS.md](../AGENTS.md); [docs/24](../docs/24-film.md)). The node gets a neutral name. The import dialog says "Opens DCTL files, the colour transform language used by DaVinci Resolve" and carries a "Not affiliated with Blackmagic Design" line, much as community authors already credit "all trademarks, specifications, and related intellectual property" to their owners ([photographic-dctls README](https://raw.githubusercontent.com/mikaelsundell/dctl/master/README.md)). None of this has been reviewed by a lawyer.

Yellowmoon would probably be among the **first non-Blackmagic hosts to run arbitrary DCTL files**. The nearest precedents run inside Blackmagic's own products or only write DCTL. Freeman's MIT Fuse rewrites DCTL source so it runs in Fusion Studio ([thatcherfreeman README](https://github.com/thatcherfreeman/utility-dctls/blob/main/README.md)). Cut Point Labs' LUT Tuner *generates* DCTL from a `.cube` ([Digital Production](https://digitalproduction.com/2026/08/24/lut-tuner-makes-luts-tunable-in-resolve/)). An MCP project drives Resolve 21.1's own encryption ([davinci-resolve-mcp #216](https://github.com/samuelgursky/davinci-resolve-mcp/pull/216)). No objection by Blackmagic to any third-party DCTL tool was found. Blackmagic's forum, where one would most likely surface, could not be read.

### Encrypted `.dctle` is off limits, and with it the paid market

Resolve's "Encrypt DCTL" command (and, since 21.1, a scripting call) produces a `.dctle` with an optional expiry date, so authors can "distribute an effect without revealing the content" ([ResolveCafe](https://raw.githubusercontent.com/CommandPost/ResolveCafe/main/docs/developers/dctl.md)). The container, cipher and keys are unpublished, and no open decrypter exists. Decrypting `.dctle` would circumvent "a technological measure that effectively controls access to a work" under 17 U.S.C. §1201(a)(1)(A). The §1201(f) interoperability exception is narrow and doubtful for third-party content ([Cornell LII](https://www.law.cornell.edu/uscode/text/17/1201)). The EU has its own protection against circumvention ([Directive 2001/29/EC](https://eur-lex.europa.eu/eli/dir/2001/29/oj)) and strict limits on decompiling software ([Directive 2009/24/EC](https://eur-lex.europa.eu/eli/dir/2009/24/oj)). It would also mean reverse engineering Resolve. **The recommendation is plain refusal**: "Encrypted DCTL files (.dctle) open only in DaVinci Resolve Studio."

That refusal has a commercial consequence worth stating to the owner, because paid DCTLs are mostly sold encrypted. Mononodes sells Color Shift at €199 "in encrypted format", with Film Elements at €399 and Utility at €99 ([Mononodes](https://mononodes.com/color-shift-dctl/); [Film Elements](https://mononodes.com/store/film-elements-dctls/); [Utility](https://mononodes.com/utility-dctl/)). PixelTools charges $74.99 to $154.99 for Split/Tone ([PixelTools](https://pixeltoolspost.com/products/split-tone-dctl-plug-in)), and DeMystify sells a "Split Tone & Contrast DCTLe" at €39.90 ([DeMystify](https://www.demystify-color.com/product-page/split-tone-contrast-dctle)). **A Yellowmoon DCTL node would serve the free ecosystem and users' own code, not the paid market.**

### GPL DCTLs: users may load them, Yellowmoon may not ship them

The strongest free DCTLs are GPL-3.0: Paul Dore's collections and Jed Smith's OpenDRT. Running a user's GPL file creates no obligation for an Apache-2.0 host that ships nothing from it. GPLv3 §2 "explicitly affirms your unlimited permission to run the unmodified Program". §0 defines propagation to exclude "executing it on a computer or modifying a private copy". Output is covered "only if the output, given its content, constitutes a covered work", which a graded photo is not ([GPLv3 text](https://raw.githubusercontent.com/jedypod/open-display-transform/main/LICENSE)). The FSF's FAQ says an interpreted program is "just data" to the interpreter. It was read here only through secondary copies ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#IfInterpreterIsGPL)). Translating a user's DCTL to WGSL and caching it locally is running and private modification. That conclusion holds on three conditions: Yellowmoon ships no GPL DCTL, header or preset; its built-in function library is written without copying GPL code; and it never distributes users' translated shaders. Hard rule 1 independently forbids shipping GPL files, even beside the app under the GPL's aggregate clause. "Get DCTLs" links must open in the system browser, and downloading collections inside the app is out under hard rule 7 ([AGENTS.md](../AGENTS.md)).

## One MIT compiler proves the GPU half; the CPU half is new work

### Prior art: one real compiler, one useful oracle trick

**nordsound/dctl-workbench** (MIT, 2026) is the only substantial open DCTL compiler found ([dctl-workbench](https://github.com/nordsound/dctl-workbench)). It is a VS Code extension, a CLI and a Rust crate, `dctl-compiler` 0.3.0. The crate uses its own tree-sitter grammar or a TypeScript parser, a regex preprocessor and about 18.7k lines of Rust that build **naga IR directly**, emit WGSL and run it on WebGPU ([dctl-compiler](https://github.com/nordsound/dctl-workbench/tree/main/rust/dctl-compiler)). It is the right shape and a fair estimate of the size of the job, but not something to adopt as is. It pins naga 28 while Yellowmoon runs wgpu and naga 30. It infers `_tex2D`'s channel from the *name* of the texture parameter (anything ending in R, G, B or A). It silently maps `double` to f32 and expands unsized array parameters to 256 elements. And it has no CPU path at all ([codegen](https://github.com/nordsound/dctl-workbench/tree/main/rust/dctl-compiler/src/codegen); [Known Limitations](https://github.com/nordsound/dctl-workbench#known-limitations)). Its MIT licence does allow Yellowmoon to study or reuse its grammar, built-in table and limitation fixtures with attribution. The limitation list doubles as a checklist of constructs real DCTLs use that WGSL cannot express: statement expressions, double pointers, function pointers, pointer returns and runtime-sized arrays.

The second useful idea is the **macro-shim oracle**. katharostech's opendrt-blend copies a DCTL's `transform()` body verbatim. It defines `__DEVICE__` as `inline`, `DEFINE_UI_PARAMS` as a variable declaration and `float3` as a C++ struct, then compiles with `g++ -std=c++17 -O2 -ffp-contract=off -fno-fast-math`, "float32 end to end" ([opendrt-blend](https://github.com/katharostech/opendrt-blend)). That repository has no licence and wraps GPL OpenDRT, so Yellowmoon would write its own shim. The trick itself gives a strict-IEEE f32 reference for any DCTL. That is exactly the oracle a CI parity test needs, and it never touches the app, because the app must not depend on an installed compiler. General shader translators such as CrossTL (Apache-2.0, Python) have no DCTL front end ([CrossTL](https://github.com/CrossGL/crosstl)). No Rust DCTL interpreter exists anywhere.

### The Rust toolchain: write the preprocessor, own the IR, let naga validate

The preprocessor has to be Yellowmoon's own. The two complete pure-Rust C preprocessors, `ancpp` and `includium`, are MPL-2.0 and less than a year old ([ancpp](https://crates.io/crates/ancpp); [includium](https://crates.io/crates/includium)). `docs/14` accepts an MPL package only as a build-time tool whose files never ship ([docs/14](../docs/14-licensing.md)). `lang-c` shells out to `gcc -E` ([lang-c](https://crates.io/crates/lang-c)). `glsl-lang-pp` is BSD-3 but GLSL-flavoured ([glsl-lang-pp](https://crates.io/crates/glsl-lang-pp)). Ownership also helps in its own right. The DCTL pre-pass must recognise `DEFINE_UI_PARAMS` and `DEFINE_LUT` *before* macro expansion, and the preprocessor is where the sandbox limits live (include depth, path confinement, expansion counts). The subset DCTL needs (object and function-like `#define`, `#if` arithmetic with `defined()`, `#include "…"`, `#`/`##`) is a few hundred lines. `cexpr` covers the `#if` arithmetic ([cexpr](https://crates.io/crates/cexpr)).

For the parser, `logos` plus a hand-written recursive-descent parser gives the cleanest typed AST ([logos](https://crates.io/crates/logos)). tree-sitter is better for an editor but yields an untyped tree and pulls in a C runtime ([tree-sitter](https://crates.io/crates/tree-sitter)). dctl-workbench needs both a TypeScript parser and a tree-sitter parser, which suggests that one parser rarely serves both jobs. Diagnostics with source spans come from `codespan-reporting` (Apache-2.0) or `ariadne` (MIT) ([codespan-reporting](https://crates.io/crates/codespan-reporting); [ariadne](https://crates.io/crates/ariadne)).

The design is one typed DCTL IR with two consumers. The first is a thin lowering to naga IR, checked by `naga::valid::Validator`, with `back::wgsl` used only for golden text diffs. naga is already in the tree through wgpu and is a dev-dependency of `ym-gpu` ([ym-gpu Cargo.toml](../crates/ym-gpu/Cargo.toml)). The lowering stays thin because naga's API changes every major release, the trap dctl-workbench fell into. The second consumer is the CPU evaluator.

The lowering must decide, explicitly and identically on both paths, every case where C, WGSL and Metal disagree. **Integer division by zero** is undefined in C, while WGSL defines it to return the dividend and wraps signed overflow ([WGSL §arithmetic](https://www.w3.org/TR/WGSL/#arithmetic-expr)). **`_powf` with a negative base** is outside WGSL's `pow` domain, because `pow` "may be computed as exp2(y * log2(x))" ([WGSL §pow](https://www.w3.org/TR/WGSL/#pow-builtin)), so it needs a helper that handles sign and integral exponents. **`_atan2f(0, x)`** is undefined under Metal's fast-math. **`isnan`** can be folded away by fast-math, so it must be a bit test, as Yellowmoon's `common.wgsl::is_nan_f` already is. **`_round`** goes half away from zero, unlike WGSL's ties-to-even, and **`switch` fall-through** has no WGSL equivalent. Large `__CONSTANT__` tables belong in a storage buffer, because WGSL guarantees only 8 KiB of private variables per shader ([WGSL §limits](https://www.w3.org/TR/WGSL/#limits)).

### The CPU evaluator: an own batched interpreter on `libm`

Rust's `f32::powf`, `exp`, `ln` and `sin` are explicitly non-deterministic: their precision "varies by platform, Rust version, and can even differ within the same execution" ([Rust std](https://doc.rust-lang.org/std/primitive.f32.html#method.powf)). Every CPU path must therefore call `libm` (MIT, musl-derived, with a `force-soft-floats` feature) or its own functions ([libm](https://crates.io/crates/libm)). Three engines are possible. The recommended one is an **interpreter over the same typed IR that runs each operation across a batch of 64 to 256 pixels** in structure-of-arrays form, the CPU equivalent of SIMT. It is the smallest dependency and keeps a step budget easy. Cranelift JIT (Apache-2.0 WITH LLVM-exception) generates code about 14 % slower than LLVM, but it needs executable memory and `unsafe` ([cranelift-jit](https://crates.io/crates/cranelift-jit); [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)). Wasmtime gives deterministic fuel and NaN canonicalisation for free ([wasmtime config](https://docs.rs/crate/wasmtime/50.0.1/source/src/config.rs)), at the price of a second code generator and a large dependency. The only ready-made naga-IR interpreter on crates.io is AGPL-3.0, so hard rule 1 excludes it ([barracuda-naga-exec](https://crates.io/crates/barracuda-naga-exec)).

| Need | Choice | Licence | Why |
|---|---|---|---|
| Preprocessor | Own, with `cexpr` for `#if` | Apache-2.0/MIT | MPL alternatives fail `docs/14` at runtime; DCTL pre-pass and sandbox limits need control |
| Lexer, parser | `logos` + recursive descent | MIT OR Apache-2.0 | Typed AST for a compiler |
| Diagnostics | `codespan-reporting` or `ariadne` | Apache-2.0 / MIT | Line-and-column build errors |
| GPU codegen and validation | naga 30 (already in tree) | MIT OR Apache-2.0 | Same IR feeds wgpu's Metal path |
| CPU maths | `libm`, own DCTL-semantics wrappers | MIT | `std` maths is non-deterministic |
| CPU engine | Own batched interpreter (Cranelift later if needed) | — | Small, deterministic, budgeted |
| CI oracle | Own C++ macro shim, strict flags | — | Strict-IEEE f32 reference per DCTL |

## Determinism holds on Yellowmoon's terms, never on Resolve's

### Metal's fast-math makes device output a tolerance, not a promise

Yellowmoon already knows this problem from its own kernels. "Metal compiles every kernel with fast-math: wgpu-hal sets only the language version and `preserveInvariance` … and offers no switch". The project chose to make every kernel correct under both fast-math and strict IEEE (**K8**), using OR barriers and exact division, rather than patch wgpu-hal ([docs/17 §13](../docs/17-gpu.md); [wgpu-hal Metal device](https://docs.rs/crate/wgpu-hal/30.0.1/source/src/metal/device.rs)). Apple's own figures show how large the effect is for user code. Under fast-math, `sin`/`cos` carry up to 2^-13 absolute error in [−π, π], about 1.2e-4, "and larger otherwise". `pow` is "Implemented as exp2(y * log2(x))". `atan2` at x = 0 or y = 0 "is undefined". Division may be off by 2.5 ulp. NaN and infinity handling "is undefined" ([MSL spec Table 8.2, §8](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)). WGSL itself lets implementations assume no NaN or infinity and specifies no rounding mode ([WGSL §15.7.2](https://www.w3.org/TR/WGSL/#differences-from-ieee754)).

**K8 cannot be met for code Yellowmoon did not write.** A DCTL that branches on a computed float, as in `if (luma > 0.5f)`, flips at rounding ties under contraction and reassociation, and no translator can know which comparisons matter. The translator can only narrow the gap. It can route `_sinf`, `_cosf`, `_powf`, `_expf`, `_logf` and `_atan2f` through Yellowmoon's own polynomial or compensated implementations on *both* CPU and GPU, as `precise.wgsl` already does for log, exp and pow. With that, a per-node parity tolerance around 1e-4 relative in normal ranges is realistic. That figure is an engineering estimate, not a measurement. Barriering every operation would close more of the gap, at the 1.15 to 3.9 times cost the project measured for its own pinned kernels ([docs/17 §13](../docs/17-gpu.md)).

What survives is the guarantee Yellowmoon already gives for its whole device pipeline. **D8**: on the same machine, adapter and driver, the app and `ym` produce identical bytes, and across machines or against the CPU path they agree "within the stated tolerances only" ([docs/17 §5](../docs/17-gpu.md)). Hard rule 6's bit-identical exports between app and CLI therefore still hold, because both run the same route on the same device. Golden images pin the CPU path. Yellowmoon would end up stricter than Resolve, which by the evidence above makes no cross-backend promise at all.

### An f32 CPU evaluator, as a stated exception

AGENTS.md asks for f64 on the CPU reference path ([AGENTS.md](../AGENTS.md)). DCTL is written in `float`: literals carry `f`, and thresholds and precision tricks are tuned on f32 GPUs. An f64 evaluator would be "more correct" and further from both Resolve and Yellowmoon's own device path. The repository already has the precedent for an exception. The SAM and Depth runtimes are "f32 on the CPU … deterministic: fixed order, no fused multiply-add, `libm`, independent of the thread count" ([docs/23](../docs/23-nodes.md)). An f32 DCTL evaluator built the same way is bit-identical across machines and thread counts, which satisfies hard rule 8. Rust never contracts multiply-adds, NaNs are canonicalised on store, and pixels are independent. One small wrinkle shows the semantic friction: DCTL exposes `_fmaf`, while D6 bans `fma()` in Yellowmoon's own kernels ([docs/17 §5](../docs/17-gpu.md)). The spec must say that a user's explicit `_fmaf` is a correctly rounded fused operation on both paths. For rule 8 the spec also defines Yellowmoon's own seeded `RAND` and fixes `TIMELINE_FRAME_INDEX` at 1, Resolve's value for a DCTL applied as a LUT.

### Sandboxing untrusted code on the GPU and CPU

wgpu's checked `create_shader_module` injects bounds checks. On Metal these use naga's `Restrict` policy, which replaces an out-of-bounds index "with some arbitrary in-bounds index" ([naga index.rs](https://docs.rs/crate/naga/30.0.1/source/src/proc/index.rs); [wgpu-types shader.rs](https://docs.rs/crate/wgpu-types/30.0.1/source/src/shader.rs)). The CPU cannot reproduce "arbitrary". The translator must therefore clamp indices itself, by a rule the spec states, and the CPU must apply the same rule. wgpu's loop bounding stops the Metal compiler from deleting infinite loops, but its counter breaks only after 2^64 iterations ([naga MSL writer](https://docs.rs/crate/naga/30.0.1/source/src/back/msl/writer.rs)), so it does nothing against hangs.

A runaway kernel is killed by macOS with `MTLCommandBufferError.timeout`, after a duration Apple does not document ([Apple](https://developer.apple.com/documentation/metal/mtlcommandbuffererror-swift.struct/timeout)). wgpu-hal 30 treats `Completed` and `Error` command buffers alike ([wgpu-hal Metal mod.rs](https://docs.rs/crate/wgpu-hal/30.0.1/source/src/metal/mod.rs)), so **a timed-out DCTL would look like a finished but wrong frame**, not a lost device. The defences follow from that. The translator rewrites every loop with its own counter and a per-node budget, for example 2^16 iterations, and sets a flag word when the budget is hit; the CPU truncates at exactly the same point. The kernel writes a completion sentinel that the host checks. Dispatches stay inside K5's `PassList` work budget, about 30 ms on an M1 ([docs/17 §6](../docs/17-gpu.md)). And each DCTL source gets its own kernel family keyed by hash, so a failure turns off only that DCTL for the process and sends the photo to the CPU, as Yellowmoon already does for whole kernel families ([docs/17 §9](../docs/17-gpu.md)).

Compile time needs caps on source size, macro expansions, include depth, AST nodes, nesting (WGSL guarantees 127) and constant-array size. naga validation must run on a thread with a large stack, because wgpu warns that `create_shader_module` "may consume a lot of stack space" on user input. On the CPU, a deterministic step budget per pixel and a cancellation flag between tiles keep `ym` from hanging. With no recursion in the IR, the interpreter's stack is bounded by nesting depth. `#include` and `DEFINE_LUT` resolve only inside the imported bundle and never to URLs, under hard rule 7. The Metal watchdog figure itself is a physical-Mac check that `docs/17` already lists as one CI cannot cover ([docs/17](../docs/17-gpu.md)).

### Texture-form DCTLs break the tile contract unless their reach is provable

`_tex2D` reads at positions that can depend on the data, so a tiled renderer cannot know the halo in advance. Other hosts handle this in one of two ways. Some ask the effect for its region of interest: OFX `GetRegionsOfInterest` ([ofxImageEffect.h](https://github.com/AcademySoftwareFoundation/openfx/blob/main/include/ofxImageEffect.h)) and vkdt's ROI pass ([vkdt api.h](https://github.com/hanatos/vkdt/blob/master/src/pipe/modules/api.h)). Others declare random access, which in Nuke Blink "can take much longer to run" ([Foundry Blink](https://learn.foundry.com/nuke/developers/16.0/BlinkUserGuide/BlinkKernelAPIReference/Images/RandomAccess.html)). Yellowmoon's scheduler is stricter than either. Every step must declare a footprint, and "a step that cannot say so is not allowed". `StepKind::declared` is a `match` without a wildcard arm, so a new kind does not compile until it has one ([docs/23](../docs/23-nodes.md); [schedule.rs](../crates/ym-color/src/schedule.rs)).

A whole-image fallback collides with K4's 128 MiB binding cap. A 50 MP picture as RGBA f16 is about 400 MB ([docs/17 §6](../docs/17-gpu.md)). Preview raises a second problem. DCTLs use `p_Width`, `p_Height` and absolute pixel offsets, so rendering a reduced view at view resolution changes the result. The workable design is **static reach inference**. If every `_tex2D` coordinate is `p_X + c` and `p_Y + c` with compile-time `c`, or a loop with constant bounds, the node becomes a Film-like spatial step with that reach. Anything else is refused with a sentence. Out-of-image reads clamp to the edge, as dctl-workbench and Blink's `eEdgeClamped` do. Resolve's own rule is undocumented, so this one must be written into the spec.

## The node slots in where Film did; colour and storage need rulings

### Graph, plan and GPU placement

`docs/23` lists DCTL among the kinds "not in this version" and says the format, validator and plan "are built so they can be added as new node kinds without changing the format" ([docs/23 §1](../docs/23-nodes.md)). The Film node is the template. It added a `NodeKind`, which touches every exhaustive `match` in [graph.rs](../crates/ym-core/src/settings/graph.rs); a schema definition, validator, patches and settings fields; a line in `plan_graph`, a step type in `node_set` and a footprint in the scheduler; its parameters in the grade cache key; and a pipeline minor version that makes older builds refuse the document. All of that was done without changing any existing graph by a bit ([docs/24](../docs/24-film.md)). A DCTL node needs the same list plus the source hash in the cache key. Bypass, masks, key outputs, thumbnails, copy and paste, dead branches, undo and DNG baking come free once the node returns LogC4 per pixel. One thing cannot be automated: **identity skipping**. Nobody can prove user code is the identity at its defaults, so a live DCTL node always runs. The default graph never contains one, so the 61 golden files stay byte-identical. The pixel readout and histogram see a DCTL only if the CPU evaluator also runs inside `ColorChain::trace`.

On the device there are two places to put the code. **(a) Splice it into the fused colour kernel's node loop.** This is cheap per frame. But every new DCTL then recompiles the whole colour kernel, about 250 ms on lavapipe ([docs/23](../docs/23-nodes.md)). The kernel already uses all eight storage buffers and one uniform that K3 allows ([color.wgsl](../crates/ym-gpu/src/shaders/color.wgsl)). And a user's validation error or hang would take the entire colour pass off the device for the process ([kernels.rs](../crates/ym-gpu/src/kernels.rs)). **(b) Run a separate pass whose picture is made before the colour pass and read from the pass buffers, as Film's is.** This isolates faults and keeps the colour kernel's bytes unchanged, at the cost of a pass and its planes. **Option (b) is the recommendation** for a feature whose whole point is running code Yellowmoon did not write.

### Colour space is the real compatibility problem

Every node works "LogC4 / AWG4 … there is no per-node colour space". The look, the cine rendering and the encode all come after the last node ([docs/23 §1.2](../docs/23-nodes.md); [docs/02](../docs/02-colour-pipeline.md)). A DCTL carries no colour-space metadata at all. Blackmagic's README calls the inputs only the "input pixel's RGB values" ([BMD README](https://github.com/thatcherfreeman/utility-dctls/blob/main/Documentation/DCTL%20Documentation.txt)). In practice authors write for the encoding of their Resolve node tree, often DaVinci Wide Gamut / Intermediate or a camera log. That is an inference the notes could not confirm against Blackmagic text. External emulators simply pick a default: dctl-workbench uses ACEScct ([dctl-workbench](https://github.com/nordsound/dctl-workbench)).

Feeding LogC4 to a DCTL tuned for DaVinci Intermediate gives a plausible-looking but wrong picture. That will be the most common complaint, and no compiler work fixes it. LogC4 values can also run negative and reach linear 469.8 at code 1.0 ([docs/02](../docs/02-colour-pipeline.md)), which can upset DCTLs written for 0-to-1 display data.

`ym-color` has typed AWG3, AWG4, AP0, Rec.709, P3, Rec.2020, XYZ, LogC4 and LogC3, plus a working LogC4 → LogC3 → back route used by LogC3 looks. It has no DaVinci Wide Gamut, no Intermediate, no ACEScct and no S-Log3 ([docs/02](../docs/02-colour-pipeline.md)). There are three ways to bridge the gap. The simplest declares LogC4/AWG4 as the contract, which is honest and suits ARRI-oriented DCTLs but leaves most others wrong. The second gives the node an **"Expects" choice** that wraps the DCTL in a conversion and back: LogC3/AWG3 and linear AWG4 can come from existing code, while ACEScct and DWG/Intermediate need new `ym-color` types whose published constants and licence have not yet been checked. The third serves display-referred DCTLs through the Film node's "variant A": the cine rendering forward, then the DCTL, then the numerical inverse. That costs about 1.7 µs a pixel on the CPU and leaves about 5 % of 8-bit sRGB colours unreachable ([docs/24](../docs/24-film.md)). The recommendation is the "Expects" choice, starting with the spaces that already exist, with the display-referred route held back until someone asks for it.

### Storage, references, and how the app and `ym` find the same file

The persistence list is exhaustive. It holds `preferences.json`, `looks/` (with a `manifest.json` of id, name, input encoding and SHA-256 per file), and logs. "The node graph adds nothing to it" ([docs/01 §Persistence](../docs/01-architecture.md)). Keeping imported DCTLs therefore needs the owner, under hard rule 4. The looks library is a ready-made model. Ids are written `user:<slug>`. Identity is id plus SHA-256, and new bytes under an old name become a new entry (`user:mine-2`). A missing or changed file shows "File missing or changed. Import again." The app and `ym` share the folder (`YELLOWMOON_HOME`) and a `.lock`. Exports record `ym:Look` and `ym:LookSHA256` ([docs/08](../docs/08-looks.md); [xmp.rs](../crates/ym-export/src/xmp.rs); [docs/10](../docs/10-cli.md)).

**Option A** copies that pattern exactly. The node stores `{ id, sha256 }` plus parameter values keyed by `DEFINE_UI_PARAMS` variable names. Import captures the DCTL's whole closure (the file, every `#include` and every `DEFINE_LUT` target, confined to its folder) and hashes each file. The XMP gains a `ym:DctlData` field like Film's `ym:FilmData`. `ym` resolves the id through the same library, so the bytes match between the app and `ym` on one machine.

**Option B** embeds the source text in the settings. That makes documents self-contained and leaves rule 4 untouched. It also breaks the JPEG XMP ceiling of 65,502 bytes for large DCTLs, forces includes and LUTs to be inlined, and puts whole source files into undo entries ([docs/23](../docs/23-nodes.md)).

Option A is recommended. Under it, a missing DCTL should be handled like a mask this machine cannot make, not like a missing look. The node shows as unable to run, the app refuses the export, and `ym` fails that photo with a plain sentence while the rest of the run continues ([docs/23 §3.10](../docs/23-nodes.md)). Silently bypassing a node changes the picture. Option A has one cost authors will notice: editing the source and re-importing creates a new entry rather than updating documents. That protects old exports, but the panel needs a "Reload from file" that makes this plain.

### The panel: controls from data, labels from the author

The panel picks its tabs by kind. Every control writes one node patch, one undo step ([NodeTabs.tsx](../src/screens/nodes/NodeTabs.tsx); [docs/24](../docs/24-film.md)). Rule 6 means the core parses the parameter list and hands it to the page through a command, as `film_catalogue` does for Film. The page then renders it generically, and values are clamped to the declared ranges with `PatchReport::clamped`. Glasscn covers four of the six control kinds. The float and int sliders map to the project's `Slider`, the value box to `ValueBox`, the check box to glasscn's `Switch` (glasscn has no checkbox) and the combo box to glasscn's `Select`. **The colour picker has no glasscn control** and needs a design decision: three sliders, or a reuse of `Wheel` ([AGENTS.md](../AGENTS.md)). Labels are the DCTL author's text, emoji included, so the project's British plain-copy rule cannot apply to them, and the spec should say so. Build errors become a plain sentence with a line number, the counterpart of Resolve's "DCTL Build Error" dialog. Yellowmoon's rule is "very few controls", but the node view already sits behind a button. A code node there leaves the default interface untouched. The process stays the one Film followed: mockups first, then Playwright on the mock API, glass-audit states and screenshots the owner reviews ([docs/23](../docs/23-nodes.md)).

### Performance: cheap on the GPU, slow on the CPU, costly on first use

A per-pixel DCTL as one extra pass should cost about as much as one more node or pass. On lavapipe the fused loop takes 10.7 to 14.6 ms for one node and 92.5 to 163.9 ms for sixteen at 512 × 384 ([docs/23](../docs/23-nodes.md)). Film is the warning case. Its separate passes made a warm viewer frame 3 to 4 times as costly (48 dispatches against 18), and the owner still closed its speed target on 0.2.1 with "Speed is fine now" ([docs/24](../docs/24-film.md); [STATUS](../docs/STATUS.md)). First use is the visible cost. A DCTL's pipeline cannot be warmed before a document uses it. A colour-kernel-sized compile is about 250 ms on lavapipe, and the on-disk pipeline cache helps only on Vulkan. So the app should compile in the background at import and at document load, and key the cache by source hash. Any parameter change frees G-13's whole-image levels, as with every node ([docs/17](../docs/17-gpu.md)).

On the CPU, an interpreted f32 IR plausibly costs 50 to 500 ns a pixel, an estimate that has not been measured. That is 2.5 to 35 s for a 50 to 70 MP export on one thread, against Film's per-pixel colour part at 0.9 µs. Viewer frames on the CPU would miss the 100 ms target by a wide margin. The GPU route is therefore a requirement for release, not an optimisation.

## Verdict: build a per-pixel DCTL subset, CPU first, in phases

The "dropped for now" decision is recorded in four places, none with a reason. `docs/23` lists "DCTL and OpenFX" as not in this version. `docs/16` has the row "Dropped | DCTL (for now), the list view". STATUS says "DCTL, OpenFX, presets and the list view are out". The node mockup notes say "DCTL was dropped at the owner's request" ([docs/23](../docs/23-nodes.md); [docs/16](../docs/16-risks-and-decisions.md); [STATUS](../docs/STATUS.md); [mockup notes](../design/nodes/mockup-notes.md)). The research cannot recover the reason. The costs set out above are the obvious candidates: a whole compiler, a colour-space contract, user code under the GPU rules, and a market whose paid half is locked. None of them is a blocker. **Reopening is the owner's call. If they make it, the build is feasible and should be scoped as follows.** Support the RGB per-pixel `transform` with full UI parameters. Run alpha forms with `p_A = 1`. Refuse texture form at first. Refuse transitions, parametric ACES and `.dctle` for good. Use a generic node name and a library reference by id and hash. Run the device as a separate pass under D8, with an f32 `libm` CPU reference. The order follows Film's F-07 → F-08 → F-09 sequence ([docs/24](../docs/24-film.md)). Effort figures are rough engineer-week estimates, not measurements. They are anchored on dctl-workbench's 18.7k-line compiler and the Film node's footprint: about 40 Rust files across four crates and the shell, about 20 frontend files and roughly a dozen test suites.

| 8 | Device policy | Device for views and exports under D8 with tolerance parity; or CPU-only exports for documents with a DCTL | Device under D8; CPU pins the goldens |
| 9 | Fast-math hardening | Own maths library only; plus barriers on every operation in exports | Own maths library always; barriers only if corpus parity shows flips |
| 10 | Texture form | Refuse; bounded reach by static inference; whole-image mode | Refuse first; bounded reach in phase 6; never whole-image on the device |
| 11 | Fixtures and oracles | MIT/BSD corpus by SHA-256; GPL or unlicensed corpora in CI; own C++ shim oracle | MIT/BSD only, avoiding ARRI-derived numbers; GPL and unlicensed excluded; shim in CI only |
| 12 | Authoring and panel | In-app code editor; or import-only with Reload; colour-picker control | Import-only with "Reload from file" (new entry on new bytes); build errors as a sentence with a line; colour picker as three sliders until a design round says otherwise |

## Conclusion

The compiler is not the hard part. One MIT project has already shown that DCTL lowers to naga IR, and Yellowmoon has the rest of the machinery: a graph built for new kinds, a Film-shaped template, a `.cube` engine and a hash-checked import library. The real difficulty is that DCTL is a contract with no stated colour space and no stated arithmetic. Resolve leaves both to whatever node tree and GPU backend the author happened to use. Yellowmoon has pinned down exactly those two things for everything else it runs, with typed colour spaces and the K8 and D-rule discipline. So a DCTL node is less a port than a translation of an informal contract into a formal one. The "Expects" choice, the clamping rule, the edge rule and the f32 `libm` reference are the actual product. The parser is plumbing.

That also changes the question of value. The paid DCTL market is locked inside `.dctle`, and the best free DCTLs are GPL, which users may run but Yellowmoon may not ship. So the node would not import an ecosystem. It would give Resolve-literate colourists a way to bring their own maths to stills. As probably the first non-Blackmagic host, Yellowmoon would also be in a position to define what "portable DCTL" means in practice. A published, clean-room specification of the subset it runs, with its edge, rounding and colour rules, could matter more to that community than the node itself. Whether that is worth 14 to 22 weeks against the product's "very few controls" promise is exactly the judgement the owner deferred with "for now".
