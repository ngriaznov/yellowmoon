All image processing happens in `ym-*` crates. `src-tauri` and `ym-cli` are thin front ends: they translate user actions into `ym-core` calls and show results.

### Building the app crate

`tauri-build` checks at compile time that every `bundle.externalBin` and `bundle.resources` path exists, on every `cargo build/test/clippy` of `src-tauri`. So:

- `tools/dev/prepare-sidecar.sh` (written in M0-01) builds `ym-cli` and copies it to `src-tauri/binaries/ym-<host triple>`; CI and `npm run tauri dev` (via `beforeDevCommand`) run it first. Release builds copy the per-architecture binaries and the universal one (`release.yml`).
- `data/models/` and `data/looks/builtin/` exist from the start with a README, so the resource paths resolve before M1/M2 fill them.

### Dependency rules

- `ym-core` depends on all other `ym-*` library crates. Nothing depends on `ym-core` except `src-tauri` and `ym-cli`.
- `ym-color` is pure maths with no GPU dependency. `ym-gpu` depends on `ym-color` for constants and CPU reference functions used in parity tests, and on `ym-noise` for the noise model the raw algorithms take (`docs/algorithms/INTEGRATION.md` §3).
- `ym-raw` has no GPU dependency; it returns CPU buffers.
- No crate under `crates/` depends on Tauri, the webview, or `tools/oracle`.
- `ym-cli` does not depend on Tauri.

## Core concepts (ym-core)

### Session

A `Session` holds the photos opened in this run, in memory only.

```rust
pub struct Session { photos: Vec<Photo>, current: usize, picked: BitSet, defaults: SessionDefaults }
pub struct Photo {
    id: PhotoId,                 // stable for the session only
    path: PathBuf,               // original, never written
    meta: RawMetadata,           // camera, lens, exposure, dimensions, compression, timestamps
    camera: CameraMatch,         // detected body + profile used + why (exact / sensor family / default)
    auto: AutoEstimates,         // illuminant, exposure, WB, noise model, sharpening — computed once
    settings: DevelopSettings,   // user offsets from auto; defaults = "Auto" everywhere
    caches: PhotoCaches,         // decoded mosaic, previews; evictable
}
```

Opening files: `Session::open(paths)` probes each file (fast metadata read, no full decode), then a background job decodes, estimates and renders a thumbnail for each. Progress events drive the start screen's "Developing N photos" list.

**As built (ym-core: `session.rs`, `auto.rs`, `camera.rs`).** The structs above are the shape, not the code: `Session` holds its state behind one mutex and a decode pool, takes `&self` everywhere (`Arc<Session>` is how the app shares it) and keeps the photo's own estimates next to the ones it serves.

- *Environment.* `SessionEnv::load(data_root)` loads the profile registry, the noise priors (`cameras/noise`) and the illuminant models (`models/illum/<profile>.json`); `with_events`, `with_thumbnails`, `with_default_look`, `with_decode_threads`, `with_forced_profile` (the CLI's `--profile`, refused with the valid ids when unknown) set the rest. `EventSink::new(callback)` or `EventSink::channel()` receives the events. The sink runs while an internal lock is held, which is what makes "no event after `close()` returns" true, so it must not call back into the session.
- *Opening.* Folders are walked for `*.ARW` (extension compared case-insensitively), one level unless `OpenOptions { recursive: true }` (the CLI's `--recursive`); other files and `.`-files (macOS's `._DSC0001.ARW` resource forks on exFAT cards) are ignored and counted in `OpenOutcome::ignored`; paths that do not exist are listed in `missing`; a file already in the session (same canonical path) is not added twice (`already_open`). A photo's path is made absolute against the working directory without resolving symbolic links (`ym render .` and `ym render DSC0001.ARW` work like their absolute forms, and the folder name and `<folder name> export` of a `.` or `..` folder come from the folder it resolves to). Photo ids count up for the life of the `Session`, also across `close()`, so a command that names a closed session's photo gets `UnknownPhoto` and can never reach a photo of the next session. What is found is sorted by path, case-insensitively, probed in parallel (`ym_raw::metadata::probe`) and registered before `open` returns, so the filmstrip has its photos at once. `OpenOutcome::no_arw()` / `message()` is the Start screen's "No ARW files in what you dropped." (nothing ARW at all; not when everything was already open). A probe that fails makes a photo that is Skipped with the `RawError` text of `docs/04`: the UI's CAN'T OPEN. The first photo of an empty session is current; `SessionState::folder_name` is the one folder given (or the one folder all photos share, else `None`), `default_export_folder` is `<parent>/<folder name> export` (the export queue still checks it is writable and falls back to `~/Pictures/Yellowmoon export`).
- *Jobs.* One job per photo on a pool of `min(available_parallelism - 2, 6)` threads (at least one; `default_decode_threads()`), CPU only: decode, `AutoEstimates::compute`, then the thumbnail hook (`ThumbnailRenderer`, implemented by the render graph; without one the photo is Ready after its estimates). The pool takes the current photo's job first. A failing job ends in Skipped for that photo only, a panic inside a development job is caught, logged with its message and reported the same way (a panic while prefetching a neighbour's mosaic is only logged, and the thread survives either way), and a decode error is `RawError`'s text (ARW 6.0 included, so the `arw6` feature needs no change here). `close()` bumps an epoch: queued jobs are dropped, running ones stop at their next stage and their results and events are discarded; the session is empty and reusable at once (it does not wait for the pool).
- *Events.* Per photo, in this order: `probe(done)`, `decode(start)`, `decode(done)`, `estimate(start)`, `estimate(done)`, `thumbnail(start)`, `ThumbnailReady`, `thumbnail(done)` (= Ready). A failure after the probe ends the sequence with one event whose `stage` is the failing one, `done = true` and `error` set (Skipped); a file that fails the probe has just `probe(done, error)`. `SessionEvent::EstimatesChanged { id }` is added to the list in this document: it is sent when other photos finishing moved a photo's shared exposure (below), and for the current photo when its pooled noise model changed.
- *Mosaic cache.* At most `MOSAIC_CACHE_LEN` (3) decoded mosaics: the current photo's and its neighbours' (by filmstrip index). A mosaic outside that window is dropped when its job is done; `Session::raw_image(id)` decodes again when something needs one (the render, Pick white, Re-run) and keeps it only if the photo is in the window. `set_current` re-fits the window and queues the missing neighbours (prefetch jobs run after development jobs). **One decode per photo at a time:** `raw_image` is single-flight, so callers that ask for a photo that is being decoded wait for that decode and share its image instead of reading the file again (after a jump to an uncached photo the viewport frame, the histogram, a tile for each look of the Look tab and the prefetch all ask at once; each used to decode a mosaic of its own, 122 MB at 61 MP, against the budget of three; a leader that fails or panics wakes the others, which look again and fail with their own error; tests: `tests/session.rs` `callers_that_ask_for_one_uncached_mosaic_at_once_share_one_decode`, the `SingleFlight` unit tests). **A prefetch is checked when it runs:** the job is dropped unless its photo is still in the window and not cached yet (stepping through photos faster than they decode left jobs for photos already passed, each decoded once and thrown away by `cache_offer`, competing with the photo finally reached for the cores; `a_prefetch_queued_for_a_photo_the_person_has_left_decodes_nothing`). Previews are not kept: the 1/8 preview is 11 MB for 61 MP and exists only while the estimates are computed.
- *Estimates the photos share.* Burst median exposure (`docs/02` Auto exposure step 6) and pooled noise (`docs/06` Batch pooling) depend on the other photos, so the session keeps each photo's own `AutoEstimates` and serves `Session::estimates(id)` / `view(id)` with the burst median in `exposure.ev` (`own_ev` stays) and the pooled model in `noise`. Photos that do not state their ISO are not pooled (each keeps its own estimate: the ISO is part of the pool key and an absent one cannot be told apart). Both are deterministic functions of the set of photos (checked for 1, 3 and 4 decode threads): the burst groups are recomputed over every photo with estimates, the pool of a group (`NoisePool`) is built from its first 16 photos in id order, whichever finished first. **App/CLI parity for early exports.** The CLI waits for the whole session (`wait_idle`) before it exports, so its files carry the final shared estimates. An export queued earlier, from the app, must write the same bytes, so `Session::estimates_final(id)` says whether the estimates of a photo that depend on other photos are final: every photo of its burst (the groups are made over every photo with a capture record, by metadata alone) and every photo of its noise pool (model, ISO, bit depth, compression) has its own estimates or has failed. It is not about thumbnails, prefetching or viewport renders, which an export must not wait for. `ExportQueue::start` records, before it snapshots each photo, whether that was already true; for a photo for which it was not, the job's turn for that photo waits (a poll of 25 ms that a cancel interrupts) until it is, then takes the estimates (burst median exposure and pooled noise) from the session again and keeps everything else of the snapshot (settings, Pick white sample) as it was queued. A photo with no estimates of its own yet cannot be snapshotted (`QueueError::Developing`, "Some photos are still being developed. Wait until they are ready, then export again."). If the session is closed while a job waits, development has stopped for good and the job goes on with the estimates it was queued with. Tests: `tests/export_queue.rs` (a job queued while its burst is developing waits, then writes the bytes the wait-for-idle path writes, and a photo outside the burst and the pool does not hold it up), `tests/session.rs` (`estimates_final`). A pooled model is used only if its variance at three signal levels is within 1.6 of the median of its members' own (`POOL_AGREEMENT_FACTOR`). That check used to be what rescued three frames of one scene, which `ym_noise::BatchPool` pooled to 1.77e-4 for a true 5e-4 because it treated merged bins as independent samples (`docs/06`, Implementation notes: a merged bin is now as precise as its best member and no more); the same frames now pool to their own fit with the check passing (`tests/auto.rs`), and the check stays for a pool that contradicts its members' own models (a group that mixes filtered and plain frames, files with different in-camera processing at one ISO), where each file keeps its own estimate. Pooling frames that cover different intensity ranges works as intended (three such frames: a within 2% of the truth and b within 20%, which no single frame resolves).
- *Apple Auto worker (`docs/19`).* With an advisor (`SessionEnv::with_apple_auto`: the app and `ym` give one through `CoreOptions::advisor`, nothing else does) the session has one more thread. While Apple Auto acts (an advisor, the `apple_auto` preference or the run's `AppleAutoMode` on, and the advisor available, read again when a session opens, when the status is asked, when the preferences change and before each export) it asks the advisor about one photo at a time: the photo on screen, then the photos an export waits for (`ExportQueue::start` moves them up, and the session moves each one's burst frames without an answer up with it), then the others in filmstrip order. The picture it shows is rendered by the `PictureRenderer` hook (`pipeline::AdvisorPictures`, a renderer of its own without the GPU) from the photo's **own** estimates, so it does not depend on the order photos develop in; the development job renders it after the thumbnail and keeps at most 64 at a time, and the worker renders the others from the file when their turn comes. The call blocks the worker only, never a caller's thread, and never under the session's lock; `rateLimited` and `concurrentRequests` are tried twice more 2 s apart, every other error fails the photo, which then uses the rule. A panic anywhere in a request fails that photo (kind `other`) and the worker goes on; a worker that cannot start or stops leaves the session as one without an advisor, so nothing waits for it. The answer (or the failure) is kept in memory with the photo, also while Apple Auto is switched off, and dropped by Re-run (which asks again), by new instructions for the model (`Session::set_apple_auto_instructions`: every photo is asked again, the photo on screen first, and an answer to the older instructions that arrives later is dropped) and by `close()`. The served estimates take its values on top of the rule's (burst frames share the median of their steps, `docs/19` section 5), the photos whose values or state moved get `EstimatesChanged`, and those whose picture changed a new thumbnail (`ThumbnailReady`; a photo still developing gets it after its first). `estimates_final` also waits, while Apple Auto acts, for the photo's and its burst's answers, so an export waits for them exactly as for the burst's exposure; `wait_idle` waits for the worker too (`ym` waits for the answers of the photos it develops). The viewer never waits: a photo is served with the rule until its answer arrives. Tests: `crates/ym-core/tests/apple_auto.rs`.
- *Photo view.* `Session::view(id)` returns a `PhotoView` (path, probe metadata, `PhotoCamera`, profile, a snapshot of the settings, the served estimates, the Pick white sample, `estimates_version`) for the render graph and the export queue. `estimates_version` changes whenever the served estimates or the Pick white sample change (the sample is taken when the pick is set, so a new pick bumps it); it belongs in the render cache key of the stages after C1.
- *Camera.* `PhotoCamera` composes `ym_profiles::detect` with `ym_raw`'s `DecodeKind`: `reduced` (Lossless M or S), `stand_in` (anything but `Exact`), the `CameraCopy` of docs/03 and, for the RAW tab, `card()`: Detected, Profile, STAND-IN, the explanation, the REDUCED tag with the note of docs/04 and, for ARW 6.0 and other layouts without a decoder, the unsupported message.
- *Estimates in detail.* See `auto.rs`. The illuminant is `ym_color::illum`'s model for the camera's profile with the as-shot white balance as its prior (`RawImage::wb_as_shot` is stored per CFA position; `auto::as_shot_rggb` reads it by colour, so a BGGR or GRBG mosaic does not swap red and blue; every Sony body is RGGB, where the two agree). **Fallback** (a profile without a model file, or a model that fails): the as-shot white balance as a camera white `[g_G/g_R, 1, g_G/g_B]` (green is the mean of the two greens of SR2 0x7313), confidence 0.5, class probabilities from its CCT alone (tungsten up to 3500 K, daylight from 4500 K, a linear blend between, nothing for fluorescent and LED); a file with no white balance at all gets the profile's 5500 K daylight white with confidence 0. The 1/8 preview bins the photo's area (the camera's crop, else the active area, else the readout) 8 × 8 per colour; its clip mask marks a block when any photosite in it is at or above `white − 4·qstep` (or 0.995 of the range without a qstep plane). A Lossless M or S file has no mosaic: its preview comes from the RGB data, normalised with **one range for the three channels, the green one**, not channel by channel (`docs/04` gives red and blue lower white levels because the camera's white balance was divided out again: dividing each channel by its own range would put the camera's balance back, and the initial gains `g0` would then balance the data a second time; found in review, a neutral grey metered 0.4 EV too bright with a strong colour cast in the estimator's view; the render's normalise stage R1 must scale this layout the same way, so that channel `c` clips at `1 / g0_c` as `docs/02` C1 says; clipping is still judged against each channel's own white level), its noise model is the centre of the body's prior (`NoiseSource::PriorOnly`; ISO 100 is assumed when the file has no ISO), and a frame the estimator refuses (too small) is treated the same. Sharpening and noise-reduction Auto come from `ym_gpu::cpu` (`auto_sharpen`, `NoiseReduction::auto`) so the card and the render agree; the base ISO of the sharpening ramp is the gain-regime table's (100 when the body is not in it). Kelvin and tint are the Auto readout of the all-Auto, EV 0 chain.
- *Auto exposure meters the picture the render makes (as built, 2026-10-13).* `docs/02` step 1 says "C1–C6 with EV = 0 on the 1/8-resolution preview" and is silent about the lens corrections; the render divides every photosite by the lens's relative illumination (R3, `docs/05`), so a preview without that gain meters a darker picture than is rendered (the tools/eval study found the lens-corrected renders of five of the nine real files 0.07 to 0.12 EV brighter than metered). `auto::build_preview` therefore also computes the R3 gain `1 / G(r)` at the centre of every 8 × 8 block (`Preview::vignette_gain`, from the same 0x7032 table and the same radius as `VignetteProfile`; none for a file without a usable table, and none for Lossless M and S, which the render does not correct either), and `Preview::metered(g0)` applies it before the initial gains, in the order of the raw stages. Only the metering reads it: `Preview::as_raw_preview` (the illuminant estimator's input, whose contract is the sensor's own picture, `docs/02`) and the clip mask are unchanged. The estimates are made when the photo is opened, before any setting changes (the CLI patches its options after the open too), so the gain does not follow the RAW tab's `decode.lens_corrections` switch: the exposure is metered as the default render shows the picture, and a user who turns the corrections off keeps the exposure of the corrected picture, as for any other setting that only Re-run would pick up. A file whose table corrects nothing (every knot 0, as the synthetic golden set's files have: `G = 1` exactly) meters byte for byte as before, so those renders are unchanged. On the nine real files (illuminant models on) `EV_auto` moved by −0.06 (ILCE-5000), −0.05 (ILCE-6300), −0.10 (A7 II), −0.07 (A7 III) and −0.10 EV (A7 IV), the five with tables (corner gain 1.2 to 1.8), and not at all for the other four, which have none; the test is a flat field behind a vignetting lens that must meter like the same field without the lens (`tests/auto.rs`: −0.585 EV both, −0.504 EV without the gain).
- *Measured here.* Synthetic scenes (`crates/ym-core/tests/common`: a known light, brightness and Poisson-Gaussian noise): the as-shot fallback reads 2800 to 7500 K back within 50 K; auto exposure of a flat neutral scene lands on `log2(0.18 / Y)` within 0.08 EV (and follows the camera's exposure compensation at half weight); a ramp's noise is recovered within 1.1% in sigma and 15% in `a` (three seeds, ISO 800); the shipped illuminant model for the A7R IV profile finds the light of a patchwork scene within 0.55° from the pixels alone and within 0.49° with the right as-shot prior (2.9° at worst, and under half the camera's own error, when the as-shot white balance is badly wrong, daylight gains under 2800 to 6500 K light). On the nine real files of `testdata/real/files` (local, not committed) every file develops (all nine in 2.2 s on two threads); auto exposure is +0.6 to +1.9 EV (median +1.0). The old M1-08 metric on those nine (our render at `EV_auto` against the embedded JPEG, median luminance in linear light, `tests/real_files.rs`, kept as an informational printout): 6 of 9 within 0.5 EV, errors in stops A300 −0.94, A500 +1.19, ILCE-5000 −0.42, ILCE-6300 −0.49, A7 II +0.37, A7 III −0.22, A7 IV −0.41, NEX-5N −0.28, NEX-7 +0.80. It is not the gate: since the decision of 2026-10-13 (`docs/16`) the gate is G3, `EV_auto` against the camera engine's own gain (`tools/eval/autoexp.py`, `docs/02` Evaluation), which removes the display transform and the shape of the camera's curve that the old metric mixes in; nine files decide nothing either way. All 48 files of `testdata/synthetic` (every raw variant, with gradient, noise, clipped and dark content) develop; the dark ones meter to the +3 EV limit.

"Auto" values resolve against `AutoEstimates` at render time. The UI shows the resolved value with an AUTO tag; moving a slider turns it to `Manual`. "Reset" restores `Auto`. "Re-run" on the Automatic card recomputes `AutoEstimates` and resets exposure, the white lift's offset, WB and noise to Auto, and contrast and saturation too while Apple Auto acts on the photo (`docs/19` section 5).

**Applying to several photos.** The Look card's "Apply to" (This photo / Picked / All) copies `look` and `look_intensity` to those photos. Other controls apply to the current photo only. Every `update_settings` names its photo and the core applies it to exactly that photo; `apply_look` names no photo (the core's own "current photo" is only what This photo means to it, and the webview never sends This photo: it sends the photo's `update_settings` alone), so the webview sends the copies in the order of the picks, one at a time, and reads again the settings of every photo whose look a copy changed (`docs/11`, *Apply to*). **Copy settings and Paste settings** (the owner's request of 2026-10-16, `docs/11` §Copy and paste settings) are the one way to move the rest between photos: `copy_settings(photo_id)` makes a `SettingsPatch` from a photo's settings (`SettingsPatch::copied_from`: every field but `crop`, `orientation` and `white_pick`, which belong to the photo's own geometry and pixels; Auto stays Auto; a white balance that came from a picked white, meaning a white picked with the light preset and the white balance both Auto, becomes the manual Kelvin and tint it resolved to; a manual white balance next to a pick, and a preset chosen after a pick, are copied as they are), and `paste_settings(photo_ids, patch)` applies a patch to many photos in one call (`Session::paste_settings`). The patch lives in the webview store for the running app only: never written to disk (hard rule 4), never put on the system clipboard. Export can target the current photo, picked photos or all.

**As built (ym-core: `settings.rs`).** `DevelopSettings`, its patch and `ResolvedSettings` have the serde shape of `src/api/types.ts` (snake_case, `kind`-tagged unions); a test compares the field names of every wire type with its interface in that file, so a drift fails in CI. The same JSON is the `ym:Settings` XMP property, the CLI's `--settings` and the golden manifest; `crates/ym-core/schema/settings.schema.json` is its JSON Schema (tested against what the core writes, against documents it refuses, and against the ranges the core clamps to).

- *Reading.* Missing fields take their defaults (a settings file may hold only what it changes), unknown fields are an error (a typo is not a silent no-op). `look` is an `ym_looks::library::LookId`. `orientation` is a number of degrees; any multiple of 90 is read and normalised (-90 is 270). Writing always writes every field. `DevelopSettings::from_json` / `from_value` read a document over the defaults of a photo opened with the user's default look (a document without `look` gets `default_look`, where `DevelopSettings::default()` alone says Neutral), clamp it like a patch and report the fields that were changed; a misspelt field or a value of the wrong type is `SettingsError::Parse` with serde's message. `ym render --settings` should read its file with it.
- *Output sharpening (`output_sharpening`, owner's decision of 2026-10-13).* An `f64` in percent, 0 to 200 (`OUTPUT_SHARPENING_RANGE`), default 100 (`OUTPUT_SHARPENING_DEFAULT`), a plain number and not an `AutoOr`: Reset (`SettingsPatch::reset`) and the UI's row Reset send 100. Its `SettingsField::OutputSharpening` belongs to `StageGroup::Output`, the last group, so a patch that changes it alone re-runs only the sharpening of the frames already rendered (below). A settings document, a `--settings` file or an `ym:Settings` written before the field reads as 100 (serde's struct default), `from_json` clamps like any field, and a value that is not a number is refused (`SettingsError::NotFinite("output_sharpening")`). It is written with every other field into the `ym:Settings` of an export (`ResolvedSettings::pinned_settings` keeps it as it is) and into the CLI's `settings` object, in `settings.schema.json` and in `ResolvedValues`; Re-run (`reset_automatic`) leaves it alone. The UI row is Detail › Sharpening › Output (`docs/11`), the CLI option `--output-sharpening` (`docs/10`).
- *Colour warp (`color_warp`, the owner's request of 2026-10-17; as built 2026-10-17).* `ColorWarp { pins }` of `ColorWarpPin`, which is `ym_color::warp::WarpPin` with serde (`From` both ways; `ColorWarp::to_color` gives the `WarpParams` of stage C9b). Reading: every pin field but `source` may be left out (`target` is then `source`, `locked` false, `range` 0.04, `shadows` and `highlights` 1, `pivot_ev` and `exposure_ev` 0); `target: null`, a pin without `source` and unknown fields are refused; writing writes every field. Checking (`validated`, every patch) keeps the first `WARP_MAX_PINS` (16) pins and clamps each with `WarpPin::clamped` (points scaled back to `|c| <= 0.5`, the range to 0.01…0.25, the weights to 0…1, the pivot to ±6 and the exposure to ±2 stops; a locked pin's target is its source and its weights, pivot and exposure the defaults), and reports `SettingsField::ColorWarp` in `clamped` when anything changed; a point that the scaling leaves one ulp outside the disc (about one in fifty) is moved inside, so a second check changes nothing and a later patch never reports the warp as changed. A number that is not finite in any pin is `SettingsError::NotFinite("color_warp.<field>")`. `SettingsField::ColorWarp` (`"color_warp"`) belongs to `StageGroup::Grade` and is in `SettingsField::ALL`, so Copy settings takes it (it is not in `COPY_LEAVES_OUT`), Reset gives no pins, and a patch replaces the whole list (`{ "pins": [] }` removes them). `ResolvedValues::color_warp` and `pinned_settings` carry the pins as stored. The render: `pipeline::color::warp_params` sets `ChainParams::warp` in `grade_plan` (the device path takes the pins from the chain's parameters), and the grade key holds the warp as the chain prepares it (`Warp::new`), so a pin that moves re-renders while locked pins alone, or a pin whose target is its source, leave the key and the frame as they are without them. `PIPELINE_VERSION` is unchanged: no pins (and locked pins alone) skip the stage, so every render without the warp has the pixels it had; the `ym:Settings` an export records now includes `"color_warp":{"pins":[]}`. The JSON Schema has `color_warp` (`$defs/warp_pin`, `$defs/chroma_point`). Tests: `tests/settings.rs` (reading with and without the optional fields, 17 pins to 16, clamping, the locked target, non-finite values, idempotence on random points, patch and Reset, Copy settings), `tests/render_api.rs` (a warp moves the picture, locked pins alone and the Before view are byte for byte unchanged, the grade key, `chroma_scatter`, `sample_chroma`), `tests/render_graph.rs` (a warp rebuilds the grade group only), `tests/session.rs` (paste), `crates/ym-cli/tests/render.rs` and `parity.rs` (`--settings` with pins, app and `ym` byte for byte).
- *Clamping.* A number outside its range is clamped, not refused; `PatchReport::clamped` names the fields. What is refused (`SettingsError`, nothing applied: patches are atomic) is a value that is not a number, a curve that is not a curve (2 to 16 points; they are clamped into the unit square and sorted by x; two points at one x are refused), a crop without area, and a Pick white spot the chain refuses. Colour-balance points longer than 1 are scaled back to the circle; a crop rectangle is moved and shrunk into the photo, its angle clamped to ±45°. Steps (0.01 EV, 50 K) are the UI's granularity: the core keeps the value it is given, so `--wb 5025` means 5025 K.
- *Patch.* `SettingsPatch` is `Partial<DevelopSettings>` with `crop: null` and `white_pick: null` clearing the field (absent leaves it). Two generosities beyond the TypeScript type: `decode`, `rolloff`, `color_balance` and `curve` may carry only the parts to change, and a manual `white_balance`, `sharpen` or `noise_reduction` may leave out a part, which then keeps its current resolved value (a patch with only `kelvin` on an Auto white balance is Manual at that Kelvin and the Auto tint: that is what moving one slider means). `apply_patch` reports the fields that changed and the first render-stage group they affect (`StageGroup::{Raw, Color, Grade, Geometry, Output}`, the table below; `SettingsField::group()`), which is what the render graph invalidates by. **Linked fields:** a patch with a `white_pick` also sets `light_source` and `white_balance` to Auto unless it says otherwise, so the picked spot renders neutral and the Kelvin and tint rows show the picked light (`docs/11` Pick white: "the core sets the white balance from the pick"; it does it through the scene light, `docs/02` C1). The frontend records undo from the settings before and after a change, so the extra fields are restored with it. A preset (`light_source`) does not clear a pick: the chain applies the pick first and the preset after it, so Day, Shade and Tungsten override it and LED and Fluorescent keep the picked chromaticity.
- *Pick white.* `white_pick` is `[x, y]` as fractions of the photo **as the camera oriented it** (EXIF orientation applied; before the user's crop, straighten and `orientation`, so the point keeps pointing at the same spot when those change). `auto::display_to_sensor` maps it back to the sensor. The session samples the 5 × 5 median of g0-balanced camera RGB at that point when the pick is set (`auto::pick_white_sample`: a cheap 3 × 3 same-colour demosaic on the raw data without the vignetting gain, which scales all three channels alike) and keeps the sample with the photo; `PhotoView::picked_white()` is what goes to the chain. The viewport (part 2) converts clicks in the photo cell to this space before it sets the pick.
- *Resolving.* `ResolvedSettings::resolve(photo_id, settings, estimates, profile, picked_white)` builds the fused chain (`AutoEstimates::fused_chain`) and takes the Kelvin and tint from it, so with `white_balance` Auto they follow a light preset (Day 5500 K, Shade 7500 K, Tungsten 3200 K, tint 0; LED and Fluorescent keep the estimate's CCT) and a picked white. `AutoFlags` says which of exposure, light source, white balance, sharpening and noise reduction are still Auto; the UI's "white balance counts as automatic only when `white_balance` is Auto, `light_source` is Auto and no white was picked" is the UI's rule on top of these flags. `ResolvedSettings::pinned_settings()` is the document an export records as `ym:Settings` and the CLI prints as `settings`: exposure, sharpening and noise reduction that are Auto are written as the manual values they resolved to (a manual value renders exactly like the Auto it came from, and the file then says which numbers were used), white balance stays Auto when it was (a manual white balance at the shown Kelvin and tint does not render like Auto: the tint scales the green gain and Kelvin is rounded to 50 K, so the numbers it resolved to go in the `auto` object of the CLI output instead).
- *Session commands* (all on `Session`, same names as the IPC commands): `state()`, `set_current`, `set_picked`, `pick_all`, `clear_picks`, `settings(id)` (`get_settings`), `update_settings(id, patch)`, `replace_settings(id, settings)` (the CLI's `--settings`: clamped like a patch), `apply_look(scope, look, intensity)` (This photo is the current photo; skipped photos are left out; intensity clamped), `rerun_auto(id)` (recomputes the estimates on the calling thread, sets exposure, `light_source`, `white_balance`, `white_pick` and `noise_reduction` back to Auto and keeps sharpening and everything else), `copy_settings(id)` (the portable patch of a photo's settings, above) and `paste_settings(ids, patch)` (below), `set_default_look`. Settings live in memory with the photo and nowhere else (hard rule 4). Commands may arrive from several threads (one per slider move; a Pick white decodes the photo again, which takes a while): `update_settings` applies its patch to the settings the photo has when it commits and starts again from the current ones if another command changed them meanwhile, so two commands on different fields both take effect in either order; `replace_settings` is the last word and never retries. A command on a session that was closed meanwhile returns `UnknownPhoto`.
- *Removing photos* (the owner's request of 2026-10-20; `ym-core`: `session.rs`, `app.rs`, `pipeline/graph.rs`, `scheduler.rs`; the UI is `docs/11` §*Removing photos*). `Session::remove(ids) -> RemoveOutcome { removed, current, estimates_changed }` takes photos out of the filmstrip and `Session::restore_removed() -> RestoreOutcome { restored, already_open, current, estimates_changed }` puts the last removal back (`restorable()` lists what it would). **The files on disk are not touched** (AGENTS rule 5; `tests/session_remove.rs` compares bytes and modification times); nothing is saved per photo (rule 4), so a photo's settings, picks, estimates and place go into one `Removal` kept in memory until the next removal that takes something out, `close()`, or files opened into the emptied session (a new session begins; ids that are not in the session are ignored and do not replace it). One call under the emit lock and the state lock: (1) the photos leave `photos`, `index`, `picked` and `known` (so the same file can be added again), their mosaics leave the cache, and the current photo hands over to the next photo that stays, else the previous one, else none (an emptied session reports no folder; the next `open` sets it); (2) queued development and prefetch jobs for them are dropped, and a job that is running stops at its next stage: `progress` and the thumbnail event check that the photo is still in the session, and each photo carries an `incarnation` that a removal bumps, which a job copies when it is queued, so the job of a photo that was removed and put back (its development restarts as `Waiting`) cannot report as the new one; **no event about a removed photo is sent once `remove` returns**; (3) the estimates the others share are made again from the photos that are left, **the burst median exposure** of the frames of its burst and the pooled noise of its noise group (`State::refresh_effective`, `rebuild_pool`: both stay functions of the set of photos), and the photos whose served estimates moved get `SessionEvent::EstimatesChanged` and are in the outcome (the shell's event sink tells the webview with `settings_changed`, as it does for every `EstimatesChanged`, and `remove_photos` and `restore_photos` queue them a new thumbnail); (4) the new current photo's neighbours are queued for decoding. `restore_removed` inserts each photo at its old place (a file added again meanwhile stays out and is counted in `already_open`), brings back picks, the folder of an emptied session, and the photo on screen: the removal's current photo is current again when it was taken away and the person has not moved since (`current == successor`). `Core::remove_photos` adds the renderer's side: `Renderer::retire_photos(ids)` marks the ids (a request that was on its way is refused as cancelled, as after a close), cancels their queued and running viewport, tile, thumbnail, histogram, readout and look-tile jobs on the CPU scheduler (`JobScheduler::cancel_photos`) and on the device (`Scheduler::cancel_owners`), forgets their graphs and the thumbnail statistic, and lets go of the photo being looked at when it is one of them; `Core::restore_photos` lifts the mark first. **Export jobs are the one thing not cancelled**: `ExportQueue::start` snapshots every photo of its scope, so a running or queued export keeps the photos it was started with and finishes them (`load_raw` decodes from the file when the session no longer has the photo, `wait_for_final_estimates` goes on with the queued estimates), and an export render of a retired photo drops the graph it made when it is done. One caveat, accepted: a job queued while the photos of its burst or noise pool were still developing re-reads the shared estimates when its turn comes, and that is from the photos that are left then. `ym` has no removal (it is a front end of one run). **Apple Auto** (`docs/19` section 6; merged on 2026-10-20). A removed photo keeps its answer or its failure in its `Removal`, with the rest of what the session keeps of it, so a photo that comes back with one is not asked again; nothing else about it stays live. `State::take_out` drops its picture (`apple_picture`, in memory only, hard rule 4), takes it out of the order of the photos an export waits for (`apple.urgent`) and bumps its incarnation; the worker only looks at `State::photos`, so a removed photo is never chosen. `Inner::apple_store` and `apple_recover` drop an answer or a failure whose photo is not in the session or has another incarnation (`AppleTask::incarnation`): that is the request that was in flight when the photo left, also when the photo was put back since (it comes back without an answer and is asked again), and the retry loop stops asking about a photo that left. The steps a burst shares are made again by the same `State::refresh_effective` that makes the burst median exposure again (`share_burst_steps` over the frames that are left); the photos whose values moved are in `estimates_changed` (they are sent `EstimatesChanged`) and their thumbnails are drawn again (`Inner::repaint`, after the event lock is let go), and `remove` and `restore_removed` wake the Apple Auto worker and whoever waits in `wait_idle`. An export that waits for the answer of a frame or a photo that left stops waiting: `estimates_final` of the frames that are left no longer counts it, and for the photo itself it is `UnknownPhoto`, which the queue reads as "go on with the snapshot it was queued with". `put_back` drops the answers of a removal whose `instructions_gen` is not the session's (new instructions dropped every answer of the session, and these photos were not in it), puts a restored photo without an answer into `apple.urgent` when a photo an export waits for has it in its burst (`State::prioritise`, which `Session::prioritise_apple_auto` also uses), and leaves the restored photos out of `estimates_changed` (the restore hands them over) but not out of the thumbnails drawn again. The tests are in `crates/ym-core/tests/apple_auto.rs` (section *Removing photos from the filmstrip, and Undo*) and `session_remove.rs` (*Apple Auto*). The shell: `AppApi::remove_photos` / `restore_photos` (commands `remove_photos(photo_ids)`, `restore_photos()`, both answering `SessionChange { photo_ids, already_open, session }`) forget the pending thumbnail requests of the photos, set their thumbnails aside in the `FrameStore` (`set_aside_photos`: not served, kept for Undo; the next removal drops the earlier ones; Undo announces them again at the addresses they had) and follow the current photo with the renderer and the viewport (`sync_current`).
- *Copy and paste (`Session::copy_settings`, `Session::paste_settings`, `SettingsPatch::copied_from`, `COPY_LEAVES_OUT`).* The patch `copied_from` makes holds every part of every manual value (a manual white balance carries both Kelvin and tint, sharpening both amount and radius, and so on), so it applies to a photo that has no automatic estimates yet and needs no seeds. `paste_settings` takes the state lock once, strips `crop`, `orientation` and `white_pick` from the patch whatever it says (a paste never touches the photo's own geometry, pick or sample), skips a photo that is not in the session, failed or has no estimates yet (the same test as `Session::view`), applies the patch to a copy of every other photo's settings first (`DevelopSettings::apply_patch`, the same code as `update_settings`, so the result is what `ym render --settings` would make of those settings: rule 6) and stores them only if every one applied, so a patch that cannot be applied changes nothing. It answers `PasteReport { pasted: [{ id, before, after }], skipped }`: `before` and `after` are patches of just the fields that changed (`SettingsPatch::of_fields` of the old and the new settings), the pair the webview keeps as that photo's one undo step; both are empty when the photo already had the settings. Nothing is rendered or resolved in the call. Cost: about 5 µs a photo in the core (59 photos took 98 µs; the same 59 with one `update_settings` each took 311 µs), so the reason for the one call is the bridge, not the core: five hundred photos are one command, not a `get_settings` and an `update_settings` each. `Core::paste_settings` refuses a look in the patch that is not in the library or whose file is gone, as `apply_look` does (`LooksError`), and changes nothing.
- *In the shell.* `AppApi::paste_settings` draws the viewport again if the current photo changed, queues a thumbnail for every photo that changed (`Thumbnails::refresh`, 300 ms settle, thumbnail priority behind the viewport: a paste onto five hundred photos does not render them on the foreground worker), and emits `settings_changed` once for each (the webview asks again only for a photo whose settings it holds that the paste did not report). `open_paths` and `open_dialog` answer with `SessionState.opened: { added, already_open }` (the counts of that call, `OpenOutcome`; null in every other answer), which is how Photos says "Added 3 photos. 2 were already open." when files are added to a session.

### Render graph

Each photo's render is a fixed chain of stages (`docs/02` and `docs/05`). Each stage has a cache key made from its inputs. Changing a setting invalidates only the stages after the first one it affects:

| Stage group | Invalidated by |
|---|---|
| Decode, black/white, clip mask | never within a session |
| Noise estimate, illuminant estimate, auto exposure, white lift estimate | Re-run |
| Vignetting, highlights, demosaic+denoise, detail controls, sharpening, lens resample (R3–R9) | `decode.*`, `noise_reduction`, `sharpen` |
| WB, sensor map, ARRI matrix, AWG4, exposure, highlight range and toe, LogC4 (C1–C8) | `light_source`, `white_balance`, `white_pick`, `exposure`, `rolloff.*` |
| Primary grade, look, curve, white lift and ACES 2 (DRT), display encode (C9–C13) | everything else (except `output_sharpening`); the white lift's amount is the photo's automatic one plus `white_offset_ev` |
| Geometry (crop, straighten, orientation) | `crop`, `orientation`: applied when sampling for display and export; no pixel stage re-runs |
| Output sharpening (the last stage: the display-linear picture at the size it is shown or written, then C13) | `output_sharpening`; it also re-runs after every change above, because it sharpens what they made. Moving its slider re-runs only this stage on the display-linear frame already rendered. |

Most edits only re-run the last group, which is cheap (one pass of per-pixel maths and two LUT lookups) and must stay interactive (< 16 ms for the viewport at screen resolution).

**As built (ym-core: `pipeline.rs` and `pipeline/*.rs`).** A `Renderer` (cheap to clone, one per app or CLI run; `Renderer::new` returns `RenderError::Thread` only when the operating system cannot start the render thread) owns one `PhotoGraph` per photo, the three most recently used (`MemoryBudget::max_photos`), and every call takes a `PhotoSource`: a snapshot of one photo's decoded image, profile, estimates, settings and Pick white sample (`PhotoSource::from_session`, `from_view`, or the thumbnail hook's input). A settings change is therefore just a new source; each group compares the key of its inputs with the key of what it holds and recomputes only on a mismatch, so "a change invalidates only the groups after the first one it affects" is a property of the keys, not of notifications (`tests/render_graph.rs` pins it by counting what ran per request: `RenderReport::runs`, and `RenderReport::timings` for how long).

- *The groups and their keys.* **Decode**: the photo's area cut out of the readout (`FrameData`: the camera's crop, else the active area, else the readout; copied only when it is not the whole readout; quantisation steps as f32) lives for one request and is not cached, because a copy per photo would be a second decoded mosaic beyond the three of the session. **Raw (R1, R3 to R9)**: an `RgbImage` (planar f32, camera RGB balanced with `g0`) per reduction `k`, keyed by `RawParams` (the gains `g0`, all four `decode.*` switches, the resolved noise reduction and sharpening, the ISO and the noise model; not the estimates' version: a burst median that moves only the exposure leaves this group alone) and `k`; the noise sigma plane is cached on the noise model and `g0` alone. **Colour (C1 to C8)**: the fused matrix and the C7 parameters, keyed by the scene light, `light_source`, `white_balance`, `white_pick` and its sample, `exposure`, `rolloff` and the noise model. **Grade (C9 to C13)**: the prepared `ym_color::display::ColorChain`, keyed by the colour key, the grade controls, the curves, the look (id, intensity and the LUT file's SHA-256), the display choice and the output. Keys are the numbers themselves (an f64's `Debug` text is its shortest exact form), so equal keys mean equal pixels. A graph also remembers a fingerprint of the decoded image (size, levels, white balance and a few thousand samples) and drops everything when the image behind a photo id changes (a second session, a file replaced), which `tests/render_scheduling.rs` checks. The renderer keeps the graphs of the `MemoryBudget::max_photos` most recently used photos **and the graph of the photo being looked at** (`Renderer::navigate`): the thumbnails of a folder that is still developing touch every photo in turn, and without the exception they pushed the current photo's reduced images, tiles and finished frames out one thumbnail at a time (found in review, `tests/render_review.rs`). **Geometry** is not a group: orientation, straighten and crop are applied while sampling (below), so changing them re-runs only the sampling and the per-pixel colour pass.
- *Why the colour and grade groups cache a plan, not an image.* The per-pixel stages are one fused pass (on the GPU one compute dispatch from camera RGB to RGBA8, on the CPU `ColorChain::render_u8`), so there is nothing between C8 and the display worth keeping: a cached C8 image would cost 4 floats a pixel, need `ym-color` to expose C9 from LogC4, and save about a fifth of a pass. What a colour or grade edit reuses is the raw group's image; what it re-runs is one pass over the pixels shown. The viewport frame cache (`FrameOptions::no_cache` to bypass) serves a repeated request without even that. (With output sharpening on, the default, one image is kept after all: the display-linear frame under the last stage, which is what makes the Output slider cheap; see *Output sharpening* below.)
- *Raw group below full resolution* (`pipeline/raw.rs`): the fit view, the thumbnails and the look tiles. R1 and R4 run on the full mosaic, R5 only on the 128-row bands that hold a clipped photosite (exactly `highlights::reconstruct`'s result; nothing at all when no photosite is clipped, which `RawPlan::has_clipped` answers by the same rule as R1's mask), the photosites are binned `k x k` (`bin_mosaic`; a box filter is the demosaic at 1/k scale): green is the mean of the block's greens, red and blue the mean over the block of their lattice interpolated linearly (a few partly weighted sites beyond the block), because the plain mean of a block's reds sits half a photosite up-left of its middle and that of its blues half a photosite down-right, which put a red and blue fringe on every sharp edge of the Fit view (a lens-blurred step came out with red and blue 85 display codes apart at 1/2 and 22 at 1/4; now 15 and 9, and the chroma-edge energy of the nine real files' Fit views falls by 10 to 42 %: found in review, `tests/render_review.rs` and `raw.rs`; a linear ramp bins to three equal planes in every CFA phase), the vignetting gain is applied per output pixel (after R5: the gain is smooth, `max(original, estimate)` commutes with it), the bilateral denoise runs with the sigma the binning left (`ym_noise::sigma_map::sigma_quad` on the unvignetted data, then times the gain and `binning_noise_factor(k)`: `sqrt(sum_c w_c^2 v_c)` with the variance factor `v_c` of each colour's mean, `2 / k^2` for green and the squared sum of the lattice weights per axis, squared, for red and blue, 0.52 at 1/2; measured against flat noisy mosaics in `pipeline/raw.rs`), and R9 resamples with the lens maps built for the smaller frame and the full-resolution auto crop scaled by 1/k. **R7 and R8 are skipped below full resolution**: radii and PSFs are in full-resolution pixels (`docs/05`) and binning has averaged the noise they cure; the fit view therefore is not sharpened, the 100 % view is.
- *Full resolution*: `ym_gpu::cpu::chain::Chain` with the photo's levels at the area's parity, vignetting profile, `g0`, the lateral CA correction on the mosaic (R5b, when the lens has a CA table), the adaptive ratio demosaic (`DEFAULT_METHOD`; it gets `g0` and the noise model on the 16-bit working scale, read as zero noise when the model is unusable; Menon, LMMSE, bilinear and log-guided only through the test-only `RenderOptions::demosaic`), the bilateral denoise (skipped when Luminance is 0), the Detail controls, R8 (Richardson-Lucy, skipped for 0 iterations; diffraction deconvolution only when the internal `PhotoSource::capture_method` asks and the photo has an f-number and a pixel pitch, `docs/05` R8), the lens maps with their auto crop, and a full-frame sigma map from `sigma_quad`. `highlight_recovery` is switched off inside the chain when the frame has no clipped photosite. The 100 % view is made of 512 px tiles (`Chain::run_tile`) cached per `RawParams`; an export renders in tiles of 1024 px (`Renderer::render_full`), each tile's source rectangle found by mapping the tile through the geometry, so only one tile of intermediates is alive. A tile or a render that is cancelled leaves nothing half-made in a cache. The tile sizes (`RenderOptions::tile_px` 512, `full_tile_px` 1024) belong to the bit-identity contract of `AGENTS.md` rule 6: the stages are tile-exact to 0 or about 2e-7 (R8 beyond its halo cap), which can move a 16-bit code, so the app and the CLI must both keep the defaults.
- *What a full render makes* (`FullTarget`). `DisplayLinear(output)`: C1 to C12 for JPEG, TIFF and PNG, with the orientation (the camera's and the user's), straighten and crop **baked into the pixels**. The two DNG targets follow `docs/09` ("Pixels": the raw pixels keep the lens auto-crop only and the user's crop goes into the default crop tags; "90° steps go into the TIFF Orientation tag without rotating pixels") and `ym_export::dng::DngParams` (the raw and the preview "not rotated"): `DngLinearAwg4` is C1 to C11 decoded to linear AWG4 in the **buffer's own orientation**, uncropped, with the user's crop as `FullImage::window` (whole pixels, on the buffer, for the default crop tags) when there is no straighten angle; with an angle the angle and the crop are baked in (a DNG has no rotated crop), still unturned, and `window` is `None`. `DngPreview` is the sRGB display-linear picture in the same unturned orientation, cropped and straightened as the user sees it, so it has the size of the window. The writer takes the `Orientation` tag from `ym_export::dng::compose_orientation` (the file's EXIF orientation and the user's quarter turns). `Geometry::upright` makes the unturned geometry from the baked one: the crop window is rounded on the canvas first and then mapped through the turns on the pixel lattice, so the three images hold exactly the same pixels, and a mirrored EXIF orientation (2, 4, 5, 7) reverses the sense of the angle; `tests/render_review.rs` and the unit test in `geometry.rs` check it against an independent forward map for all 8 orientations, 4 turns, three angles and fractional crops. (Before the review `DngLinearAwg4` baked the turns and the crop too, which the DNG writer would have turned a second time through its tag.)
- *The Before view's raw front (2026-10-16, `docs/02` *The Before view*).* The Before view leaves out R3: `PhotoSource::for_before_view` marks the source, `RawParams::vignetting` is off for a photo that has a vignetting table to apply, and the flag is part of the raw group's key, so the Before view's groups, tiles and display and frame entries are its own. The graph keeps two plans and two prepared chains per photo (with and without R3); the sigma plane, which is made before the gain, is shared; a photo with no table to apply shares the final picture's raw front.
- *Camera-processed files (Lossless M and S)*: one range (green's) for the three channels in R1, `g0`, the light bilateral denoise with a prior-only noise model, R7 and R8 at full resolution; no R3, R5, R6 or R9 (the camera applied its own shading and lens corrections to the pixels it wrote). Reduced scales bin the RGB image; the full-resolution image is the group at `k = 1`, there are no tiles.
- *Geometry* (`pipeline/geometry.rs`, the frontend's model from `src/fixtures/grade.ts`): the buffer is turned by the EXIF orientation, then by the user's `orientation` (clockwise quarter turns) into the *canvas*; `crop.angle_deg` rotates the photo about the canvas centre (clockwise positive, the canvas keeps its size, its corners may be empty) and `crop.rect` is a rectangle of the canvas, normalised. Every output pixel maps to a buffer position through one composed affine map and the dihedral turn; a pixel copy where the grid lines up (orientation only), Catmull-Rom while rotating or magnifying, a box-filtered bilinear when shrinking by more than 1.25. Pixels that fall outside the photo are the paper colour in a viewport frame and zero in a full render. **At full resolution the grid is on the pixel grid** (`Geometry::at_full_resolution`, used by the 100 % tiles and exports): the crop rectangle is a fraction of the canvas, so its edges fall between pixels, and sampling it as it was made every cropped export and every 100 % view of a crop a bicubic resample half a pixel off (visibly softer than the uncropped export, found in review); now the crop origin is rounded to a whole pixel (kept inside the canvas), an output of exactly the crop's size maps one pixel to one pixel, and without a straighten angle sampling copies pixels. Viewport frames at exactly 100 % do the same for the pan (below). A reduced image keeps the fractional crop: it is resampled anyway. `white_pick` is in the oriented photo over the image area before the lens crop; `Renderer::pick_point_at` converts a click (through the straightening, the turn and the lens maps) to it.
- *Output sharpening, the last stage (as built, 2026-10-13; the owner's decision, `docs/16`).* Every display-referred picture ends with `docs/algorithms/04-output-sharpening.md` at the size it is shown or written: the screen preset (radius 1 px, threshold 1 level, method smooth gain, halo suppression 60 %, reference luma weights) at the amount `DevelopSettings::output_sharpening`, so the slider "Output" is the spec's `amount_pct` and nothing else is exposed. **Where.** In a viewport frame, a thumbnail or a look tile (`pipeline/frame.rs`, module documentation) the colour chain stops at C12 and gives display-linear f32 for the view **grown by the stage's receptive field** on every side (`ViewSharpening::halo`, `SharpenPlan::halo_px`: 17 px at full size, less when shrunk, 21 at most), the stage sharpens the photo's own pixels in it, the border is cut off and C13 (the transfer function and the dither at the pixel's place in the view) makes the 8-bit frame; for an export the stage sits in the writer right after the Lanczos-3 resize (`docs/09`), and never for a DNG. **Scale.** `s = long edge shown / long edge rendered at full resolution` (`scale_for_edges`): for a viewport frame the zoom, for a thumbnail its size over the photo's, 1 for the 100 % view and for a full-size export. **Above 100 %** the stage runs on the 100 % picture the view magnifies (`s = 1`: the pixel grid an export has, over the part of the final image the view covers plus the halo and the 2 px of the magnifying filter, clipped to the final image), and the sharpened picture is then magnified to the view with the Catmull-Rom filter every magnified view uses, so the view at 200 % is the sharpened export at 200 % (`tests/render_sharpen.rs`, within one code); the colour chain then also runs at 100 % and the magnifying is done in display-linear light. **The picture's own edge.** The stage works on the bounding box of the pixels inside the photo and mirrors at its edge, as it does at the edge of an export, so a letterbox (paper around a fitted photo) never leaks into the photo and a straightened photo's empty corners are sharpened against black, as an export sharpens them. **Caching.** The display-linear frame of the grown view is cached per photo (`PhotoGraph::cached_display`, `DisplayFrame`, the byte budget of the finished frames), keyed by everything the frame depends on **except the amount** (the raw group's key, the grade plan's key, geometry, the view and the halo): moving the slider samples and colours nothing again and runs only the stage and C13 (`StageRuns { output_passes: 1, display_hits: 1 }`, the test `tests/render_sharpen.rs`); the finished 8-bit frame is cached too, with the amount in its key, so going back to a value that was shown is a frame-cache hit. An edit of any group above re-runs the stage on its new display-linear frame. 0 (and anything below 0.1 %) creates no stage: the plain road runs (sampling and the fused colour pass, `output_passes` stays 0) and the frame is what the viewport drew before the stage existed. The Before view, the histogram and the pixel readout are not sharpened (the Before view is not the finished picture, the others read colour at a point). **100 % view.** The tiles the grown view reads are prepared with it (`Renderer::prepare_tiles` reads the same frame geometry: the view grown by the halo, or the 100 % picture a magnified view covers, or a coarse frame would wait for tiles nothing computes), and a view at 100 % shows exactly the part of the sharpened export it covers: a pan is a window of the whole picture within one code (the dither is the only difference), and a view the size of the photo equals the exported picture sharpened at `s = 1` and encoded (`tests/render_sharpen.rs`). **GPU.** The stage and C13 run on the device with the colour pass when the renderer's stages allow it (*View stages on the device*, below); otherwise the colour pass (on the device or not) gives display-linear f32 to the host and the stage and C13 run on the CPU. **The CPU stage is cancellable:** it runs in strips of 256 rows with the stage's receptive field of context above and below (the tiling contract of spec 04 section 5.2, so the whole-frame result bit for bit: `sharpening_tests::the_cpu_stage_in_strips_is_the_stage_on_the_whole_frame_bit_for_bit`), side by side on the rayon pool, and each strip looks at the request's cancel token before it starts, so a frame nobody wants any more stops after the strips that are running (about 0.45 Mpixel each on a 2 MP fit frame) instead of after the 0.5 to 2.6 s of the whole stage. One strip after the other the frame took 1.8 times as long as in one piece (a strip gives the stage's own bands of 128 rows too little to share among four cores); side by side it takes 1.02 to 1.17 times as long (1764 x 1189 and 2948 x 1988 at the fit scale, four shared cores). **Cost.** See *Measured* below: the stage is the largest cost of a finished frame at the CPU, and every edit above it pays it again.
- *View stages on the device (`pipeline/frame.rs` and `pipeline/frame/device.rs`).* With a `ym_gpu::device::Gpu` in `RenderOptions::gpu`, a viewport frame, a thumbnail and a look tile are **one device job each**: the raw group's pixels (the reduced image, or the window of 100 % tiles the view reads, cut to the rectangle the view samples from) are uploaded as camera RGB, the sampler maps them through orientation, turns, straighten and crop into four planes (RGB and the letterbox mask), the colour chain makes C1 to C12 from them with the persistent tables of `ym-gpu` (an unchanged chain uploads nothing, a look cube goes up once), and output sharpening fused with C13 and the dither makes the RGBA8 frame, which is the one readback; a frame without the stage (amount 0, the Before view as the colour kernel's RGBA8 stop) is the colour pass to C13 in one dispatch. The job carries the request's priority (Viewport, TileNeural, Thumbnail; a thumbnail's job never passes a viewport's) and owner, and the render's own cancel token: a cancelled render or a navigation to another photo drops its queued job at once, a running job ends within itself. Nothing in the job waits for the rayon pool (the upload planes, the sampler's grid and the photo's bounding box are made on the render thread). **Which stage runs where** follows `GpuStages` (`RenderOptions::gpu_stages`, the policy's set: `Auto` runs `SIGNED_OFF`: since 2026-10-14 the raw chain, the sampler, the colour pass, output sharpening and C13, and since 2026-10-15 the export tail and the raw front, each signed off after Metal CI passed (`docs/16`); `On` and `Require` all): `SAMPLER` off means the CPU samples (`sample_to_camera`, a call of `ym_gpu::cpu::sampler`, the kernel's CPU reference, kept bit for bit equal to the function it replaced by `sampler_tests`) and the sampled pixels are uploaded; `COLOR` off means the CPU colours; the stage and C13 are one fused device pass, which runs when `OUTPUT_SHARPEN`, `ENCODE` and `COLOR` are all on, else both stay on the CPU, which then reads the display-linear frame back. Every one of the 16 subsets renders the CPU's picture within the golden gates (`tests/render_gpu.rs` `every_subset_of_the_view_stages_renders_the_picture_of_the_cpu`). **A view magnified above 100 %** (since 2026-10-20; before, its stage and magnification ran on the CPU) is one device job as well when the tail is on: the colour pass makes the 100 % picture under the view, the stage sharpens it at `s = 1` into a copy of it, and the magnification kernel (`ym_gpu::kernels::magnify`, `magnify.wgsl`) samples that copy with the Catmull-Rom filter for every device pixel of the view, paints the paper and encodes (C13 fused) into the RGBA8 frame. The kernel reads taps the host makes (`ym_gpu::cpu::magnify::MagnifyMap`: per column and per row of the view, the four source indices with the edge replicated, the four `f32` weights, the mask sample and the inside test, in `f64` by the CPU reference's own code, `frame::magnify_map`) and does only the sums, in the CPU's order behind the fast-math barrier, so the magnified values are the CPU reference's bit for bit and the codes differ only by C13's rounding (`docs/17-gpu.md` section 16). A magnified view whose 100 % picture (16 bytes a pixel) or RGBA8 frame does not fit `view_band_bytes` is cut into bands of rows like any other view (`band_split`): each band reads the 100 % picture under its own rows, the stage's window is the whole view's box moved to where that picture starts (`magnified_band_window`, so the stage mirrors only at the photo's edge, as in one piece), the dither counts from the band's row, and a row's taps come from the band's map (the view's with the band's offset folded in, one `f64` rounding, as for the sampler's bands), so the bands are the view in one piece (`tests/device_frames.rs` finds them identical, straightened photos with the empty corner across the cuts included). With the tail off, or a map that is not a scale and a translation (no viewport makes one), the view keeps the host road: the device colours the 100 % picture and the CPU sharpens and magnifies it (`magnify_and_encode`, which runs the same reference, `magnify_with`). **The Output slider.** With the tail on the device the display-linear frame (`DisplayFrame`, four f32 planes over the view grown by the stage's receptive field) **stays resident on the device** in the display cache, its bytes counted in the cache's budget and in the pool's ledger; a move of the slider is one small job that sharpens and encodes it again (measured on lavapipe for a 576 x 384 cell: one submission, 2 KB of uniforms uploaded, the 884,736-byte frame read back, `StageRuns { output_passes: 1, display_hits: 1 }`, no sampler and no colour pass; `a_move_of_the_slider_is_one_small_job_with_no_sampler_and_no_colour_pass`). A resident frame is used only for a tail on the same device, a host frame only for a tail on the CPU. **Views too big for one binding.** A view whose frame (16 bytes a pixel over the grown view) or camera RGB does not fit `RenderOptions::view_band_bytes` (128 MiB, the design binding of `docs/17-gpu.md` section 4, a constant so that the cut does not depend on the machine) is cut into horizontal bands, each a view of its own with its own grown frame and the dither counted from the band's place in the view; the bands give the pixels of the view in one piece bit for bit (`a_view_cut_into_bands_has_the_pixels_of_the_view_in_one_piece`, also for the reduced images of a large photo). A 5K cell or the retina fit view of a 50 MP photo (its 1/2 image is 150 MB) is cut. Three rules keep the cut exact and keep it on the device (found in review, `tests/render_gpu.rs`): **the stage's window is the whole view's.** The stage works on the bounding box of the pixels inside the photo, so every band is given the box of the frame of the view in one piece, cut to its rows (`band_window`; a band's own box is narrower where a straightened photo's edge is slanted, and the stage would mirror there where the view in one piece sees the black of the empty corner: 4 codes at the slanted edge, `bands_of_a_tilted_photo_with_empty_corners_have_the_pixels_of_the_view_in_one_piece`); the box is found from the geometry alone (`prepare_view_with(.., pixels: false)` assembles no tile) and is part of a band's display-cache key. **Whichever stages are on.** The cut is made whenever the colour pass is on the device: with the sampler off the CPU samples each band and uploads it, and with the tail off (`Auto`, the colour pass alone) the device makes the display-linear frame in bands of rows (`build_display_in_bands`: the chain is pointwise) and the CPU stage then takes the whole frame; before this a frame above 8.39 Mpixel (a 5K cell) went to the CPU quietly under `Auto`. **A band of paper** (a panorama in a tall cell) reads nothing of the photo, uploads nothing and is the device's like any other band (`Done::paper`); before this it counted the whole group against the binding and sent the whole frame to the CPU. A rotated strip is read through its bounding box, `width * tan(angle)` rows tall even for one row, so a view whose single row would still read more than one binding (about 8000 pixels wide at a tilt of 10 degrees, at 100 %) cannot be cut by rows and is made on the CPU, with `Require` too; cutting such a view into tiles is left to a later task. **Faults.** A device error makes the whole frame again on the CPU with the note "The graphics card could not render this frame, so the CPU did: ..." (never a frame of both, also when one band of a cut view fails); a shader that does not compile switches the view stages off for the process, any other error but a buffer that does not fit (tried once more after the pool and the colour tables were let go, then the CPU for that frame) ends the route for the photo, and `Require` fails the request with `RenderError::Gpu` instead. The histogram's sample comes from the device sampler when it is on, and the counting stays on the CPU (`docs/17-gpu.md` section 11, the histogram row). Against the CPU reference on Mesa lavapipe (`tests/render_gpu.rs`, the raw chain on the CPU so that only the view stages differ): fit, retina, 100 %, a straightened crop, a quarter turn, amounts 0 and 200, a magnified view, ΔE00 on the golden runner's 1/4 downsample median 0, p99 0, max 0.082, at most one code of 255 and a mean of at most 7.1e-5 codes. The raw stages are on the device per `docs/05`.
- *Resident caches (`pipeline/graph.rs`, `pipeline/frame.rs`, `pipeline/frame/device.rs`).* With a device that runs the sampler (`GpuStages::SAMPLER`) and `RenderOptions::resident_caches` on (the default), the caches of the raw group hold `Backing { Cpu(Arc<RgbImage>), Gpu(Arc<ResidentImage>) }`: the reduced group `Job::group_backing(k)` as the bands of rows the device made it in (`GpuReduced`, one job per slab of work so that a viewport frame queued behind it waits for one step and not for the group), and the tiles of the 100 % view as the images `GpuChain::run_tile_device` left on the device. A view reads them in place: the sampler's input is the window of the group the view samples from, **gathered with the copy kernel** (`ym_gpu::kernels::copy::encode_gather`: a window that is one piece is that piece, else a copy made in the sampling job), which moves samples and changes none, so the frame is the one the host round trip (read the group back, upload the window) makes bit for bit; the fit frame of a photo reads back its RGBA8 frame and nothing else, and a 100 % frame over cached tiles uploads nothing. An entry is on one side only. A consumer that needs host pixels (the CPU colour pass, a device that failed under the frame, a device other than the one the pieces are on) reads the pieces back and **replaces the entry with the host image** (`Job::demote`: the cache's byte count is then the memory the entry takes where it is); if the device cannot hand them over (lost, out of memory) the CPU makes the group or the tile again, with a note, and the cache keeps that. The readout under the pointer (`Renderer::sample_pixel`, asked for on every move of the mouse) is such a consumer only when the pixels are on the host: pixels on the device are sampled there (`sample_view_in_place`) and one pixel comes back, so moving the mouse over the photo does not bring the caches back to the host and the next frame uploads nothing (found in review: the host read of a resident group replaced the entry and read the whole group back on the first hover). Device bytes are counted in the same `ByteLru` budgets as host bytes, with the budget of a cache that keeps images on the device clamped to an eighth of the device budget (`min(cpu_bytes / 6, gpu_bytes / 8)`), so the groups and tiles of a photo cannot fill the pool the working buffers of a render need; leaving the photo drops its tiles (`release_full_resolution`) and forgetting it drops everything, and the pool's ledger is back at the resident set (the raw words of at most two photos) when it does. The work ahead of a view (`Job::warm_tiles`) leaves its tiles on the device and brings no pixel to the host. **Neighbours.** `Renderer::prefetch_raw` (queued by `spawn_raw_prefetch` at `Priority::Thumbnail`) uploads the raw words of a photo the person has not reached yet, only while fewer than `RESIDENT_PHOTOS` (2) photos have theirs on the device, so that the photo being looked at and the one before it keep theirs; a thumbnail's own upload follows the same rule of the two-photo LRU. The numbers (readbacks, submissions, the ledger) are in `docs/05` "Device residency".
- *Look and display sources.* `LookProvider` (implemented for `ym_looks::library::Library`, `RwLock<Library>` and `Mutex<Library>`; `NeutralOnly` for tests) returns a look with a fingerprint; a look that cannot be loaded renders as Neutral in the viewport, with the library's words ("File missing or changed. Import again.") in `RenderReport::notes` of **every** request that uses the plan (a cached plan or frame carries its notes too, as does a cached lens plan with its "table ignored" lines; they were only on the request that built it, found in review), and is an error (`RenderError::Look`) for a look tile. `Renderer::set_display(DisplayChoice::{Aces2, ArriLut(id)})` is Preferences › Display rendering.
- *Noise floor of C7*: the read noise of the photo's model (`sqrt(b + sigma_row^2 + q^2 / 12)`), balanced by `g0`, carried through the fused matrix (exposure included) channel by channel as independent noise, and averaged over the three AWG4 channels.

### Preview strategy

- **Viewport at fit:** classical demosaic at reduced resolution (half or quarter, chosen so the image covers the viewport at ≥ 1 device pixel per image pixel), full colour pipeline.
- **Viewport at 100% and above:** neural demosaic+denoise on the visible tiles plus a margin, computed in the background; the classical result shows until each tile is ready.
- **Thumbnails:** quarter-resolution classical path, rendered once after open and on look changes.
- **Export:** full resolution, neural path (unless `decode.neural_demosaic` is off or no usable GPU).

The status text in the header ("Neural · 42 ms · Display P3") shows the active demosaic path, last render time and output space.

**As built.** The scale of the fit view is read as "the image has at least as many pixels as the viewport shows, so it is never upscaled" (the spec's "at ≥ 1 device pixel per image pixel" taken the other way round would shrink a 6000 px photo to 1500 px for a 1440 px cell and blur it): with `z` the zoom in device pixels per full-resolution image pixel, `z <= 25 %` uses the 1/4 image, `z <= 50 %` the 1/2 image and anything larger the full-resolution tiles (`frame::scale_for_zoom`). Thumbnails use the largest of 1/8, 1/4 and 1/2 that leaves twice the thumbnail size **of the picture they show** (after the crop: a crop to a quarter of the width is made from a finer image than the whole photo; full resolution for small photos or small crops), are rendered in **sRGB** (the webview shows a PNG without a profile as sRGB; the viewport is Display P3) with the photo's crop, straighten and turn applied, and are never enlarged. The neural path does not exist yet: every render uses the classical one, `render_stats.path` says `classical` and `RenderReport::notes` records "No trained demosaic model is installed yet, so the classical demosaic was used." (nothing when the user switched `decode.neural_demosaic` off). `Renderer::viewport_frame` can be asked for a `coarse_only` frame: when the zoom needs full-resolution tiles that are not cached, it serves the 1/2 image at once and marks the frame `sharp: false`; the app then queues `Renderer::spawn_tiles` at tile priority and asks again. `Renderer::last_stats` is the `render_stats` of the last **viewport frame** of a photo (a cached frame included): thumbnails, look tiles, the histogram, pixel readouts and exports of the same photo do not replace it (an export's 17 s must not become the header's status text). Moving to another photo (`Renderer::navigate`) frees the full-resolution intermediates (tiles, the prepared chain and its sigma map) of the photo left; its reduced images stay, so going back is a colour pass. The spec's "preview buffers for all photos" is kept for the three most recent photos and, for every photo, the thumbnail PNG the app holds: a 24 MP quarter-resolution image is 18 MB, five hundred photos would be 9 GB.

### Scheduling and threads

- **Decode pool:** `min(available_parallelism − 2, 6)` threads, CPU only. Decoding and metadata parsing never touch the GPU.
- **GPU thread:** one thread owns the wgpu `Device` and `Queue`. All GPU work is submitted through a priority queue: viewport frames > visible-tile neural passes > thumbnails > export.
- **Cancellation:** every job carries a token. Moving to another photo cancels its pending viewport and tile jobs, and the requests of the panels for it (the Look tab's tiles and the histogram). Filmstrip thumbnails and export jobs are never cancelled by navigation. Taking a photo out of the filmstrip cancels all of its jobs but its exports (*Removing photos*, above).
- **Memory budget:** keep at most 3 decoded mosaics (current, previous, next) and preview buffers for all photos in the session. Full-resolution intermediates live only while a tile job needs them. Budget defaults: 4 GiB GPU, 6 GiB CPU; read the actual limits from wgpu and the OS and scale down (the CPU budget is at most half of the installed RAM, 512 MiB at least). **Shared memory (`docs/17-gpu.md` section 8; proposal pending the owner, STATUS question 16):** on a machine whose GPU is the CPU's memory (Apple silicon; wgpu's `DeviceType::IntegratedGpu`) the two budgets come out of one pool (`MemoryBudget::for_unified_memory`): the GPU gets `clamp(RAM / 4, 512 MiB, 4 GiB)` and the CPU budget becomes `min(its own, 0.6 x RAM - GPU)`, so together they stay under 0.6 of the RAM and the CPU loses only what that bound takes (8 GB: 2 GiB GPU and 2.8 GiB CPU; 16 GB: 4 GiB and 5.6 GiB; 24 GB and up: 4 GiB and the CPU's 6 GiB). The first form of the rule lowered the CPU budget by the whole GPU amount and left every Apple-silicon Mac 2 GiB of CPU budget while only the colour pass used the device; the GPU figure is unchanged. A GPU with its own memory keeps 4 GiB and the CPU's 6 GiB. The device is opened with the GPU figure (`MemoryBudget::gpu_bytes` goes into `GpuConfig::memory_budget_bytes`; `ym_core::app::gpu::open_gpu`, which both front ends call, opens it again with the shared-memory figure when the first budget turns out to be wrong for the adapter) and the renderer's CPU budget follows (`Renderer::set_budget`). The rule is `MemoryBudget::for_unified_memory` and its constants in `scheduler.rs`.

**As built (ym-core: `scheduler.rs`).** Viewport, tile and thumbnail jobs run on one worker thread through `ym_gpu::queue::Scheduler` (the queue that fronts the GPU thread: highest priority first, equal priorities in submission order, no pre-emption, tokens, panics caught), so the ordering and cancellation rules are the ones its tests pin; each job is data-parallel inside (rayon, scoped threads), so a second *foreground* worker would only compete for the same cores. **Export jobs run on a second worker that gives way to the first** (`JobScheduler`): an export job starts only when no foreground job is queued or running, and `Renderer::spawn_full` looks again before every tile (`JobScheduler::wait_for_foreground`). With one queue and one worker an export was one long job that nothing could pass, so a viewport frame asked for during an export waited for all of it (4.5 s for a 6 MP test photo, about 36 s for 50 MP on four cores; found in review; `docs/13`: "an export cut into one job per tile row" is how `ym-gpu` does it, a count of pieces that is unknown here before the photo's plan exists). While an export tile runs a foreground job shares the cores with it; the overlap is bounded by one tile. The two workers have their own `JobError`/token rules unchanged: navigation cancels only foreground jobs, `cancel_all` and `shutdown` reach both, a cancelled export that is still waiting is called with its token set and returns `Cancelled`. `Priority::{Viewport, TileNeural, Thumbnail, Export}`; `Renderer::spawn_viewport_frame`, `spawn_tiles`, `spawn_thumbnail`, `spawn_look_thumbnail` and `spawn_full` submit at those priorities and return a `JobHandle`; `Renderer::thumbnail_renderer()` is the session's thumbnail hook (it queues the render at thumbnail priority and waits, polling the session's cancel flag, so a viewport frame asked for meanwhile runs first). `Renderer::navigate(photo)` cancels the pending and running viewport and tile jobs of the photo being left (their tokens are set; the render checks them between stages and tiles) and releases its full-resolution intermediates; filmstrip thumbnail and export jobs are untouched, and an export stops only through its own handle. **Panel requests are superseded** (`JobScheduler::submit_superseded`, used by `Renderer::spawn_look_thumbnail` and `spawn_histogram`): the Look tab asks for a tile per look and the Light tab for a histogram for every photo the person steps to, and a queued job holds its photo's decoded mosaic, so stepping faster than ~120 ms a tile (24 MP) piled up jobs and mosaics for photos nobody was looking at, and the current photo's own tiles waited behind them. Navigating away from a photo now cancels its queued panel requests, **drops their closures and with them the mosaic at once**, and sets the token of the one that runs (the handle resolves as `JobError::Cancelled`, and the app answers "The render was cancelled.", which the webview ignores); a request for the photo being moved to is never cancelled, whatever the order in which the move and the request arrive (`tests/render_scheduling.rs`). Memory: `MemoryBudget { max_mosaics: 3, max_photos: 3, cpu_bytes, gpu_bytes }` (`detect()`: 6 GiB CPU scaled down to half the RAM, 4 GiB GPU; `max_mosaics` is the session's figure, `MOSAIC_CACHE_LEN`, and `gpu_bytes` the budget the application opens the GPU context with: the renderer reads neither); the decoded mosaics are the session's (`MOSAIC_CACHE_LEN`), the render caches are byte-bounded LRU maps (`ByteLru`: reduced images one sixth of the CPU budget per photo, tiles one sixth, finished frames one thirty-second), and a full-resolution render reserves the output image plus one tile's working set in the `MemoryLedger` first, refusing with `RenderError::Memory` ("There is not enough memory to render this photo at full size. Close other apps or export a smaller size.") instead of starting.

### GPU tiling

- A 50 MP frame in RGBA f32 is ~0.8 GiB and exceeds wgpu's default 256 MiB buffer and 8192 px texture limits. Process in tiles of 1024 or 2048 px (configurable) with halos: half the network's receptive field (computed from the architecture; 64 full-res px for the starting U-Net), plus the resample's maximum displacement for the lens stage. A tiled-versus-whole-image test guards against seams.
- **Storage format f32** (`docs/17-gpu.md` section 2; the earlier choice was f16). Every image plane that crosses a kernel boundary is f32 in memory, in every mode, and `StoragePreference::Auto` resolves to `StorageMode::F32` on every device; the two f16 modes (`array<f16>` with `SHADER_F16`, or two halves per `u32` with `pack2x16float`) stay behind `StoragePreference::Force` for the legacy kernels and their tests. Why: f16 storage differed from the CPU reference by 7.9e-4 to 6e-3 (`docs/05`, "f16 storage and the 1e-3 gate") and the raw-algorithm kernels already needed f32. The price is twice the plane memory (the 50 MP spike chain peaked at 0.28 GiB of pool ledger with f16 storage and peaks at 0.355 GiB with f32, measured on lavapipe by `gpu_spike_50mp`, against the 1.5 GiB gate; the first estimate was 0.56 GiB; the full device chain has its own gate, `docs/17-gpu.md` section 8). Raw words are `u16` pairs in a `u32`, look cubes and tables are f32. Per-pixel colour maths in f32 registers. Pending the owner's confirmation (STATUS question 2, option 1, and question 13).
- Tiles are independent after decode, so export runs tile by tile and writes rows to the encoder as soon as a tile row is complete.

### Export, preferences and looks

**As built (ym-core: `export.rs`, `export_queue.rs`, `cli_preview.rs`, `preferences.rs`, `looks.rs`, `app.rs`).** The options, the queue rules and the file formats are specified in `docs/09`; this is how the core is put together, and what the front ends call.

- *One export function.* `export::export_photo(&ExportContext, &ExportPhoto, &ExportParams, &ExportControl) -> Result<ExportReport, ExportError>` is the only thing that turns a photo into a file. The app's queue and the CLI both call it, so the same photo, settings and options are the same bytes whichever front end made them (`tests/export.rs`: three contexts on three threads at once, and a second process, give identical JPEG and DNG bytes; two exports of a real file, in all four formats, repeat exactly). `ExportPhoto` is the render's `PhotoSource` (decoded image, profile, estimates, the settings that are exported) plus the path, probe metadata, camera match and `ResolvedSettings` the metadata needs; `ExportPhoto::from_session` builds one, `PhotoSnapshot::take` + `with_raw` is the same in two steps (the queue snapshots at queue time and reads the image when the photo's turn comes). `ExportParams` is the job's options, the `{seq}` of the photo and the preference "Remove location from exports" **as it was when the job was queued**. `ExportControl` is a `CancelToken` and a progress callback (0 to 1, any thread, not always in order). The CLI starts after `Session::wait_idle` and builds its core without a thumbnail renderer (`CoreOptions::thumbnails = false`: an export's render gives way to foreground work, thumbnails included, so there is nothing to gain from them). The app may start an export earlier, because the queue waits per photo for the shared estimates to be final (Session, "App/CLI parity for early exports"). The CLI has nothing to gain from thumbnails, so it builds its core without a thumbnail renderer (`CoreOptions::thumbnails = false`; an export's render gives way to foreground work, thumbnails included). The app keeps its thumbnails: an early export waits only for estimates, which come before a photo's thumbnail, and its render then yields to foreground work between tiles as above.
- *What `export_photo` does.* (1) The look and the chosen display LUT must load: **an export never falls back to Neutral or ACES 2 the way the viewport does**, because the file's XMP says which look and transform made it; a look that is gone is `ExportError::Look("File missing or changed. Import again.")` (CLI exit 3). A DNG of a look with its own display rendering is made, approximately (owner's decision of 2026-10-14, `docs/09` "What a DNG carries"): its pixels are the scene values that ACES 2 turns into the look's picture. The look's and the display LUT's fingerprints are taken again once the pixels are rendered (a render takes seconds to minutes, a DNG's two renders even longer): a look replaced, removed or switched, or a Display rendering preference changed, in between fails that photo with "The look or the display rendering changed while this photo was exporting. Export it again." (`CHANGED_DURING_EXPORT_MESSAGE`, kind `look`, CLI exit 3) instead of writing a file whose XMP names a look or transform it was not made with. A panic below `export_photo` (a writer, a look provider) is that photo's `ExportError::Render` ("This photo can't be exported because of an unexpected problem…", logged with the panic text), never an unwinding queue thread. (2) The name and folder: `{name}`, `{look}` (the slug of the photo's look id, also when the look is gone), `{date}` (capture date), `{seq}`, `{camera}` (slug of the body); the folder from `ym_export::naming`; with "If the file exists: Skip" and a file in the way **nothing is rendered**. (3) The render, on the render scheduler's export worker (`Renderer::spawn_full_reporting`: gives way to the viewport between tiles, reports the fraction of tiles done): JPEG, TIFF and PNG take `FullTarget::DisplayLinear(output)` for the chosen colour space and hand it to `ym_export::write_export`, which resizes in linear light and does C13; a DNG takes `DngLinearAwg4` and `DngPreview` (both rendered with R8 capture sharpening off, `FullTarget::is_dng`), the raw pixels unturned with the user's crop in `FullImage::window` (`CropRect` of the default crop tags; none when a straighten angle baked the crop in) and the `Orientation` tag from `compose_orientation(camera, user turns)`. A DNG therefore costs two renders (a single pass making both is a follow-up). The DNG profile is the fitted one, `FittedProfile::embedded()` (`data/dng/profile.json` by `tools/dngfit`, compiled in; `ExportContext::new` holds it, `with_dng_profile` replaces it), written with `BaselineExposure::Auto { fit_offset_ev }`, so the app and the CLI write the same DNG bytes (`docs/09`); `DngProfile::identity()` is for structure tests only. (4) The metadata: EXIF from the probe (`exif_of`: never copied from the file; GPS left out when the preference is on, both here and in the writer), XMP with the `ym:` properties: `PipelineVersion`, `Profile` and `ProfileVersion` of the profile the render used, `ProfileMatch` (`exact`, `sensor family`, `default`, `forced`), `Look`, `LookSHA256` (the hash of the look's file; for a built-in look the hash of `data/looks/builtin/<slug>.json`, absent for a look with no file), `LookIntensity`, `DisplayTransform` (`aces2-sdr100-rec709lim` for sRGB, `aces2-sdr100-p3lim` for Display P3, `aces2-sdr100-p3lim-rec2020` for Rec.2020, or the id of the imported display LUT, `arri-display:logc4:rec709-g24`; a DNG records the sRGB one, which is what its preview is), `Models` (absent: the classical demosaic has none; `docs/07` fills it when the network runs) and `Settings` (`ResolvedSettings::pinned_settings()`, `docs/01` DevelopSettings), all dates the capture time. A DNG's scaling (`x_white`, clipped fractions) goes to the log at info level. (5) Progress: render 0 to 75 % of the photo (a DNG: raw 0 to 35 %, preview 35 to 70 %), then the writer; cancel is polled between render tiles and between writer bands (about a million pixels), and the temporary file is removed.
- *Estimates.* `export::estimate` is the `export_estimate` size and time: `ym_export::estimate_bytes_with_detail` for the output size worked out from the probe alone (`estimated_output_size`: the camera's crop, orientation, the user's turn and crop; not the lens auto-crop or straightening) and the detail statistic of the photo's newest thumbnail (`DetailStat::measure_rgb8` of the 240 px sRGB render, never the embedded camera JPEG, which is the camera's own rendering). The renderer keeps the statistic per photo when it makes a thumbnail (`Renderer::thumbnail_png`, so the session's first thumbnail and every refresh after a look, crop or turn update it; a look tile does not; it goes with the session), and `ExportQueue::estimate` reads it with `Renderer::thumbnail_detail`; a photo without a thumbnail yet is estimated as a picture of typical detail (`None`, what `estimate_bytes` assumes). The app's thumbnails come from a reduced raw group, not from a box average of the full render the estimate was calibrated on, so this was measured on the nine real files (`tests/export_real.rs`, ignored, `cargo test -p ym-core --test export_real the_detail_statistic -- --ignored --nocapture`): the thumbnail's statistic over the full-size render's is 0.98 (A300), 0.96 (A500), 0.85 (ILCE-5000), 0.99 (ILCE-6300), 0.94 (A7 II), 1.02 (A7 III), 1.10 (A7 IV), 0.89 (NEX-5N), 0.97 (NEX-7), geometric mean 0.965, which moves a quality 92 estimate (size grows as the statistic to the power 0.46) by −7 % at worst, +4 % at best and −1.6 % on average. `ExportSpeed` gives the seconds. `ExportSpeed` starts from the numbers measured in `docs/01` Preview strategy (17.44 s per 24 MP render) and `docs/09` (encode timings) and is replaced by the speed of this machine after the first exported photo (the first sample outright, later ones as a running mean); a DNG counts two renders. On the nine real files (`testdata/real/files`, 183 MP in all) the starting numbers said 183 s for the job and the job took 200 s; the size estimate said 77 MB and the files came to 30 MB (the table of `docs/09` is from film scans; a denoised camera frame at quality 92 came to 0.7 to 2.7 bits a pixel, 1.3 on average over the nine, where the table says 3.3), so that table wants the re-measurement `docs/09` already asks for. `ExportSpeed` keeps one set of numbers per path, the CPU reference and the export tail on the device (a photo that fell back to the CPU teaches only the CPU set), and the estimate reads the device's when the renderer runs the tail; the device set starts as the CPU's until the Mac session measures it (`docs/09`, "As built (export tail on the device)").
- *The queue* (`ExportQueue`). `start(session, job, remove_location)` snapshots every photo of the scope **now** (settings, estimates, Pick white, camera, metadata: editing a photo or closing the session does not change a queued job) and returns the job id; one worker thread runs jobs in order and the photos of a job in order, decoding the next photo (from the session's mosaic cache, else from the file) while the current one renders. A scope with no photo (for This, a current photo that cannot be developed is refused with the reason it was skipped with, not with "open a photo"), a DNG of a look with its own display rendering, options the writers refuse, and a photo that is still developing are refused at `start` with a plain message and queue nothing. Events (`ExportEvent`): `Progress(ExportProgress)` is `export_progress` in the order the panel's `applyProgress` expects: when a photo starts `{ file, done: i, total, file_percent: 0 }` (`file` is the name with the "Keep both" number the folder will need), then whole percents each at most once, a photo that failed or was skipped once as it finishes with the new count (`error`, or `skipped: true`), and a last event with `done == total`; a cancelled job sends nothing more. `File(FileDone)` is sent for every photo that was exported, skipped or failed, just before the `Progress` event that counts it: the photo, its position, the `ExportReport` (path, bytes, size, timings, the render's notes) or the failure (kind, message, CLI exit code), and the milliseconds its decode took; the CLI can run its jobs through the queue and print one JSON object per file from these. `Busy(bool)` is sent by the worker when a busy period starts (before its first progress event) and ends. `ExportEvent` is `#[non_exhaustive]`: a consumer matches the variants it knows and ignores the rest. **A name the job has already written is numbered, whatever "If the file exists" says.** Replace and Skip look at the disk, and a file this job wrote a moment ago is on the disk too: two photos of one job that map to one name (two cards that both hold `DSC00001.ARW`, or a template with `{date}` and no `{seq}`) used to replace each other with both reported as saved (Skip: the second reported as "already existed"). The queue makes one `WrittenFiles` set per job (the device and inode of every file written, so that a name differing only in case on a case-insensitive volume is recognised too) and passes it in `ExportParams::written`; `export_photo` numbers a photo whose name is in it as "Keep both" numbers it (`DSC00001_neutral 2.jpg`), the panel's `file` shows that name, and the report carries the note `SAME_NAME_IN_JOB_NOTE`. A file from before the job is still replaced or skipped as asked. Tests: `tests/export_queue.rs` (`two_photos_of_one_job_with_one_name_never_overwrite_each_other_whatever_if_exists_says`, `replace_still_replaces_a_file_from_before_the_job_and_skip_still_skips_it`), `crates/ym-cli/tests/render.rs`. One photo failing (a look that is gone, a full disk, a panic) does not stop the job. An event listener that panics loses that event only; a job that panics outside `export_photo` ends with one last `export_progress` (`done == total`, `error`) so that the panel closes instead of waiting. Percent events are sent in the order they are counted, also when two writer threads report together. `cancel(job_id)` stops after the current tile or band, deletes the partial file and skips the rest; a job that has not started is dropped. `is_busy()` is true from `start` until the last job has finished or been cancelled: **"Restart to update" (`docs/12`) stays disabled while it is**. `summary(job_id)` keeps the last sixteen jobs (counts, files written, destination folders, the error of each failed file; `files` lists what was **written**, a photo skipped because its file exists is counted in `skipped` and not listed, as the CLI prints no path for it, while its folder is still in `folders`); `reveal_path(job_id)` is what "Show in Finder" opens: the file when the job wrote exactly one, else the first folder (a job that wrote nothing opens its destination). Several folders happen when no destination is chosen and the photos come from several (each goes next to its own source folder, as the CLI does).
- *`cli_preview`.* `cli_preview::cli_preview` builds `ym render <inputs> --look … --format … --out …` (one option to a line, each line but the last ending in a backslash, as the mockup shows) with the options and none of the defaults (`--compression lzw`, `{name}_{look}`, Keep both). The inputs are the folder when the job is exactly every ARW file in one folder, else each file by absolute path; `--out` is the chosen folder, else `<source folder> export` when the photos share a folder (none with several: the CLI then does what the app does). Words are shell-quoted only when they need it. A command has one look: the look (and intensity, `--intensity` when not 100) most photos of the job have, the first on a tie, as its slug when the slug names exactly that look. `adjusted_photos` (also `ExportEstimate::adjusted_photos`) counts the photos whose settings are not *Auto with that look at that intensity*: adjustments beyond the look, and also a different look, which the command would silently export with the wrong one. The sentence is `cli_preview::adjustments_note`.
- *Preferences* (`PreferencesStore`). `preferences.json` is `Preferences` of `src/api/types.ts` and nothing else; the folder is `ym_looks::library::default_root()` (the Mac's `~/Library/Application Support/app.yellowmoon`, `$XDG_DATA_HOME/app.yellowmoon` on Linux, `YELLOWMOON_HOME` replaces it). Reading never fails: a missing file is the defaults and creates nothing, a missing or unknown field is ignored, a value that does not fit takes its default while the rest is kept (field by field, also inside `export_defaults`), a file that is not JSON is all defaults; each logs a warning and is in `warnings()`. A change re-reads the file first (the CLI may have changed another field), validates the export defaults, and writes atomically (temp file, fsync, rename, fsync of the folder); a patch that changes nothing writes nothing, and a failed write changes nothing. Defaults: Neutral, ACES 2, the export defaults of `docs/09`, location kept in exports, update check on, Downloads watch off. A full open, edit and export cycle writes **no file** unless a preference changes (`tests/core.rs` compares the trees; choosing an export folder remembers it in `last_used_folders` and writes `preferences.json`, which is on the list).
- *Looks* (`LookService`). One `ym_looks::Library` behind a lock; the renderer reads through `LookService::provider()` (a `LookProvider` that also gives `look_sha256`). An import or a removal works on a second `Library` over the same folder, under `looks/.lock`, and takes the write lock only to re-read the manifest, so a slow import (or a CLI import holding the lock) never stalls a frame (`tests/looks_service.rs`). `list()` is `looks_list` (flags `is_default` and `missing`), `display_luts()`, `import(path, ImportRequest { input, cancel }, progress)` (the wizard's importer: same recognition, hashes and library folder as `ym looks import`; the result has the looks added or replaced, display LUTs added and files unchanged), `remove(id)`, `set_default(id)`, `set_display_rendering`, `apply_look(session, scope, id, intensity)`, `resolve(query)` (`--look`, exit 2 or 3), `verify()` and `reload()`. A look whose file is gone or changed stays in the list, `missing`, and cannot be made the default or applied ("File missing or changed. Import again."); a default look that is gone is not used (new photos get Neutral, `effective_default()`) but the preference is kept until the look is removed or the user chooses another; removing the default look or the chosen display LUT resets the preference to Neutral or ACES 2. The display rendering in effect is `display_choice()`: the chosen display LUT while it is imported and its file is there, else ACES 2 (the viewport falls back; **an export with a chosen display LUT that is gone is refused**, `check_display_rendering`). `on_change(f)` is `looks_changed`: it runs after an import, a removal, a new default, or a `reload`/`verify` that found a different list, outside every lock. "Different" is judged from before `reload` re-reads the preferences and the manifest: the ids, whether each can be used, the SHA-256 of each file (an ARRI look replaced in place by a newer file) and the default look (the CLI chooses it through the preferences file). `Core::looks_list` reloads first, so an import made by the CLI shows up, and so does `Core::export_start`, so that a look or display LUT whose file has gone since the last look at the library is noticed when the job is queued (a display LUT refuses the job; a look fails the photos that use it).
- *`Core`* (`app.rs`). `Core::open(CoreOptions)` builds the preferences, the look service, the renderer (reading looks through the library and showing the preferred display rendering), the session (new photos get the effective default look), the export context and the queue, and keeps the session and the renderer in step with `looks_changed`; it writes nothing. Its methods are the IPC commands of the table below: `preferences_get/set` (validated against the library, then the session and renderer follow), `looks_list/import/remove/set_default`, `apply_look`, `export_estimate/start/cancel`, `cli_preview`, plus `export_summary`, `export_reveal_path`, `export_busy`, `close_session` (cancels the viewport, tile, thumbnail, histogram and look-tile renders, queued and running, forgets what the renderer cached and **retires the closed session's photo ids** with `Renderer::retire_through`, which refuses any such request for those photos that was still on its way, such as a command that read its photo before the close and queued its job after the scheduler's cancel and used to refill the caches of a photo that was gone, 6 times in 25 in `closing_the_session_cancels_its_queued_renders...`; export renders are not refused and leave exports running) and `shutdown` (cancels the exports and the renders, then **waits up to `SHUTDOWN_EXPORT_WAIT`, 5 s, for the export queue to go idle**: the process ends the moment it returns, so a worker still writing would never delete its hidden `.yellowmoon-*.tmp`, tens or hundreds of megabytes in the person's export folder for good; a cancel is noticed between render tiles and writer bands, about 0.4 s at 24 MP; `tests/core.rs` `quitting_while_an_export_is_writing_leaves_no_partial_file`, and `AppApi::shutdown` in `src-tauri/src/api/tests.rs`). `CoreError::scope()` is the `AppError` scope. All of it is `Send + Sync`.

## Native viewport

The webview covers the whole window and is transparent where the photo is. A wgpu surface (CAMetalLayer) sits behind it inside the same NSWindow.

"Transparent where the photo is" means every box under the photo cell, not only the cell: while the Photos screen shows with the native viewport, the page's root, body, `#root` and the Photos screen draw no background (`data-native-viewport` on the root element, set by `PhotoView`; the rule is in `src/styles/screens.css`). The window behind the page is paper (`PAPER_SRGB` in `src-tauri/src/native.rs`, which a test keeps equal to `--paper`; paper is the dark `#0f0f10` since the dark glass interface of 2026-10-16, `docs/11`; the letterbox of the frames the core draws for the app is the same colour, `PAPER_RGB8` in `src-tauri/src/api.rs`, set by the app alone: `RenderOptions::background` stays white by default and exports have no letterbox, so the command line and every export are unchanged), so the page looks the same wherever it draws nothing, and the cell shows paper before the first frame and after the picture is taken away. The first build tested on a Mac (0.1.0) had only the cell transparent: the page's paper covered the layer and the photo never showed. `index.html` paints the root paper in an inline style (so nothing shows through before the style sheet loads), which only an `!important` rule overrides. `PhotoView` also sets `background-color: transparent !important` inline on the same four boxes and puts back what was there when the view goes: on 2026-10-16 the viewport job of the 0.1.4 build found the root and the screen still paper in WebKit with the attribute set and the rule loaded (Chromium applied it), so the stylesheet alone is not relied on. The cause was a transition: the reduced-motion rule of `global.css` set `transition-duration: 0.001ms` on every element, so with Reduce motion on (as on the runner) every property change became a transition, which sits above `!important` in the cascade, and WebKit left the backgrounds at their old paper. That rule now sets `transition-property: none` (no transitions at all with Reduce motion), and the four boxes have `transition: none` while the native viewport shows. The job's page line also prints the root's inline style, whether the rule's selector matches, which loaded sheet carries the rule, whether Reduce motion is on and the page's running animations. The viewport job of `.github/workflows/build.yml` runs the app on a Mac runner with photos and fails when the page paints anything under the middle of the cell or the layer never shows a picture; its screenshot is the artefact.

1. The frontend measures the photo cell (`<div data-viewport>`) and sends `viewport_set_rect { x, y, width, height, scale }` on mount, resize and layout change (ResizeObserver). The shell draws nothing, and applies no zoom, pan or Before, until the first rectangle with an area (both sides at least 2 CSS pixels) has arrived: the controller starts with a 1 × 1 cell, and a photo that was ready first used to be drawn into it, a frame of one pixel for the webview or the native layer to throw away.
2. `src-tauri` positions the Metal layer to that rect and asks `ym-core` for frames.
3. Pointer input over the photo arrives in the webview first. The frontend sends `viewport_input` events (zoom to point, pan delta, double-click to toggle fit/100%, white-pick click) to the core. M0's spike measures latency; if it is above one frame, move pan/zoom handling to native event monitoring and keep only clicks in the webview. (Before that, what the shell does with an input matters: see *Which request stops which render* below, and `docs/13` §Performance logging for the counters that show where the time goes.)
4. Surface colour space: Display P3 with an sRGB-encoded 8-bit or 10-bit format; the DRT outputs Display P3 for the viewport. HDR/EDR is V2.
5. The photo cell is always exactly 3:2 (see `docs/11-ui.md`); the image is letterboxed inside it with the paper colour, never with grey.

M0 task M0-06 proves this design or switches to the fallback (a native child view placed by the same rect messages).

**As built (ym-core: `pipeline/viewport.rs`, `pipeline/frame.rs`).** The core keeps one `ViewportState` for the current photo: the cell (`ViewportRect`, the payload of `viewport_set_rect`), `ViewportMode` (`fit` or `percent { value }`), the pan centre and the Before switch. The wire types are the ones of `src/api/types.ts`. Conventions the frontend relies on:

- *Zoom* is device pixels per pixel of the final image (after lens crop, orientation, straighten and crop, at full resolution), so 100 % is one image pixel on one device pixel and the header's "Fit 24 %" is `fit_zoom`. At exactly 100 % the view's origin is rounded to a whole image pixel (`ViewportState::view_to_final`): a pan, or a cell of odd width, would otherwise leave the origin between pixels and every frame would be a half-pixel bicubic resample of the photo, softening every edge at the zoom people use to judge sharpness (found in review). The cell is capped at `MAX_CELL_PX` (8192) device pixels a side, and a size that is not a number is one pixel: a hostile or glitched rectangle must not ask for a frame of gigabytes. A fixed zoom below the fit zoom is the fit zoom. The upper limit is 800 %.
- *Pointer coordinates* in `viewport_input` and `sample_pixel(x, y)` are CSS pixels inside the cell (origin at the cell's top left, as the webview reports them); the cell's `scale` turns them into device pixels. `sample_pixel` returns nothing for a point in the letterbox.
- `zoom` multiplies the zoom about the pointer (the point under the pointer stays put), `pan` moves the image with the pointer and is clamped so the cell never shows beyond the image, `toggle_zoom` flips between Fit and 100 % about the pointer, and `pick_white` does not change the view: the core converts the click to a point of the photo as the camera oriented it (`Renderer::pick_point_at`, the space of `white_pick`, through the straightening, the turns and the lens maps) and the application sends that point as `white_pick` through `update_settings`, where the session takes the sample the chain uses (`auto::pick_white_sample`, from the raw data). (There is no second sample taken from the render: `Renderer::pick_white_sample` was removed because the chain never read it; the "no vignetting gain" contract is tested on the session's sample, `tests/render_review.rs`.)
- The core reports its zoom: `RenderStats::{zoom_percent, fit_percent}` come from the same `ViewportState::zoom` and `fit_zoom` that choose the frame (`Renderer::viewport_frame` sets `RenderReport::zoom`, also on a frame served from the cache; a thumbnail, a look tile or an export has none) and ride on `render_stats`, which is sent after every viewport frame by both backends. The webview used to estimate them from the photo's size and the cell, which cannot see the lens crop, the straighten angle or the crop; it now takes the Fit zoom from the stats (`fitZoomOf`) and keeps its own estimate only until the first frame has reported and in the mock. A wheel zoom is still mirrored at once, before the core has drawn a frame to report, and the header's number for a fixed zoom is the requested one, which is what the core draws (above Fit, up to 800 %).
- The frame is RGBA8 in Display P3 (`Renderer::viewport_frame`), the size of the cell in device pixels, with the letterbox painted in the paper colour and the 8-bit output dithered (the GPU colour pass and the CPU pass dither the same way). The Before view is the same frame with the colour chain replaced by the camera default rendering: the camera's as-shot white balance, the body's D65 colour matrix, the camera gain and the camera tone curve, then the output primaries and C13 (`docs/02`, *The Before view*; since 0.1.4, before that it was the LogC4 signal at C8). No setting reaches it except the decode switches and the lens corrections, which change the raw.
- A frame asked for with `coarse_only` is served from the reduced image when the full-resolution tiles are not ready yet and says so (`RenderedFrame::sharp` is false); the tile job (`Renderer::spawn_tiles`) then runs at the lower priority and the next frame is sharp.
- *Which request stops which render (2026-10-16).* A frame being drawn finishes and is shown; the next round starts at once from the newest state; only the speculative sharp-tile pass gives way. The shell (`src-tauri/src/viewport.rs`) records what the webview asks for (inputs, settings patches, look changes, a cell that moved, Before, the mode) and wakes its worker; it no longer cancels the render in flight for each of them. Until 0.1.3 every request did, and a frame is only "finished" at the end of a render (the core checks for cancellation between stage groups and before the readback, so a cancelled render yields no frame): once a render took longer than the gap between two requests, which is a wheel's 8 ms or a slider's 16 ms, no frame reached the screen until the hand stopped, and the picture then jumped. Now: (1) a request (`Shared::request`) stops only the pass that makes sharp tiles (`Flight::Tiles`, which nobody is waiting for: the round that follows draws a coarse frame first); (2) a request that makes the frame being drawn *wrong* rather than old (`Shared::request_now`: another photo or none, which includes the session closing, and a cell of another size or scale) stops the frame as well, and a round taken before such a request does not start drawing; a cell that only moved is the first kind; (3) the frame that finishes is presented, and the operations (pan, zoom) that arrived meanwhile are applied at the start of the next round, from the newest state, so the picture follows the hand at the rate the renderer can keep. `snapshot_synced` (Pick white, the Option-key readout) waits for the next round to apply what is pending, so up to one frame, and still gives up after 1.5 s. A follow-up that applies pan and zoom eagerly (once the final image size is cached in the state), or that shows the last frame offset by the input delta at once, is the next step if the counters (`docs/13`) show that a frame is still too slow to follow the hand; both are Mac work. Exports never go through the viewport, so the byte-for-byte parity of `ym` and the app is untouched.

**One device, zero-copy (as built 2026-10-19, the owner's request).** The native sink draws with the core's own graphics device. `AppApi::start` opens the device first (`open_gpu`, as before) and makes the sink with it (`make_sink(Some(&gpu))`); `NativeSink::create` makes the surface of its `NSView` from that device's `wgpu::Instance` (the instance the adapter came from, `Gpu::wgpu_setup`), checks that the adapter can draw to it, and configures it with the core's `Device` (still `Bgra8Unorm`, Display P3, and still refused, so the fallback viewport is used, without Display P3). The worker then asks for frames that stay on the device (`FrameSink::takes_device_frames`, `Renderer::spawn_viewport_frame_to(…, FrameOutput::Device)`): the view job runs the same kernels and waits for them, but reads nothing back, and the frame (`RenderedFrame::on_device`, a `DeviceFrame`: the pool buffer of RGBA8 the kernels wrote, its size and its device) is bound as a read-only storage buffer of the sink's full-screen triangle (`src-tauri/src/present.rs`), which writes it texel for texel into the surface texture on the core's queue. The pass is submitted after the job that wrote the buffer, so the queue orders them; the frame is borrowed until the pass is submitted, then dropped, and its buffer goes back to the pool (a later job that gets it is submitted later still). Before, every frame went device → host (one readback, 24 MB for a 3000 × 2000 cell) → host → a second device of the sink's own (`write_texture`). What stays a host frame, uploaded and drawn as before: a frame the CPU made (a device error, a stage that is off). Since 2026-10-20 a view magnified above 100 % is a device frame too (the stage and the magnification on the device, *View stages on the device* above), so the viewport draws zero-copy at every zoom. The sink's own device remains for a core without one (policy `off`, no adapter, a software adapter under `auto`, a device lost at start) and replaces the core's device if that one is lost later (the next frame rebuilds the surface on a device of the sink's own, and the worker asks for host frames from then on). The sink's work on the core's device runs inside error scopes, so a mistake of the viewport never taints the device the renderer uses. The log says at start which way it draws: "native viewport: zero-copy on the core's device" or "native viewport: own device, host frames"; `YM_PERF` counts the frames drawn each way and times the wait for a drawable and the pass (`docs/13`). The view stays our own `NSView` behind the transparent webview (Tauri's multi-webview API was not used), and the compositing is unchanged. `docs/17` §16 has the device side.

**Events** (core → webview)

`photo_progress { id, stage, done }`, `thumbnail_ready { id, url }` (changed from `png_bytes`, below), `render_stats { ms, path, space, zoom_percent, fit_percent }` (the header's status text: `path` is `neural` or `classical`, `space` `srgb`, `display_p3` or `rec2020`; `RenderStats::status_text` makes "Classical · 42 ms · Display P3"; `zoom_percent` is the zoom the last viewport frame was drawn at and `fit_percent` the zoom at which the whole final image fits the cell, both in percent and not rounded, `null` for anything that is not a viewport frame and from the mock), `export_progress { job_id, file, done, total, error? }`, `looks_changed`, `update_state { phase, version?, percent?, message? }`, `error { scope, message }`.

Thumbnails do not cross the bridge as bytes. `thumbnail_ready` first carried the PNG as a JSON array of byte values (≤ 240 px long edge, about 250 KB of PNG and four times that as JSON per photo, 125 MB of bridge traffic for 500 photos); it now carries the photo's id and the **address** of the picture, which the shell keeps and serves on the `ym-frame` scheme that already serves the fallback viewport's frames (`ym-frame://localhost/<launch>/thumb-<id>-<version>.png`, `http://ym-frame.localhost/…` on Windows; `img-src` allows it). The `<img>` loads it. Every new thumbnail of a photo (a look, a crop or a turn was applied) has a new version and so a new address, and the shell keeps the last two versions of a photo's thumbnail, so a picture the webview is still showing can be loaded again a moment after a newer one was announced; closing the session forgets them all (the old addresses answer 404). The pictures live in the shell instead of the webview: the same bytes, held once, not copied through JSON, `Blob`s and object URLs. After a reload of the webview the store asks `thumbnails()` for the addresses of the pictures the shell holds (the core announces each thumbnail once). The Look tab's tiles travel the same way: `look_thumbnail` used to answer with the PNG as a JSON array of byte values, and now answers with the address (`ym-frame://localhost/<launch>/look-<photo>-<n>.png`; a new address for every request, the shell keeps the last two tiles of each photo and look, at most `LOOK_TILE_BUDGET_BYTES` (256 MiB, about 4,500 tiles) in all, and when that is passed the photos used least recently (a tile put or served counts as a use) lose all theirs, the photo just given a tile never; closing the session forgets them all. A photo whose tiles were let go answers 404 for the addresses it was given, until the webview asks again, which it does when the photo's settings change). The store caches the address per photo, look and settings, as it cached the bytes before. The mock announces and answers with `blob:` addresses of its own. Full images never cross the bridge.

**The `ym-frame` handler and its cache (2026-10-16).** The scheme is registered as an *asynchronous* protocol (`register_asynchronous_uri_scheme_protocol`): wry calls a synchronous handler on the main thread, and a request copies the PNG under a mutex (the filmstrip asks for hundreds of pictures when a folder opens, the Look tab for as many whenever it is shown), so the handler now only hands the path to a blocking thread, which builds the response and answers; the main thread gets the response and nothing else (`app.rs` `serve_frame`; a test holds the tiles' mutex and checks that the handler returns at once and the answer arrives after the release). Every address starts with a **launch id** (`ym-frame://localhost/<launch>/…`: the start time in hexadecimal milliseconds, a hyphen and a count of the stores the process made; not a secret): the version counters of thumbnails and tiles start at 1 in every launch, so the first thumbnail of photo 3 would otherwise have the same address in two launches, and a request with another launch id is a 404. That is what makes caching safe: a 200 for a thumbnail or a look tile is sent as `Cache-Control: private, max-age=31536000, immutable` (the address names the same picture for as long as the app runs and is never used for another), so the `<img>`s that the Look tab remakes when it is shown again do not ask the shell again. Frames of the fallback viewport and every 404 stay `no-store` (a frame is replaced by the next, a 404 for a tile that was not made yet may be a 200 later). The webview is not known to keep custom-scheme answers between launches, and the launch id makes that irrelevant; whether WKWebView honours `Cache-Control` for a custom scheme at all is one of the Mac checks (`docs/STATUS.md`).

**Event coalescing (2026-10-16).** Each event the shell sends costs the main thread a message that runs a script in the webview (`evaluateJavaScript`). `render_stats` comes once per presented frame and `photo_progress` four or five times per photo (thousands when a folder of hundreds opens), so `TauriEmitter` sends them through `Throttle` (`events.rs`): one thread, at most one `render_stats` and one batch of `photo_progress` per 33 ms (30 Hz), the first after a quiet period at once. `render_stats` is latest-wins. `photo_progress` is latest per photo while the waiting event of that photo only says a stage started; an event with `done` or an `error` is never dropped and never moved past a later event of its photo (a photo that is Ready and then developed again arrives as Ready, then Developing), so what the webview knows about every photo is what it was told last. What waits is sent when the emitter is dropped. The event names and payloads are unchanged, and every other event is sent as it comes.

**As built (ym-core: `app.rs`).** `Core` has one method per command above (`export_estimate`, `export_start`, `export_cancel`, `cli_preview`, `preferences_get`, `preferences_set`, `looks_list`, `looks_import`, `looks_set_default`, `looks_remove`, `apply_look`; the session commands are `Core::session`'s) and takes the events as callbacks: `CoreOptions::session_events` (`photo_progress`, `thumbnail_ready`, `estimates_changed`), `CoreOptions::export_events` (`ExportEvent::Progress` is `export_progress`, `ExportEvent::Busy` tells the updater when the queue starts and stops) and `Core::on_looks_changed` (`looks_changed`). The wire types the export, preferences and looks commands use serialise to the interfaces of `src/api/types.ts` (a test compares the field names of `ExportOptions`, `ExportJob`, `ExportEstimate`, `ExportProgress`, `Preferences`, `LastUsedFolders`, `Look`, `DisplayLut` and `LooksImportResult` with the interface text, so a drift fails in CI). `cli_preview` answers with the command as the CLI is named (`ym`, the decision of 2026-10-12); `ExportEstimate::adjusted_photos` and `CliPreview::note()` carry "N photos have adjustments this command doesn't include."

## Finding `data/`

The app and the CLI look for the data folder in this order:

1. `YELLOWMOON_DATA` environment variable (tests, development).
2. Next to the canonicalised executable inside the bundle: `Contents/MacOS/<exe>` → `Contents/Resources/data/`. Canonicalise first, because the CLI on PATH is a symlink into the bundle.
3. Debug builds only: `<workspace root>/data/`, from `CARGO_MANIFEST_DIR` at compile time.

If none exists, fail with "Yellowmoon's data folder is missing. Reinstall the app." and exit code 2 in the CLI.

## Errors and logging

- `tracing` with a local file subscriber. Log levels: info for user actions and job summaries, debug for stage timings. Never log file contents or full paths at info level in a way that would leak into bug reports without consent; `ym doctor` prints what it includes. **As built:** nothing of the person's own (a photo, an export folder or file, the preferences file, the looks list) is named in a log line at info level or above (warn and error included, the default filter being info): a failed export logs its job and the kind of failure (`export failed job=3 kind="write"`), a failed preferences write the kind (`PreferencesError::kind`), a damaged preferences file the sentence about it, a damaged looks list the kind of problem (`kind="manifest"`); the file name, the message (which names the folder) and the paths are logged at debug level (`YELLOWMOON_LOG=debug`), where a person looking for the cause can ask for them. Errors that name the application's own files (a model or the shipped `data/` folder) are still logged whole. `tests/export_queue.rs` `a_failed_export_logs_its_kind_and_job_but_no_folder_or_file_name`, `tests/looks_service.rs` `a_damaged_looks_list_is_logged_without_the_path_of_the_persons_folder` and the test in `preferences.rs` check it.
- Every error that reaches the UI carries a plain message and an action ("This file is from a camera mode we can't read yet: ARW 6.0 compressed. Export it as uncompressed or lossless in the camera, or wait for an update.").
- A file that fails to decode stays in the filmstrip with an error tag; it never blocks other photos.
