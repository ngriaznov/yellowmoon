# 09 · Export

Crate: `ym-export` (writers), `ym-core` (export queue). UI: `design/mockups/export.html`. CLI: `ym render` (`docs/10-cli.md`). App and CLI share one code path, so the same inputs and settings give byte-identical files (apart from the XMP timestamp, which both write as the capture time, not "now").

## Options

**Output sharpening (2026-10-13, owner's decision).** Every raster export (JPEG, TIFF, PNG; never DNG) is sharpened after the resize by a linear-light luma unsharp mask with halo control (`docs/algorithms/04-output-sharpening.md`). It is a per-photo develop setting, not an export option: Detail › Sharpening › Output, 0–200 %, default 100 %, with the spec's screen preset otherwise (radius 1 px, threshold 1 level, halo suppression 60 %). The same setting applies to the viewport, tiles and thumbnails at their own size. There is no export switch for it (the Export panel and `ym render` have no on/off option beyond the amount, and 0 is off), and no print preset in the app or in `ym`: the spec's print preset exists only in the code (`ym_gpu::cpu::output_sharpen::OutputSharpen::print`). An earlier plan shipped the stage off behind `ExportOptions::output_sharpen`; the owner's decision of 2026-10-13 replaced it (`docs/16`).

| Option | Values | Default |
|---|---|---|
| Photos | This photo / Picked · N / All · N | Picked if any are picked, else This photo |
| Format | JPEG, TIFF, PNG, DNG | JPEG |
| JPEG quality | 50–100 | 92 |
| TIFF bit depth / compression | 8 or 16 / None, LZW, ZIP | 16 / LZW |
| PNG bit depth | 8 or 16 | 16 (shares the bit-depth preference with TIFF, as in the mockup) |
| Colour space (not DNG) | sRGB, Display P3, Rec.2020 | sRGB ("Best for sharing and the web.") |
| Size (not DNG) | Full, or Long edge 1000–full px in 20 px steps | Full |
| Save to | folder | `<source folder> export` next to the source folder; `~/Pictures/Yellowmoon export` if that isn't writable |
| File name | template with `{name}`, `{look}`, `{date}`, `{seq}`, `{camera}` | `{name}_{look}` |
| If the file exists | Skip, Replace, Keep both (adds " 2", " 3" …) | Keep both |

The export panel shows an estimate ("≈ 120 MB") from `export_estimate`, and the equivalent CLI command with a Copy button. The command carries the export options, the look and, when it is not the default 100 %, the output sharpening (`--output-sharpening N`: the amount most photos of the job have, the earliest on a tie, like the look; a photo with another amount counts among the adjusted ones below). Per-photo adjustments beyond these don't fit on one command line; when any included photo has them, the panel adds "N photos have adjustments this command doesn't include." (the CLI can take them through `--settings`, `docs/10`). Defaults are remembered as preferences; per-photo settings are not.

## Queue

- Jobs run one photo at a time on the GPU (full-resolution neural path, tiled), with decode of the next file overlapping.
- The panel shows each file as Waiting / n% / Done or an error. "Cancel" stops after the current tile and deletes the partial file.
- Exports keep running while the user browses or edits other photos; edits to a photo already queued don't affect its job (settings are snapshotted at queue time). The same holds for photos taken out of the filmstrip (Remove from filmstrip, `docs/11`) or a session that is closed: the job keeps the photos it was started with and finishes them, and the files on disk are never touched.
- Files are written to a temporary name in the destination folder and renamed when complete. Originals are never touched.
- Auto-update waits: "Restart to update" stays disabled until the queue is empty.
- Finished state: "N photos saved to <folder>." with "Show in Finder" and "Done" (back to the tool panel).

## Pixel pipeline per format

- **JPEG, TIFF, PNG:** full chain through C13 (`docs/02`) for the chosen colour space, crop, straighten and orientation applied to the pixels, then resize (if Long edge) with a Lanczos-3 filter in linear light, then **output sharpening** (Detail › Sharpening › Output, `DevelopSettings.output_sharpening`, default 100 %, 0 is off) on the picture at the size it is written, in linear light, then the display encode, then 8-bit dither (8-bit outputs only). The stage is the screen preset of `docs/algorithms/04-output-sharpening.md` at the photo's amount, with the scale `s = long edge written / long edge rendered` (1 for a full-size export), and runs after the resize and before C13 for a full-size export too. JPEG uses 4:4:4 chroma at quality ≥ 90 and 4:2:0 below; baseline (not progressive); optimised Huffman tables. On the graphics card (`GpuStages::EXPORT_TAIL`: part of `On`, and of `Auto` on a hardware adapter since 2026-10-15, when the Apple runners passed it) the sampler, the colour chain, the resize, the output sharpening and C13 all run on the device and the writers pull the finished rows band by band, so the display-linear picture is never a host frame; the CPU path described here is the reference and the fallback (see "As built (export tail on the device)").
- **DNG:** **is never sharpened, in any way** (owner's decision of 2026-10-14; before it the pixels and the preview carried R8). Both renders of a DNG, the raw pixels and the preview, are made with R8 capture sharpening off (neither Richardson–Lucy nor diffraction deconvolution runs, whatever Detail › Sharpening says) and without output sharpening. The adaptive ratio demosaic's own shadow step (`shadow_sharpening`) stays on: it belongs to the demosaic, not to R8. (`--sharpen` and `--output-sharpening` with `--format dng` are warned about and ignored; both settings are still recorded in the XMP's `ym:Settings`, which is the photo's settings, not a record of what the DNG holds.) It stops after C11 (look and curve applied), decodes LogC4 back to linear AWG4 and writes LinearRaw (below); the placement is carried by `BaselineExposure`. **A look with its own display rendering (LogC3 to Rec.709) is allowed, approximately** (same decision; before it the DNG option was disabled for such looks): ARRI's display rendering has no scene-linear form, so the DNG's pixels are the scene values that our ACES 2 rendering (with the display placement) turns into the look's picture at the chosen intensity, and Adobe's renderer, which runs the profile fitted to ACES 2, shows approximately that picture (*What a DNG carries* below has the measured numbers). The same holds when an imported ARRI display LUT is chosen in Preferences. The help text says it in one sentence (`ym_export::dng::OWN_DISPLAY_NOTE`, used word for word by `ym render --help` and, when the job has such a look or display rendering, by the export panel): **"With a look that includes its own display rendering, the DNG is close to, not the same as, the picture you see."**

## Colour management

Embed an ICC profile in every JPEG, TIFF and PNG: sRGB IEC61966-2.1, Display P3, or Rec.2020 (BT.1886 transfer to match our encoding), generated with moxcms or shipped as small v4 profiles with permissive licences. PNG also gets a `cICP` chunk. TIFF uses tag 34675.

## DNG with the look baked in

Goal: a Yellowmoon DNG opens in other raw editors looking like our render, and keeps room to adjust exposure, highlights and white balance. Research and app-by-app behaviour: `research/notes/dng-export.md`.

### Pixels

- LinearRaw (PhotometricInterpretation 34892), 3 samples, 16-bit unsigned, scene-linear **AWG4** after C1–C11: demosaiced, denoised, lens-corrected, look and curve applied in LogC4 and decoded back to linear (`ColorChain::apply_dng_pixel`). The highlight range of C7 is in them like every stage before C8 (`docs/02` C7), so the DNG's pixels are exactly the scene values the app feeds ACES 2 and `BaselineExposure` and the fitted profile give the app's picture, highlights included. Its brightest values reach the ALEXA clip of the range, scene-linear 35.9 (`HIGHLIGHT_CAP_STOPS`); the scale below follows them (`x_white` is the photo's 99.99th percentile, at least 16).
- Scale: `stored = round(65535 · clamp(x / x_white, 0, 1))` with `x_white = max(p99.99 of the photo's max(R,G,B), 16)`, the floor being `2^-fit_offset_ev` of the fitted profile (`BaselineExposure::white_floor`; below and *As built (M3-12 `tools/dngfit`)* say why). BaselineExposure compensates: `log2(x_white) + fit_offset_ev + k` with `k = ym_color::display::DISPLAY_PLACEMENT_EV` (+0.85, the brightness the app's ACES 2 path adds before the transform, `docs/02` C12 step 1a), which is `k` for every photo whose 99.99th percentile is below 16.
- Negative values (out-of-gamut) are clipped to 0 at this point; record the clipped-pixel fraction in the export log.
- Shadow precision: with the floor at 16 a stored code is the scene value over 16 times 65535 (a step of 2.4e-4 in scene light; mid grey 0.18 is code 737, scene 0.011 four stops below it is code 46), so 16-bit linear holds about 9.5 stops below grey before codes drop under 1. Acceptable for denoised data (the step in ACES 2's output is about a quarter of an 8-bit code at worst: 0.26, at scene 0.019, measured on greys with OpenColorIO's ACES 2 Rec.709 view); a shadows push of +3 EV in another editor would show it. Revisit float or a LinearizationTable only if testing shows banding.
- Full resolution. When the crop has no straighten angle, pixels keep the lens auto-crop only and the user's crop goes into DefaultCropOrigin/Size, so other apps can undo it. DNG has no rotated-crop tag, so a non-zero straighten angle is baked into the pixels (rotated, then cropped to the straightened rectangle). 90° steps (`orientation`) go into the TIFF Orientation tag without rotating pixels.

### Profile (embedded)

- `ColorMatrix1` = `inv(AWG4 → XYZ)` (XYZ under D65 → camera, i.e. → AWG4) with `CalibrationIlluminant1 = 21` (D65). `ForwardMatrix1` maps white-balanced camera RGB to **XYZ D50**, as the DNG spec requires: `Bradford(D65 → D50) · (AWG4 → XYZ)`, scaled so camera white (1,1,1) maps to D50 XYZ. `AsShotNeutral = 1, 1, 1`.
- `ProfileToneCurve` and a `ProfileLookTable` (HSV, ≤ 36×32×16, `ProfileLookTableEncoding = 1`) **fitted to our default display transform (ACES 2)**, never to ARRI's display LUTs, so Adobe's pipeline shows nearly what we show.
  - Fit procedure (`tools/dngfit`): render a set of synthetic test images (neutral ramp, hue/saturation sweeps, our golden photos) through ACES 2 (target) and through Adobe's reference pipeline using `dng_validate` from the DNG SDK (candidate). Fit BaselineExposure and the tone curve on the neutral axis first, then the LookTable for chroma, minimising ΔE00. The LookTable can't change neutrals (spec), so all neutral tone lives in the tone curve.
  - The fitted profile is the same for every photo (it depends only on ACES 2); BaselineExposure is per photo (`x_white` changes), but `x_white` is floored at 16 so that it is never negative: see *As built (M3-12 `tools/dngfit`)* below. The profile stays fitted to the plain transform; the placement `k` is added to BaselineExposure, where Adobe's renderer applies `2^BaselineExposure` to the linear values before the profile, so `2^k · x` through the plain transform is the placed transform of `x` and the DNG opens as bright as the app.
- `UniqueCameraModel = "Yellowmoon AWG4"` so Lightroom doesn't substitute Adobe's Sony profiles. `ProfileName = "Yellowmoon"`, `ProfileEmbedPolicy = 3`, `ProfileCopyright` with our notice.
- ARRI looks are baked into pixels only, never into profile tables: a table derived from an ARRI LUT would put a copy of ARRI's data into every file.

### What a DNG carries

Owner's decision of 2026-10-14: **a DNG carries every change Yellowmoon makes except sharpening.** Where each stage and setting of a render goes in a DNG (the columns say how: *pixels* are the LinearRaw data, *tag* a TIFF/DNG tag, *profile* the fitted `ProfileToneCurve` and `ProfileLookTable`); "before" is the state until that decision. Four rows changed with it; the white lift (C12, below) is a fifth, added the same day.

| Stage or setting | Before | Now |
|---|---|---|
| R1 black and white levels, R2 noise and light estimates, R3 vignetting, R4 initial gains | pixels | pixels, unchanged (`decode.lens_corrections` switches R3) |
| R5 highlight reconstruction, R5b lateral CA on the mosaic | pixels | pixels, unchanged (`decode.highlight_recovery`, `decode.chromatic_aberration`) |
| R6 demosaic (adaptive ratio, with its own shadow step) and bilateral denoise, R7 colour and detail controls | pixels, `NoiseReductionApplied` 1.0 | pixels, unchanged; **the demosaic's shadow step stays on** (it is part of the demosaic) |
| **R8 capture sharpening** (Richardson–Lucy, or diffraction deconvolution) | pixels **and preview** | **dropped**: both renders run with R8 off, whatever Detail › Sharpening says; `BaselineSharpness` 1.0 now means "an unsharpened demosaic, like any camera's raw" |
| R9 distortion, auto crop | pixels | pixels, unchanged |
| C1 to C6: white balance (Kelvin, tint, light presets, Pick white), sensor map, exposure (Auto, manual, burst median) | pixels (`AsShotNeutral` 1, 1, 1: nothing of the white balance is left to undo in the other app) | unchanged |
| C7 highlight range and low-light toe, C8 LogC4 | pixels | unchanged (the highlight range replaced the roll-off shoulder in pipeline 0.4.0, 2026-10-17; it is a scene-linear gain like the rest of C7) |
| C9 grade (contrast, brightness, zones, colour balance, saturation, the Tone card) | pixels | unchanged |
| C10 look (CDL and LUT) and its intensity, log-to-log | pixels | unchanged |
| C10 look with its own display rendering (LogC3 to Rec.709) | **refused** (the DNG option was disabled) | **pixels, approximate**: the scene values ACES 2 turns into the look's picture (below) |
| C11 curves | pixels | unchanged |
| **C12 white lift** (`white_offset_ev`, the automatic amount sized per photo, `docs/02` C12 step 1b; ACES 2 path only) | not in the app yet | **pixels**: a scene-linear gain (`2^(A · smoothstep)` on the luma, ratios kept, exactly 1 up to +1 stop), baked into the AWG4 pixels after the look and curve and before the fitted profile, like the look. Nothing of it is left to undo in the other app, and the DNG's pixels through ACES 2 with the placement are the app's picture to 1e-5 of display light (`tests/white_lift.rs`). With an imported ARRI display LUT, or a look with its own display rendering at 100 %, the picture has no lift (ARRI's highlights) and neither has the DNG; at an intermediate intensity the app blends our lifted C12 with the look's, and the DNG's inverse step takes that blend as it is |
| C12 ACES 2 | profile (tone curve and look table fitted to the plain transform) | unchanged |
| C12 display placement (`DISPLAY_PLACEMENT_EV`, +0.85) | not in the app yet | `BaselineExposure` (`+ k`; the DNG opens as bright as the app) |
| C12 imported ARRI display LUT (Preferences › Display rendering) | **not in the pixels**: the preview showed the LUT's picture, Adobe's renderer showed ACES 2 | **pixels, approximate**, like a look with its own rendering |
| C13 display encode and dither, colour space, size, ICC | not in a DNG (16-bit linear pixels; the preview is an sRGB JPEG, `PreviewColorSpace` 2) | unchanged |
| Output sharpening | never | never |
| Orientation (camera and user turns) | tag (`Orientation`) | unchanged |
| Crop without a straighten angle | tags (`DefaultCropOrigin/Size`; pixels keep the lens auto crop) | unchanged |
| Crop with a straighten angle, the angle itself | pixels (a DNG has no rotated-crop tag) | unchanged |
| EXIF, GPS (unless removed), look, profile and pipeline version, the settings (`ym:Settings`) | Exif IFD and XMP | unchanged (the settings are the photo's, so a DNG records an R8 amount that it does not carry) |

**How a look with its own display rendering (or an imported display LUT) goes in.** A DNG holds scene-linear AWG4 that Adobe's renderer turns into a picture with the profile fitted to ACES 2, so the pixels are chosen as the scene values ACES 2 turns into the picture the chain makes. `ColorChain::apply_dng_pixel` runs C1 to C11, takes the chain's display-linear sRGB picture (C12 with the look's LUT blended in at the intensity, or the display LUT's output), inverts ACES 2 SDR with Rec.709 limiting primaries (`Aces2Transform::inverse_ap0_linear`, the port of the reference's inverse output transform: it round-trips the display value to 5.5e-10 and agrees with OpenColorIO's inverse to 1.3e-4 relative, `docs/02` C12), takes the placement out (`2^-k`: Adobe's renderer puts it back through `BaselineExposure`) and goes to AWG4. Two clamps. **Display values clamp** to what ACES 2 can output (negative, above white, outside Rec.709: a colour outside the display's gamut is clipped, not gamut-mapped). **Scene values stop at the top of the profile's range** (`DNG_SCENE_LIMIT / 2^k` = 16 / 2^0.85 = 8.9 in AWG4): display white is scene 128 for ACES 2 and has no finite value in practice, and the tone curve of the profile ends at 16 anyway, so a colour whose scene value would be higher is **dimmed in display light** (all three channels by one factor, found by bisection: the largest factor in 0.5 to 1 whose scene value fits) until it fits. A white of the look therefore comes out of Adobe's renderer at the display value of scene 16 (linear 0.9435, code 0.975 against 1.0, CIE76 2.2), a slightly tinted near-white keeps its tint and loses at most a few percent of light, and the white level of the file stays at its floor instead of crushing the shadows. (The first version scaled the scene value down with its ratios kept; the forward transform compresses chroma more the lighter the colour, so a tinted highlight came back with a strong cast: display (1, 1, 0.95) as (1, 0.99, 0.63), CIE76 20, and a pale sky (0.93, 0.97, 1) as (0.74, 0.88, 1), CIE76 8, found in review. Dimming the display colour instead gives CIE76 at most 2.3 over the 819 colours of the top of the display cube that were tested, mean 0.06 against 0.39, `chain_cpu.rs`; through Adobe's renderer, on a synthetic LogC3-to-Rec.709 look of ours that reaches display white and a bright patchwork scene, the highlights (215,000 pixels) against the unsharpened picture went from CIEDE2000 p95 3.0, p99 3.3, worst 3.6 to p95 0.70, p99 0.76, worst 1.00, `export_dng_adobe.rs`.) A look with its own rendering at 0 % intensity is our C12 exactly and gets the plain DNG. The preview is the look's picture itself.

*Measured* (`tests/export_dng_carries.rs`, `crates/ym-color/tests/chain_cpu.rs`, `tools` measurement below; a look of our own, never an ARRI file): in the app's own arithmetic the DNG's pixels through ACES 2 with the placement are the app's picture to 9e-8 of display light for Neutral, a log-to-log look, a LogC3-to-Rec.709 look at 100, 60 and 0 % and a display LUT, wherever the picture is inside what ACES 2 reaches (every pixel of the test scene for the LUT looks). Through Adobe's renderer (`dng_validate` 1.7.1 with the embedded profile, ΔE00 of its sRGB render against the app's picture), for a synthetic LogC3-to-Rec.709 look of ours (33 points: a filmic tone curve darkened to put mid grey at display 0.12, then gamma 2.4, with a little warmth and a little blue density), on eight synthetic chart photos (seven bodies, D55 to LED and mixed light, ISO 400 and 12800): against the same render without any sharpening (16-bit TIFF, `--sharpen 0,1 --output-sharpening 0`, which isolates what the DNG model costs) **median 0.043, 95th percentile 0.45, 99th percentile 1.04, worst pixel 7.9**; Neutral (plain ACES 2) on the same chart gives 0.093, 0.30, 0.70 and 10.0, so the approximation costs nothing the profile did not already cost. At 60 % intensity (three files) 0.046, 0.34, 0.82, 7.8. The worst pixels are saturated blues at the display's gamut edge (the app's picture has red at 0), where the profile's own fit is also weakest (*As built (M3-12)*: median 0.43 and 99th percentile 2.9 for chroma above 80). Against the app's JPEG as written (sharpened, which the gate keeps comparing with): median 0.77 over all pixels, per-file medians 0.68 to 0.91 (Neutral 0.71), 99th percentile 36 because of the sharpened chart edges (Neutral 38.7). On four real photographs (local evaluation, every third pixel, 8.8 million pixels: ILCE-7M3, DSLR-A300, NEX-7 and an A1 photo of the owner's) the same look gives, against the unsharpened 16-bit TIFF, **median 0.045, 95th percentile 0.20, 99th percentile 0.34, worst pixel 1.05** (per-file medians 0.031 to 0.062; at 60 % intensity on two of them, the DSLR-A300 and the A1 photo: 0.032, 0.18, 0.45 and 1.03), and against the JPEG as written a median of 0.63 (per-file medians 0.52 to 0.91, the A1 photo being the sharpest) with a 99th percentile of 8.6 that is the sharpening's halos; every DNG passes `dng_validate` with no warning. The same numbers on the repository's own test scene (`tests/export_dng_adobe.rs`, which runs them when `dng_validate` is built): median 0.025, 99th percentile 0.70, worst 0.77 against the TIFF; median 0.60, 99th percentile 2.2 against the JPEG (Neutral: 0.090, 0.24, 0.51 and 0.44, 5.7).
- **What the DNG model cannot carry** (reported, not closed): (1) white balance, exposure, the look and the tone controls are baked into the pixels; nothing can be undone in the other app, and a white balance change made there acts after the look (said in the help text). (2) A look with its own display rendering, and a display LUT, are approximate by construction: colours outside Rec.709 are clipped, display white comes out at code 0.975, and the scene values are not a scene any more (a push of exposure in the other app moves the picture's tone curve, not its light). (3) A rotated crop (a straighten angle) is baked. (4) Apps other than Adobe's ignore the profile, so they show the stored image darker and without ACES 2 or the placement (*What other apps show*). (5) Adobe's renderer ends the tone curve at an AWG4 value of 16 / 2^k = 8.9 (5.6 EV over mid grey): brighter values keep their stored value but render at the display value of the plain transform at 16 (the placement note under *As built*). (6) The one deliberate loss is sharpening: the converter's own raw sharpening is the only sharpening a DNG gets, the app's capture and output sharpening are not in it, so a DNG opened in Lightroom looks softer than the JPEG until its sharpening is on.

White-balance changes made later in another app act after the baked look, so they're approximate. Say so in the help text.

The help text also says, in one sentence (`ym_export::dng::OTHER_APPS_NOTE`, used word for word by `ym render --help`): **"Apps other than Adobe's show the stored linear image darker until their own exposure handling is applied."** The reason is the white floor above: the stored image is the scene divided by at least 16 (4 EV), and only Adobe's apps undo that through `BaselineExposure` and the profile. ## Tests

- Golden exports: fixed A1 and corpus files × each format × each colour space, hashed. A change in hash needs an explanation in the PR (and usually a `pipeline_version` bump).
- App vs CLI: the same job exported through both is byte-identical.
- ICC: every output decodes in a colour-managed reader (ImageMagick or moxcms) to the expected values at test patches within 1 code value.
- Resize: Lanczos in linear light; check a zone plate for ringing limits.

## As built (M1-13 export writers, M3-12 DNG writer)

Crate `ym-export`. It depends on `ym-color` only (not on `ym-raw` or `ym-core`): its inputs are plain structs that `ym-core` fills in. Entry points: `write_export(&ExportRequest, &ExportDestination, &ExportHooks) -> ExportOutcome` (one photo to one file, atomically), `encode_to_vec` / `encode_to_writer` (the same bytes into memory, for tests and hashes), `estimate_bytes(width, height, format, size)` and `estimate_bytes_with_detail(width, height, format, size, Option<DetailStat>)` for `export_estimate` (see Size estimate below). `ExportOptions` serialises exactly as `ExportOptions` in `src/api/types.ts` (flat: `format`, `jpeg_quality`, `bit_depth`, `tiff_compression`, `color_space`, `size`, `destination`, `name_template`, `if_exists`); `ExportOptions::format_spec()` gives the richer `ExportFormat` enum the writers take.

**Output sharpening in the writer (`PictureStages`, `resize::sharpen_output`).** The photo's amount reaches the writer as `PictureStages { output_sharpening_pct }` (`encode_to_writer_with`, `encode_to_vec_with`, `write_export_with`; the plain `encode_to_writer`, `encode_to_vec` and `write_export` take the default, which is nothing, so every existing caller writes the bytes it wrote). `ExportRequest` is unchanged: the amount is not an export option and `ExportOptions` (the wire type) has no field for it. `ym-core::export_photo` passes `DevelopSettings::output_sharpening` for JPEG, TIFF and PNG and nothing for a DNG. In `encode_to_writer_with` the stage sits between the resize and the encode: the resized `LinearImage` (or the rendered pixels, for a full-size export, decoded to linear first when they are `DisplayEncoded`) goes through `sharpen_output`, which runs `ym_gpu::cpu::output_sharpen::OutputSharpen::screen()` at the amount and the scale `scale_for_edges(out long edge, rendered long edge)`, and the writers take the result. **No amount, no stage:** 0, and anything below 0.1 % (spec 04: `A < 0.001`), makes no image and no change, so the bytes are exactly those of the plain call (tested for JPEG, TIFF 8 and 16 bit, PNG 8 and 16 bit, at full size and resized). The stage runs in strips of 1024 core rows with the stage's own receptive field (`SharpenPlan::halo_px`, 17 px at full size for the screen preset, at most 21) above and below: the tiling contract of spec 04 section 5.2 gives the whole-frame result bit for bit (tested against the whole-frame run on a 1100-row image, so two strips), a cancel check and a progress report fall between strips, and the working planes stay a few tens of megabytes at any size. The progress shares are: resize 0 to 30 %, the stage 35 % (right after the resize, or from 0 without one), the encode the rest. A full-size export holds one more copy of the picture while it runs (12 bytes a pixel: the sharpened image next to the rendered one); a resized one holds the resized image and its sharpened copy. `ym-export` therefore depends on `ym-gpu` (CPU code only; `ym-gpu` depends on `ym-color` and `ym-noise`, no cycle). The amount is checked (0 to 200, finite: `ExportError::InvalidInput` otherwise). The written file's XMP records it in `ym:Settings`; an export made before the field existed reads, when its settings are fed back, as 100.

**Pixels in.** JPEG, TIFF and PNG take `f32` RGB, interleaved: `DisplayLinear` (linear light in the export colour space's primaries, the output of C12; the writers do C13 with `ym_color::encode`) or `DisplayEncoded` (already C13-encoded, 0 to 1; a resize decodes it to linear first). DNG takes `SceneLinearAwg4` (C11 output decoded from LogC4) plus a display-linear sRGB preview. The writers convert a band of about one million pixels at a time, in parallel row by row, so the bytes do not depend on the thread count (tested). The input buffer is one full image; streaming tile rows into the writers is a follow-up.

**Names and folders.** `{name}` is the source file name without extension, `{look}` the look's slug, `{date}` the **capture date** as `YYYY-MM-DD` (`undated` when unknown; never the export date, for determinism), `{seq}` the 1-based number of the photo in the job with at least three digits, `{camera}` the camera body as a slug (`sony-a1`; see the review notes below). Unknown `{words}` stay as typed (as in the UI preview). The stem is made safe: `/ \ : * ? " < > |` and control characters become `_`, leading dots and trailing dots and spaces are dropped, at most 200 bytes. The default folder is `<source folder> export` next to the source folder, then `~/Pictures/Yellowmoon export`; a folder the user chose is never replaced by a fallback. The default folder is named after the source folder as the photo was opened; symbolic links in the path are not resolved (on a Mac `/var/…` stays `/var/…` and does not become `/private/var/…`, and a source folder that is itself a link gets its export folder next to the link, which is where the panel and the CLI command say it goes), except for a folder with no name as written (`..`, or a file with no folder part), which takes the name of the folder it resolves to; a name that is not UTF-8 is kept byte for byte (`ym_export::naming::default_destination` is the one implementation; `ym-core` re-exports it). Skip and Keep both never overwrite, even if another process creates the file during the export (the final step is a hard link, or a checked rename on file systems without hard links such as exFAT). A name that an earlier photo of the same export job has already written is always numbered (the Keep both style, " 2", " 3" …), whatever "If the file exists" says, so Replace never overwrites the job's own earlier photo and Skip never takes it for a file from before the job (a file that was there before is replaced or skipped as asked; when the choice was Replace or Skip, the numbered photo carries a note saying why, and with Keep both it needs none). The temporary file is `.yellowmoon-<pid>-<n>.tmp` in the destination folder, fsynced before the rename; an error, a cancel or a panic deletes it. A target that resolves to the photo's original file is refused. Cancel is polled between bands of about one million pixels, so "after the current tile" is a fraction of a second of work (a batch of TIFF strips or a PNG band compresses in well under a second).

**JPEG.** Baseline, 4:4:4 at quality 90 and above, 4:2:0 with box-averaged chroma below, optimised Huffman tables, JFIF 300 dpi, then `APP1` Exif, `APP1` XMP and the ICC profile in `APP2` chunks. The `jpeg-encoder` crate writes optimised-table output as one scan per component, which `zune-jpeg` (Rust's `image` crate) decodes with wrong colours; `src/jpeg/interleave.rs` rewrites it as a single interleaved scan with tables rebuilt by T.81 Annex K.2 (coefficients and quantisation tables unchanged; the decoded pixels are identical to the standard-table interleaved file, tested over 17 sizes, both samplings and three quality settings). Sizes above 65,535 px are refused with a message.

**TIFF.** RGB strips of about 512 KB, compressed in parallel with the `tiff` crate's LZW and Deflate; the horizontal predictor for both compressed modes; ICC 34675; XMP 700; Exif and GPS sub-IFDs; orientation 1; 300 dpi; all out-of-line values start on even offsets (the `tiff` crate does not align them; the writer pads). Files above 4 GB are refused. **Deflate backend:** the bytes of the ZIP strips and of the PNG `IDAT` and `iCCP` depend on which deflate implementation `flate2` is built with (zlib-rs and miniz_oxide write different, equally valid streams, zlib-rs about 1 to 2 % smaller). Cargo features are additive and `ym-looks` pulls `zip` with `deflate-flate2-zlib-rs`, so every workspace build used zlib-rs while `cargo test -p ym-export` alone used miniz_oxide, and `golden_hashes_match` failed under `cargo test --workspace`. `ym-export` now declares `flate2` with the `zlib-rs` feature itself (`Cargo.toml`), so the bytes are the same in every build, and the 16 PNG and TIFF-ZIP entries of `tests/data/golden_hashes.json` were regenerated (JPEG, DNG, uncompressed and LZW TIFF unchanged). zlib-rs picks its CPU-specific code at run time; its output for the levels used here (level 6) is not known to depend on it, but that is unchecked on Apple silicon against Intel (a Mac check for M0-H4: `golden_hashes_match` must pass on both). LZW on noisy 16-bit samples can produce a file as large as the uncompressed one (measured 0.8 to 1.2 of raw on noisy data); Deflate is smaller. The default "16-bit, LZW" of the table above is therefore a candidate for "16-bit, ZIP".

**PNG.** `iCCP`, `cICP` (written by hand; the `png` crate parses but does not write it), `pHYs`, `eXIf` and an `iTXt` with `XML:com.adobe.xmp`. cICP code points `[primaries, transfer, matrix, full range]`: sRGB `1, 13, 0, 1`; Display P3 `12, 13, 0, 1`; Rec.2020 `9, 1, 0, 1` (H.273 has no code for the BT.1886 curve; transfer 1 is the one it pairs with a BT.1886 display, and the ICC profile carries the exact gamma 2.4). The `iCCP` profile name written by the `png` crate is `_`.

**ICC (`icc.rs`).** Generated, 612 to 632 bytes each: v4.3, class `mntr`, `RGB `/`XYZ `, fixed creation date 2026-10-01, MD5 profile ID, `desc` and `cprt` as `mluc`, `wtpt` and the header illuminant = D50 PCS (0.9642, 1, 0.8249), `chad` = Bradford from D65 (x 0.3127, y 0.3290) to D50, colorants = `chad` times the primaries' D65 matrix from `ym-color`, one shared `para` tone curve: type 3 `g 2.4, a 1/1.055, b 0.055/1.055, c 1/12.92, d 0.04045` for sRGB and Display P3, type 0 `g 2.4` for Rec.2020. Verified with LittleCMS 2.14 (C library through ctypes, and Pillow's ImageCms): 15 files (5 formats x 3 spaces) x 272 patches (a 6x6x6 cube, a grey ramp, four near-blacks): XYZ within 1.7e-5 of `ym-color`'s maths, sRGB codes within 1 (LittleCMS with `NOOPTIMIZE`; its default fixed-point matrix-shaper optimisation is off by up to 11 codes on extreme out-of-gamut dark patches, which is its approximation and not the profile).

**EXIF (`exif.rs`).** Built from `ExifInfo` (make, model, lens make and model, exposure time, f-number, ISO, focal length and 35 mm equivalent, exposure compensation, capture time with sub-seconds and UTC offset, optional GPS), never copied from the source: orientation 1, no thumbnail, no maker note, no serial numbers, text reduced to ASCII. `ComponentsConfiguration` is Y, Cb, Cr plus `YCbCrPositioning` for JPEG and R, G, B for TIFF and PNG; `ColorSpace` is 1 for sRGB and 0xFFFF for the others. ISO above 65,535 uses `ISOSpeed` with `SensitivityType` 3. With "Remove location" on, the GPS directory is not written (the output is byte-identical to one made without a position; tested). `DateTime` (IFD0) is the capture time.

**XMP (`xmp.rs`).** `xmp:CreatorTool`, `xmp:CreateDate`, `xmp:ModifyDate` and `xmp:MetadataDate` (all the capture time), `dc:format`, then the twelve `ym:` properties in the order of the table above (`ym:Auto` and `ym:AppleAuto` after `ym:Models`, added with Apple Auto, `docs/19` section 9; `ym:AppleAuto` is written only when Apple Auto was on for the photo, so with Apple Auto off an export carries today's properties plus `ym:Auto` = `rule`); `ym:Settings` is the compact JSON of a `serde_json::Value` (keys sorted), in which Auto contrast and saturation are pinned to the numbers they resolved to, as Auto exposure is. Fixed property order, no padding.

**Resize (`resize.rs`).** Lanczos-3, separable, support scaled by the reduction factor, taps outside the image dropped and weights renormalised: the same convolution as Pillow's `LANCZOS`, to which it is compared on float images (worst difference 0, six size pairs). Accumulation in f64, so a flat field is exact. Step-edge overshoot stays under 10 %; the zone-plate test bounds the output to [-0.10, 1.10] for shrink factors 2, 3 and 5. The long edge never upscales; the short edge is rounded half up. The UI grid (1000 px up in 20 px steps, then the full size) is `Size::ui_long_edge_choices`; the library accepts any long edge from 16 to 65,535 px.

**DNG (`dng.rs`).** Layout: IFD0 is an 8-bit RGB thumbnail (long edge at most 256 px, `NewSubFileType` 1) carrying the DNG profile tags, the Exif IFD, the GPS IFD and the XMP; `SubIFDs` points to the LinearRaw IFD (`NewSubFileType` 0, 3 x uint16, `Compression` 1, `BlackLevel` 0, `WhiteLevel` 65535, `NoiseReductionApplied` 1, `DefaultCropOrigin/Size`, `ActiveArea`) and to the preview IFD (full-size JPEG, quality 92, 4:4:4, `PreviewColorSpace` 2). The directories are written before IFD0, so IFD0 is last in the file. **`PreviewColorSpace` 2 is sRGB** (1 is "Gray Gamma 2.2"); exiftool reported the first draft's value 1. The preview and the thumbnail are in the raw pixels' orientation (not rotated) and cropped as the user sees the render, because the `Orientation` tag of IFD0 applies to all three. `compose_orientation(camera exif orientation, user quarter turns)` gives the tag value. `x_white` is the upper edge of the histogram bin (2048 bins per octave) that holds the 99.99th percentile of `max(R, G, B)`, at least `BaselineExposure::white_floor` (1.0 for `Fixed` or a zero offset, 16 for the fitted profile); `DngReport` has `x_white`, `baseline_exposure_ev`, the fraction of pixels with a negative channel (clipped to 0) and the fraction above `x_white`. **`BaselineExposure` = `log2(x_white)` + a fitted offset + the display placement** (`BaselineExposure::Auto { fit_offset_ev, placement_ev }`, -4 and +0.85 for the embedded profile via `FittedProfile::baseline_exposure()`; 0 and 0 for `BaselineExposure::default()`, the identity profile of the structure tests), or `Fixed(ev)`. `white_level(raw, baseline_exposure)` gives the white level before writing; an `Auto` offset that is not a number or is outside -12 to 4 EV, or a placement that is not a number, is refused. `RawDataUniqueID` is the first 16 bytes of the SHA-256 of the stored pixels. `ProfileToneCurve` and the look table are inputs (`DngProfile`); `DngProfile::identity()` writes the identity curve and a 2 x 2 x 2 identity table (an identity tone curve shows a flat, dark image in Adobe's apps, so it is for structure tests only: the product embeds the fitted profile, see *As built (M3-12 `tools/dngfit`)*). **A look table with one value division (a "2.5D" table) must use linear encoding (`ProfileLookTableEncoding` 0):** with encoding 1 (sRGB) Adobe's reference renderer (DNG SDK 1.7.1) darkens even an identity table (mid grey 0.18 comes out as 0.027). `LookTable::validate` rejects the combination; `tools/dngfit` should fit a table with at least two value divisions when it uses sRGB encoding, as the 36 x 32 x 16 of this document does. Matrices: `ColorMatrix1 = inv(AWG4 to XYZ)`, `ForwardMatrix1 = Bradford(D65 to D50) * (AWG4 to XYZ)` scaled per row so (1,1,1) maps to D50 exactly, both as `SRATIONAL` with a denominator of 10^7. Checks (`tools/dng/check_dng.py`, run by `tests/dng_validate.rs`, 63 checks per file; the tests that run `dng_validate` need the binary and are skipped without it): exiftool lists every tag with the expected value and `exiftool -validate` reports no warnings; tifffile parses IFD0 and the two SubIFDs; LibRaw (rawpy) opens the file and returns exactly the stored pixels, which are compared with the formula computed independently from the original floats; the matrices are recomputed from the AWG4 primaries and agree with colour-science. `tools/dng/build_dng_validate.sh` builds Adobe's `dng_validate` from the DNG SDK 1.7.1 (the AOSP copy, `GrapheneOS/platform_external_dng_sdk` at `0f23d021`, pinned by commit; about 10 minutes on 4 cores) with the XMP toolkit and JPEG XL stubbed out. With it, five DNG variants (plain, 5 x 3, 131 x 77, rotated and cropped with a fitted-style tone curve and look table, mirrored) validate with no warning or error, and Adobe's own renderer, given flat AWG4 patches and an identity profile, returns the sRGB and Display P3 colours `ym-color` computes to within 3.0e-4 and 9e-5 in encoded values (16 patches, saturated ones included): `ColorMatrix1`, `ForwardMatrix1`, `AsShotNeutral`, D50 and the Bradford adaptation agree with Adobe's code, not only with ours.

**Size estimate (`estimate`, M3 re-fit).** A file's size depends on the pixels as much as on the pixel count: the nine real renders below range from 0.7 to 2.7 bits per pixel at JPEG quality 92 at full size. The estimate therefore takes a cheap measure of the picture's fine detail next to the export's size and options.

- *The statistic.* `ym_export::estimate::DetailStat` is the mean absolute difference between neighbouring pixels (horizontal and vertical) of the luma (Rec.709 weights on the display-encoded values) of the picture box-averaged by a whole factor to at most 240 px on its long edge, normalised to 240 px with `(s/240)^0.25` for a preview a little smaller (the scale exponent is the median of the measured change between 240 and 480 px). `DetailStat::measure_rgb8(w, h, &[u8])` takes an 8-bit sRGB preview such as the thumbnails `ym-core` already makes (at most 240 px); `measure_encoded_f32` takes display-encoded floats. It returns `None` for a mismatched buffer or under 16 px on the short side. It is 0.006 for a smooth, denoised frame and 0.05 for foliage or visible noise, and costs one pass over the preview.
- *The model.* For every format variant `ln(y) = a + b·x + c·y + d·x·y` with `x = ln(g / G0)` and `y = ln(output megapixels / 10)`; `y` is bits per pixel for JPEG and the size over the raw size for TIFF and PNG. `G0` is `TYPICAL_GRADIENT` (0.0175, the geometric mean of the real renders). One `(a, b, c, d)` per JPEG quality knot (50, 60, 75, 80, 85, 89, 90, 92, 95, 100, interpolated in the log domain, never decreasing with quality) and per TIFF (LZW, ZIP) and PNG at 8 and 16 bits; the detail is clamped to 0.003 to 0.12 and the ratio of a TIFF or PNG to 1.25. DNG is the 6 bytes per pixel of its LinearRaw plus the q92 preview. `estimate_bytes` (no preview) assumes the typical detail. The coefficients are the constants `JPEG_FIT` and `RATIO_FIT` in `estimate.rs`.
- *Calibration data (Oct 2026).* The nine real files of `testdata/real` (A300, A500, ILCE-5000, ILCE-6300 cRAW, A7 II, A7 III, A7 IV, NEX-5N, NEX-7; 10 to 31 MP after the lens crop) rendered by the current `ym` with its defaults (classical demosaic, automatic noise reduction and sharpening; 16-bit sRGB PNG), and the synthetic chart of the A7R IV at ISO 100, 400, 800, 3200 and 12800 (1248 x 832). **Review notes (independent review of M1-13 and the M3-12 writer).** Clarifications and decisions that came out of re-checking the writers against the spec and against independent readers; the code and tests are in `crates/ym-export`.

- **Directories start on even offsets.** The `tiff` crate writes a directory where the previous data ended, so an odd-length text value (a 12-character lens name gives 13 bytes with the NUL; an app version such as `0.1.10`) put the next directory at an odd offset, which the TIFF specification forbids. Every TIFF and DNG directory is now padded to an even offset before it is written (`exif::finish`), and `tests/structure.rs` walks every directory of TIFF and DNG files built with odd-length text.
- **Look table rule.** `LookTable::validate` also enforces the DNG specification's "all zero input saturation entries are required to have a value scale factor of 1.0" (the first saturation division of every hue and value division) and non-negative scales. `tools/dngfit` must produce tables that satisfy it: neutral tone belongs in `ProfileToneCurve`.
- **`BaselineExposure`.** Checked against Adobe's renderer, not only against our arithmetic: a scene with `x_white` 2.6 renders to the colours `ym-color` computes from the original scene-linear values with `BaselineExposure = log2(x_white)` (worst difference 2.9e-4 in encoded values), and a fitted offset of -1 EV halves the light as expected.
- **Exif pixel dimensions of a DNG** are the size of the default crop when there is one (the meaningful image), not of the whole raw frame.
- **`{camera}` and `{look}`** are slugs, exactly as the export panel previews them (`Sony A1` gives `sony-a1`); `naming::slugify` is the same function as `slugify` in `src/export/template.ts`, so `ym-core` and the CLI should pass `slugify(body)`.
- **Disk-full and other write errors (review fix).** An encoder that cannot write its output (a full disk, a folder that went away) used to say "Encoding the PNG failed: No space left on device" with no next step, and a DNG said "TIFF" because the `tiff` crate writes it. The I/O errors of the JPEG, PNG and TIFF encoders now map to `ExportError::Write { format, source }` ("Couldn't write the PNG: No space left on device (os error 28). Check that the folder exists, is writable and has free space."), the same advice as `ExportError::Io`; `write_dng` relabels the TIFF encoder's errors as DNG. Non-I/O encoder failures keep "Encoding the X failed". The temporary file is still removed and a failed Replace keeps the old file. Test: `tests/disk_full.rs` (a sink that fails with ENOSPC after N bytes, for every format).
- **GPS seconds** are computed on whole ten-thousandths of an arc second, so a latitude a hair below a minute carries into the minute instead of writing "60 seconds".
- **Open question for M3-H6: undoable crop.** `DefaultCropOrigin` and `DefaultCropSize` are, for Adobe's apps, the bounds of the final image; they do not give the user an adjustable crop. DNG 1.4's `DefaultUserCrop` (tag 51125, four rationals relative to the default crop) is the tag Lightroom and Camera Raw show as an initial, adjustable crop. This document says `DefaultCropOrigin/Size` and the writer does that; try `DefaultUserCrop` when the DNG is opened in Lightroom (M3-H6).
- **Licence acknowledgement for the JPEG encoder.** `jpeg-encoder` is `(MIT OR Apache-2.0) AND IJG` (its forward DCT is ported from the Independent JPEG Group's software). `cargo deny check licenses` fails until `IJG` is added to `deny.toml`, and the IJG licence asks that documentation accompanying a binary says "This software is based in part on the work of the Independent JPEG Group." (`NOTICE`, the About window, `docs/14`).
- **What `exiftool -validate` says about the other formats.** JPEG and PNG: no warnings. TIFF: three minor remarks (`ComponentsConfiguration`, `ExifImageWidth` and `ExifImageHeight` are "compressed data" tags in the Exif specification and are kept because readers use them), a note that `GPSProcessingMethod` is not written, and, for Deflate (compression 8), a note that it is not among the values it expects (the `tiff` crate and tifffile read these files). The DNG validates cleanly.
- **Rec.2020 `cICP`.** PNG readers that honour `cICP` use it instead of the ICC profile, and H.273 has no code for the BT.1886 curve, so they decode the BT.709 code point (transfer 1), which is not the pure gamma 2.4 of the embedded profile and of our encode. If that shows in practice, write no `cICP` for Rec.2020 and leave the colour to the ICC profile.
- **Size estimate on a real 24 MP frame, and the TIFF default.** The ILCE-7M3 sample (6024 x 4024) developed by LibRaw, which does not denoise and is not a Yellowmoon render, exported to (actual / estimate, MB): JPEG q50 2.4 / 3.0, q75 4.0 / 4.5, q89 7.1 / 7.1, q92 15.2 / 9.9, q100 43.9 / 30.9; TIFF 8-bit LZW 61.4 / 50.9; TIFF 16-bit LZW 182.4 / 130.9 and ZIP 132.3 / 107.6 (the raw size is 145 MB); PNG 8-bit 51.2 / 43.6 and 16-bit 132.7 / 104.7. Sensor noise compresses worse than a film scan, so the estimate runs low for the quality 90 and above (4:4:4) JPEGs and the 16-bit files; the quality 50 and 75 JPEGs are over-estimated. A Yellowmoon render is denoised, so re-measure on renders in M3 (the ignored `calibrate_estimate` test takes any set of images): done, see Size estimate above (the table of the Kodak scans is gone; the 24 MP numbers of this note are for a frame without noise reduction). **16-bit LZW wrote a file 26 % larger than the uncompressed one and 38 % larger than ZIP** for similar time (10 s and 12.5 s in a release build on a loaded 4-CPU Linux machine): the default "16-bit, LZW" of the Options table should become "16-bit, ZIP" (a decision for Mykyta; nothing changed here). Release timings of the same run for 24 MP: JPEG q92 5.9 s, TIFF 8-bit LZW 4.8 s, PNG 8-bit 7.3 s, PNG 16-bit 9.9 s (including the display encode, with other builds running).

## As built (export tail on the device)

`docs/17-gpu.md` section 10. With `GpuStages::EXPORT_TAIL` (part of `On` and `Require`, and of `SIGNED_OFF` since 2026-10-15, after Metal CI run 38694506557 passed its suites, so `Auto` runs it on a hardware adapter) a JPEG, TIFF or PNG export never makes the host frame of display-linear `f32` (600 MB at 50 MP). The CPU path described above is unchanged, byte for byte (the 61 golden exports are identical), and stays the reference and the fallback.

**`BandSource` (`ym-export::pixels`).** The writers no longer take a finished picture; they pull encoded rows (stage C13 done) from a `BandSource`: `width`, `height`, `rows_u8(y0, rows, &mut Vec<u8>)` for JPEG and 8-bit TIFF and PNG, `rows_u16(..)` for 16-bit. A source is read in order (`y0` is the row after the last one it gave), so it may stream. `ImageBands { ImageRef, OutputSpace }` is the CPU source: it calls `encode_rows_u8` and `encode_rows_u16` and gives the same bytes every export gave before (`tests/bands.rs`: for every format, depth and colour space the file written through a `BandSource` equals the file written from the image; a source that fails half way leaves no file; progress never goes back; and, added in review, a source that hands out a band of the wrong size ends the export with an error and no file instead of a corrupt file). `write_jpeg_bands`, `write_png_bands` and `write_tiff_bands` are the writers; `write_jpeg`, `write_png` and `write_tiff` wrap them over `ImageBands`. `request::write_export_bands(&BandRequest, &mut dyn BandSource, &ExportDestination, &ExportHooks)` is `write_export` for a source (metadata, XMP, the temporary file in the destination folder, the rename; it refuses a DNG). The DNG keeps `ImageRef`: its two renders are host frames of `f32` as before (the raw pixels and the preview), with the colour stage of each tile on the device when the tail is on, read back tile by tile (`Stop::DngLinearAwg4` and the preview; agreement with the CPU 2.3e-6 and 3.5e-6 relative at worst, `tests/gpu_export.rs`; no output sharpening and no R8 for a DNG, as before).

**The tail (`ym-gpu::tail`).** The raw chain renders tile by tile as before (on the device too when its stages are on); each tile's camera RGB goes to the device, through the sampler and the colour chain C1 to C12 (persistent tables) into **slabs** of the rendered picture (four planes, at most 512 rows and 128 MiB, the design binding of `docs/17-gpu.md` section 4, so the cut does not depend on the device). A horizontal Lanczos-3 pass runs on each slab when it is complete, a vertical pass makes chunks of output rows (about a megapixel) from the rows they need, output sharpening takes a chunk with the stage's halo (17 to 21 rows), and C13 (with the blue-noise dither at absolute coordinates, so any cut gives the same codes) makes the bytes of a **band** (about a megapixel, 8 to 1024 rows). Each stage reads rows from a store of the pieces the stage before it made and releases a piece as soon as no later row needs it, so at 61 MP the device holds a few slabs and a chunk, not the 700 MB picture (`tests/gpu_tail.rs`: the bytes do not depend on the tile size, a finished tail holds nothing, a cancelled one gives everything back). The resize taps are planned on the CPU in `f64` (`ym_gpu::kernels::resize::Taps`; `ym_export::resize` re-exports them, so the CPU resize and the kernel use the same taps) and the kernel sums in difference form, `out = r + sum w (v - r)` with `r` the middle tap: a flat field is exact in any arithmetic.

**Threads and memory.** `Renderer::start_export_tail` queues the render on the export worker; the job sends the bands through a bounded channel (`BAND_DEPTH` = 3) and the queue's thread (or `ym`'s) pulls them through `GpuBands` while the writer compresses and writes, so the render of the rows that follow overlaps the encoding of the rows before. A writer that stops drops the bands and the job ends at its next tile. The host holds a few bands of codes (a few megabytes each) and the working set of a tile; the ledger's peak of an export is the CPU path's less the frame (`tests/gpu_export.rs`: 33,560,064 B against 27,080,064 B for a 900 x 600 photo, the difference exactly 6,480,000 B = 900 x 600 x 12). JPEG still fills its 8-bit buffer before it encodes (the `jpeg-encoder` crate takes a whole image): the render and the C13 rows overlap, the DCT does not.

**Look, cancel, progress.** The check that the look did not change while the picture rendered runs when the last rows are asked for, before the writer can finish the file (`GpuBands::check_before_last_rows`). A cancel between bands removes the temporary file and hands every device buffer back (the pool returns to its baseline); the progress an export reports is the writer's, by rows written, and never goes back, also when the photo is made again on the CPU. Queue semantics are unchanged: settings are snapshotted at queue time, a job waits for the shared estimates, files are written under a temporary name and renamed, cancel deletes the partial file.

**When the device fails.** A device error in the tail or in the raw chain of a tile ends the attempt with a `RenderError::Gpu`; the writer has seen some rows, so the export removes its temporary file and makes the **whole photo again on the CPU reference path** (`Renderer::spawn_full_cpu`: the same render with no device at all), with the note "The graphics card could not render this photo, so the CPU did: <reason>." in `ExportReport.notes` and `device = cpu`. The file is then the CPU export's, bit for bit (`tests/gpu_export.rs`, with `--features fault-injection`: a shader that does not compile, an allocation out of budget, a lost device; the tail alone and every stage; PNG and TIFF; the pool returns to its baseline; and, reviewed, a device that fails **part way**, after the writer has taken and compressed rows: a raw-chain tile that fails at the 20th of 32, a device lost once the writer has taken a fifth of the rows of a picture that comes out in eight bands, for PNG, TIFF and JPEG, each equal to the CPU export bit for bit, one file in the folder, progress never going back). The fallback is for that export only: the next photo tries the device again, **except after a shader of the tail that does not compile**: that is a property of the machine, so the export tail is switched off for the renderer (`Renderer::export_tail_disabled`, also for a DNG's device colour stage; the application and `ym` have one renderer, so it is off for the process), the photo that met it is made again on the CPU, and the next exports go straight to the CPU path without trying the same shader first (`gpu_export.rs`, faults: the second export is the CPU's bytes, carries no note about the card, and the device's submission counter does not move; a strict policy still fails the photo instead of turning the switched-off tail into a quiet CPU export). The raw chain's and the view stages' shaders have their own switches. When the photo's raw words cannot be put on the device again after tiles ran on it (an upload that finds no room, `YM_GPU_FAULT=upload@N`), the export starts again on the CPU as for any device error. A strict policy (`ym render --require-gpu`, `GpuPolicy::Require`) fails the photo instead, error kind `gpu`, and leaves no file. A DNG whose colour stage fails on the device is made again on the CPU in the same way. A DNG is two renders (the raw plane and the preview), and a device error that fires once is spent by one of them: when the raw render fell back the preview is made on the CPU reference path, and when only the preview fell back the raw plane is made again on it, so the file is wholly the CPU's and the report says `device = cpu` (`FullImage::fell_back_to_cpu`, the typed signal; `gpu_faults.rs::a_dng_after_a_one_shot_device_error_is_the_cpu_export_whole`). A file that appears under the name between the check at the start and the writer's own ("If the file exists: skip") is skipped as on the CPU path, not reported as cancelled: the writer pulls no row, the render is stopped, and the other file is left alone (`gpu_export.rs::a_file_that_appears_before_the_first_row_is_skipped_not_cancelled`).

**Speed priors.** `ExportSpeed` keeps one set of numbers per path, the CPU reference and the tail on the device, each replaced by the photos that took that path (the first sample outright, later ones as a running mean that weighs the newest half); a photo that fell back to the CPU teaches the CPU set only. The set is the path's, not the raw chain's: an export whose raw chain ran on the device but whose colour pass and writer ran on the CPU (what `Auto` does) teaches the CPU set, which is the one its estimate reads (`RenderReport::device`, not the ranges; `gpu_export.rs::an_export_teaches_the_numbers_of_the_path_the_estimate_reads`; a review found it recording the device's set, so that the estimate of the default configuration never learned). **The path is named by the reader, never selected as a side effect**: `estimate()` takes the path from `Renderer::export_tail_enabled` into a local, and `ExportSpeed::render_s_per_mp(device)`, `encode_s_per_mp(device, format)` and `combined_s_per_mp(device, format)` say which set they read; nothing holds a "current path" any more (the old `use_device` flag was set by `estimate()` and read by whoever came next). On the device the writer pulls the picture while it renders, so the time of a photo covers both. **One format's time says nothing about another's**: such a sample is recorded for the format it was taken with (`record_overlapped(format, megapixels, seconds)`), a device estimate for a format that has one is that combined time per megapixel and adds no encode on top, and the formats that have none keep the CPU's numbers (a slow PNG export, limited by deflate, used to mark all four formats as overlapped and so to set the estimate of a fast JPEG one, which is limited by the DCT). **No speed of the graphics card has been measured yet**: until the Mac session (M0-H4) the device's set starts as the CPU's. `ExportReport.device` says which path made the file.

## As built (M3-12 `tools/dngfit`, DNG gates)

`dngfit fit` writes `data/dng/profile.json`; `dngfit eval` and `dngfit gate` measure it; `tools/dng/run_gates.sh` runs both; the CI job is the `dng` job of `.github/workflows/ci.yml`. Method, model and tests: `tools/dngfit/README.md`. What was decided and measured:

- **Adobe's renderer, as found.** `dng_validate` (DNG SDK 1.7.1) renders a LinearRaw DNG per pixel: `x * 2^BaselineExposure` (clipped to 0 to 1), `ForwardMatrix1` to XYZ D50 and to linear ProPhoto, the look table in HSV of that RGB, the tone curve, the matrix to sRGB, the sRGB encode. `tools/dngfit/src/model.rs` is a model of that, checked against the renderer on 3000 random colours with a random table and curve (median error 1.4e-4 in encoded values, worst 2e-3). Two facts the specification does not give: the look table's **value scale multiplies the sRGB-encoded value** (with `ProfileLookTableEncoding` 1) and the result is decoded again (a linear scale was off by up to 0.12 in code values); and the tone curve is applied by the SDK's *RGB tone*: the largest and smallest channels go through the curve and the middle one keeps its position between them, with the curve sampled into a table of 4096 steps and interpolated linearly. The curve's own spline through the points matters only through that table.
- **A negative `BaselineExposure` is not a gain (decision).** For an exposure below zero the renderer applies a highlight shoulder instead (linear with slope `2^b` up to 0.25 of the range, then a quadratic that ends at 1): with `b = -3` and an identity profile scene 0.40 renders at 0.086 of display light instead of 0.050 and 0.84 at 0.654 instead of 0.105 (`tests/model.rs` pins it). A profile cannot be fitted for that, because the shoulder depends on `b`, which depends on the photo's `x_white`. And the tone curve's input range is `[0, 1]` after the gain, while ACES 2 is at 94 % of display light only at a scene value of 16. So the profile covers scene values up to 16 (`fit_offset_ev` -4) and **`x_white` must be at least 16: `x_white = max(p99.99, 16)`, `BaselineExposure = log2(x_white / 16)`** (plus the display placement since 2026-10-14, below), which is zero for every photo whose 99.99th percentile is below 16 (nearly all) and positive for the rest. The cost is shadow precision: stored codes are scene value / 16 * 65535, a step of 2.4e-4 in scene light (mid grey 0.18 is code 737; scene 0.011, four stops below it, is code 46); the step it makes in ACES 2's output is about a quarter of an 8-bit code at worst (0.26 at scene 0.019, 0.07 at mid grey, measured on greys with OpenColorIO's ACES 2 Rec.709 view), but a shadows push of +3 EV in another editor would show it (the open point of "Shadow precision" above, now with a number). The writer floors `x_white` at `2^-fit_offset_ev` (`BaselineExposure::white_floor`).
- **Profile.** 65-point `ProfileToneCurve` (geometric through the shadows), a 36 x 16 x 16 `ProfileLookTable` with `ProfileLookTableEncoding` 1 (a 36 x 32 x 16 table is barely better, median 0.070 against 0.075, and twice the size), `fit_offset_ev` -4. The fit takes about 2 s. Against ACES 2, through `dng_validate`, in CIEDE2000, on sets the fit does not use:

| Set | n | median | p95 | p99 | max |
|---|---|---|---|---|---|
| neutral ramp, 0.002 to 16 | 400 | 0.004 | 0.019 | 0.028 | 0.031 |
| hue and chroma sweep (36 hues, 10 chromas, L* 25 to 85) | 1314 | 0.077 | 0.50 | 1.02 | 2.06 |
| random photograph-like colours | 20000 | 0.075 | 0.46 | 0.73 | 8.65 |
| chart patches of the synthetic golden scenes, -4 to +3 EV | 56240 | 0.103 | 0.60 | 0.92 | 4.68 |
| the same random colours with the tone curve only (no look table) | 20000 | 0.69 | 3.7 | 7.4 | 12.2 |

The worst colours are very saturated blues at the edge of the AWG4 gamut (ProPhoto hue 4.1 to 4.2 of 6, saturation 0.9) where ACES 2's gamut mapping bends faster than an HSV grid follows, and the darkest part of the range, where the first value division of the table spans three stops (median 0.27 at -3 to -4 stops from grey). Colours that need a negative ProPhoto channel are clipped by the renderer before the table; the scene data has few.
- **Gates, golden set (`dngfit gate`).** Every file: `ym` writes the DNG and our JPEG with the same settings; the DNG is checked as `ym` wrote it (the numbers below were first measured on DNGs written again with the fitted profile, before `ym` embedded it; the as-written numbers are in the next bullets); `dng_validate -v -32 -cs1 -tif` must report no warning and no error on the file it renders, and its render, against the JPEG, must have a median CIEDE2000 of at most 1.5 **per file** (stricter than the median over the set). The 61 files of the default synthetic set: **all pass validation; the median of the per-file medians against the JPEG is 0.69, the worst file 1.04 (ISO 12800)**. Most of that is the JPEG and its dither, not the profile: against the 16-bit PNG of the same render the per-file medians are 0.075 (worst 0.095), and a profile without the look table is at 1.2 against the JPEG and 0.38 against the PNG, the identity profile at 11.5. **Real files** (`testdata/real/files`, local evaluation: nine Sony bodies from the A300 to the A7 IV, 10 to 31 MP, one portrait file, one cRAW, rendered in full): all nine pass validation with no warning; the per-file medians against the JPEG are 0.45 to 1.06 (median 0.73, worst the NEX-5N), against the 16-bit PNG 0.028 (ILCE-6300 cRAW), 0.036 (A300) and 0.048 (NEX-5N), with a 99th percentile of 0.59 for the ILCE-6300 (7.6 against its JPEG). The distance to the JPEG on real files is therefore mostly the JPEG's own coding and dither on noisy pixels; the profile costs about 0.04.

- **Display placement in `BaselineExposure` (decision of 2026-10-14).** The app's ACES 2 path brightens the scene by `2^k` (`k` = `DISPLAY_PLACEMENT_EV`, +0.85) before the transform (`docs/02` C12 step 1a); the fitted profile is of the plain transform, so the writer adds `k` to `BaselineExposure` (`log2(x_white) + fit_offset_ev + k`, 0.85 for a photo below the floor) instead of refitting. Adobe's renderer scales by `2^BaselineExposure` (clipped to 0..1) before the look table and the tone curve, which is the same operation, so the DNG opens as bright as the app. The profile, `dngfit` and the white floor are unchanged: the floor stays at scene 16, because the fit offset alone sets it and the placement only adds to a value that is never negative (lowering the floor to `2^-(fit_offset_ev + k)` = 8.9 would give 0.85 EV finer shadow codes and take away the stored headroom that a user who lowers the exposure in the other editor needs). **What changes for bright scene values:** the tone curve's input range ends where `x · 2^k / 16 = 1`, so Adobe's renderer clips at scene 16 / 2^0.85 = 8.9 (5.6 EV over mid grey) instead of 16 (6.5 EV), at the display value of the plain transform at 16 (Y 0.9435, code 0.975). The app keeps rising slowly above that (ACES 2 of 2^k · x), so Adobe's picture is flatter in the last stops: CIEDE2000 against the app 0.16 at scene 10, 0.38 at 12, 0.65 at 16, 0.92 at 24 and 1.14 at 40 (neutral greys, OpenColorIO; it was 0.88 at 40 before the placement). At the default exposure (+1.11 EV) the C7 shoulder tops a frame out near 1.5 times its clip level, about scene 3.3, so a photo reaches Adobe's clip point only after about +1.4 EV more exposure. Measured with `dng_validate` (the product DNG against the placed ACES 2 target, `tests/dng_validate.rs`): a photo below the floor (`BaselineExposure` 0.850) worst CIEDE2000 0.012 for greys and 0.55 for colours, a photo above it (x_white 40, `BaselineExposure` 2.172) 0.058 and 1.14.
