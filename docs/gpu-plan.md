# GPU plan (2026-10-13)

The plan of the GPU wave: every image stage after decoding moves onto the wgpu device (Metal on the Mac), in the app and in `ym`, exports included (the owner's direction of 2026-10-13, `docs/16`). It was written by merging two independent designs (performance-first and risk-first) after checking them against the code at commit 4968c11: the risk-first ladder and contracts are the spine; device residency, the export band pipeline, the persistent colour tables and what the targets need come from the performance-first design. Since 2026-10-14 Metal correctness is also checked in CI on GitHub's Apple-silicon runners (`.github/workflows/mac-gpu.yml`, section 7). The tasks are G-01 to G-10 (section 11); `docs/STATUS.md` records their state and the owner's answers to section 9.

Conventions. "(verified)" means the code or the crate source was read, or `ym doctor` was run on lavapipe. "(docs)" is a number recorded in the docs (4 shared x86 cores, mostly 24 MP). "(est.)" is an estimate from flops and bytes: it orders work and is never an acceptance criterion. M0-H4 is the Mac session (HUMAN).

## 1. Verification of the designs

### 1.1 Checked and true (every file path and "exists / missing" claim in both inventories was spot-checked; these are the load-bearing ones)

- Every GPU wrapper uploads a CPU slice and blocks on a readback per call: `kernels/adaptive_ratio.rs::run_rect` (`write_buffer` of the CPU `Mosaic`, `submit_with_readback`, `Readback::finish`), `kernels/color.rs::PreparedChain::{render, render_tiled}` (`upload_planar`, readback), `output_sharpen.rs`, `diffraction.rs`. Only `PreparedChain::dispatch` takes a device buffer.
- `ym-core/src/pipeline/frame.rs::{color_pass, display_linear_pass}` call `PreparedChain::new(ctx, &chain)` inside `gpu.run` on every frame (it re-bakes the four curve tables, rebuilds the table `Vec` with the ACES 2 tables and re-uploads the look cube, 4.4 MB for 65 points, 34 MB for 129), after cloning the sampled image into an `Arc`.
- `Renderer::render_full_with` ends in `job.finish(1, ComputeDevice::Cpu, ..)`: a host `Vec<f32>` of `fw * fh * 3` (600 MB at 50 MP), `sample_to_camera` and the CPU colour chain per tile.
- `ym` never gives its `Core` a GPU: `render.rs` only probes (`BackgroundProbe`, `probe_gpu` start `Gpu::start` and shut it down). The app opens it in `src-tauri/src/api.rs::start_gpu` (line 914), by default on macOS only (lines 61 to 72), skips a software adapter unless `YELLOWMOON_GPU=on`, and honours `=off`. There is no `--cpu` flag (`cli.rs` has `--require-gpu` only). `docs/10` line 139 says exports render on the CPU.
- `BufferPool::acquire` returns recycled buffers uncleared. `Readback::finish` waits with `timeout: None` and `wait_indefinitely`. There is no device-lost callback and no uncaptured-error handler in `ym-gpu`.
- `Scheduler::submit` (queue.rs:371) creates a fresh `CancelToken` for every job; `JobSpec` holds priority and owner only. `ym-core` never calls the GPU scheduler's `cancel_navigation` (the `scheduler()` calls in `app.rs`/`thumbs.rs` are its own `JobScheduler`). The worker loop skips a job whose token is already set (queue.rs:540), so a shared token works.
- `KernelId::ALL` has 33 entries: adaptive ratio 11, diffraction 9, output sharpening 8, spike 3, colour 1, log-guided 1. `tests/shaders_naga.rs` validates with `Capabilities::all()`; the `naga` dev-dependency has `msl-out` and `spv-out` only (no `hlsl-out`).
- `Cargo.lock`: one `wgpu` 30.0.1, one `naga` 30.0.1, `burn` 0.22.0, `burn-wgpu` 0.22.0, `burn-cubecl` 0.22.0, `cubecl` 0.11.0, `cubecl-wgpu` 0.11.0 (`ym-ml` builds burn with `["std", "wgpu"]` behind its off-by-default `burn` feature). `cubecl_wgpu::WgpuSetup { instance, adapter, device, queue, backend }`, `init_device`/`try_init_device(setup, RuntimeOptions)` exist ("each call allocates a new runtime identity"; they require at least two storage bindings and "do not validate every native requirement"); cubecl builds its feature table from `setup.adapter.features()` (runtime.rs:692); its own WGSL device request is `adapter.features()` minus `MAPPABLE_PRIMARY_BUFFERS`, the adapter's limits and the unsafe `ExperimentalFeatures::enabled()`; `burn-wgpu` re-exports `WgpuSetup`, `WgpuResource`, `init_device`; `burn-tensor` 0.22 has `Device::wgpu_options().setup(WgpuSetup)` (the route `ym-ml`'s own docs name).
- wgpu-hal 30.0.1 Metal (`device.rs:272`): `MTLCompileOptions` gets the language version and `setPreserveInvariance(true)` only, so fast-math stays at Apple's default. Metal reports `max_storage_buffer_binding_size = max_buffer_size`, `DeviceType::IntegratedGpu` exactly when `hasUnifiedMemory`, and the feature list contains `MAPPABLE_PRIMARY_BUFFERS`, `SHADER_F16`, `TIMESTAMP_QUERY` and `_INSIDE_PASSES`.
- `StoragePreference::Auto` picks `F16Native` whenever `SHADER_F16` exists (`ym doctor` on lavapipe: "GPU storage f16-native"), so today's colour pass rounds its input planes to f16 on lavapipe and on Metal. The four RA kernels are f32 in every mode.
- `ym-export`: `pixels.rs::{band_rows, encode_rows_u8, encode_rows_u16}` (C13 with dither at absolute coordinates, bands of about 1 M pixels), `encode_to_writer_with` = `resize_lanczos3` (f64 taps and accumulation) then `sharpen_output` (strips of 1024 rows plus the stage halo) then the writer; TIFF and PNG pull bands through `encode_rows_*`; the JPEG writer collects every 8-bit band into one `Vec` and then calls `Encoder::encode` once; DNG takes `ImageRef`s. `jpeg-encoder` 0.7.1 has `ImageBuffer::fill_buffers(&self, y, ..)` and `encode_image`.
- `MemoryBudget::detect` (scheduler.rs:81): CPU = min(6 GiB, RAM/2), GPU 4 GiB; `start_gpu()` does not pass `gpu_bytes` (it uses `GpuConfig::default()`), so the GPU budget is not scaled to RAM (STATUS known issue confirmed). `MOSAIC_CACHE_LEN` = 3. Defaults `tile_px` 512, `full_tile_px` 1024 (`RenderOptions`).
- `ViewSpec` is the only place with a `gpu_priority`. `Job` carries the render's `CancelToken` (`Job::check`).
- `native.rs` (Mac viewport) creates its own `Instance`, adapter and device.
- The R-stage CPU-second figures in the designs match `docs/05` (normalise 0.35, vignetting 1.3, gains 0.05, highlights 2.2, demosaic 9.2 LMMSE / 10.0 to 10.8 adaptive ratio, bilateral 19.4, guided 9.7, detail 0.9, RL 12.1, lens 9.9; R6 to R9 about 61 of about 71).

### 1.2 Corrected or qualified

- V-1 (risk design). "`FullChain::with_method` already computes `Prepared.offsets` on the CPU (f64, fixed band order)." Only the reduced path's `reconstruct_banded` is banded. `FullChain` goes through `Chain::prepare`: a whole-frame CPU `mosaic_of` (about 250 MB of temporary at 50 MP) and one `highlights::chroma_offsets` accumulate over the whole frame, only when `highlight_recovery && has_clipped`. The decision (keep it on the CPU for the full chain) stands, but the cost is real and is a Mac measurement.
- V-2 (perf design). "One uniform buffer is created per dispatch." It is `pool.acquire` (recycled) plus `write_buffer`, with one bind group per pass; there is no allocation per dispatch. The gain of a `UniformArena` / `BindGroupCache` is unmeasured; it moves to G-10 behind a measurement.
- V-3 (perf design). Overlap "wall time = max(GPU, encode)" holds for TIFF and PNG (band-wise writers). The JPEG writer needs the whole 8-bit image before `Encoder::encode`; in this wave a JPEG export is a GPU phase followed by an encode phase. A `jpeg-encoder` `ImageBuffer` adapter would allow overlap later.
- V-4 (both). Stage-wise parity needs a way to stop the CPU chain between stages. `Chain::run_tile` is one loop with local state; there is no `run_until`, and `demosaic_inputs` is private. G-03 adds a tile stepper to `cpu/chain.rs` (mechanical; the golden check proves it changes nothing).
- V-5 (both). "Unified-memory rule" numbers are untested; they are proposals (section 4.8).
- V-6 (perf design). The sampler's CPU reference `sample_to_camera` is `pub(crate)` in `ym-core`, and `ym-gpu` cannot depend on `ym-core`. The reference is ported into `ym-gpu/src/cpu/sampler.rs` (risk design's choice) and `ym-core` calls it after a bit-equality test.
- V-7 (perf design). The tile/slab sizes assume the 128 MiB default binding; this is true on the CI adapter (section 1.3, N-1) and was only estimated in both designs.

### 1.3 New findings neither design had

- N-1. `ym doctor` on lavapipe (verified): "buffer 2047 MiB, storage binding 128 MiB, 8 storage buffers, 256 invocations", although `GpuContext::open` asks for up to 2 GiB. So on the CI adapter no single binding exceeds 128 MiB. Consequences: (a) the adaptive ratio scratch is 12 planes x 4 B = 48 B per compute pixel with shadow matching, so a compute rectangle must stay at or below 2.5 Mpixel (120 MB); the risk design's 4 Mpixel constant would break it (192 MB); (b) the cut rule must use a constant, not the device limit, or the app and `ym` would cut differently; (c) a 61 MP raw plane (9504 x 6336 x 2 B = 114.9 MiB) fits one binding, a 61 MP cRAW `qstep` plane in f32 (230 MiB) does not; (d) the display-linear export frame (600 MB at 50 MP) is held in slabs of at most 128 MiB.
- N-2. After this wave only the encoder is left on the CPU. From `docs/` the 50 MP CPU export on the dev box is roughly: raw chain 18 s (71 CPU-s on four cores), colour pass 17 s (3 Mpixel/s), output sharpening 11 to 22 s (220 to 450 ms/MP), JPEG encode 12 s (5.9 s per 24 MP, extrapolated), TIFF 16-bit 21 s and PNG 16-bit 21 s (10 s and 9.9 s per 24 MP, extrapolated); sum for JPEG about 63 s. Colour plus sharpening is as large as the raw chain (about half of the CPU export together), so the view kernels are first-class for exports. When the rest is on the device the JPEG export time is the encode time; the 6 s target needs the encode to be under about 4 to 5 s on the M1, unknown. The 6 s target in `docs/05` is for "Full neural export, JPEG": TIFF and PNG 16-bit encode alone are about twice that on the dev box. G-08 profiles the split (C13 in f64 against DCT and Huffman, LZW, Deflate) before any export claim.
- N-3. On a Mac today the default Output sharpening (100 %) runs on the CPU after the GPU colour pass: 0.5 to 2.6 s per retina fit frame (STATUS known issue). The colour-only target depends on the sharpening kernel, not on the colour pass alone.
- N-4. `StoragePreference::Auto -> F32` also removes `enable f16;` from the prelude of every kernel, including the f32-only RA kernels (`shader_source` prepends it in `F16Native` mode), and halves the shader-variant matrix of `shaders_naga.rs`.
- N-5. `FullChain` builds the 200 MB expanded sigma map (`full_sigma_map`, `w * h * 4 B`) eagerly. On the GPU path it is wasted CPU memory; the device expands the half-resolution plane itself (`sigma(x, y) = plane[y/2][x/2] * gain(cell centre)`, exactly `full_sigma_map`'s rule).
- N-6. `RenderReport.device` is one `Cpu`/`Gpu` value. With stage ranges a render can be both; the report needs one value per range group.
- N-7. A queued GPU job's closure holds `Arc<FrameData>` (the mosaic). Navigation must resolve queued GPU jobs at once (`Scheduler::cancel_navigation`), not only set tokens, or neighbours' mosaics stay alive behind them (the same issue `submit_superseded` solved for the CPU queue).
- N-8. The reduced (fit) path normalises the whole mosaic twice on the CPU (`sigma_plane` and `reduced_bayer` each call `normalize`, 200 MB each at 50 MP). On the device both read the same `u16` upload.
- N-9. `hlsl-out` and the `Capabilities::empty()` baseline are cheap to add to `shaders_naga.rs` and are the only offline check for DX12 and for "needs an optional feature" mistakes.

### 1.4 Not verified (cannot be, here)
Every GPU time in both designs (estimates from flops and bytes at the M1 base figures); Metal's real limits beyond what wgpu-hal's source says; fast-math and FMA behaviour on Metal; MSL compile time of the large shaders; the memory behaviour of a 100 MB `queue.write_buffer` on Metal; whether cubecl accepts a shared device without the experimental opt-in (G-09 tests it); `jpeg-encoder`'s time split (G-08 measures it); and the limits of the CI runner's lavapipe (a different Mesa version may report another binding size: the plan designs for the lower figure measured here, 128 MiB, and the `max_binding_bytes` tests assert against that constant, not against the device).

## 4. Contracts (the spine)

### 4.1 Device policy, flags, one device
- `GpuPolicy { Auto, On, Off, Require }` and one `open_gpu(policy, budget) -> GpuSlot` in `ym-core` (`app/gpu.rs`). The app and `ym` both call it and nothing else creates a device (`start_gpu` and `probe_gpu` are removed). Adapter choice is the existing `pick_adapter` (high-performance first), shared, so a dual-GPU Mac picks the same adapter in both.
- Auto: hardware adapters only, never a software one (lavapipe, WARP); On: any adapter, all stages (CI, development); Off: never; Require: like On, strict (no silent fallback; `--require-gpu`: exit 4 when no device opens at start; a per-photo GPU error fails that photo with kind `gpu`). Env `YELLOWMOON_GPU=auto|on|off|require` (today's `1` kept as `on`); `ym render --cpu` (conflicts with `--require-gpu`: usage error, exit 2).
- `GpuStages`: a small bit set, one member per device range that can be switched independently (raw chain, sampler, colour C1 to C12, output sharpening, C13, export tail). `Auto` runs `SIGNED_OFF`; `On` and `Require` run all. Each wiring task keeps the host boundary that exists today for any member that is off. Proposed rule (owner to confirm, question 2): a member joins `SIGNED_OFF` when its parity, tile and determinism suites pass on the Metal CI runners (`mac-gpu.yml`); a physical-Mac session (M0-H4) can still remove one. Initially the colour pass only. **Confirmed and applied (owner, 2026-10-14):** after every suite passed on macOS 14 and 15 (run 38557455494, commit 6d277b8), `SIGNED_OFF` is the raw chain, the sampler, the colour chain, output sharpening and C13; the export tail joins after G-08.
- `ym` opens the device in the background at launch (while photos decode), runs `warm_up` as an Export-priority job and attaches it to `Core` (`Renderer::set_gpu`) before the export queue is built, so one export is wholly GPU or wholly CPU.
- Nothing about the device goes into a file or its XMP; `PIPELINE_VERSION` does not change; `ym render --json` gets additive `device` and `notes`.

### 4.2 Precision
f32 for every image plane that crosses a kernel boundary, in every storage mode (X-3). `StoragePreference::Auto` resolves to `F32`; `Force(F16Native | F16Packed)` stays for the legacy kernels and their tests. Raw words are `u16` pairs, look cubes and tables are f32 (already). `docs/01` "Storage format f16" is rewritten (STATUS question 2, option 1, pending Mykyta).

### 4.3 Types and the entry-point shape (in `ym-gpu`; it does not depend on `ym-core`)
```text
GpuImage  { buf: PooledBuffer, width, height, stride /* even */, planes /* 1, 3, 4 */, place: Placement }   // planar f32
DeviceRaw { words: PooledBuffer /* 2 x u16 per u32 */, qstep: Option<PooledBuffer>, width, height, cfa }   // named GpuRaw in this plan until G-07; the unused GpuRaw wrapper was removed in G-10
PassList  { encoder, kept-alive buffers, uniform slots, dispatch count }  -> submit() -> Pending
// each kernel module:
pub fn encode_<stage>(ctx, passes: &mut PassList, inputs: &GpuImage.., params) -> Result<GpuImage, GpuError>   // device in, device out
pub fn <stage>(ctx, host inputs..) -> Result<RgbImage, GpuError>      // thin host wrapper: upload, encode_, submit, read; what tests and phase-A wiring call
GpuChain<'a>  { chain: &'a Chain, prepared: &'a Prepared, sigma: SigmaHalf<'a>, range: StageRange }
  run_tile(ctx, &RawFrame, out: Rect, cancel) -> Result<RgbImage, GpuError>      // same contract as Chain::run_tile
  run_tile_device(runner, &Arc<DeviceRaw>, out: Rect, cancel) -> Result<GpuImage, GpuError> // G-10
GpuReduced::run(ctx, &DeviceRaw, &ReducedParams, cancel) -> Result<RowBands, GpuError>   // G-07; in bands of rows and a series of jobs since G-10
```
`SigmaHalf { width, height, data, gains }` and `ReducedParams` are plain data built by `ym-core` from `SigmaPlane`, `gain_plane` and the raw plan. `GpuChain` is built from the same `Chain` and `Prepared` the CPU uses, and walks `Chain::stages()` with `TilePlan` / `required_input_rect`, so settings, stage choice and halos are single-sourced; the noise model goes through `Chain::noise_dn()`. `StageRange { first, last }` is the test and gating lever: stages outside it run on the CPU stepper (V-4), the boundary is a host copy. Resident images are plain `Arc` values: `PooledBuffer` returns to the pool on drop, so `PhotoGraph`'s existing `ByteLru` caches can hold `Arc<GpuImage>` like they hold `Arc<RgbImage>`.

### 4.4 Tiles and halos
- Logical tiles are the CPU's constants: `tile_px` 512 for the 100 % view, `full_tile_px` 1024 for exports, the same `Job::region` rectangles. The device budget decides how many tiles are in flight, never their shape. An allocation failure is an error and a CPU fallback, never a smaller tile.
- `MAX_PHYS_AREA` = 2.5 Mpixel of compute rectangle (from N-1: 48 B/px scratch in a 128 MiB binding). A rectangle above it is split in halves recursively (a function of the rectangle alone, the same in the app and in `ym`), each half with its full halos. Everything except Richardson-Lucy beyond its 24 px halo cap is tile-exact, so the split changes pixels by at most the documented 2e-7.
- Halos are the measured ones of `docs/05`: from `Chain::stages()`; mosaic origins even; outputs in lens-crop coordinates; display-domain output sharpening uses `SharpenPlan::halo_px(scale)` (17 px at full size, at most 21).

### 4.5 Determinism rules
- D1 No float atomics anywhere; integer atomics only if ever needed.
- D2 No order-dependent reduction on the device except the R5 chroma-offset reduction of the reduced path: a per-workgroup binary tree in thread-index order, partials to a buffer, a second pass folding the partials in index order with compensated summation, counts in `u32`.
- D3 No subgroup operations.
- D4 No whole-row running sums (box filters, prefix sums): fixed-length direct sums (radius at most 8) or blocked sums with absolute block origins, so a pixel never depends on the tile origin. Positions, dither and noise use absolute frame coordinates; source positions are small displacements or a per-tile f64 rebase (integer origin plus an f32 2x2 over local coordinates), never absolute f32 coordinates of order 1e4. Test: the far corner of an 8658 x 5772 frame.
- D5 A pixel depends only on its receptive field: tiles equal the whole frame bit for bit on the GPU, for every new kernel and for the chain, at two tile sizes (RL beyond its cap is the stated exception).
- D6 Operation order as in the specs; `fma()` is not called (verified: no `fma(` in `shaders/`); NaN by bit test (`common.wgsl::is_nan_f`). Metal's fast-math default is an M0-H4 check (10 identical runs byte-equal, app = CLI, GPU vs CPU within tolerance); escape hatch for a kernel that cannot be made safe: an MSL passthrough with fast-math off (Mac-only, per kernel, documented).
- D7 A job's output never depends on what ran before it (poison test) or on how viewport and export jobs interleave (test: an export with viewport jobs injected between its tiles equals one without).
- D8 Same machine, adapter and driver: identical bytes between runs and between the app and `ym` (one `open_gpu`). Across machines or against the CPU path: within the stated tolerances only.

### 4.6 Kernel contract (checked offline in `shaders_naga.rs` and by a source lint)
K1 core WGSL only; no `enable` except `f16` in legacy modes; no subgroups, push constants, binding arrays, 64-bit integers, float atomics, texture sampling. K2 workgroups 16 x 16 or 256; workgroup memory at most 16 KiB. K3 at most 8 storage buffers plus 1 uniform per stage. K4 dispatch at most 65535 workgroups per dimension; `u32` indexing guarded (`plane_len * planes <= u32::MAX`); no binding above 128 MiB at the documented maximum rectangle (each kernel module exports `max_binding_bytes(rect)` and a test checks it at `MAX_PHYS_AREA`). K5 a job (one tile x stage group, or one sharpening strip) is at most about 30 ms on an M1 (est.), which respects the Windows TDR (2 s) and the Metal watchdog. K6 features required at device creation: none beyond compute; optional and used when present: `TIMESTAMP_QUERY` (+ `_INSIDE_PASSES`), `PIPELINE_CACHE`, legacy `SHADER_F16`. K7 constants written from `ym_color::consts` / CPU planners, never typed twice. K8 correct under fast-math and under strict IEEE. Metal compiles with fast-math and wgpu cannot switch it off, so a kernel whose result depends on a rounding (a decision that compares sums, a rank count, an error-free transformation) hides every operation that matters from the compiler with a barrier and computes divisions and square roots exactly (`ar_div`/`ar_sqrt`, `sharpen_div`/`sharpen_sqrt`, `lg_log2`/`lg_exp2` are the patterns). **The barrier is an OR, never an XOR:** `bitcast<f32>(bitcast<u32>(x) | zero)`, where `zero` is a uniform word that is `+0.0` bits at run time and that the compiler cannot know. An XOR applied twice cancels (`x ^ z ^ z == x`, folded by the compiler) and fast-math folds the `0 + x` that starts a running sum, so the first product of an unrolled sum loses its barrier and is fused into the next sum (the Metal model of the adaptive ratio with an XOR: 617,935 samples of 2,638 demosaic calls off the written order, 0 with an OR); an OR is idempotent. One operation per barrier: every product that meets a sum, every partial sum and every difference gets its own. A lib test (`every_fast_math_barrier_is_an_or_never_an_xor`, `kernels/adaptive_ratio.rs`) scans every kernel's source for the XOR form. The zero word must stay `+0.0` on the host (a `-0.0` would set every sign bit).

### 4.7 Cancellation, priority, job granularity
A GPU job is one tile x stage group (raw front, detail, lens + colour) or one sharpening strip. The render's own `CancelToken` is passed to the job (`submit_with_token`); the token is checked at job start, between stage groups and before readback; a submitted command buffer cannot be stopped, so cancel latency is one job. At most two jobs of an export are in flight, so a viewport job queued behind them waits for one or two tiles. Priorities as today (viewport frame: `Viewport`; 100 % tile prefetch: `TileNeural`; thumbnails, look tiles, histogram sample: `Thumbnail`; export: `Export`); `Job` gets a `gpu_priority` for raw tiles. `JobScheduler::wait_for_foreground` stays the export gate (X-15). `Renderer::navigate` also calls `gpu.scheduler().cancel_navigation(Some(left))` (N-7).

### 4.8 Memory
- The pool ledger is the authority (wgpu 30 has no portable "VRAM left"). On `DeviceType::IntegratedGpu` (Metal on Apple silicon): `gpu_budget = clamp(RAM / 4, 512 MiB, 4 GiB)`, the CPU budget is lowered by the same amount, and `cpu + gpu <= 0.6 x RAM` is asserted in a unit test. `open_gpu` passes `MemoryBudget::gpu_bytes` into `GpuConfig` (closes the known issue). Discrete GPUs keep separate budgets.
- Gate (lavapipe, `--release`, G-10): the 50 MP full chain peaks under 2 GiB by the pool ledger (the spike's gate was 1.5 GiB for 0.28 GiB used with f16, 0.56 with f32), and the ledger returns to its resident set after an export. Peak figures in the designs (about 1 GiB export, 1.5 GiB viewport) are estimates.
- `OutOfBudget` / `BufferTooLarge`: trim the pool, retry once, then the CPU for that photo.
- `FullChain` builds the expanded sigma map only when the CPU path runs (N-5).

### 4.9 Errors and fallback
Per photo, never per tile, and never a mix of GPU and CPU tiles in one export. `GpuError` classes: out of budget or too large: retry once, then CPU; shader: disable that kernel family for the process, CPU; device lost or tainted (uncaptured error, readback timeout of 30 s): rebuild the context at most twice, then the GPU is off for the process with one note; cancelled: propagate. A viewport frame or thumbnail falls back for that request with the existing note ("The graphics card could not render this frame, so the CPU did: ..."); a photo that fails mid-session renders on the CPU from then on (view caches may then hold GPU and CPU tiles of one photo, which differ within tolerance; viewing only). An export restarts the whole photo on the CPU, the report carries `device = cpu` and the note, the CLI warns and exits 0, unless `Require` (kind `gpu`, nothing written for that photo).

### 4.10 Export tail (G-08)
```text
for each tile row (1024 rows, one Export-priority job per tile x stage group):
    GpuChain tile -> camera RGB (device-resident since G-10: `run_tile_device`, `ExportTail::add_tile_device`) -> sampler -> C1..C12 f32 -> written at the tile's x offset into the slab of the row
slabs: at most 128 MiB each (1024 rows x 8658 px x 3 f32 = 106 MB)
no resize:  sharpen rows of slab r-1 (needs 17 to 21 rows from slab r) -> C13 -> u8/u16 bands
resize:     horizontal Lanczos-3 pass as a slab completes -> mid slab; after the last row a vertical pass -> the small final image -> sharpen strips -> C13 -> bands
bands (128 rows): readback ring -> bounded channel (depth 3) -> BandSource -> writer (TIFF, PNG pull; JPEG fills its 8-bit buffer, then encodes)
DNG: GPU colour stage per tile (Stop::DngLinearAwg4) read back into the host f32 frame as today; the p99.99 white and the writer stay on the CPU
```
Resize taps come from the CPU in f64 (difference form so a flat field is exact); dither at absolute coordinates; cancel and progress are polled per tile job and per band, the partial file is deleted as today.

### Metal after wave 2 (run of b6f2e4b; fixes of the "Metal fix" lane, GPU wave 3)

Six tests failed on both runners (macOS 14 and 15, same numbers): output sharpening 4 (the HDR vector 1.36e-5; the busy 130 x 97 frame with three stages, p99.9 1.5e-4; the flipped image, method 2 with halo, 8.6e-4; the 2048 px export of the 2048 x 1365 frame, 1.96e-3), log-guided 1 (stripes at a scale of 1e30, 1.06e-5 of the peak against 1e-5) and the device chain's strong-lens corner (921 samples over 1e-4 against 630, up to 2.07e-2). None was inherent to `f32`. The wave-2 Metal columns had been fitted to the first failing case only and hid the cause.

**Model of Apple's compiler.** naga's MSL of a kernel (the text wgpu hands to Metal, `per_entry_point_map` with the real buffer slots) is compiled as C++ with clang through a small Metal shim, unsuffixed literals as `float`, once strict (`-fno-fast-math -ffp-contract=off`) and once as Metal does (`-O2`/`-O3 -ffast-math -ffp-contract=fast -mfma`, `-mrecip=all` for an approximate division and square root). The dispatches a lavapipe run records (uniform blocks, groups, inputs) are replayed through it. Validation: the strict build gives lavapipe's bits; the fast build of the b6f2e4b kernels reproduces Metal's worst `edge_knight` and `ca_weighting` differences (6.595e-4, 1.078e-3) and the 2048 px export's 1.959e-3 to the digit. The scripts are scratch tooling, not in the repository.

**Causes and fixes** (all kernels: lavapipe numbers within the existing bounds; no CPU code changed):
- *Output sharpening.* Metal's `sqrt` left 27 to 37 % of the lumas 1 or 2 ulp off. One ulp at one of 5 pixels of the busy frame moves the output by 4.7e-4 to 2.1e-3 (a limiter rank count flips). Its division is a reciprocal product, and it fused the gain-map blur into multiply-adds (the 1.96e-3). Fix: the square roots are integer square roots, every quotient is the device's estimate corrected with the exact integer remainder (correctly rounded, 0 of 3.2e8 quotients differ from IEEE, also under `-mrecip`), and every product, partial sum and difference whose rounding matters is behind the barrier. Model: lavapipe's bits on all 67 cases of the four tests. The hardware columns (`HW_*`) are removed and the luma test asserts the CPU's bits on every adapter. A device test runs the two routines against IEEE.
- *Log-guided.* Metal's fast `log2` is up to 3 ulp off, and an ulp of L near 116 is a relative 5e-6 of the guide `2^L`. A C model with `log2` 2 ulp off gives 1.07e-5 at 1e30, like Metal. Fix: the shader's own `lg_log2` and a two-part `lg_exp2(Lc, acc)`, so that `Lc + acc` is never rounded to an ulp of 116, with every filter sum pinned. Lavapipe improved everywhere (stripes 1.1e-6 to 1.25e-7, hostile frames 1.3e-6 to 4.2e-7, vectors 3.1e-6 to 4.8e-7); the model gives at most 1.8e-7 at every scale.
- *Adaptive ratio (the chain).* Fused and re-associated decision sums and the approximate division move near-ties, and every later value depends on a decision. Pinning the sums alone is not enough: with the device's division the model still gives 3,606 chain samples over 1e-4. Fix: every product, sum and difference behind the barrier, every quotient and the CA square root exact as above. Model: lavapipe's bits on 18 vectors, 240 frames and the strong-lens corner's three demosaic calls (24.6 million samples); the Metal column of `gpu_adaptive_ratio.rs` is removed. Lavapipe itself had followed the written order only up to NIR's re-association (a few samples 1 to 3 ulp off in 10 of 258 cases); with the barriers it gives the strict bits. The strong-lens counts are unchanged (293, 740, 2.6e-3).
- *The barrier must be an OR.* `bitcast(bitcast(x) ^ zero)` applied twice cancels (x ^ z ^ z == x), and fast-math folds the `0 + x` that starts a running sum, so the first product of an unrolled sum lost its barrier and was fused into the next sum. The model caught it in step 2 of the adaptive ratio: 1 ulp in 6 % of the values. All six kernels with a barrier now use an OR (idempotent): the three of this lane, and `diffraction.wgsl`, `guided.wgsl` and `detail.wgsl` (switched in the review; lavapipe's printed numbers are identical before and after, and the MSL model of the detail and guided kernels gives lavapipe's bits with either form, and the diffraction kernel's the same output with either form). Review check of the finding (naga's MSL of the eleven passes, patched to the XOR form, compiled with clang `-O2`/`-O3 -ffast-math -ffp-contract=fast -mfma`): the adaptive ratio with an XOR differs from lavapipe in 1,316 of 2,638 demosaic calls (617,935 samples) and in all three calls of the strong-lens corner (510,242 samples); with the OR, in none. A four-term running sum behind barriers: the XOR form differs from the strict sum in 28,867 of 200,000 random cases and `opaque(opaque(x))` compiles to nothing; the OR form differs in 0 and compiles to one `or`. A lib test scans every kernel for the XOR form (K8).
- *Cost.* In the scalar model the adaptive ratio passes run 3.9 times as long (the barriers alone 1.15 times; the exact division is the rest), and lavapipe's tiled 2048 x 1365 sharpening 4.2 s instead of 3.3 s. GPU timing is an M0-H4 item.

**Switching fast-math off instead.** (a) `[patch.crates-io] wgpu-hal`: add `options.setFastMathEnabled(false)` (deprecated, available on every macOS), or `setMathMode(MTLMathMode::Safe)` with `setMathFloatingPointFunctions(Precise)` on macOS 15, after `setLanguageVersion` in `wgpu-hal-30.0.1/src/metal/device.rs` line 273 (the options are made on line 272; `objc2-metal` 0.3.2 has all three setters). It stops re-association and the reciprocal division for every kernel. Whether it stops contraction (`fp contract`) is not documented for the default, and the precise `log2` is still not correctly rounded, so the pinned kernels stay. It is a fork to rebase on every wgpu update, a root `Cargo.toml` change, and it makes the colour kernels' transcendentals slower. (b) MSL passthrough (`Features::PASSTHROUGH_SHADERS`, `unsafe Device::create_shader_module_passthrough`, `msl` field): wgpu-hal compiles it with default options (line 1303, fast-math on), so the source must carry `#pragma METAL fp math_mode(safe)` / `fp contract(off)` (MSL 3.2, macOS 15; the macOS 14 runners have no equivalent). The `[[buffer(n)]]` slots must reproduce wgpu-hal's per-stage counters and no sizes buffer is sent. Pipelines need explicit layouts (no reflection) and workgroup sizes per entry point, and the crate gets a runtime naga for `msl-out` and a second `unsafe`. (c) Upstream: wgpu trunk of 2026-10-14 (60036cdc0) still sets only the language version and invariance (`wgpu-hal/src/metal/device.rs` lines 271 to 276; passthrough MSL with default options at line 1397), its changelog mentions no math mode or compile options, and none of the 11,472 commit messages of trunk mentions fast math, a math mode or `MTLMathMode` (the only commit on the options is `99b3a6ebf`, 2022, `preserveInvariance`); open issues and pull requests could not be searched from either session (the GitHub search and GraphQL APIs are blocked, the repository is not attached). Apple's header for `MTLCompileOptions` (objc2-metal 0.3.2) says `fastMathEnabled` defaults to YES and is deprecated for `mathMode`, whose default "depends on the language standard version"; the identical failure numbers on macOS 14 (MSL 3.1) and 15 (MSL 3.2) are consistent with both defaults contracting and re-associating (not verified: no Mac here). Recommendation: keep the pinned kernels (they work under fast-math and under IEEE, on every backend); propose upstream an opt-in `MTLMathMode` field (for example on `ShaderRuntimeChecks` or the Metal backend options), and revisit (a) only if the Mac measurements show the exact divisions cost real time.
