# 16 · Risks and design choices

This file lists the open risks of the project with their mitigations, then the standing design choices with the reason for each, grouped by area. A choice is written as the current fact; the algorithm, the constants and the measurements are in the spec named at the end of each entry.

## Risks

### Colour accuracy

| Risk | Effect | Mitigation |
|---|---|---|
| ALEXA curve estimate is off by more than 5% | emulated colour drifts, mostly in saturated reds and greens | ensemble spread published; validate against the HdM and CIC 2015 curves if obtainable; swap in measured data if released |
| Far-red tail above 660 nm is unconstrained | skin and red fabrics under tungsten may render wrong | ensemble variants for the tail; targeted review of skin under tungsten (M1-H5) |
| Estimate pulled toward the stills-camera prior | real Sony-to-ALEXA differences understated | prior variants without Sony bodies (already within 2.6% RFSE); compare with ARRI-rendered sample footage offline |
| Light class is hard to estimate from RGB alone | wrong map under LEDs and fluorescents | blend maps by class probability; light presets in the Colour tab; as-shot white balance prior |
| Kelvin readout differs between measured and stand-in bodies | the A1 reads a daylight photo near 5200 K, a measured body near 4650 K, because Sony's Kelvin presets sit about 30 mired warmer than the published curves place them | the white scale moves the light class, the mired of the sensor map and the ARRI matrix, not the neutral, which Auto balances exactly (0.22 to 0.31 median ΔE00 on three A1 photos); `docs/03` |
| No controlled captures in V1 | illuminant, noise and lens accuracy on the A1 is validated only indirectly (synthetic scenes, other cameras, oracles) | public-data gates per `docs/13`; noise biased toward over-estimating; captures in V2 tighten the A1 numbers |
| Few openly licensed A1 photos | the golden set is thin on scene and light variety | three licence tiers (`docs/test-photo-sources.md`); A1 II and A7R IV-family files as stand-ins; the maintainer's own photos |
| Other apps render our DNGs differently | the look's tone differs outside Lightroom | look baked into pixels; full-size preview; per-app behaviour documented (`docs/09`) |
| CIE-derived tables | fitted sensor-map and white coefficients derive from CIE data (CC BY-SA 4.0) and might count as derived data | only fitted coefficients ship, never the SPDs; [HUMAN M1-H4] confirms, or fitting restricts to blackbody and daylight formulas plus our own SPDs (`docs/14`) |

### Platform and GPU

| Risk | Effect | Mitigation |
|---|---|---|
| Metal surface under a transparent Tauri webview | flicker, input routing or resize glitches | the native viewport has a checklist on a Mac (`docs/11`); a fallback of PNG frames with a Display P3 profile over `ym-frame://` exists for other systems and for a native view that fails |
| wgpu's Apple wide-gamut support depends on upstream fixes | colour shifts in Display P3 output | pin the wgpu version; compare P3 output against exported files |
| GPU limits on 50 MP frames | crashes or slow previews on smaller GPUs | tiled device pipeline (f32 planes, 512 px view tiles, 1024 px export tiles, rectangles above 2.5 Mpixel split by a rule that does not depend on the device); CPU fallback; memory budget from device limits |
| burn API churn | rework on upgrades | ONNX models as the stable artefact; ort as fallback runtime |
| No physical GPU on CI runners | speed and Metal behaviour on real hardware are not covered in CI | lavapipe job for correctness; Metal correctness on GitHub's Apple-silicon runners (`mac-gpu.yml`, macOS 14 and 15); timings on a Mac before each gate (M0-H4) |
| Device and CPU renders differ within tolerance | the adaptive ratio demosaic is not bit-identical on the device (a direction test that ties in f64 can flip in f32: worst 1.55e-2 of white on real mosaics); method A's thresholds and the output-sharpening halo limiter flip at a few samples (median about 1e-4 ΔE00 and worst 0.03 on a real photo, up to 1.9 on synthetic chart edges) | exports stay byte-identical between the app and `ym` on one machine; golden hashes pin the CPU reference; GPU renders are checked against it within the golden gates (median 2.2e-4, p99 6.9e-2, worst 6.5, share over 8 codes 4.3e-2); kernel parity is judged against an f32 emulation of the oracle (`docs/17-gpu.md`) |
| Apple Auto answers vary between Macs and macOS updates | the same photo can get other automatic values on another Mac | the answer is a step from fixed lists mapped by a fixed table; `ym` and the export metadata record which model chose the values; with Default Auto chosen the rule is used (`docs/19`) |
| Claude Code and Antigravity answers differ from run to run, and the programs send a picture to a cloud service | no temperature or seed exists; the photo's picture goes to Anthropic or Google through the person's own program, with a consent first | the answer is bounded by the same fixed form and table; every export records the provider, the program's version and the model and says `reproducible: false`; the pinned `ym:Settings` reproduce the picture; Yellowmoon opens no connection itself (`docs/22`) |

### Data and decoding

| Risk | Effect | Mitigation |
|---|---|---|
| ARRI changes download URLs or objects to automated access | the import wizard breaks | import from file is the primary path; the wizard opens ARRI's page rather than deep links |
| Some Sony variants decode wrongly (older bodies, cRAW quirks, M/S) | wrong colour or artefacts | every corpus file checked against LibRaw in CI; clear message for anything unverified |
| ARW 6.0 codec: undocumented, hard-coded constants, possible Sony patents | A7 V and A7R VI compressed files do not open, or decode wrongly | ship last behind a feature flag; check against LibRaw master and lightcraft; ask Sony; clear message meanwhile |
| Lossless M/S files are not Bayer | emulation is approximate | reduced path, flagged in the app |
| Noise estimate off on textured or filtered files | over- or under-smoothing | texture fallback, filtered-file check, bias toward over-estimating, σ jitter in training |
| Training compute unavailable | the learned demosaic and denoise network slips | small models (hours on one GPU); Apple MPS fallback; the classical path ships regardless |

### Legal and release

| Risk | Effect | Mitigation |
|---|---|---|
| Updater signing key lost or leaked | installed copies cannot update, or a third party could ship updates | key generated once, kept outside the repository, backed up in the maintainer's password manager; never logged |
| No Apple Developer ID | macOS asks the user to allow the app on first launch | ad hoc signature; the README and the cask caveat say how to allow it; revisited before 1.0 (`docs/12` Signing) |
| Yellow Moon Post Production (Northern Ireland) works in a neighbouring field | naming dispute in the UK | trademark clearance search (EUIPO/TMview, INPI, WIPO, UK IPO; classes 9 and 42) or an attorney before announcing |
| Patent US 11948279 | claim against the joint demosaic+denoise network | freedom-to-operate check before 1.0; the classical path is the fallback |
| Patent leads for the raw algorithms (`research/raw-algorithms-prior-art.md` §2.2: Kodak, Epson, Sony, Apple and IBM families; diffraction restoration filters) | the adaptive ratio demosaic is the default and the diffraction and sharpening stages ship | freedom-to-operate check before 1.0 (M4-H4); the survey records where each piece comes from; Menon stays selectable |
| Creative Commons' conservative reading asks that models based on ShareAlike content share its licence | weights trained on CC BY-SA data could be claimed to carry that licence | such weights are themselves CC BY-SA 4.0, in separate data files (`docs/14` rule 5) |

## Design choices

### Product and scope

- **Free and open source under Apache-2.0.** Everything shipped is compatible with that licence, so the app has no non-open dependency. ARRI's Look Library and display LUTs stay on the user's machine and are imported at runtime. `docs/14`.
- **Camera colour comes from published measurements only (V1).** Weta's curves for 11 Sony bodies (rawtoaces-data, Apache-2.0); every other body uses a same-sensor sibling's profile or the A7R IV profile. Our own measurements are V2 work, so V1 needs no test shoot. `docs/03`, `docs/validation-data.md`.
- **The default render has to give ARRI-like colour without adjustment.** The app is meant to beat a camera raw processor plus a static ARRI-like LUT; a local-only comparison against commercial LUT pipelines (never committed) shows where per-photo stages help. `docs/00-overview.md`, `research/dynamic-vs-lut-2026-10-14.md`.
- **The command-line tool is called `ym`.** The binary, the Homebrew cask link, "Install Command-Line Tool…", the help text and the `ym doctor` request in the issue template use it; the crate stays `ym-cli`. Inside the bundle the sidecar is `Contents/MacOS/ym`, which does not collide with the `Yellowmoon` main binary on case-insensitive file systems.
- **The repository is `github.com/ngriaznov/yellowmoon`**, on the maintainer's personal account like plugout.

### Platform, signing and release

- **The oldest supported system is macOS 14 Sonoma.** The dark glass interface's CSS needs WebKit 16.4, which macOS 14 ships (Safari 17) and 12 and 13 have only after a Safari update. `minimumSystemVersion` is 14.0, the cask says `>= :sonoma`, the build target is Safari 17, and there are no CSS fallbacks for older Safari.
- **There is no Apple Developer ID.** The bundle is signed ad hoc and the README says how to allow the app once, as for plugout. `docs/12` Signing, `docs/release-signing.md`.
- **Downloads are GitHub Releases.** Every build that goes out for testing is the next 0.1.x version: `tools/release/bump-version.sh patch`, a CHANGELOG section, a push to `main`. `release.yml` publishes the universal disk image with the CHANGELOG section as notes and every asset the in-app updater needs (`.app.tar.gz`, `.sig`, `latest.json`). It refuses to release without the updater signing key, so no version ships that could not update itself. `build.yml` makes test builds by hand.
- **The maintainer generates the updater signing key.** The build environment is ephemeral and cannot set repository secrets. The private key and its password live in GitHub secrets and in one local backup file outside the repository, never in the repository, logs or issues. The commands are in `docs/release-signing.md`.

### Interface

- **The shell is Tauri with a React webview; the interface is dark glass built on glasscn.** glasscn's components (MIT, a shadcn registry; `src/components/glass/`) on Tailwind 4 and Radix, in the layout of `design/mockups/`, every control a glasscn component, visual reference `design/screenshots-c2/`. The mockups draw the pre-glass look; `docs/11-ui.md` wins where they differ.
- **GUI toolkits have to be Apache-2.0 compatible.** Slint is not used: its free licence for an app (Royalty-free 2.0) is not an open-source licence (attribution required, no embedded use), and GPLv3 and the paid licence are excluded for the same reason. A toolkit trial uses a licence-clean candidate such as egui (MIT or Apache-2.0). An sRGB-only photo view is acceptable if a toolkit cannot show Display P3, because the default export is sRGB.
- **The ground is neutral graphite.** A still aurora of three grey blobs on a near-black paper (`#0f0f10`, also the window's background and the letterbox of the core's frames), with every hue taken out of the ground, the frost, the fills and the labels. Yellow (`#FFC20E`) is only a button and tab accent. Colour is a small accent, never a large tinted area, which is why glasscn's Midnight palette (its warm aurora tints the tool panel maroon) is not used. `docs/11` Style.
- **The Before view shows the camera's default rendering.** It is the picture as a Sony camera would produce it, so the user sees what Yellowmoon changes: the raw stages, the camera's as-shot white balance, the body's published D65 colour matrix, `CAMERA_GAIN_EV` and a per-channel tone curve fitted to embedded JPEGs, then the output primaries. No sensor map, look, grade, curve, display transform, white lift or output sharpening acts, no lens vignetting correction (R3) runs, and the Detail controls are read at Auto, so no setting reaches it. The label is "Before · camera default". The A1 II uses the A1's matrix and the A3000 the generic E-mount matrix (`data/cameras/color-matrices.json`). `docs/02` The Before view.
- **Add photos, Copy settings and Paste are in the editing page.** Copy takes every setting except the crop, the orientation and the Pick white point; a white balance that came from a picked white is pasted as the manual Kelvin and tint it resolved to. The copy is kept in the webview store for the running app, never on disk or on the system clipboard (nothing is saved per photo). Paste applies to the current photo, "Paste Settings to Picked" to every picked one, one undo step per photo. One core command, `paste_settings(photo_ids, patch)`, holds the rules (`SettingsPatch::copied_from`). The CLI has no copy command; `--settings` files do the job. `docs/01`, `docs/11`.
- **Removing a photo takes it out of the session, never off the disk.** The filmstrip entry, picks, caches and edits go; the file is never touched. A right-click menu (Remove from filmstrip, Remove picked photos) and Delete or Backspace for the photo on screen start it; there is no multi-selection, so a forgotten pick never turns a key press into a bulk removal. Exports in progress keep the photos they were started with. Undo is the last removal only, kept in memory until the next removal or the end of the session, as a button in the notice and as ⌘Z. Work for the removed photo stops at once. `ym` has no removal. `docs/01` Removing photos, `docs/11`.
- **F shows the photo alone.** Header, filmstrip, tool panel and camera line are hidden and the window goes into macOS full screen unless it already was; F again or Esc leaves. There is no menu item for F, because a plain-letter key equivalent would take F from every text box. `docs/11` Full screen.
- **The Look card's "Apply to" starts on This photo.** A look picked on one photo is not copied to the others unless the person chooses Picked or All; the choice is not remembered between runs.
- **The Look tab has a Tone card** with Temperature, Contrast and Saturation, the same settings as Colour › White balance › Kelvin, Light › Contrast and Colour › Saturation. Moving Temperature makes the white balance manual and Reset returns it to Auto; Tint stays on the Colour tab.
- **Colour warp is a Chroma Warp with pins** (stage C9b), a card on the Colour tab with Pick colour on the photo and a scatter of the photo's colours on the plane. Range is the range: a pin's Range is kept as set and the pixel moves along a flow in steps, so a small Range moves only nearby colours. A new pin's Range is 2 (`WARP_RANGE_DEFAULT` 0.02). `docs/02` C9b, `docs/11`.

### Colour and rendering

- **The default look is Signature.** A LogC4 luma curve pivoting at mid grey (the departure from the identity scaled by 1.6, slope at mid grey about 1.40, with a soft toe and shoulder) followed by CDL saturation 1.45; mid grey is unchanged. Parametric looks are baked into 65-point cubes because the steeper curve needs a finer cube. Neutral stays as the identity. The default look comes from the preferences (`DEFAULT_LOOK` is `builtin:signature`); `DevelopSettings::default()` stays Neutral. It is a built-in look made for the app, not derived from any ARRI or commercial LUT. `docs/08`.
- **The display transform is ACES 2, placed 0.85 EV brighter.** `DISPLAY_PLACEMENT_EV` multiplies the scene by 2^0.85 after the look and the curve, before ACES 2. ACES 2 SDR is a cinema rendering that puts scene 0.18 at display 0.10, 0.85 EV under a camera JPEG, and Yellowmoon is a photo processor. Imported ARRI display LUTs and the LogC3-to-Rec.709 looks keep ARRI's brightness. The DNG carries the placement in `BaselineExposure`. `docs/02` C12.
- **Auto exposure uses the camera's exposure.** `CAMERA_GAIN_EV` is +1.11 EV before the highlight guard (level 8.0, an ALEXA at EI 180), exposure compensation in full. The M1-08 gate compares our `EV_auto` with the camera engine's own gain (metric G3: `log2(0.18/x)`, `x` the scene-linear level the embedded JPEG renders as mid grey), so the display transform and the camera's tone curve do not enter; a file passes within ±0.5 EV and the gate is met at 80% of files. `docs/02` Auto exposure.
- **The highlight range control reaches ARRI's clip.** `rolloff.highlights` (0 to 1, default 1) remaps the Sony's highlights toward an ALEXA at EI 800, which clips 7.638 stops over grey by ARRI's formula; the knee sits one stop under the Sony clip and never under +1 stop. At 1 the clip is at white. C7 sits before LogC4, so imported display LUTs and LogC3-to-Rec.709 looks receive the remapped range. `docs/02` C7.
- **The white lift stays beside the range.** The range moves only highlights within about a stop of the camera's clip, so a photo whose brightest areas sit well under the clip would lose its top tones. The lift (C12 step 1b) raises the tones above +1 stop over grey by an amount sized from the photo's highlights, on the ACES 2 path only, driven by Rec.709 luma, with a −3 … +3 stop offset (`white_offset_ev` −3 switches it off). Its estimator meters the preview after C7 at its defaults, so a photo whose highlights the range already took to white gets less lift. `docs/02` C12.
- **Stand-in bodies get a white scale.** A body that renders through another body's profile has raw whites on another scale (the A1 reads daylight as about 4430 K on the A7R IV profile). The per-body `white_scale` is fitted from the white-balance presets the camera writes into its own files, only a white is scaled and no 3×3 corrects the colour response. `docs/03`.
- **Contrast is a tone curve on the luma; saturation keeps the luminance.** Contrast adds one offset `T(L) − L` to all three channels, so black, grey and the top code value stay and channel ratios hold on the log segment, then restores part of the colour a curve on each channel would give (`CONTRAST_COLOR` 0.5). Saturation scales the chroma about the pixel's luminance in linear AWG4 (`SATURATION_BOOST` 1.5), so more saturation does not darken colours and never takes a channel below 0. Contrast 0 and Saturation 0 are bit-exact identities. `docs/02` C9.
- **The illuminant estimator is FFCC-style, one model per profile.** A log-chroma filter with an edge channel, a class head, a learned confidence and the as-shot prior, 13 k parameters, median angular error 1.22–1.30° on held-out synthetic scenes for all 11 profiles (gate 2°). It beats grey world (with the prior), grey edge, shades of grey, white patch and the as-shot value alone; C5 and DMCC need a multi-camera real dataset that V1 cannot get. `docs/07`, `data/models/illum/MODEL_CARD.md`.
- **The sensor map is a table blend of Lab-optimal, white-preserving 3×3 matrices per reference light.** The Lab objective passes 8 of 9 held-out lights for the A7R IV (LED-V2 stays a reported failure: 0.759 median, 1.515 p95); a tiny MLP is not used, because free and root-polynomial maps reach only LED-V2 ≈ 0.51. `docs/02` C2.
- **Locus and Duv tables use the published raw-scale curves; the sensor maps and ALEXA white tables use per-channel peak-normalised curves** (scale-invariant there), because the scene white at run time is raw data. `docs/03`.
- **Tint is our green-gain mapping (±0.5 stop at ±50)**, because ARRI's tint mapping is unpublished. `docs/02` C3–C4.
- **The tone curve (C11) acts in LogC4 after the look (C10).** It travels into the DNG export and behaves the same under every display transform. `docs/02` C11.

### Raw processing

- **The classical default demosaic is the adaptive ratio demosaic** (`Method::AdaptiveRatio`). In linear light over nine cells (Kodak, McMaster, the synthetic set; signal scales 1, 0.1, 0.01) it averages 36.05 dB against Menon's 34.43 and LMMSE's 34.28; zipper falls from 39% to 20% of edge pixels on the synthetic set. With the noise model scaled along with the signal the nine-cell mean is 35.45 dB (+1.02 over Menon) and on the six photographic cells it is level with Menon and LMMSE, so the procedural set carries the aggregate. The stage costs 1.5–1.7× Menon on the CPU. `docs/05` R6.
- **The R6 method is not a user setting.** `RenderOptions::demosaic` is a test-only switch (the cargo feature `force-demosaic` reads `YM_FORCE_DEMOSAIC`, and only test builds of `ym` have it). Menon, LMMSE, bilinear and log-guided stay selectable through it; the log-guided demosaic passes its gate and no render uses it.
- **A missing or invalid noise model is read as zero noise.** A model that is missing, fails `NoiseDn::is_valid` or has non-finite black-level offsets gives K = T = 1 DN for the whole raw group with one warning, so a photo never fails to render because of it. Gains that are not positive and finite still refuse the render. `docs/algorithms/INTEGRATION.md` §10.
- **A coarse colour pass follows method A** (pipeline 0.5.2, after the owner's report of colour blobs on uniform colours in 0.1.12). Method A's 8 × 8 blocks and 8 px search cannot see colour noise that varies over 16 to 64 px; a bilateral filter of the colour of 4 × 4 cells within the photo's chroma noise (`k = 0.2`, radius 8 cells, 37 px halo) takes those blotches to about a quarter on a real ISO 3200 photo at no measurable PSNR cost on the synthetic sets, and leaves the luma alone. A learned denoiser would see the whole range of scales; it waits for trained weights (M2-06). `docs/algorithms/05-single-frame-denoise.md` *Coarse colour*.
- **R8 capture sharpening is Richardson–Lucy.** Diffraction deconvolution (`CaptureSharpen::Diffraction`, `docs/algorithms/03`) is implemented and tested, has no setting, UI control or flag (the internal `PhotoSource::capture_method`), and Amount and Radius do not act on it. `docs/05` R8.
- **Output sharpening is a per-photo setting.** `DevelopSettings.output_sharpening`, 0–200%, default 100%, the Output row of Detail › Sharpening. The preset is the screen preset of `docs/algorithms/04` (radius 1 px, threshold 1 level, halo suppression 60%, smooth gain). It runs on every display-referred render at its own size (viewport, 100% tiles, thumbnails, look tiles, raster exports after the resize), never on DNG. The halo limiter is continuous (`halo_tie_tolerance`, a window sample within 2^-12 of the centre counts on both sides), so exact comparisons that tie on clipped or flat values do not flip between the device and the CPU. `docs/09`, `docs/algorithms/04` §3.5.
- **Lateral CA is corrected on the mosaic (R5b), before the demosaic, at full resolution.** A green-guided demosaic keeps only about half of the CA, so correcting in R9 after it applies the full table to a half-corrected image and over-corrects (red/blue shift 0.3–0.7 px instead of 0.04–0.2 px). The binned fit view and the thumbnails keep it in R9. R5b on five real files leaves a root-mean-square red/blue shift of 0.03–0.28 px. `docs/05` R5b and R9.
- **Lens corrections follow darktable's embedded-metadata conventions**, verified with darktable-cli as a separate-process oracle (distortion and CA within 0.009 px, gain within 0.008%; gates 0.2 px and 0.5%). `docs/05` R3 and R9.
- **The raw-algorithms package is implemented in Rust from its specs.** The four specs (`docs/algorithms/`) are algorithm descriptions: known techniques plus our own combinations and constants, with the prior-art record in `research/raw-algorithms-prior-art.md`. No C++ enters the repository; the generated vectors are the fixed test oracle. A provenance check found no GPL, LGPL or AGPL code or tables. `docs/14`.

### Automatic settings

- **Automatic settings are rule-based.** Exposure follows the camera's exposure with the highlight guard, the white is the estimated white, and contrast and saturation are 0. Learned automatic settings are not used, because a learned approach did not beat the camera JPEG in a blind A/B (preferred in 58.0% of trials, Wilson lower bound 51.4%). The research is in `research/ml-auto-settings-2026-10-18.md` and `research/scene-understanding-2026-10-19.md`.
- **Apple Auto grades the photo where Apple Intelligence's on-device model can look at it** (macOS 27 or later, Apple silicon, Apple Intelligence on, its model downloaded). It sets exposure, a warmer or cooler nudge of the estimated white, tint, contrast, saturation, highlights, shadows, black and the two colour wheels. It is one entry of the **Auto grading** dropdown in Preferences (`auto_provider`), the default where the model is available and shown only where something can grade; with Default Auto chosen, or anywhere Apple's model is not available (other Macs, the Linux CLI, golden tests), Auto is the rule. `docs/19`, `docs/22`.
- **Claude Code and Antigravity can grade too** (the owner, 2026-10-26: "Additionally to Apple Intelligence I want to support Google AGY CLI and Claude Code"). They are the person's own programs, started by Yellowmoon; they make their own network connections, Yellowmoon makes none (the owner: "Ym won't access network, we will invoke agy and Claude - they will access network"). A cloud provider is never chosen by default and is asked for consent the first time; Antigravity is marked Experimental (`docs/22`).
- **Apple's models are used at runtime only.** Their answers never train, label or tune anything of ours (Apple's developer agreements forbid training on their output). The model answers in steps from fixed lists; a table chosen by eye (`ym_core::apple_auto::TABLE`) maps them to values and is never fitted to Apple's answers. macOS downloads the model itself when the person turns Apple Intelligence on; Yellowmoon adds no network access.
- **The person can edit the instructions.** The `apple_auto_instructions` preference (empty means `ym_core::apple_auto::DEFAULT_INSTRUCTIONS`, at most 2000 characters) is set in Preferences under the Auto grading dropdown with a "Reset to default" button, and for one run with `ym --auto-instructions FILE` (`--apple-auto-instructions` is the old name); one text for every provider. The request and the answer's form stay fixed. The default text asks for the best finished photograph the scene allows and for no style; it names ARRI as the colour reference, never as the product's name, which hard rule 3 allows. Every report that names the model says `default` or `edited` with the first 12 hex digits of the instructions' SHA-256.
- **A value the model leaves empty sets nothing.** When generation stops part way, the values filled so far are used and the control keeps Default Auto's value; an answer with no value is a failure. A request that runs out of time (30 s) is a timeout even if some values were filled, because where it stopped depends on the time and the same photo must give the same answer.
- **The Start screen counts Apple Auto's wait, but "Open photos →" does not wait for it.** The core reports `PhotoSummary.apple_pending`; the model answers one photo at a time (about 1–4 s each), so waiting for a large folder would keep the person out for minutes. The photo on screen is asked first. `docs/11` Start, `docs/19` section 6.

### GPU path

- **Every image stage after decoding runs on the wgpu device, Metal on the Mac, in the app and in `ym` alike, exports included.** The kernels are WGSL, translated by naga, and nothing Mac-only goes into them; the native viewport is the Mac-specific part. The CPU reference stays for tests, parity and machines without a usable GPU. `docs/17-gpu.md`.
- **One device policy for the app and `ym`.** `Auto` (hardware adapters only), `On`, `Off`, `Require`; `ym render --cpu`; the environment variable `YELLOWMOON_GPU`. `Auto` on a hardware adapter runs every stage (`GpuStages::SIGNED_OFF`), because every suite passes on Metal CI; a stage that proves slower on a physical Mac than on the CPU goes back to the CPU.
- **Image planes are f32 on the device, and logical tiles are the CPU's constants** (512 px for the view, 1024 px for exports). A compute rectangle above 2.5 Mpixel is split by a rule that depends on the rectangle only, never on the device, so the app and `ym` cut every frame the same way on every machine.
- **Golden hashes pin the CPU reference.** GPU renders are compared with those pictures within tolerance in a strict job, and `PIPELINE_VERSION` does not change with the device. Exports are byte-identical between the app and `ym` on one machine and between runs; across machines, or against the CPU fallback, they may differ within the stated parity tolerances. The device is recorded in no file. A JPEG export on the device is judged on the 8-bit codes in front of the DCT (`docs/09`).
- **A GPU error re-renders the whole photo on the CPU with a note**, never one tile; `--require-gpu` fails the photo instead. A viewport tile or thumbnail falls back for that request.
- **The GPU golden gates are twice the worst of the 61 synthetic files on lavapipe** (pipeline 0.5.0): median 2.2e-4, p99 6.9e-2, worst 6.5, share over 8 codes 4.3e-2. Method A's threshold decisions go the other way where they lie within rounding of f32 against f64, identically on lavapipe and Metal; on a real photo the device stays far inside (median 1e-4, worst 0.044). `docs/17-gpu.md` §12.
- **The Metal bound on JPEG samples more than one code off is 8.8e-4** (the owner, 2026-10-21; it was 4.25e-4). Pipeline 0.5.1's picture put the 331 px JPEG of `gpu_export.rs` at 4.37e-4 on Metal, while the 8-bit PNG of the same codes stayed within one code; the bound is twice the new worst. `docs/13-testing.md`.
- **Not on the device:** decoding and metadata, the small automatic estimates on the 1/8 preview, the test-only demosaic methods (Menon, LMMSE, bilinear, log-guided), camera-processed files, the histogram counts, the DNG white and writer, and the encoders. With every other stage on the device, the encoder is the CPU's share of an export (JPEG about 12 s per 50 MP on a development machine, TIFF and PNG 16-bit about 21 s, extrapolated).
- **The ML runtime is a seam, not an adoption.** `ym-gpu` keeps its `Instance` and `Adapter`, has a burn-compatible feature recipe and one lavapipe test; a runtime that runs on the same wgpu device (burn's wgpu backend) is preferred to a Mac-only one, subject to the benchmark in `docs/07`.
- **The native viewport draws with the core's own device.** The surface is made from the device's instance and the view job keeps its RGBA8 frame on the device (`FrameOutput::Device`), so a viewport frame is not read back and uploaded again; magnified views above 100% are device frames too. A core without a device keeps host frames. `docs/01` Native viewport.

### Licensing and data

- **Numeric facts may come from any source.** Colour matrices, white-balance coefficients and similar camera constants may be taken as numbers from any source, keeping no reference to sources we cannot license and copying no code, file, table layout or text. ARRI LUT data stay excluded in every form. `docs/14` rules 4 and 8.
- **ShareAlike data may train shipped weights.** CC BY-SA data (Google's HDR+ bursts, most Play Raw raws) may train weights we ship when its licence does not prohibit that use, with attribution in the model card and `NOTICE`. No dataset exists that combines Sony raw files, human edits and a licence that allows training shipped weights; MIT-Adobe FiveK and its derivatives are research-only.
- **Weights trained on CC BY-SA data are licensed CC BY-SA 4.0.** They are separate files in `data/models/<name>/` with their own `LICENSE`, loaded as data, listed in `NOTICE` and `THIRD-PARTY.md`; the code stays Apache-2.0. This meets ShareAlike literally instead of relying on a reading of the licence. `docs/14` rule 5, `docs/07`.
- **The IJG licence is allowed in `deny.toml`.** `jpeg-encoder`'s forward DCT is ported from the Independent JPEG Group; the acknowledgement "This software is based in part on the work of the Independent JPEG Group." is in `NOTICE`, `docs/14` and the About window.
- **The maintainer's own photos may be used as test and evaluation data, in CI and in published images.** The raw files live on the orphan branch `readme-photos` in Git LFS, never merged, with their reference exports beside them; clones of other branches fetch only LFS pointers. `tools/fetch/owner-photos.sh` fetches them with SHA-256 checks. README screenshots show the real app on these photos. The photos are the maintainer's own, carry no credit line and are never bundled with the app. `docs/test-photo-sources.md`.
- **Raw files, training data and other large test data are never committed.** The exception is the maintainer's own photos above. `tools/fetch/` downloads the rest into git-ignored `testdata/` with SHA-256 checks. `docs/validation-data.md`.
