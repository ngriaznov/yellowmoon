# 05 · Raw processing (mosaic to scene-linear camera RGB)

Crates: `ym-core` (orchestration), `ym-gpu` (kernels), `ym-ml` (network), `ym-noise` (σ map). All stages run in scene-linear float, in tiles on the GPU, with a CPU reference for tests and for machines without a usable GPU.

**CPU reference (M1-12).** `ym-gpu::cpu` holds the reference implementation of R1 and R3 to R9 (one module per stage, `cpu::chain` for the whole chain, whole frame or one tile). The WGSL kernels are parity-tested against it. Conventions: `f32` storage; `f64` for positions, spline evaluation and anything that accumulates; images are *planar* (all R, then all G, then all B) because the GPU reads a plane as one coalesced range and R7 to R9 treat planes separately; every buffer carries its position in the full frame (`Placement`) so tiles give the whole-frame result; borders mirror (parity-preserving) except R9, which clamps. Inputs are plain slices and a 2×2 `Cfa`; the mapping from `ym_raw::RawImage` is in the module documentation of `ym-gpu::cpu`.

## Order

| # | Stage | Notes |
|---|---|---|
| R1 | Black subtract, white normalise, clip mask | per CFA position, from SR2 levels |
| R2 | Noise estimate and illuminant estimate | on binned planes / the 1/8 preview (`docs/06`, `docs/02`) |
| R3 | Vignetting correction | Sony 0x7032 |
| R4 | Initial white-balance gains `g0` | from the illuminant estimate |
| R5 | Highlight reconstruction on the mosaic | opposed-channel method |
| R5b | Lateral CA on the mosaic | Sony 0x7035; red and blue photosites resampled from their own colour, full-resolution path only (§R9) |
| R6 | Demosaic + denoise | neural (export, 1:1) or classical (preview, fallback); no network is trained yet, so the classical path runs everywhere, with the adaptive ratio demosaic as its default (below) |
| R7 | Detail controls | colour noise, detail re-injection |
| R8 | Capture sharpening | Richardson–Lucy with a Gaussian PSF (default), or diffraction deconvolution from the f-number and pixel pitch (internal switch, not the default; below) |
| R9 | Distortion resample (and the lateral CA below full resolution) | Sony 0x7037 (0x7035 on the binned preview) |

Output: camera RGB balanced with `g0`, white = 1.0 before gains, consumed by the colour pipeline (`docs/02`, stage C1).

Output sharpening (`docs/algorithms/04-output-sharpening.md`) is not a raw stage. It is the last stage of every display-referred picture, after C12 and before C13, at the size the picture is shown or written (`docs/01` *Output sharpening*, `docs/09`); its halo is in the table below for completeness.

## R1 · Normalise

`x = (raw − black[c]) / (white[c] − black[c])` per CFA position. Negative values stay (they carry noise statistics); clamp at −0.05. Clip mask: `raw ≥ white[c] − 4·qstep` (or `≥ 0.995` normalised where qstep is absent). The mask travels with the image to R5, R6 and C7. Black and white levels are indexed by CFA *position* `2·(y&1) + (x&1)` of the active area (for the all-RGGB Sony bodies that is R, G1, G2, B); a tile uses the frame parity of its photosites. `Levels::from_rggb` maps values in the R, G1, G2, B order of the SR2 tags onto the positions of any pattern phase (a frame cropped to an odd origin starts with GRBG, say). `qstep` present with value 0 (lossless files fed to the network as a zero plane) means "clipped only at exactly the white level"; the 0.995 rule applies only when no qstep plane exists.

## R3 · Vignetting (0x7032)

Knots `v_i`, i = 0…n−1 (n = 16 on current bodies). Knot `i` sits at the normalised radius `r_i = (i + 0.5)/(n−1)`, where r = 1 is the half-diagonal of the active area (the last knot lies half a step beyond the corner). A knot gives the relative illumination the lens leaves at its radius: `G_i = 2^(0.5 − 2^(v_i·2^−13 − 1))`. Interpolate `G(r)` **linearly** between the knots (end values held outside them) and **divide** each photosite by `G(r)`, clamping `G` at 1e-4.

*Status (M1-12, verified):* the first reading of this section (squared gain, knots at `i/(n−1)`, a monotone cubic, multiplying by the gain) was wrong on four counts, found by running the lens oracle (§Verifying lens corrections) on synthetic Sony files. `darktable-cli` 4.6.1 (embedded metadata, algorithm 2, the module's default) applies exactly the rule above: the radial gain it produces agrees with `VignetteProfile::gain_at` to 8e-5 (gate: 0.5%; `tests/cpu_lens.rs::vignetting_matches_darktable`). Readings rejected by the same renders (maximum gain deviation): this section's first reading, multiplying by `G²` with a cubic through knots at `i/(n−1)` (66%); the same dividing by `G²` (17%); darktable's older algorithm 1, dividing by `G²` with the right knots (15%); the right gain with knots at `i/(n−1)` (1.4%). So positive `v` means a darker corner (`G < 1`, a gain up to 181 at the largest encodable knot) and negative `v` a gain below one; a typical lens has `v` from 0 at the centre to a few thousand at the corner. Radius: the centre of a pixel measured from the centre of the active area, over half its diagonal, `hypot(width, height) / 2` (darktable counts pixel indices instead of pixel centres, a half-pixel shift worth about 1e-5 in the gain). `ym_raw::LensTable::knots()` drops the stored count; note that the count of tag 0x7035 is 2n (darktable rejects the data unless it is), not n.

*Real files (RA-03c):* the reading holds on real raw data. The even part of the horizontal brightness profile of a sky band follows `G(r)` of the table on ILCE-7M4, ILCE-1 (three frames) and A6300 (section R9, "Real files", point 3), so the raw is not vignetting-corrected by the camera (`0x7031` = 257 or 272, `Auto`) and R3 does not correct twice. The `n`-knot grids of 11 (APS-C, or the crop mode of a full-frame body) and 16 (full frame) are one physical grid and need no special case.

*The Before view leaves R3 out (2026-10-16, `docs/02` *The Before view*):* a render for the Before view runs the raw stages without this one (`RawParams::vignetting` off; the plan has no profile; the device's prep kernel gets no vignetting table), because the camera's own picture is not brightened at the corners by it. Nothing else of the chain changes for that view, and the final picture, the thumbnails and the exports always have R3.

## R4 · Initial gains

`g0 = 1 / w_scene_initial` (green = 1), from the illuminant estimate at open. If the estimate fails, use the as-shot gains from SR2 0x7313. Gains are applied to the mosaic before R5 and R6 because both work better on balanced data. Later white-balance changes do not re-run R5–R9 (`docs/02` C1 applies a residual). The clip mask is not changed by the gains; a clipped photosite then sits at `g0_c` (times the vignetting gain), and R5 finds it through the mask, not by a threshold. SR2 0x7313 levels are multipliers (green about 1024), so `g0 = [R/G, 1, B/G]` with `G` the mean of the two green levels (`gains::g0_from_wb_levels`); from a scene white `w`, `g0 = [w_G/w_R, 1, w_G/w_B]` (`gains::g0_from_scene_white`).

## R5 · Highlight reconstruction (opposed channels)

Clean-room from darktable's published description ("inpaint opposed"); don't read or port its code.

1. Build a half-resolution superpixel image from each 2×2 quad: R, G = mean of the two greens, B, with a per-channel clipped flag.
2. For each clipped channel `c` of a superpixel, the **opposed estimate** is the cube-root mean of the unclipped other channels over the 3×3 superpixel neighbourhood: `ŷ = (mean(x^(1/3)))³`.
3. **Global chroma correction:** over all unclipped superpixels that border clipped ones, average `x_c − ŷ_c`; add that offset to every estimate for channel `c`.
4. Reconstructed value: `max(original, ŷ_c + offset_c)`. Write it back into the mosaic photosites of that channel, keeping the clip mask so later stages know these values are estimates.

*Implementation notes (M1-12):*

- A superpixel's green is flagged clipped when either green photosite is; the estimate is written to the clipped green photosites only. With no usable neighbour (all other channels clipped over the whole 3×3) step 4 leaves the photosite at its value, and step 5 below decides what a fully clipped quad becomes.
- **Fully clipped quads (step 5, review fix).** R1 clips each channel at its own white and R4 then scales, so a quad whose four photosites are all clipped holds `[g0_R·v, 1·v, g0_B·v]` (`v` the vignetting gain), for example `[2.0, 1, 1.7]` for the as-shot balance of an ILCE-7M3. That is a colour cast, not a measurement: C7 scales by `f(n)/n` (n the largest channel), keeps the ratios, and showed a neutral sun disk or lamp as saturated pink (and darker than the neutral pixels just below it). Such a quad has no colour of its own, so all its clipped photosites are raised to the largest of them, a neutral at the brightest bound. The step-4 estimate can still lift a channel above that. A quad with one green still measured is not fully clipped and is left to step 4. The level is continuous with a neutral ramp just below the last clip (red at `g0_R`), and luminance is monotone through the clip. The rule looks only at one quad, so tiles and the whole frame agree, and with recovery switched off nothing changes. Tests: `tests/cpu_highlights.rs::fully_clipped` (a neutral ramp through the real R1-then-R4 order, neutral to 0.01 in sRGB code values and non-decreasing in luminance) and the unit tests in `cpu::highlights`.
- Step 3 is read per channel: for channel `c`, the reference superpixels are those with no clipped channel that have channel `c` clipped somewhere in their 3×3 neighbourhood, so a red lamp does not bias the blue offset. `ŷ_c` there is computed as if `c` were clipped, from the unclipped other channels of the neighbourhood.
- The offsets are a global reduction. For tiles, accumulate `OffsetAccumulator`s over the tile cores in a fixed order, merge, and pass the same `ChromaOffsets` to each tile (`highlights::{accumulate_offsets, apply_offsets}`); applying needs only one superpixel (2 px) of context, the table below keeps the documented 4 px. Tiles start on even coordinates.
- Because the offset is one additive constant per channel, calibrated where a channel has just clipped, it under-reconstructs cores that are many stops over the clip level: a source at 2.6× the clip level comes back at roughly 1.3× with a paler hue (synthetic scenes in `tests/cpu_highlights.rs`). Region chroma (chroma-only ΔE00 of the mean colour of the blown region against the unclipped surround, through the stand-in camera matrix in `cpu::metrics`) is within 4.7 of the surround in all ten synthetic scenes (gate: 5; up to 10.4 without recovery), and the hue at the clip boundary is within 13° of the truth for gentle falloffs (18° and 24° without recovery on the two scenes where it matters). For hard-edged sources (all channels clip within a few pixels) recovery changes the boundary hue only a little (37° and 67° against 39° and 69° without). Whether this passes the blind review on the 20 real photos is open.
5. A quad clipped in all four photosites is levelled to its brightest clipped value (see the notes above).
6. `decode.highlight_recovery = false` skips R5; clipped values stay at their clip level, `g0_c` after R4 (they then render as white or a hue cast, which is the point of the switch).

Gate: on 20 test photos with blown skies and lamps, no magenta or cyan fringes at the clip boundary in blind review, and the reconstructed region's chroma within ΔE00 5 of the surrounding unclipped area.

## R6 · Demosaic and denoise

### Neural (default for export and 1:1)

One U-Net does both (`docs/07-ml-models.md`). Per tile, inputs:

- packed Bayer planes (4 × H/2 × W/2), balanced with `g0`;
- σ map (1 plane, `docs/06-noise.md`), scaled by the Luminance control;
- quantisation-step map (1 plane; zeros for lossless files);
- clip mask (1 plane);

output: linear camera RGB at full resolution. Tiles overlap by half the network's receptive field, computed from the architecture (64 full-res px for the starting U-Net in `docs/07`), and are cropped, not blended. A test renders a frame tiled and whole and requires a max difference ≤ 1e-4.

### Classical (the path that ships; the fallback once a network exists)

No network is trained yet (M2-H4), so the classical path runs everywhere: the 100 % view, every export and R7's `Y_classical`. It stays the fallback after that (`decode.neural_demosaic = false`). The fit view and the thumbnails at a reduction of 2 or more bin the mosaic (`docs/01`) and run no demosaic at all.

**Which methods exist, and which can be reached.** `ym_gpu::cpu::demosaic::Method` has five. **Method choice is not a user setting**: there is no settings field, no UI control and no CLI flag, and nothing is stored per photo. The renderer uses `DEFAULT_METHOD`. Tests and evaluation tools can force another method through the test-only switch `RenderOptions::demosaic` (in builds with the cargo feature `force-demosaic`, also the environment variable `YM_FORCE_DEMOSAIC`; `docs/algorithms/INTEGRATION.md` section 10).

| Method | Where it comes from | Reached by | Halo | Used for |
|---|---|---|---|---|
| Adaptive ratio (`AdaptiveRatio`) | `docs/algorithms/01-adaptive-ratio-demosaic.md`, the owner's package, written in Rust from the spec | **the default** | 13 px (11 without shadow matching; the scheduler always uses 13) | 100 % tiles, every export, R7's `Y_classical` |
| Menon (`Menon`) | port of colour-demosaicing (BSD-3), below | the test switch only | 8 px | the default until 2026-10-13; the reference of the comparisons |
| LMMSE (`Lmmse`) | our own implementation of the Zhang–Wu idea, below | the test switch only | 8 px | comparisons |
| Bilinear (`Bilinear`) | plain | the test switch only; also what a mosaic under 2 × 2 gets | 1 px | comparisons, a floor |
| Log-guided (`LogGuided`) | `docs/algorithms/02-log-guided-demosaic.md`, written in Rust from the spec | the test switch only | 5 px | a fast preview method; no render path uses it |

A light bilateral denoise in an opponent space, with a strength from σ (below), follows every method, so previews aren't noisier than the export. The adaptive ratio demosaic reads the gains `g0` and the noise model of the photo (its offsets and gates depend on them). Like every method it receives the *balanced* mosaic of R4 and R5 and undoes R4 itself, by dividing each photosite by `g0` of its colour inside `demosaic_with` (with unit gains that is the identity). A noise model that is missing or unusable is read as zero noise (K = T = 1 DN), so a render never fails for it (`docs/algorithms/INTEGRATION.md` section 10). How the package plugs into the chain: `docs/algorithms/INTEGRATION.md`; its tasks and gates: `docs/algorithms/TASKS.md` (RA-03 to RA-06).

The log-guided demosaic meets its gate (within 1 dB of Menon on the synthetic set: −0.84 / −0.80 / −0.73 dB at signal scales 1 / 0.1 / 0.01; about half of Menon's CPU time) and is **not used by any render path**. The fit view and the thumbnails at a reduction of 2 or more bin the mosaic and never demosaic. A `k = 1` thumbnail shares its chain and cache key with the 100 % view and the exports, so switching it would need a second chain with its own key, for a rare case, and the method trails Menon by 3.4 to 3.6 dB on Kodak in linear light (`docs/algorithms/02-log-guided-demosaic.md` section 9.3).

**Decision (2026-10-13, owner): the default classical method is the adaptive ratio demosaic** (`DEFAULT_METHOD = Method::AdaptiveRatio`). Three things led to it.

1. *The rule of this document*, "the method with the best PSNR becomes the default" (RA-05). In linear light over nine cells (procedural set, Kodak, McMaster; signal scales 1 / 0.1 / 0.01) the mean PSNR is 36.05 dB for adaptive ratio, 34.43 for Menon and 34.28 for LMMSE, and adaptive ratio is best in 7 of the 9 cells. The caveat from the RA-05 review: with the noise model scaled along with the signal, instead of the fixed absolute model, it wins 5 of the 9 cells, the nine-cell mean is 35.45 (+1.02 dB over Menon), and on the six photographic cells it is level with Menon and LMMSE (35.72 against 35.84 dB). The procedural set (+3.2 to +3.3 dB over Menon) carries the aggregate under either protocol. On gamma-encoded Kodak and McMaster it is below Menon: the method is made for linear light, which is what R6 receives.
2. *Artefacts.* At signal scale 1, zipper pixels are 20.3 % of the edge pixels against Menon's 39.1 % on the procedural set (24.2 against 34.3 % on Kodak, 26.6 against 41.8 % on McMaster), and false-colour pixels 4.3 against 7.6 % on Kodak and 6.3 against 11.2 % on McMaster.
3. *The owner's blind look (RA-H4)* at 1:1 crops of six real files (edges, texture, colour, shadows), with the labels shuffled per file (`docs/16`), and his decision to spend the CPU time on it: about 1.5 to 1.7 times Menon's in the demosaic stage, +3 to +13 % of an export's CPU time ("What the new default costs" below).

Menon, LMMSE, bilinear and log-guided stay selectable through the test switch. The pixels of every default render move with the change, so the golden set (61 synthetic files) is re-baselined with `golden update --note` (`docs/STATUS.md`, `docs/16`). The details of the measurement are in the RA-05 bullet below.

*Earlier decision (M1-12, revised 2026-10-12; replaced on 2026-10-13 by the one above): the default classical method is **Menon**; LMMSE and bilinear stay selectable (`demosaic::Method`). LMMSE wins on gamma-encoded sRGB test images (below), but the pipeline demosaics scene-linear data, where our LMMSE's fixed regularisation constants make it scale-dependent: on Kodak in linear light it gives 36.67 / 36.17 / 35.61 dB at signal scales 1.0 / 0.1 / 0.01 against Menon's constant 36.43 dB. Shadows matter more than a 0.2 dB lead at full scale. Revisit if LMMSE is made scale-invariant.* (The review of RA-05 could not reproduce those linear-light figures; see the end of the RA-05 bullet.) All methods handle the four Bayer phases and mirror at the borders.

- **Menon** is a port of `colour_demosaicing.demosaicing_CFA_Bayer_Menon2007` (BSD-3-Clause, Copyright 2015 Colour Developers; licence text in the source and to be listed in `NOTICE`), checked against the package's output on fixtures (max difference < 3e-5, all phases, with and without the refining step).
- **LMMSE**: Getreuer's IPOL code could not be fetched (ipol.im is unreachable from the build environment), so this is our own implementation of the Zhang–Wu idea, not a port: horizontal and vertical colour-difference estimates (from the `[−1 2 2 2 −1]/4` filter) are Wiener-smoothed over a 9-tap Gaussian window with local statistics (noise variance from the second-difference energy, `eps` 1e-5), fused with weights inverse to their error variances; red and blue come from colour-difference interpolation along the diagonal of smaller variation.
- **PSNR** (sRGB 8-bit images mosaicked as RGGB, 10 px border excluded, mean of per-image dB, local evaluation only: the sets are never committed; `tools/fetch/demosaic-sets.sh` downloads them into `testdata/demosaic/{kodak,mcmaster}` at pinned commits and checks every file's SHA-256 (`tools/fetch/demosaic-sets.json`), and `cargo test -p ym-gpu --test cpu_demosaic --release -- --ignored --nocapture` prints the numbers): Kodak (24 images, the 500×500 version distributed with cszn/FFDNet) bilinear 29.82, Menon 38.88, **LMMSE 39.16**; McMaster (18 images, the copy in JingyunLiang/SwinIR) bilinear 32.31, Menon 34.21, **LMMSE 35.09**. On the procedural set in `tests/cpu_demosaic.rs` (edges, fine text, correlated-channel scenes) LMMSE also leads; on the zone plate and flat patches all methods are within 0.7 dB.
- **Denoise** (`denoise::bilateral_opponent`): 5×5 bilateral on `(Y, R−Y, B−Y)`, spatial σ 1.5 px, range bandwidth `h = strength · √6 · σ_noise` on the Euclidean opponent-space distance (`√6 σ` is the RMS distance of two pure-noise pixels, so strength 1 gives a typical noise pair weight about 0.6); σ is the scalar or σ-map value at the centre pixel, scaled by `(L/L_auto)^1.5` like the network's σ. σ = 0 leaves a pixel untouched.

## R7 · Detail controls

`noise_reduction` resolves to `{ luminance L, color C, detail D }`, each 0–100. Auto values: `L_auto = clamp(10 · (1 + log2(ISO/100)), 10, 90)` (ISO 100 → 10, ISO 400 → 30, ISO 3200 → 60, ISO 25600 → 90; the number grows with ISO so the slider reads naturally), `C_auto = 50`, `D_auto = 50`. The Automatic card shows the resolved values ("Luminance 30").

| Control | Operation |
|---|---|
| Luminance `L` | σ fed to the network = `σ_est · (L / L_auto)^1.5`: the estimated noise at the auto value, 0 at L = 0 (the network demosaics without denoising), up to (100/L_auto)^1.5 × at 100. The network is trained across σ including 0, so this is a true strength control. |
| Colour `C` | After the network: guided filter on the two chroma channels of an opponent space (Y, R−Y, B−Y), guided by Y. Radius `2 + 6·C/100` px at full resolution, ε from `σ_est² · (C/50)²`. |
| Detail `D` | Re-inject fine luma texture: `Y += β · (Y_classical − Y_net)` with `β = 0.15 · (D/50)²` (0 at D = 0, 0.6 at 100). `Y_classical` is the classical demosaic of the same tile, computed only when β > 0. |

*Implementation notes (M1-12):* `C = 0` returns the input untouched (the literal formula gives `ε = 0`, and a guided filter with `ε = 0` still smooths chroma noise that is uncorrelated with the guide). The radius is `round(2 + 6·C/100)` px (2 to 8). The guided filter (He et al.) runs two box filters in series, so its receptive field is **twice** the radius, up to 16 px: the halo table below says so. `ε` is per pixel when σ is a map. Both operations leave the other half of the opponent space exactly as it was: the chroma filter touches only `R−Y` and `B−Y`, the detail term adds the same delta to all three channels. In the classical path the "network output" is the denoised image and `Y_classical` the plain demosaic before the denoise, so Detail puts back a fraction of what the denoise removed.

## R8 · Capture sharpening

Two methods exist and exactly one runs per photo (either/or; stacking them is an open evaluation option, `docs/algorithms/03-diffraction-deconvolution.md` section 7.1 item 8): `CaptureSharpen::{RichardsonLucy(SharpenParams), Diffraction(DiffractionParams)}` in `Chain` and `Stage::Sharpen`, each with its own halo (table below). R8 runs at full resolution only (the 100 % view and exports, and the rare thumbnail made at a reduction of 1), after R7; the binned fit view and the thumbnails made from binned images are not sharpened by it.

**R8 is off for a DNG** (owner's decision of 2026-10-14, `docs/09` "What a DNG carries"): both renders of a DNG, the raw pixels and the preview, run with R8 off (`RawParams::without_capture_sharpening`, set by `Job::without_capture_sharpening` for `FullTarget::DngLinearAwg4` and `DngPreview`: amount 0 and no diffraction controls, so `capture_sharpen()` is `None` and the chain, on the CPU and on the device, has no sharpening stage). It is a render-time switch of the internal chain parameters, not a setting: Detail › Sharpening says nothing to a DNG, the key of the cached chains and tiles changes with it (a render with R8 off never reads a chain made with R8 on), and JPEG, TIFF and PNG are unchanged. The adaptive ratio demosaic's own shadow step (`shadow_sharpening`, part of R6) stays on.

| Method | Default | Reached by | Controls |
|---|---|---|---|
| Richardson–Lucy, Gaussian PSF | **yes** (`DEFAULT_CAPTURE_METHOD`) | every photo | the Sharpening card's Amount and Radius, Auto from the ISO and the f-number |
| Diffraction deconvolution (RA-07, `docs/algorithms/03-diffraction-deconvolution.md`) | **no**, until the owner decides (RA-H2, open) | the internal `PhotoSource::capture_method`, set by tests and evaluation tools only: no settings field, no UI control, no CLI flag | none of its own: the PSF comes from the f-number and the pixel pitch, and Amount and Radius do not act on it (strength 1; the mapping of spec 03 section 2.5 is not made) |

**Selection rule, as built** (`ym_core::pipeline::raw`: `CaptureMethod`, `DEFAULT_CAPTURE_METHOD`, `pixel_pitch`, `diffraction_params`, `RawParams::capture_sharpen`). Richardson–Lucy runs unless the photo was given the diffraction method *and* the stage is active for it, which takes three things: an f-number from 1 to 50 (`RawMetadata::f_number`; missing, 0 and NaN count as none), a pixel pitch of 0.5 to 20 µm, and a plan that passes the gate of spec 03 section 3.1 for the photo's gains and noise model. The pitch is `1000 · sensor_width_mm / active_width_px` from the camera registry (`data/cameras/registry.json`, 27 of its 28 bodies, from the makers' published figures, `docs/03`), else `43266.6 / (crop · √(W² + H²))` µm from the EXIF crop factor `focal_length_35mm / focal_length_mm` (about 2 % high on APS-C), else none. A camera-processed reduced file (Lossless M or S) takes the registry pitch with `scale = frame width / active_width_px`. In every other case, including a stage that turns out inactive, R8 is Richardson–Lucy with the resolved Amount and Radius (and nothing when that Amount gives no iteration).

Richardson–Lucy (the default): deconvolution on linear luminance with a Gaussian PSF, clean-room from RawTherapee's published description.

- `sharpen` resolves to `{ amount A 0–300, radius ρ 0.3–2.5 px }`. Iterations `n = round(A / 30)` (0–10), damping in flat areas proportional to σ to avoid amplifying noise, PSF σ = ρ at the centre and `1.25ρ` in the corners (linear in r²).
- Auto: ρ = 0.8 (0.7 at f/8 and above, 0.9 below f/2); A = 120 at base ISO falling linearly in log ISO to 60 at ISO 12800.
- Applied to luminance only; chroma is untouched.

*Implementation notes (M1-12):* the PSF is truncated at `ceil(3σ_max)` and varies slowly, so the forward blur and its transpose are both gathers with the kernel of the pixel being written, separable (horizontal then vertical), kernels interpolated from a 33-level bank between `ρ` and `1.25ρ`. Damping (Lucy-style): the correction ratio `d/e` becomes `1 + w·(d − e)/e` with `w = r²/(r² + (σ_n)²)`, `r = d − e`, `σ_n` the luminance noise σ; residuals well below the noise (flat areas) get `w ≈ 0`, structure gets plain RL. The result adds `Y' − Y` to all three channels. Iterations: `round(A/30)` clamped to 0 to 10; the Auto amount interpolates linearly in `log2(ISO/base)` from 120 to 60 at ISO 12800. Each iteration blurs twice, so the exact dependency radius is `2·n·ceil(3σ_max)` (24 px for the Auto values n = 4, ρ = 0.8): twice the "3σ·n" of the table below. The scheduler caps it at 24 px; beyond the cap (A near 300) tiles differ from the whole frame by about 2e-7 on photographic content.

**Diffraction deconvolution (RA-07, not the default).** Luma only, no iteration. It plans one polychromatic Airy-pattern PSF per frame from the f-number and the pixel pitch (461 to 619 nm; kernel radius `R` ≤ 7 px, and a Gaussian of radius `r_G` ≤ 8 px for a high-pass), then fits three coefficients per pixel (a dark layer, a bright layer and the high-pass) by weighted least squares over a 9 × 9 window, with weights from the inverse noise variance and a penalty near clipping. The result is gated against the noise, averaged over 5 × 5 and carried into RGB as a capped ratio (gain at most 1.5). The port follows the C++ oracle operation by operation: all 13 image vectors are bit-identical, the planner agrees to 1.3e-8, tiles with the halo `10 + R + r_G` (at most 25 px, **not** capped at Richardson–Lucy's 24) equal the whole frame bit for bit, and 1 thread equals 4. Cost on the CPU: about 0.5 to 1.0 s per megapixel on four loaded cores, so 30 to 60 s for a 60 MP frame (the GPU kernel exists, below).

*A/B for RA-H2 (RA-07, 2026-10-13).* `cargo run -p ym-gpu --example ra07_ab` (slanted edges, fine text and natural texture blurred with the Airy PSF of a 3.76 µm pixel at f/5.6 to f/22, model noise at ISO 100, 800 and 6400; the crops and `index.html` are in the git-ignored `testdata/ra07/`, 25 of them). ## R9 · Lens geometry (0x7037 distortion, 0x7035 CA)

One resample, bicubic (Catmull–Rom), from the output pixel position to the source position:

- Distortion knots `d_i` → factor `F_i = d_i·2^−14 + 1`, knot `i` at the radius `r_i = (i + 0.5)/(n−1)` (half-diagonal = 1), linear interpolation between knots. Source radius `r_s = r · F(r)`.
- CA knots: the tag holds 2n values, red then blue. `K_c,i = ca_i·2^−21 + 1`, same knot radii and interpolation. Red and blue sample at `r_s · K_c(r)`; green at `r_s`.
- **Where the CA is applied.** At full resolution the CA is not part of the R9 resample but of **R5b, on the mosaic, before R6** (`lens::correct_mosaic_ca`): every red and blue photosite takes the value its own colour has at the position where green shows the same feature (Catmull–Rom on the lattice of that colour, shift `s_c(r) = r_s·(K_c(r) − 1)` along the radius; green is never touched), and R9 then moves the three colours by the distortion alone. Below full resolution (the binned fit view and the thumbnails) the CA stays in R9: binning averages every colour from its own photosites, so nothing has pulled red and blue towards green there. Reason and evidence: "Real files" below.
- `decode.lens_corrections = false` skips distortion and vignetting; `decode.chromatic_aberration = false` skips CA only.
- After distortion correction, crop to the largest rectangle of valid pixels with the original aspect ratio (the "auto crop"), before the user's crop. The crop is that of the whole geometry, CA included, wherever the CA is applied.

The factors above come from public reverse-engineering, not a Sony document; the check on real files is the next section.

### Real files (RA-03c: why R9's CA made real files worse)

*Question.* On ILCE-5000, 6300 and 7M3 (camera setting `Auto`) R9 with the 0x7035 tables raised the measured red/blue misregistration from 0.04 to 0.2 px to 0.3 to 0.7 px, flipping the knot sign was worse, and 7M2 (setting `Off`) was mixed. Either the camera had already corrected the raw, or the reading is wrong for real files, or something else. *Answer: neither of the first two.* The reading is right, the raw is not corrected, and the cause is the order of the stages.

*Method (local files only, nothing committed; `tools/lens/real_eval.py`, `ca_measure.py`, `fit_ca_readings.py`, `jpeg_geometry.py`, outputs in the git-ignored `testdata/lens-eval/`).* A signed radial shift of red and blue against green is fitted on blocks of 96 px by Gauss-Newton on high-passed planes (σ 5 px): `X(p) = a·G(p − s·u)`, `u` the unit vector away from the centre, positive `s` outward. On the **mosaic** it uses the photosites of the colour itself and the bilinear green, no demosaic (checked on synthetic mosaics with a known shift, `ca_measure.py selftest`: error below 0.04 px plus 25% of the shift, no shift found where there is none, also with a 30% colour drift; red and blue are read 8 to 30% low, and a bilinear demosaic of the A7 II reads 1.3 times the mosaic value, so the amplitudes fitted below are lower bounds). The same fit runs on RGB images (a demosaic, darktable's `--dump-pipe lens` PFMs, the camera's own JPEGs, the full-size `JpgFromRaw` of ILCE-7M4 and ILCE-1). The table's own prediction for the same quantity is `r_g·hd·(K_c(r) − 1)` with `r_g` the green's source radius.

*1. What is in the files (`exiftool -a -G1 -u`).* The raw sub-IFD holds the three tables of the recorded image: `n` = 11 knots for an APS-C lens or for a full-frame lens in APS-C crop mode (ILCE-1 here), 16 for full frame, the CA tag leading with `2n` (eight files carry the three tags there: A5000, A6300, A7 II, A7 III, A7 IV, ILCE-1 ×3; the NEX-5N and NEX-7 only carry them in the encrypted SR2 sub-IFD, which `ym-raw` does not read yet, hence "Lens data: none"; the A300 and A500 have none). A7 IV and ILCE-1 write `0x7031 = 272`, the others 257 (`Auto`) or 256 (`Off`, the A7 II). The maker note holds a second copy with 16 slots (11 used for APS-C): the CA values are the raw copy before it was rounded to multiples of 128 (the raw copy of the A7 III is `512 384 256 128 0 …`, the maker note's `520 360 224 120 48 16 …`), the vignetting knots are identical, and **the distortion knots are 1.113 times the raw copy** on all eight bodies that have both (`DistortionCorrParams`). The 11 and 16 knots lie on one physical grid, `(i + 0.5)/15` of the full-frame half-diagonal, which is `(i + 0.5)/10` of the APS-C one for a crop factor of 1.5: `(i + 0.5)/(n − 1)` over the half-diagonal of the recorded image is right for both.

*2. The raw is not corrected, and the table describes it.* Measured on the mosaics, the sign, the shape and roughly the size of the table are there, on the bodies set to `Auto` as on the A7 II set to `Off`. Rejected readings (rms over all blocks of measured minus predicted, px, 8 files, `fit_ca_readings.py`): sign flipped 0.31 to 1.70, red and blue swapped 0.29 to 0.91, against 0.13 to 0.37 as read. Knots at `i/(n−1)` or `(i+0.5)/n` are as good on the full-frame bodies (differences below 0.05) and worse on the APS-C ones (ILCE-5000 0.30 and 0.35 against 0.27; NEX-5N 0.21 and 0.25 against 0.16); a free knot-radius scale (which also covers normalising to the whole readout instead of the crop, 0.3 to 1% of the radius) lands on 1.00 (A5000), 1.07 (NEX-5N), 0.88 (A7 II), 1.35 (A6300) and at the edge of the search range (0.70, 1.60) on ILCE-1 and A7 IV, and gains less than 0.03 px of rms except on the A6300 (0.24 to 0.14) and the A7 IV (0.29 to 0.23): no consistent scale, so no normalisation to change; `K` at the source instead of the output radius makes no difference (within 0.01); the maker-note copy fits no better on average (0.26 against 0.25): better on the A7 IV (0.31 against 0.37) and one ILCE-1 frame (0.11 against 0.13), worse on two others, which is the rounding of the raw copy at work. Best amplitude `α` of the table (mosaic estimator, red/blue): A5000 0.92/0.76, A6300 0.78/0.56, A7 II 0.45/0.90, A7 IV 1.13/0.27, NEX-5N 1.21/0.70. The camera's own corrected JPEGs say the amplitude is right for Sony's pipeline: the full-size JPEG of the A7 IV leaves 0.00 to 0.03 px of red and 0.00 to 0.16 px of blue shift at every radius (the table predicts up to 0.72 and 1.20 px), ILCE-1 0.00 to 0.02 and 0.01 to 0.07, the 1616 px previews of A5000, A6300 and A7 III at most 0.27 px (mostly below 0.15; 4:2:2 chroma, so they under-read) where the raw of the A5000 shows 1.7 px; the preview of the A7 II (`Off`) shows the CA. So there is no decisive "already corrected" tag for CA: `0x7034` is 1 on the files whose raw still carries the CA.

*3. Distortion and vignetting are right.* The camera's JPEG against the raw (block matching of the green, then `rho_raw = ζ·rho_j·F(ζ·rho_j)` fitted for the zoom `ζ` and the table amplitude `α`): the raw copy of the distortion table gives `α` = 0.998 on the A7 III and 1.03 on the A5000 (the maker-note copy 0.90 and 0.92: do not use it), about 0 (−0.19) on the A7 II whose distortion setting is `Off`. Vignetting: the even part of the horizontal brightness profile of a sky band (the sky's own gradient is odd and drops out) is the vignetting if the raw is uncorrected. It follows `G(r)` of the table on A7 IV (−0.23 measured against −0.18 expected at r = 0.83), ILCE-1 ×3 (−0.24 against −0.19, −0.09 against −0.10, −0.09 against −0.10) and A6300 (−0.22 against −0.11): **the raw is not vignetting-corrected either**, and R3 (divide by `G`) is right. A puzzle that is not resolved: a fit of the camera JPEG to the raw (monotone tone curve, a gain per radial band) finds no radial gain at all on A7 III and A6300 (1.00 where the tables say 1.55 and 1.18 at the outer radii) and 0.95 on the A5000 (table 1.16), the same as on the A7 II set to `Off` (0.91 to 1.00, the method's own floor); either the preview JPEG is not shading-compensated or the fit is blind to it. A noise test (variance at equal signal level against radius, which would rise with a gain applied to the raw) rises like the table on the A7 III (1.53 against 1.55 at r = 0.93) and does not on A5000, A7 IV and ILCE-1. Nothing here says R3 is wrong; a flat-field frame (a V2 measurement) would settle the preview question.

*4. The cause: a green-guided demosaic absorbs about half of the CA.* The mosaic keeps the CA; after R6 a colour-difference or ratio demosaic has pulled red and blue towards green. *Stage-order consequences.* R5b needs `max |shift| + 6` px of context (`lens::mosaic_ca_halo_px`, even, in `Stage::MosaicCa`); tiles reproduce the whole frame bit for bit and do not depend on the thread count (tests). *Implementation notes (M1-12):* the knot positions and the linear reading are those of darktable 4.6.1 and were measured against it, not assumed: the positions of 373 dark-line centres in its distortion-only render agree with `LensGeometry::source_position` (after undoing its zoom) to 0.002 px rms and 0.009 px at most, the three colour planes of its CA-only render to 0.003 px rms (gate: 0.2 px; `tests/cpu_lens.rs::{distortion,lateral_ca}_matches_darktable`). Knots at `i/(n−1)` would be 1.5 to 2 px off, and a monotone cubic through the right knots 0.15 px off at the corner for a quadratic profile, which is most of the gate. darktable does not crop: it zooms the corrected image by the largest value of `F(r)·K_c(r)` between the half-short-side radius and the corner (200 samples, three planes) so that no black corner is left; our crop and its zoom show the same mapping (`tools/lens/lens_model.py: darktable_zoom`). Coordinates are continuous (pixel `i` covers `[i, i+1)`, centre `i + 0.5`); the frame centre is `(W/2, H/2)` and `r` is the distance over half the source frame's diagonal. `K_c(r)` is evaluated at the *output* radius `r` and multiplies the same direction as `F(r)`: red and blue sample at `centre + (p − centre)·F(r)·K_c(r)`, green at `centre + (p − centre)·F(r)`. The CA tag needs an even count of at least 4. A source position is valid when it lies in the hull of the pixel centres, `0.5 ≤ s ≤ size − 0.5`; taps beyond the buffer edge replicate the edge pixel. The auto crop is the largest centred rectangle whose pixels sample valid positions in all three channels, with the frame's aspect ratio and even width and height (a 10% barrel correction on 600×400 crops to 552×368); the whole frame when nothing needs cropping. The resample works on any output rectangle of the cropped image; `LensGeometry::source_rect` gives the source rectangle it needs (bounding box of all channels' positions plus the Catmull–Rom support and one pixel). With `lens_corrections = false` the distortion tag is ignored, with `chromatic_aberration = false` the CA tag is.

## Tiling and halos

|---|---|

| R6 neural | half the receptive field (64 px for the starting U-Net) |
| R6 classical | the demosaic's `Method::halo()` + the bilateral denoise's 2 px. Adaptive ratio (the default) 13 px (11 without shadow matching; the tile scheduler always uses 13), log-guided 5, Menon and LMMSE 8 (measured), bilinear 1. For the default 13 + 2 = 15 px |
| R7 guided filter | 2 × radius, up to 16 px; with the detail term at least 13 px, because `Stage::Detail` takes the default demosaic's halo for `Y_classical` |
| R8 Richardson–Lucy | 2·n·⌈3σ_max⌉, capped at 24 px |
| R8 diffraction | 10 + R + r_G, at most 25 px (R ≤ 7 the PSF kernel radius, r_G ≤ 8 the high-pass Gaussian radius; `DiffractionParams::halo_px`), 0 when the stage is inactive. Not capped at 24 |
| R9 | bounding box of the tile's source positions, ±2 px Catmull–Rom support, +1 px (`LensGeometry::source_rect`) |
| Output sharpening (display-linear, after C12; not in the raw tile walk) | the exact receptive field of the plan, `SharpenPlan::halo_px(scale)`: for the screen preset 17 px at full size and 9 px for a 2048 px long edge from 6000, never more than 21 (`OutputSharpen::max_halo_px`); for the print preset 14 px at full size, never more than 41 (spec 04 section 1.4). Callers cut strips with this halo (`docs/09`, `docs/01`) |

The scheduler computes a tile's required input rectangle by walking the stages backwards (`ym_gpu::cpu::tiling::required_input_rect`); mosaic-domain rectangles start on even coordinates. The receptive fields of the demosaic methods are measured by perturbing single photosites (`tests/cpu_demosaic.rs`). Tiled-versus-whole tests (`tests/cpu_tiling.rs`, `cpu::chain`) give a maximum difference of 0 (pointwise stages bit-exact; the others also 0 in practice, 2e-7 for RL beyond its cap), against a limit of 1e-4. The halos of the raw-algorithm stages are checked against the code's declared ones (`Method::halo()`, `CaptureSharpen::halo_px()`, `SharpenPlan::halo_px`) and each is pinned by a tiling test: tiles with exactly that halo equal the whole frame bit for bit.

**GPU tiling, as built (M0-07).** `ym_gpu::tiles::TilePlan::new(width, height, tile_px, stages)` cuts the frame into cores of 1024 or 2048 px (`tiles::TILE_SIZES`; `kernels::raw::recommended_tile_px` picks the largest that fits half the memory budget with two tiles in flight and one storage binding) and gives each tile its `compute` rectangle from `required_input_rect` over the stages (the table above, so the halos are the measured ones, mosaic origins even). The kernels run over the whole compute rectangle and mirror at its edge like the CPU reference; only the last kernel is restricted to the core, so the outer ring (one halo wide) is never read back: tiles are cropped, not blended, and the tiled result equals the whole-frame result bit for bit for the pointwise and bilinear stages (`tests/gpu_spike.rs`, `tests/gpu_pipeline.rs`: 0.0 difference, gate 1e-4). Tile rows complete in raster order and `kernels::raw::RowStreamer` hands the encoder a full-width band as soon as the last tile of a row is in. The device thread never pre-empts a running job (`ym_gpu::queue`), so an export that must not hold up viewport frames is cut into jobs at Export priority, one per tile row or per tile (`TilePlan::tile_rows`, `TilePlan::tile_range`: same frame and tile numbers, fewer tiles; one `RowCollector` or `RowStreamer` on the full plan collects the pieces); `tests/gpu_pipeline.rs` shows a Viewport job running between the rows of such an export and the pixels equal to the single-job run. `GpuContext::warm_up` compiles every kernel at start-up, so the colour chain's large shader does not land on the first viewport frame. A plan whose tiles lack the demosaic's 1 px of halo, or a raw frame whose pattern differs from the parameters, is refused with `GpuError::InvalidInput` instead of rendering seams or a wrong Bayer phase. Row strides are even, so two f16 samples share a 32-bit word and one thread writes both; image intermediates were f16 in memory when M0-07 was built (`SHADER_F16` native, else two halves per `u32` with `pack2x16float`, else f32) and f32 in registers. **Since the GPU foundation (G-02, `docs/gpu-plan.md` X-3) image planes are f32 in memory by default**: `StoragePreference::Auto` resolves to `StorageMode::F32` on every device (an adapter with `SHADER_F16` no longer changes it), and the f16 modes are reached only through `StoragePreference::Force` for the legacy kernels and their tests. Every existing parity test passes in all three modes, with every pool buffer NaN-filled first (poison mode, below).

**GPU plan (2026-10-13, the owner's direction in `docs/16`; ten tasks, `docs/gpu-plan.md`).** Every image stage after decoding moves onto the wgpu device, in the app and in `ym`, exports included, in steps that each ship behind the device policy with the CPU reference as their twin: the adaptive ratio demosaic on a `GpuChain` that takes the same `Chain` and `TilePlan` as the CPU (host mosaic in, host planes out); the view stages (geometry sampler, colour chain C1 to C12 with a persistent table set, output sharpening, C13 with dither) as one device job per frame; the bilateral denoise, R7 and Richardson-Lucy; the raw front (R1, R3, R4, R5 with the CPU's chroma offsets as uniforms, R5b), R9 and the binned fit-view path; the export tail (Lanczos-3 resize, strip sharpening, C13 into bands that the CPU encoders pull); and last the device-resident handoff between them. The contracts: image planes are f32 in every mode; the logical tiles are the CPU's constants (512 px view, 1024 px export) and a compute rectangle above 2.5 Mpixel is split by a rule that depends on the rectangle alone (lavapipe's storage binding is 128 MiB and the adaptive ratio scratch is 48 bytes per pixel), so no tile depends on the device; a pixel depends only on its receptive field, with no float atomics, no subgroup operations, fixed-length sums and absolute coordinates, so tiles equal the whole frame bit for bit on the GPU and one machine gives the same bytes in the app and in `ym`; pooled buffers are filled with NaN in tests so that a kernel cannot read what an earlier job left. A GPU error re-renders the whole photo on the CPU with a note, never one tile; `--require-gpu` fails the photo instead. Golden hashes pin the CPU reference (`ym render --cpu`) and GPU renders are compared with those pictures in a separate strict job. On the CPU stay the decode and the 1/8-preview estimates, the R5 offsets of the full chain, the methods behind the test-only switch (Menon, LMMSE, bilinear, log-guided), camera-processed files, the histogram counts, the DNG white and the encoders; after the wave the encoder is what is left of an export's CPU time. The performance targets below are for the Mac (M0-H4); the plan states no GPU speed as a result.

**Wiring.** Of the four, the adaptive ratio demosaic is wired into the render of a photo since G-03 (below); the log-guided demosaic stays the test-switch method on the CPU, and the diffraction deconvolution and output sharpening have device entry points (`PreparedDiffraction::encode`, `encode_sharpen`, `PreparedSharpen::encode_*`) that later tasks of the wave chain in. Outside the raw chain, the only image stage on the GPU is the colour pass of viewport frames and thumbnails (`docs/01`). Exports stay byte-identical between the app and `ym` on one machine, and the golden hashes pin the CPU reference (`ym render --cpu`), so a GPU render is checked against it within the tolerances above and below.

**The adaptive ratio demosaic in the render (G-03).** `ym_gpu::chain::GpuChain` steps the very `Chain` and `Prepared` the CPU runs, through the tile stepper `Chain::begin_tile` / `TileRun` (the CPU's own `run_tile` is a loop over it, bit for bit): R1 to R5b, the R4 undo of the balanced entry, the CA curves and the noise model (`Chain::noise_dn`, `cpu::chain::demosaic_inputs`) are the CPU's own code, so the device cannot be given other numbers than the CPU. The demosaic of the tile runs on the device (host mosaic in, host planes out: `GpuChain::run_tile` takes a `DeviceRunner`, which a `GpuContext` is, and the CPU chain continues with the denoise, R7, R8 and R9). The range of stages that ran on the device is a `StageRange` (R6 only today) in the render report, so the next tasks widen it without a new interface. A demosaic core whose padded plane is above `MAX_PHYS_AREA` (2.5 Mpixel; the scratch is 48 bytes per padded pixel with shadow matching, 120 MB against lavapipe's 128 MiB binding) is cut by a rule that depends on the core rectangle alone (`split_core`: the longer side in halves, recursively), never on the device, so a split core equals the unsplit one bit for bit (tested down to a few hundred pixels; a corner tile of a strong lens cuts into two rectangles with a largest binding of 97 MiB). A mosaic below 2 x 2 photosites is a CPU stage. `GpuStages::RAW_CHAIN` is run by the policies `on` and `require` (every stage) and not by `auto` (only the signed-off stages, the colour pass): the Mac checks decide when a stage is signed off (`docs/gpu-plan.md` X-8, question 2).

*Faults and cancellation.* The policy is per photo: a device error during an export re-renders the whole photo on the CPU with a note (never a photo of both), a viewport tile re-renders that tile on the CPU, with a note, and the photo stays on the CPU from then on; `require` fails the render with `RenderError::Gpu` (export error kind `gpu`). A shader that does not compile switches the raw chain off for the process; an out-of-memory or a too-large buffer is tried once more after the buffer pool is trimmed. All device jobs of a render carry the render's cancel token and one priority (Export, Viewport, TileNeural or Thumbnail, never mixed in a render); going to another photo drops the photo left's device jobs that are still queued, and a render cancelled while its job waits returns at once. A full render (one photo of an export) takes one snapshot of the options (`options()`) when it begins and makes all of its tiles from it, so a device attached part-way cannot put the tiles of one file on two devices. The same holds when the route goes away part-way (the device is lost between two tiles, or another request ends the photo's use of it): an export whose first tiles ran on the device starts again on the CPU instead of finishing there, and a strict policy fails the next photo as well once a shader error has switched the raw chain off for the process (it never renders that photo quietly on the CPU).

*Fast-math on Metal (G-03).* The first run on the Apple runners (`docs/gpu-plan.md` section 12) failed eight tests of these three kernels. Metal's compiler runs with fast-math (wgpu-hal 30.0.1 sets only the language version and `preserveInvariance` on `MTLCompileOptions`; no wgpu option turns fast-math off), which re-associates and contracts. Causes and changes, each checked without a Mac by compiling the same sequence of operations with clang `-O2 -ffast-math` (also LLVM, and reproducing the Metal numbers): (1) the **exact luma** of the diffraction kernel failed because the error sum `(a - ad) + (b - bb)` of the Knuth sum was in the open: the optimiser rewrites it to `(a + b) - (bb + ad)`, which is 0, and the luma was the plain f32 sum (Metal: 30,304 of 60,000 off the CPU's; the model: 54 % of 2 million). Every error term is now hidden behind the runtime-zero barrier like the rounded results (an OR since the Metal-fix review: an XOR applied twice cancels, `docs/gpu-plan.md` K8) (the model: 0 of 2 million, also with `-ffp-contract=fast`); the envelope counts that this luma feeds are what the other four diffraction failures (edge vector, random frames, scale 1/4, the large frame) measured, and they should return to the lavapipe values. (2) A **1e30 in one sample** left a non-finite sample because the products of the solve overflow f32 and the code relied on the infinities being caught afterwards; the luma pass now bounds every finite input sample (about 15 times white), so no product can overflow in any evaluation order (`a_finite_sample_beyond_the_bound_acts_like_the_bound`). (3) The **log-guided** reconstruction `x * (a / b)` is re-associated to `(x * a) / b`, which overflows from a mosaic scale of 1e20 (the model: infinity from 3e21; with a barrier after each of the four quotients, the IEEE numbers). (4) The **tie vectors** of the adaptive ratio kernel (`edge_knight`: 40 samples over 1e-4 on Metal against 10 on lavapipe; `ca_weighting` 56 against 58) are decisions that rounding noise settles; Metal has its own column in the test for `edge_knight` only (80, twice the Metal measurement; `ca_weighting` passed within the lavapipe limit of 100 and keeps it) and the lavapipe limits are untouched. Not done: a Metal-specific compile of these kernels with fast-math off. wgpu 30 has `Features::PASSTHROUGH_SHADERS` with `ShaderInput::Msl` (source compiled with default options, so the source must carry `#pragma METAL fp math_mode(safe)` and `fp contract(off)`, MSL 3.2, macOS 15) and `MetalLib` (a `.metallib` built offline with `xcrun metal -fno-fast-math`); both need a Mac to build and to test, so they are the escape hatch for a kernel that these changes do not make safe, not part of this change. The Metal numbers after these changes come from the next Apple run.

*f16 storage and the 1e-3 gate (review note).* The gate is met by the 50 MP scene and by the smooth test scenes, but it is data dependent: the balanced mosaic and the demosaiced planes are rounded to f16 (relative step 4.9e-4, absolute 4.9e-4 to 9.8e-4 between 1 and 4), and the gains push saturated or clipped samples to 2 to 4. A frame of full-range, uncorrelated noise on every photosite (an unrealistic worst case, `white_noise_scene` in `tests/gpu_spike.rs`: values up to 1.4 × white, gains 2 and 1.6, a matrix with negative terms, so a dark output is a difference of large f16-rounded terms that the sRGB toe then multiplies by 12.9) reaches 4.8e-3 to 6.1e-3 against the plain f32 reference, five times the gate. Against a reference that rounds to f16 at the same two places (`f16_aware_reference`) the GPU agrees to 1.4e-6 in every storage mode and every scene, so the difference is storage precision, not kernel error; `spike_matches_an_f16_aware_reference_to_rounding_noise` pins it at 2e-5 for at least 99.9 % of the samples. A tight colour gate should be judged against the f16-aware reference or on the f32 device. Since G-02 the f32 device is the default one, so this caveat applies to the forced f16 modes only.

**Device foundation (G-02): poison, health, shared tokens, kernel sets.** A pool buffer is no longer handed out as it was left: with poison mode (`GpuConfig::poison`, `YM_GPU_POISON=1`, always on in the test helpers) `BufferPool::acquire` fills the whole size class with `0x7FC07FC0`, a NaN as one f32 and as two f16 (and `COPY_DST` is added to the usage so the fill is an ordinary queue write), so a kernel that reads what it did not write produces NaN instead of passing by luck on a zeroed fresh buffer; every existing GPU test passes under it. Several of the older parity tests measure their error in a way that skips a NaN (`fold(0.0, f64::max)`, `ratio > worst`), so they alone would not catch a stale read: `tests/gpu_device.rs` (`existing_kernels`) is the NaN-proof check, running every existing host wrapper (adaptive ratio, log-guided, diffraction, output sharpening, the colour chain on every configuration of `tests/common/chains.rs`, the raw front end to display), whole and tiled, on a poisoned and on a plain device and requiring the same bits and no NaN or infinity; and `common::exact::assert_tiles_equal_whole` refuses a non-finite frame, because a frame of NaN equals itself. An uncaptured wgpu error (a validation error nobody scoped, an out-of-memory) taints the device instead of panicking its thread, a device-lost callback marks it lost, and a readback that does not finish within 30 s taints it too (`GpuConfig::readback_timeout`; on Mesa lavapipe a second `queue.submit` blocks behind a running one, so the timeout covers the wait, not the submit); `Gpu::is_lost()` reports either, and the next allocation, submission or readback of a job fails with `GpuError::DeviceLost`. A driver out-of-memory while creating a buffer is reported as `OutOfBudget`. `Gpu::submit_with_token` and `Gpu::run_with_token` take the render's own `CancelToken`: setting it skips the jobs of the render that have not started and is seen by the one that runs. `KernelSet { View, Raw, Tail, All }` and `GpuContext::warm_up_set` compile a group of kernels at a time; kernels the plan has still to write are registered as placeholders (`KernelId::is_placeholder`, a stub that writes one NaN, skipped by the warm-up) so that their ids, sets and offline checks exist before they do. `tests/shaders_naga.rs` validates every kernel in every mode with `Capabilities::empty()` (the f16 modes add the capability of their own declarations), translates to MSL, SPIR-V and HLSL, and lints the source for the kernel contract (`docs/gpu-plan.md` 4.6: entry point and workgroup size, at most 8 storage and 1 uniform buffers, 16 KiB of workgroup memory, no subgroups, float atomics, texture sampling, `fma()` or extra directives); the colour kernel's two uniform blocks are the one listed violation, for G-04 to remove.

**View kernels (G-04): persistent colour tables, device colour stage, encode, sampler, fused sharpen tail.** The view stages after the chain have device entry points that take and give `GpuImage`s, so a frame can stay on the device from the sampler to the bands the encoders pull. (1) *Persistent tables* (`kernels/color.rs`, `ChainTables`, one set per device thread, keyed by the device's counters): the ACES 2.0 tables and the 64 x 64 dither table are uploaded once per device, the curve tables (four tables of 1024 `f32`, 16 KB a set; the last 12 sets are kept) once per curve edit, and look cubes are kept in an LRU of 6 entries or 192 MiB keyed by a 128-bit hash of the cube's content (a second look of the same content uploads nothing). (2) *Colour stage* (C1 to C12): `PreparedChain::encode_stage` reads a `GpuImage` window and writes a `GpuImage` (f32 planes, with a destination stride and x offset, so a wider destination can take a tile), `encode_rgba8` stops at RGBA8 for the Before view; the host wrappers `render` and `render_tiled` are layers on them, and device to device equals the host wrapper bit for bit (tested). (5) *Sampler* (`kernels/sampler.rs`, CPU port `cpu/sampler.rs`): the eight EXIF orientations, quarter turns, the straighten angle and the crop in one pass with copy, Catmull-Rom or box filtering and an outside plane; positions come from per-column and per-row tables (an integer and an `f64`-split fraction) and exact row intervals for the inside mask, computed on the CPU, so a pixel does not depend on the window it is computed in (tiles equal the whole bit for bit; positions never form an `f32` of the order of 10^4). Every bounded test prints its measured value in a `[G-07] ...` line, so the Metal log carries the numbers; a Metal column is added only when a Metal run shows a difference that is inherent to `f32`, with that evidence.

**Device residency (G-10).** What a tile, a group and an export leave on the device between two jobs, and the proof that this changes no bit. *The tile stays.* `GpuChain::run_tile_device` is `run_tile_front` that does not read the tile back: the range R1..R9 from the resident words ends in a three-plane `GpuImage`, cropped on the device when the last stages were identities and assembled on the device from its parts when the demosaic core was cut above `MAX_PHYS_AREA`, both with the **copy kernel** (`copy.wgsl`, `kernels::copy`), which moves samples and computes on none, so fast-math cannot touch it; the readback of the image has the host tile's bits (`gpu_residency.rs`: four CFA phases, lens and none, whole, corner and inner rectangles, a cut core), and the job is one submission and no readback. *The export reads it in place.* `ExportTail::add_tile_device` binds the tile as the sampler's source: the tile of a 1024 px row no longer goes down to the host (12 MB) and up again; the bands are the ones `add_tile` makes from the host copy, bit for bit (plain and sharpened, 8 and 16 bit, shrunk), and the DNG's device colour stage takes the tile the same way (`colour_device_tile_to_host`). **At most three submissions per tile**: the chain's job, one job that makes the slabs the tile opens (a tile of 1024 rows over slabs of 512 opens two, and they are one job; the 50 MP gate found four submissions when each slab was a job of its own), and the tile's own; the only readbacks of an export are the bands. *The reduced group is a series of jobs, in bands.* `GpuReduced` makes the group of the fit view as `RowBands` (`REDUCED_SLAB_ROWS / k` rows of the result each, a buffer of its own per band), the bilateral denoise and R9 working on windows of rows (`RowBands::window`: a band itself when the rows lie in one, else a copy; the bilateral reads two rows beyond its window and the lens stage reads the rows its displacement reaches, `LensTable::source_rect`), the sigma binned into bands too, and `ReducedRun` steps through it one slab, band or plane of work at a time, so that **a viewport frame queued behind the group waits for one step and not for the whole group**. The bands put together are the one-piece run's bits (tested); at 50 MP and `k = 2` no buffer of the run is above 22 MiB (the group of 3912 x 2608 in six bands), where the group in one piece needed 150 MB and a device with a 128 MiB binding refused it; the CPU composition agrees to 4.5e-5 scaled (the bound is twice that: an f32 displacement doubles its error as `k` halves). `Job::group_backing` makes it a job per step (`GpuRoute::reduced_resident`; a cancelled render drops the state between steps and the buffers go back to the pool). *The caches keep it there.* `Backing { Cpu, Gpu }` in the group and tile caches of `PhotoGraph` (`docs/01`, "Resident caches"): the sampler gathers its window out of the cached pieces (`kernels::copy::encode_gather`), so a fit frame reads back its RGBA8 frame and nothing else, and a 100 % frame over cached tiles uploads next to nothing.

*Measured on Mesa lavapipe (llvmpipe, LLVM 20.1.2, a loaded machine: the other lane's tests ran beside, so times are indications; counts are exact).* One job at a time on the device, so what matters for a frame that waits is the longest job: a regular chain job for a 1024 px tile of a 50 MP photo (about 1.1 MP of mosaic with its margins) takes 2.2 s on average and 4.3 s at the longest over 54 tiles (`--release`); the steps of the group at `k = 2` of the same photo take, longest by kind, 1.0 s (offsets, 6 steps), 0.13 s (fold), 1.4 s (bin, 6), **5.9 s (the sigma plane, one step)**, 1.4 s (denoise, 6) and 0.75 s (R9, 6): 26 steps and 36 s together, where the group was one job of that length. The longest step is about 2.7 times the mean tile job and 1.4 times the longest, the same order of work: no step was split further (the sigma plane is a whole-frame kernel and a cut of it would change a kernel for a job of one tile's size). *Submissions and transfers.* A chain tile from the resident words: 1 submission, 42 dispatches, 46 small uploads (11 KB) and no readback for a 248 x 186 tile; tiles handed to the tail on the device: at most 3 submissions per tile, plain 8 bit 6 tiles with 1 readback in all (7 with host copies), sharpened 16 bit 9 tiles with 1 (10), shrunk and sharpened 6 tiles with 1 (7); an export of a 900 x 600 photo in 12 tiles reads back 1 time with the raw front on the device and 13 with the front behind the CPU; the first fit frame of a photo reads back 1 time with a resident group (5 submissions) and 2 with the host caches (6); a 100 % frame over cached tiles uploads 14 KB, with host caches 993 KB. *The 50 MP memory gate* (`--release`, `fifty_megapixels_through_the_chain_and_the_tail_stay_under_two_gib`, 8436 x 5624, 54 tiles of 1024 px, 16 bit, sharpened, through the chain and the tail): the pool ledger peaks at **600 MiB** (the gate is 2048 MiB), is back at **0 MiB** (its value before) when the run is over, at most 3 submissions per tile and no tile read back. The ledger of the renderer: a photo with its words and a fit group holds 3.2 MB (the 900 x 600 test photo), the tiles of a 100 % view 3.1 MB more, navigating away lets the tiles go and forgetting the photo gives everything back (`ym-core/tests/gpu_residency.rs`).

*Recording cost (UniformArena, BindGroupCache, ReadbackRing: not built).* The plan builds these only if the CPU time of recording shows it (X-17). Recording one dispatch (a uniform buffer from the pool, a queue write, a bind group, a compute pass) takes 66 to 67 us on lavapipe on this machine; a chain tile of 248 x 186 records 42 dispatches, which is 1.0 % of its 273 to 279 ms. Nothing here justifies an arena. On Metal the tile takes milliseconds and the share may be several times larger: `what_recording_costs_per_dispatch_and_per_tile_is_measured_for_the_arena_decision` prints the same lines (`[G-10] ...`, as GitHub annotations on the runners), and the Mac session (M0-H4) decides from them; the three structures stay unbuilt until a number says so.

*Warm-up order.* `KernelId::ALL` is the order a cold start needs the kernels: the fit view of a mosaic photo (R1 to R5, the binning, the sigma, the denoise, R9, the copy), the view stages (sampler, colour, output sharpening, C13), the full-resolution chain (demosaic, denoise, R7, capture sharpening, diffraction), the export tail's resize, and last the spikes and the probe, which no render uses. `KernelSet::kernels` and `warm_up` compile in this order, so the first frame of the first photo does not wait for the demosaic. Compile times on Metal are an M0-H4 number.

## Performance targets (Apple M1, 50 MP)

| Path | Target |
|---|---|
| Fit preview after open (classical, 1/4 res) | < 300 ms |
| Colour-only edit, viewport refresh | < 16 ms |
| 1:1 neural tiles visible on a 1440p viewport | < 1.5 s |
| Full neural export, JPEG | < 6 s per photo |
| CPU-only fallback export | < 90 s per photo |

These are targets; report measured values at each gate.

**CPU reference, measured (M1-12, 4-core x86-64, `cargo bench -p ym-gpu --bench cpu_stages`).** The machine was shared with other jobs (load average 13 to 17 on 4 cores), so wall times are inflated several-fold; CPU seconds are the dependable number. Whole classical chain R1 to R9 (LMMSE, bilateral, guided filter, RL with the Auto values, distortion + CA resample), 50 MP: 69 CPU-seconds (with LMMSE as the demosaic; the adaptive ratio default is 10.0 to 10.8 CPU-s per 50 MP at that stage against LMMSE's 8.2 to 8.6, RA-05, so about 2 CPU-s more), i.e. about 17 s on four idle cores if it scales (measured wall 103 s under that load). Per stage at 50 MP, CPU seconds: normalise 0.35, vignetting 1.3, gains 0.05, highlights 2.2, demosaic (LMMSE) 9.2, bilateral 19.4, colour guided filter 9.7, detail 0.9, RL (n = 3) 12.1, lens resample 9.9. The CPU-only fallback target (< 90 s per photo) therefore looks met with a wide margin on four cores; confirm on an idle machine and on the M1.
