# 05 · Raw processing (mosaic to scene-linear camera RGB)

Crates: `ym-core` (orchestration), `ym-gpu` (kernels), `ym-ml` (network), `ym-noise` (σ map). This document describes the raw chain R1 to R9: what each stage does, how the demosaic and the denoise are chosen and measured, how the chain is tiled, and which stages run on the device. All stages run in scene-linear float, in tiles on the GPU, with a CPU reference for tests and for machines without a usable GPU.

**CPU reference.** `ym-gpu::cpu` holds the reference implementation of R1 and R3 to R9 (one module per stage, `cpu::chain` for the whole chain, whole frame or one tile). The WGSL kernels are parity-tested against it. Conventions: `f32` storage; `f64` for positions, spline evaluation and anything that accumulates; images are *planar* (all R, then all G, then all B) because the GPU reads a plane as one coalesced range and R7 to R9 treat planes separately; every buffer carries its position in the full frame (`Placement`) so tiles give the whole-frame result; borders mirror (parity-preserving) except R9, which clamps. Inputs are plain slices and a 2×2 `Cfa`; the mapping from `ym_raw::RawImage` is in the module documentation of `ym-gpu::cpu`.

## Order

| # | Stage | Notes |
|---|---|---|
| R1 | Black subtract, white normalise, clip mask | per CFA position, from SR2 levels |
| R2 | Noise estimate and illuminant estimate | on binned planes / the 1/8 preview (`docs/06`, `docs/02`) |
| R3 | Vignetting correction | Sony 0x7032 |
| R4 | Initial white-balance gains `g0` | from the illuminant estimate |
| R5 | Highlight reconstruction on the mosaic | opposed-channel method |
| R5b | Lateral CA on the mosaic | Sony 0x7035; red and blue photosites resampled from their own colour, full-resolution path only (§R9) |
| R6 | Demosaic + denoise | the classical path runs everywhere (no network is trained): the adaptive ratio demosaic, then the single-frame denoise of `docs/algorithms/05-single-frame-denoise.md` (method A, block matching and 3D DCT hard thresholding in a display-like working encoding), then its false-colour step and its coarse colour pass. The binned fit view and thumbnails run a light bilateral denoise instead. The neural path (export, 1:1) is specified below and waits for a trained network |
| R7 | Detail controls | with the single-frame denoise the three controls set that stage (Luminance and Colour the thresholds, Detail the blend with the noisy image), and of R7 only the colour guided filter runs, where the luma alternates (the false-colour step). The bilateral path runs the colour noise reduction and the detail re-injection |
| R8 | Capture sharpening | Richardson–Lucy with a Gaussian PSF (default), or diffraction deconvolution from the f-number and pixel pitch (internal switch, not the default; below) |
| R9 | Distortion resample (and the lateral CA below full resolution) | Sony 0x7037 (0x7035 on the binned preview) |

Output: camera RGB balanced with `g0`, white = 1.0 before gains, consumed by the colour pipeline (`docs/02`, stage C1).

Output sharpening (`docs/algorithms/04-output-sharpening.md`) is not a raw stage. It is the last stage of every display-referred picture, after C12 and before C13, at the size the picture is shown or written (`docs/01` *Output sharpening*, `docs/09`); its halo is in the table below for completeness.

## R1 · Normalise

`x = (raw − black[c]) / (white[c] − black[c])` per CFA position. Negative values stay (they carry noise statistics); clamp at −0.05. Clip mask: `raw ≥ white[c] − 4·qstep` (or `≥ 0.995` normalised where qstep is absent). The mask travels with the image to R5, R6 and C7. Black and white levels are indexed by CFA *position* `2·(y&1) + (x&1)` of the active area (for the all-RGGB Sony bodies that is R, G1, G2, B); a tile uses the frame parity of its photosites. `Levels::from_rggb` maps values in the R, G1, G2, B order of the SR2 tags onto the positions of any pattern phase (a frame cropped to an odd origin starts with GRBG, say). `qstep` present with value 0 (lossless files fed to the network as a zero plane) means "clipped only at exactly the white level"; the 0.995 rule applies only when no qstep plane exists.

## R3 · Vignetting (0x7032)

Knots `v_i`, i = 0…n−1 (n = 16 for full frame, 11 for APS-C or a crop mode; both are one physical grid). Knot `i` sits at the normalised radius `r_i = (i + 0.5)/(n−1)`, where r = 1 is the half-diagonal of the active area (the last knot lies half a step beyond the corner). A knot gives the relative illumination the lens leaves at its radius: `G_i = 2^(0.5 − 2^(v_i·2^−13 − 1))`. Interpolate `G(r)` **linearly** between the knots (end values held outside them) and **divide** each photosite by `G(r)`, clamping `G` at 1e-4.

- Positive `v` means a darker corner (`G < 1`, a gain up to 181 at the largest encodable knot) and negative `v` a gain below one; a typical lens has `v` from 0 at the centre to a few thousand at the corner.
- The radius is that of the centre of a pixel, measured from the centre of the active area, over half its diagonal `hypot(width, height) / 2`.
- `ym_raw::LensTable::knots()` drops the stored count. The count of tag 0x7035 is 2n, not n.
- The reading is pinned against `darktable-cli` 4.6.1 (embedded metadata, algorithm 2, the module's default) run on synthetic Sony files (§Verifying lens corrections): the radial gain agrees with `VignetteProfile::gain_at` to 8e-5 (gate: 0.5%; `tests/cpu_lens.rs::vignetting_matches_darktable`).
- It holds on real raw data. The even part of the horizontal brightness profile of a sky band follows `G(r)` of the table on ILCE-7M4, ILCE-1 (three frames) and A6300, so the raw is not vignetting-corrected by the camera (`0x7031` = 257 or 272, `Auto`) and R3 does not correct twice.
- The Before view leaves R3 out (`docs/02` *The Before view*): a render for it runs the raw stages without this one (`RawParams::vignetting` off; the plan has no profile; the device's prep kernel gets no vignetting table), because the camera's own picture is not brightened at the corners by it. Nothing else of the chain changes for that view; the final picture, the thumbnails and the exports always have R3.

## R4 · Initial gains

`g0 = 1 / w_scene_initial` (green = 1), from the illuminant estimate at open. If the estimate fails, use the as-shot gains from SR2 0x7313. Gains are applied to the mosaic before R5 and R6 because both work better on balanced data. Later white-balance changes do not re-run R5–R9 (`docs/02` C1 applies a residual). The clip mask is not changed by the gains; a clipped photosite then sits at `g0_c` (times the vignetting gain), and R5 finds it through the mask, not by a threshold. SR2 0x7313 levels are multipliers (green about 1024), so `g0 = [R/G, 1, B/G]` with `G` the mean of the two green levels (`gains::g0_from_wb_levels`); from a scene white `w`, `g0 = [w_G/w_R, 1, w_G/w_B]` (`gains::g0_from_scene_white`).

## R5 · Highlight reconstruction (opposed channels)

Written from the published description of the opposed-channel method; no code of other projects is used.

1. Build a half-resolution superpixel image from each 2×2 quad: R, G = mean of the two greens, B, with a per-channel clipped flag. A superpixel's green is flagged clipped when either green photosite is; the estimate is written to the clipped green photosites only.
2. For each clipped channel `c` of a superpixel, the **opposed estimate** is the cube-root mean of the unclipped other channels over the 3×3 superpixel neighbourhood: `ŷ = (mean(x^(1/3)))³`. With no usable neighbour (all other channels clipped over the whole 3×3) the photosite stays at its value and step 5 decides what a fully clipped quad becomes.
3. **Global chroma correction.** For channel `c`, the reference superpixels are those with no clipped channel that have channel `c` clipped somewhere in their 3×3 neighbourhood, so a red lamp does not bias the blue offset. Over them, average `x_c − ŷ_c`, with `ŷ_c` computed as if `c` were clipped from the unclipped other channels of the neighbourhood. Add that offset to every estimate for channel `c`.
4. Reconstructed value: `max(original, ŷ_c + offset_c)`. Write it back into the mosaic photosites of that channel, keeping the clip mask so later stages know these values are estimates.
5. **Fully clipped quads.** R1 clips each channel at its own white and R4 then scales, so a quad whose four photosites are all clipped holds `[g0_R·v, 1·v, g0_B·v]` (`v` the vignetting gain), for example `[2.0, 1, 1.7]` for the as-shot balance of an ILCE-7M3. That is a colour cast, not a measurement: C7 scales by `f(n)/n` (n the largest channel) and keeps the ratios, so a neutral sun disk or lamp would render as saturated pink and darker than the neutral pixels just below it. Such a quad has no colour of its own, so all its clipped photosites are raised to the largest of them, a neutral at the brightest bound. The step-4 estimate can still lift a channel above that. A quad with one green still measured is not fully clipped and is left to step 4. The level is continuous with a neutral ramp just below the last clip (red at `g0_R`), and luminance is monotone through the clip. The rule looks only at one quad, so tiles and the whole frame agree, and with recovery switched off nothing changes. Tests: `tests/cpu_highlights.rs::fully_clipped` (a neutral ramp through the real R1-then-R4 order, neutral to 0.01 in sRGB code values and non-decreasing in luminance) and the unit tests in `cpu::highlights`.
6. `decode.highlight_recovery = false` skips R5; clipped values stay at their clip level, `g0_c` after R4 (they then render as white or a hue cast, which is the point of the switch).

**Tiles.** The offsets of step 3 are a global reduction. For tiles, accumulate `OffsetAccumulator`s over the tile cores in a fixed order, merge, and pass the same `ChromaOffsets` to each tile (`highlights::{accumulate_offsets, apply_offsets}`); applying needs only one superpixel (2 px) of context, and the halo table keeps the documented 4 px. Tiles start on even coordinates.

**Limits.** Because the offset is one additive constant per channel, calibrated where a channel has just clipped, it under-reconstructs cores that are many stops over the clip level: a source at 2.6× the clip level comes back at roughly 1.3× with a paler hue (synthetic scenes in `tests/cpu_highlights.rs`). Region chroma (chroma-only ΔE00 of the mean colour of the blown region against the unclipped surround, through the stand-in camera matrix in `cpu::metrics`) is within 4.7 of the surround in all ten synthetic scenes (up to 10.4 without recovery), and the hue at the clip boundary is within 13° of the truth for gentle falloffs (18° and 24° without recovery on the two scenes where it matters). For hard-edged sources (all channels clip within a few pixels) recovery changes the boundary hue only a little (37° and 67° against 39° and 69° without).

**Gate.** On 20 test photos with blown skies and lamps, no magenta or cyan fringes at the clip boundary in blind review, and the reconstructed region's chroma within ΔE00 5 of the surrounding unclipped area. The synthetic part of the gate is met; the blind review on the 20 real photos has not been done.

## R6 · Demosaic and denoise

### Neural (V1: no network is trained)

One U-Net does both (`docs/07-ml-models.md`). Per tile, inputs:

- packed Bayer planes (4 × H/2 × W/2), balanced with `g0`;
- σ map (1 plane, `docs/06-noise.md`), scaled by the Luminance control;
- quantisation-step map (1 plane; zeros for lossless files);
- clip mask (1 plane);

output: linear camera RGB at full resolution. Tiles overlap by half the network's receptive field, computed from the architecture (64 full-res px for the starting U-Net in `docs/07`), and are cropped, not blended. A test renders a frame tiled and whole and requires a max difference ≤ 1e-4. No weights exist (M2-H4), so this path is never taken today.

### Classical

The classical path runs everywhere today: the 100 % view, every export and R7's `Y_classical` on the bilateral path. It stays the fallback once a network exists (`decode.neural_demosaic = false` forces it everywhere, exports included). The fit view and the thumbnails at a reduction of 2 or more bin the mosaic (`docs/01`) and run no demosaic at all.

**Which methods exist, and which can be reached.** `ym_gpu::cpu::demosaic::Method` has five. **Method choice is not a user setting**: there is no settings field, no UI control and no CLI flag, and nothing is stored per photo. The renderer uses `DEFAULT_METHOD`. Tests and evaluation tools can force another method through the test-only switch `RenderOptions::demosaic` (in builds with the cargo feature `force-demosaic`, also the environment variable `YM_FORCE_DEMOSAIC`; `docs/algorithms/INTEGRATION.md` section 10).

| Method | Where it comes from | Reached by | Halo | Used for |
|---|---|---|---|---|
| Adaptive ratio (`AdaptiveRatio`) | `docs/algorithms/01-adaptive-ratio-demosaic.md`, written in Rust from the spec | **the default** | 13 px (11 without shadow matching; the scheduler always uses 13) | 100 % tiles, every export, R7's `Y_classical` |
| Menon (`Menon`) | port of colour-demosaicing (BSD-3) | the test switch only | 8 px | the reference of the comparisons |
| LMMSE (`Lmmse`) | our own implementation of the Zhang–Wu idea | the test switch only | 8 px | comparisons |
| Bilinear (`Bilinear`) | plain | the test switch only; also what a mosaic under 2 × 2 gets | 1 px | comparisons, a floor |
| Log-guided (`LogGuided`) | `docs/algorithms/02-log-guided-demosaic.md`, written in Rust from the spec | the test switch only | 5 px | a fast preview method; no render path uses it |

All methods handle the four Bayer phases and mirror at the borders. The adaptive ratio demosaic reads the gains `g0` and the noise model of the photo (its offsets and gates depend on them). Like every method it receives the *balanced* mosaic of R4 and R5 and undoes R4 itself, by dividing each photosite by `g0` of its colour inside `demosaic_with` (with unit gains that is the identity). A noise model that is missing or unusable is read as zero noise (K = T = 1 DN), so a render never fails for it (`docs/algorithms/INTEGRATION.md` section 10). How the algorithms of `docs/algorithms` plug into the chain: `docs/algorithms/INTEGRATION.md`; the gates of each algorithm: section 6 of its spec.

**Why adaptive ratio is the default.** The rule is that the method with the best PSNR becomes the default (the demosaic gate), checked on artefacts and on a blind look.

1. *PSNR in linear light* (the state R6 receives), over nine cells (procedural set, Kodak, McMaster; signal scales 1 / 0.1 / 0.01): mean 36.05 dB for adaptive ratio, 34.43 for Menon and 34.28 for LMMSE; best in 7 of the 9 cells. With the noise model scaled along with the signal instead of a fixed absolute model, it wins 5 of 9, the nine-cell mean is 35.45 (+1.02 dB over Menon), and on the six photographic cells it is level with Menon and LMMSE (35.72 against 35.84 dB). The procedural set (+3.2 to +3.3 dB over Menon) carries the aggregate under either protocol. On gamma-encoded Kodak and McMaster it is below Menon: the method is made for linear light.
2. *Artefacts.* At signal scale 1, zipper pixels are 20.3 % of the edge pixels against Menon's 39.1 % on the procedural set (24.2 against 34.3 % on Kodak, 26.6 against 41.8 % on McMaster), and false-colour pixels 4.3 against 7.6 % on Kodak and 6.3 against 11.2 % on McMaster.
3. *Blind look* at 1:1 crops of six real files (edges, texture, colour, shadows), with the labels shuffled per file (`docs/16`). The cost is about 1.5 to 1.7 times Menon's in the demosaic stage, +3 to +13 % of an export's CPU time (*Measured* below).

**Method notes.**

- **Menon** is a port of `colour_demosaicing.demosaicing_CFA_Bayer_Menon2007` (BSD-3-Clause, Copyright 2015 Colour Developers; licence text in the source and in `NOTICE`), checked against the package's output on fixtures (max difference < 3e-5, all phases, with and without the refining step).
- **LMMSE** is our own implementation of the Zhang–Wu idea, not a port: horizontal and vertical colour-difference estimates (from the `[−1 2 2 2 −1]/4` filter) are Wiener-smoothed over a 9-tap Gaussian window with local statistics (noise variance from the second-difference energy, `eps` 1e-5), fused with weights inverse to their error variances; red and blue come from colour-difference interpolation along the diagonal of smaller variation. Its fixed regularisation constants make it scale-dependent on scene-linear data.
- **Log-guided** meets its gate (within 1 dB of Menon on the synthetic set: −0.84 / −0.80 / −0.73 dB at signal scales 1 / 0.1 / 0.01; about half of Menon's CPU time) but no render path uses it: the fit view and the thumbnails at a reduction of 2 or more never demosaic, a `k = 1` thumbnail shares its chain and cache key with the 100 % view and the exports, and the method trails Menon by 3.4 to 3.6 dB on Kodak in linear light (`docs/algorithms/02-log-guided-demosaic.md` section 9.3).

### Denoise

- **Full resolution** (the 100 % view and every export; `frame_denoise::FrameDenoise`, `docs/algorithms/05-single-frame-denoise.md`). The balanced linear RGB is encoded with `W(x) = srgb(2^CAMERA_GAIN_EV · x)` (`denoise_space`), denoised by method A (`bm_dct`: block matching and 3D DCT hard thresholding) with the thresholds derived from the photo's noise model at middle grey (`kL` 3.5 and `kC` 8 standard deviations), and decoded. Then the false-colour step (`false_color`, R7 below) runs R7's colour guided filter where the luma alternates, which removes the demosaic's false colour on fine stripes that method A keeps, and the coarse colour pass (`coarse_chroma`) averages the colour of 4 × 4 cells within the photo's chroma noise, which removes the colour blotches of 16 to 64 px that method A's 8 × 8 blocks cannot see. On the synthetic measurement the render is 0.3 to 2.5 dB above the bilateral path at every ISO-like level from 100 to 12800 (`docs/algorithms/05-single-frame-denoise.md` *Measurement*). Methods B and C and the bilateral path stay behind the renderer's internal switch (`RenderOptions::denoise`, `DenoiseMethod`), like the demosaic methods above.
- **Reduced renders** (the binned fit view and thumbnails) and the switch's `bilateral` (`denoise::bilateral_opponent`): a 5×5 bilateral on the opponent space `(Y, R−Y, B−Y)`, spatial σ 1.5 px, range bandwidth `h = strength · √6 · σ_noise` on the Euclidean opponent-space distance (`√6 σ` is the RMS distance of two pure-noise pixels, so strength 1 gives a typical noise pair weight about 0.6). σ is the scalar or σ-map value at the centre pixel, scaled by `(L/L_auto)^1.5` like the network's σ; σ = 0 leaves a pixel untouched. Previews are therefore not noisier than the export.

### Measured

**Protocol.** `tools/eval/demosaic/gate.sh` runs `crates/ym-gpu/examples/demosaic_gate.rs` and `demosaic_timing.rs`; the protocol and the metric definitions are in `crates/ym-gpu/tests/common/demosaic_metrics.rs`, notes in `tools/eval/demosaic/README.md`. *Linear light* means the 8-bit sRGB images decoded with the sRGB transfer function first (the procedural set is linear already), mosaicked as RGGB, 10 px border excluded, mean of per-image dB, with signal scales 1 / 0.1 / 0.01 multiplying image and peak. The adaptive ratio demosaic gets unit gains and the nominal low-noise model of its spec (`a = 2e-5`, `b = 1e-8`, `q = 1/65535`), the same at every scale; the log-guided demosaic gets the zero model (`p = 1`, spec 02 section 6.4). On Kodak and McMaster the adaptive ratio numbers equal the C++ oracle's at all three scales, and the Menon numbers (scale-invariant) those of the `colour-demosaicing` package, to three decimals.

The sets are never committed. `tools/fetch/demosaic-sets.sh` downloads Kodak (24 images, the 500×500 version distributed with cszn/FFDNet) and McMaster (18 images, the copy in JingyunLiang/SwinIR) into `testdata/demosaic/{kodak,mcmaster}` at pinned commits and checks every file's SHA-256 (`tools/fetch/demosaic-sets.json`). Gharbi hard/moiré and PixelShift200 are optional: the gate reads them from `testdata/demosaic/{gharbi_hard,gharbi_moire,pixelshift200}` when they are there; `tools/fetch` has no recipe for them and no numbers exist for them.

That is **+3 to +13 % (+3 to +12 CPU-s)**; wall time of a real photo +1 to +6 s; memory the same (1.2 to 1.3 GB peak). `--jobs` counts photos in flight, not the threads of one photo.
- *Viewport and full render* (`perf.rs`, opt-level 3, 24 MP synthetic, best of three alternating runs at load 4 to 5): first frame of a 512 px tile at 100 % 767 ms against 671 ms, cold 1440 × 960 view of 12 tiles 2.7 s against 2.3 s, full-resolution render 22.2 s against 17.3 s: **+15 to +40 % of wall time** on the 100 % view and the full render, as the demosaic is one stage of several.
- *Determinism:* the JPEGs are byte-identical for `--jobs 1` and `--jobs 4` (ILCE-7M3, NEX-7, the synthetic, and three photos in one run) and for one thread against four (`RAYON_NUM_THREADS`, NEX-5N), and between the app path and `ym` (`src-tauri/tests/app_cli_parity.rs`, `crates/ym-cli/tests/parity.rs`).

A blind A/B page of 1:1 crops (nine real files and the 55 synthetic golden scenes that have a mosaic, randomised, key in `key.json`) is made by the gate: `testdata/demosaic_gate/index.html` (`tools/eval/demosaic/README.md`).

## R7 · Detail controls

`noise_reduction` resolves to `{ luminance L, color C, detail D }`, each 0–100. Auto values: `L_auto = clamp(10 · (1 + log2(ISO/100)), 10, 90)` (ISO 100 → 10, ISO 400 → 30, ISO 3200 → 60, ISO 25600 → 90; the number grows with ISO so the slider reads naturally), `C_auto = 50`, `D_auto = 50`. The Automatic card shows the resolved values ("Luminance 30").

| Control | Single-frame denoise (default, full resolution) | Bilateral path (reduced renders, internal switch) and network |
|---|---|---|
| Luminance `L` | `r = L / L_auto`: the luma threshold is `r` times the Auto one, 3.5 standard deviations of the photo's luma noise in the working encoding at middle grey | σ fed to the denoise or the network = `σ_est · (L / L_auto)^1.5`: the estimated noise at the auto value, 0 at L = 0 (the network demosaics without denoising), up to (100/L_auto)^1.5 × at 100. The network is trained across σ including 0, so this is a true strength control |
| Colour `C` | `c = C / 50`: the chroma threshold is `c` times the Auto one, 8 standard deviations of the chroma noise. Colour is also the strength of the false-colour step's guided filter and of the coarse colour pass (0 turns both off) | after the denoise: guided filter on the two chroma channels of an opponent space (Y, R−Y, B−Y), guided by Y. Radius `2 + 6·C/100` px at full resolution, ε from `σ_est² · (C/50)²` |
| Detail `D` | the blend with the noisy image, `100 · 0.15 (D / 50)²` percent (15 % at Auto, 60 % at 100, 0 at 0) | re-inject fine luma texture: `Y += β · (Y_classical − Y_net)` with `β = 0.15 · (D/50)²` (0 at D = 0, 0.6 at 100). `Y_classical` is the classical demosaic of the same tile, computed only when β > 0 |

The Auto values, the Automatic card and the sliders are the same on every path; the single-frame denoise's strengths are derived in `docs/algorithms/05-single-frame-denoise.md` *Controls*.

**False colour.** After the single-frame denoise, R7's colour guided filter runs at Colour `C` only where the luma has fine alternating stripes, where the demosaic leaves false colour (`cpu/false_color.rs`; `docs/algorithms/05-single-frame-denoise.md` *False colour*).

**Coarse colour.** After the false-colour step, a bilateral filter of the colour of 4 × 4 cells, with a weight as wide as `0.2 · C / 50` standard deviations of the photo's chroma noise at each cell's colour, removes the colour blotches of 16 to 64 px method A leaves on flat colours and leaves the luma alone (`cpu/coarse_chroma.rs`; `docs/algorithms/05-single-frame-denoise.md` *Coarse colour*).

**Colour guided filter and detail term** (`detail.rs`). `C = 0` returns the input untouched (the literal formula gives `ε = 0`, and a guided filter with `ε = 0` still smooths chroma noise that is uncorrelated with the guide). The radius is `round(2 + 6·C/100)` px (2 to 8). The guided filter (He et al.) runs two box filters in series, so its receptive field is **twice** the radius, up to 16 px: the halo table says so. `ε` is per pixel when σ is a map. Both operations leave the other half of the opponent space exactly as it was: the chroma filter touches only `R−Y` and `B−Y`, the detail term adds the same delta to all three channels. In the classical path the "network output" is the denoised image and `Y_classical` the plain demosaic before the denoise, so Detail puts back a fraction of what the denoise removed.

## R8 · Capture sharpening

Two methods exist and exactly one runs per photo (either/or; stacking them is an open evaluation option, `docs/algorithms/03-diffraction-deconvolution.md` section 7.1 item 8): `CaptureSharpen::{RichardsonLucy(SharpenParams), Diffraction(DiffractionParams)}` in `Chain` and `Stage::Sharpen`, each with its own halo (table below). R8 runs at full resolution only (the 100 % view and exports, and the rare thumbnail made at a reduction of 1), after R7; the binned fit view and the thumbnails made from binned images are not sharpened by it.

**R8 is off for a DNG** (`docs/09` "What a DNG carries"): both renders of a DNG, the raw pixels and the preview, run with R8 off (`RawParams::without_capture_sharpening`, set by `Job::without_capture_sharpening` for `FullTarget::DngLinearAwg4` and `DngPreview`: amount 0 and no diffraction controls, so `capture_sharpen()` is `None` and the chain, on the CPU and on the device, has no sharpening stage). It is a render-time switch of the internal chain parameters, not a setting: Detail › Sharpening says nothing to a DNG, the key of the cached chains and tiles changes with it (a render with R8 off never reads a chain made with R8 on), and JPEG, TIFF and PNG are unchanged. The adaptive ratio demosaic's own shadow step (`shadow_sharpening`, part of R6) stays on.

| Method | Default | Reached by | Controls |
|---|---|---|---|
| Richardson–Lucy, Gaussian PSF | **yes** (`DEFAULT_CAPTURE_METHOD`) | every photo | the Sharpening card's Amount and Radius, Auto from the ISO and the f-number |
| Diffraction deconvolution (`docs/algorithms/03-diffraction-deconvolution.md`) | **no** | the internal `PhotoSource::capture_method`, set by tests and evaluation tools only: no settings field, no UI control, no CLI flag | none of its own: the PSF comes from the f-number and the pixel pitch, and Amount and Radius do not act on it (strength 1; the mapping of spec 03 section 2.5 is not made) |

**Selection rule** (`ym_core::pipeline::raw`: `CaptureMethod`, `DEFAULT_CAPTURE_METHOD`, `pixel_pitch`, `diffraction_params`, `RawParams::capture_sharpen`). Richardson–Lucy runs unless the photo was given the diffraction method *and* the stage is active for it, which takes three things: an f-number from 1 to 50 (`RawMetadata::f_number`; missing, 0 and NaN count as none), a pixel pitch of 0.5 to 20 µm, and a plan that passes the gate of spec 03 section 3.1 for the photo's gains and noise model. The pitch is `1000 · sensor_width_mm / active_width_px` from the camera registry (`data/cameras/registry.json`, 27 of its 28 bodies, from the makers' published figures, `docs/03`), else `43266.6 / (crop · √(W² + H²))` µm from the EXIF crop factor `focal_length_35mm / focal_length_mm` (about 2 % high on APS-C), else none. A camera-processed reduced file (Lossless M or S) takes the registry pitch with `scale = frame width / active_width_px`. In every other case, including a stage that turns out inactive, R8 is Richardson–Lucy with the resolved Amount and Radius (and nothing when that Amount gives no iteration).

### Richardson–Lucy (the default)

Deconvolution on linear luminance with a Gaussian PSF, written from the published description of the method.

- `sharpen` resolves to `{ amount A 0–300, radius ρ 0.3–2.5 px }`. Iterations `n = round(A / 30)` (0–10), PSF σ = ρ at the centre and `1.25ρ` in the corners (linear in r²).
- Auto: ρ = 0.8 (0.7 at f/8 and above, 0.9 below f/2); A = 120 at base ISO falling linearly in `log2(ISO/base)` to 60 at ISO 12800.
- Applied to luminance only; the result adds `Y' − Y` to all three channels, so chroma is untouched.
- The PSF is truncated at `ceil(3σ_max)` and varies slowly, so the forward blur and its transpose are both gathers with the kernel of the pixel being written, separable (horizontal then vertical), with kernels interpolated from a 33-level bank between `ρ` and `1.25ρ`.
- Damping (Lucy-style): the correction ratio `d/e` becomes `1 + w·(d − e)/e` with `w = r²/(r² + σ_n²)`, `r = d − e`, `σ_n` the luminance noise σ. Residuals well below the noise (flat areas) get `w ≈ 0`; structure gets plain RL.
- Each iteration blurs twice, so the exact dependency radius is `2·n·ceil(3σ_max)` (24 px for the Auto values n = 4, ρ = 0.8). The scheduler caps it at 24 px; beyond the cap (A near 300) tiles differ from the whole frame by about 2e-7 on photographic content.

### Diffraction deconvolution (not the default)

Luma only, no iteration. It plans one polychromatic Airy-pattern PSF per frame from the f-number and the pixel pitch (461 to 619 nm; kernel radius `R` ≤ 7 px, and a Gaussian of radius `r_G` ≤ 8 px for a high-pass), then fits three coefficients per pixel (a dark layer, a bright layer and the high-pass) by weighted least squares over a 9 × 9 window, with weights from the inverse noise variance and a penalty near clipping. The result is gated against the noise, averaged over 5 × 5 and carried into RGB as a capped ratio (gain at most 1.5). The port follows the C++ oracle operation by operation: all 13 image vectors are bit-identical, the planner agrees to 1.3e-8, tiles with the halo `10 + R + r_G` (at most 25 px, **not** capped at Richardson–Lucy's 24) equal the whole frame bit for bit, and 1 thread equals 4. Cost on the CPU: about 0.5 to 1.0 s per megapixel on four loaded cores, so 30 to 60 s for a 60 MP frame; the device kernel is in *GPU stages* below.

## R9 · Lens geometry (0x7037 distortion, 0x7035 CA)

One resample, bicubic (Catmull–Rom), from the output pixel position to the source position:

- Distortion knots `d_i` → factor `F_i = d_i·2^−14 + 1`, knot `i` at the radius `r_i = (i + 0.5)/(n−1)` (half-diagonal = 1), linear interpolation between knots. Source radius `r_s = r · F(r)`.
- CA knots: the tag holds 2n values, red then blue. `K_c,i = ca_i·2^−21 + 1`, same knot radii and interpolation. Red and blue sample at `r_s · K_c(r)`; green at `r_s`.
- **Where the CA is applied.** At full resolution the CA is not part of the R9 resample but of **R5b, on the mosaic, before R6** (`lens::correct_mosaic_ca`): every red and blue photosite takes the value its own colour has at the position where green shows the same feature (Catmull–Rom on the lattice of that colour, shift `s_c(r) = r_s·(K_c(r) − 1)` along the radius; green is never touched), and R9 then moves the three colours by the distortion alone. Below full resolution (the binned fit view and the thumbnails) the CA stays in R9: binning averages every colour from its own photosites, so nothing has pulled red and blue towards green there. The reason and the evidence are in "Real files" below.
- `decode.lens_corrections = false` skips distortion and vignetting; `decode.chromatic_aberration = false` skips CA only.
- After distortion correction, crop to the largest rectangle of valid pixels with the original aspect ratio (the "auto crop"), before the user's crop. The crop is that of the whole geometry, CA included, wherever the CA is applied.

The table formats and factors are those documented by independent decoders (darktable, exiftool), not a Sony document; the checks against real files are in the next section.

### Resample details

- The knot positions and the linear reading are those of darktable 4.6.1 and are pinned against it: the positions of 373 dark-line centres in its distortion-only render agree with `LensGeometry::source_position` (after undoing its zoom) to 0.002 px rms and 0.009 px at most, the three colour planes of its CA-only render to 0.003 px rms (gate: 0.2 px; `tests/cpu_lens.rs::{distortion,lateral_ca}_matches_darktable`). darktable does not crop: it zooms the corrected image by the largest value of `F(r)·K_c(r)` between the half-short-side radius and the corner (200 samples, three planes) so that no black corner is left; our crop and its zoom show the same mapping (`tools/lens/lens_model.py: darktable_zoom`).
- Coordinates are continuous (pixel `i` covers `[i, i+1)`, centre `i + 0.5`); the frame centre is `(W/2, H/2)` and `r` is the distance over half the source frame's diagonal. `K_c(r)` is evaluated at the *output* radius `r` and multiplies the same direction as `F(r)`: red and blue sample at `centre + (p − centre)·F(r)·K_c(r)`, green at `centre + (p − centre)·F(r)`.
- The CA tag needs an even count of at least 4. A source position is valid when it lies in the hull of the pixel centres, `0.5 ≤ s ≤ size − 0.5`; taps beyond the buffer edge replicate the edge pixel.
- The auto crop is the largest centred rectangle whose pixels sample valid positions in all three channels, with the frame's aspect ratio and even width and height (a 10% barrel correction on 600×400 crops to 552×368); the whole frame when nothing needs cropping.
- The resample works on any output rectangle of the cropped image; `LensGeometry::source_rect` gives the source rectangle it needs (bounding box of all channels' positions plus the Catmull–Rom support and one pixel). With `lens_corrections = false` the distortion tag is ignored, with `chromatic_aberration = false` the CA tag is.

### Real files (CA is corrected on the mosaic)

On real files the tables describe the raw correctly, but applying the CA table after the demosaic over-corrects (on ILCE-5000, 6300 and 7M3, camera setting `Auto`, it raised the measured red/blue misregistration from 0.04 to 0.2 px to 0.3 to 0.7 px). The cause is the order of the stages, which is why the CA is corrected on the mosaic (R5b).

**Method** (local files only, nothing committed; `tools/lens/real_eval.py`, `ca_measure.py`, `fit_ca_readings.py`, `jpeg_geometry.py`, `ca_xcorr.py`, outputs in the git-ignored `testdata/lens-eval/`). `ca_measure.py` fits a signed radial shift of red and blue against green on blocks of 96 px by Gauss–Newton on high-passed planes (σ 5 px): `X(p) = a·G(p − s·u)`, `u` the unit vector away from the centre, positive `s` outward. On the **mosaic** it uses the photosites of the colour itself and the bilinear green, no demosaic (checked on synthetic mosaics with a known shift, `ca_measure.py selftest`: error below 0.04 px plus 25 % of the shift, no shift found where there is none, also with a 30 % colour drift; red and blue are read 8 to 30 % low, so the amplitudes fitted are lower bounds). The same fit runs on RGB images (a demosaic, darktable's `--dump-pipe lens` PFMs, the camera's own JPEGs, the full-size `JpgFromRaw` of ILCE-7M4 and ILCE-1). The table's own prediction for the same quantity is `r_g·hd·(K_c(r) − 1)` with `r_g` the green's source radius and `hd` the half-diagonal in pixels. `ca_xcorr.py` shares no code with it (block cross-correlation of band-passed planes, a parabolic sub-pixel peak, projection on the outward direction; its self-test recovers synthetic shifts to within about 5 % up to 2.5 px).

**Findings.**

1. *What is in the files* (`exiftool -a -G1 -u`). The raw sub-IFD holds the three tables of the recorded image: `n` = 11 knots for an APS-C lens or for a full-frame lens in APS-C crop mode (ILCE-1 here), 16 for full frame, the CA tag leading with `2n`. Eight files carry the three tags there (A5000, A6300, A7 II, A7 III, A7 IV, ILCE-1 ×3). The NEX-5N and NEX-7 only carry them in the encrypted SR2 sub-IFD, which `ym-raw` does not read for lens tables ("Lens data: none"); the A300 and A500 have none. A7 IV and ILCE-1 write `0x7031 = 272`, the others 257 (`Auto`) or 256 (`Off`, the A7 II). The maker note holds a second copy with 16 slots (11 used for APS-C): the CA values are the raw copy before it was rounded to multiples of 128, the vignetting knots are identical, and **the distortion knots are 1.113 times the raw copy** on all eight bodies that have both (`DistortionCorrParams`); the render reads the raw copy. The 11 and 16 knots lie on one physical grid, `(i + 0.5)/15` of the full-frame half-diagonal, which is `(i + 0.5)/10` of the APS-C one for a crop factor of 1.5: `(i + 0.5)/(n − 1)` over the half-diagonal of the recorded image is right for both.
2. *The raw is not corrected, and the table describes it.* Measured on the mosaics, the sign, the shape and roughly the size of the table are there, on the bodies set to `Auto` as on the A7 II set to `Off`. The rms over all blocks of measured minus predicted (8 files, `fit_ca_readings.py`) is 0.13 to 0.37 px as read, against 0.31 to 1.70 with the sign flipped and 0.29 to 0.91 with red and blue swapped. Knot radii at `(i + 0.5)/(n − 1)` fit as well as the alternatives on the full-frame bodies and better on the APS-C ones; a free knot-radius scale lands on no consistent value, so none is applied; `K` at the source instead of the output radius makes no difference (within 0.01). The camera's own corrected JPEGs say the amplitude is right for Sony's pipeline: the full-size JPEG of the A7 IV leaves 0.00 to 0.03 px of red and 0.00 to 0.16 px of blue shift at every radius (the table predicts up to 0.72 and 1.20 px). No tag says "already corrected" for CA: `0x7034` is 1 on the files whose raw still carries it.
3. *Distortion and vignetting are right.* The camera's JPEG against the raw (block matching of the green, then `rho_raw = ζ·rho_j·F(ζ·rho_j)` fitted for the zoom `ζ` and the table amplitude `α`): the raw copy of the distortion table gives `α` = 0.998 on the A7 III and 1.03 on the A5000 (the maker-note copy 0.90 and 0.92: not used), about 0 on the A7 II whose distortion setting is `Off`. Vignetting: §R3.
4. *A green-guided demosaic absorbs about half of the CA.* The mosaic keeps the CA; after R6 a colour-difference or ratio demosaic has pulled red and blue towards green. A7 II, red shift at r = 0.45 and blue at r = 0.93: bilinear (each colour from its own photosites) 0.60 and 1.88 px, Menon 0.31 and 1.55, LMMSE 0.30 and 1.49, adaptive ratio 0.34 and 1.56: 51 to 57 % of the red and 79 to 83 % of the outer blue stay. Applying the full table to what is left over-corrects: on the A6300 it turns a red residual of −0.20 … −1.20 px (inward) into +0.28 … +0.50 (outward), a change of sign of about the size of the table. darktable 4.6.1 does the same on the same files with its own demosaic. Correcting on the mosaic (R5b) removes the interaction.

**Measured with R5b.** rms of the radial shift over r ≥ 0.25, red / blue, px, by `ca_xcorr.py` on the output of the shipped chain (`lens_eval_dump --chain`: R1, R3, R4, R5b, adaptive ratio demosaic, R9). The tangential rms, which a lateral CA does not have, is the noise floor (0.10 to 0.15 on most files, 0.15 to 0.22 on the A7 III, 0.26 to 0.37 on the A5000), so differences of 0.1 px and less mean nothing:

| file | no CA correction | R5b (the render) |
|---|---|---|
| ILCE-6300 | 0.67 / 0.25 | **0.17 / 0.12** |
| ILCE-5000 | 0.59 / 0.51 | **0.30 / 0.38** |
| ILCE-7M2 | 0.36 / 0.40 | **0.21 / 0.22** |
| ILCE-7M3 | 0.14 / 0.28 | 0.16 / 0.26 |
| ILCE-7M4 | 0.28 / 0.17 | 0.18 / 0.18 |
| ILCE-1 (A1M01749) | 0.28 / 0.24 | **0.11 / 0.20** |

- With `ca_measure.py` on five files R5b leaves ILCE-5000 0.07 / 0.09, ILCE-6300 0.17 / 0.09, ILCE-7M2 0.16 / 0.28, ILCE-1 0.03 / 0.15 and ILCE-7M4 0.16 / 0.19 px (no correction: 0.58 / 0.32, 0.64 / 0.25, 0.27 / 0.68, 0.21 / 0.19, 0.32 / 0.18).
- After R5b no band of any file is further than 0.21 px from zero except the outermost blue band of the A7 IV (+0.38). Two files do not gain over no correction, the A7 III and the A7 IV blue: the green-guided demosaic had already carried the CA of the *edges* over to green, which is all these estimators see; what R5b changes there is the registration of the smooth colour ratio the demosaic interpolates, and no edge-based estimator measures that.
- Synthetic files made consistent with their own tables (`tests/cpu_lens.rs::mosaic_ca`): with Menon, LMMSE and adaptive ratio R5b leaves 0.07 / 0.06, 0.03 / 0.03 and 0.05 / 0.05 px (no correction: 0.45 to 0.49 / 0.35 to 0.40), and the PSNR against the scene is about 3 dB above that of correcting after the demosaic; with bilinear, which does not follow green, the two orders are within 0.05 px and 0.5 dB.
- The crops of `tools/lens/strip.py` show the fringes gone and no visible softening; the gradient energy of the planes in three 800 × 600 windows away from the centre of the A6300 is 4 to 38 % lower than without any CA correction (the fringes' own energy is part of it); at the centre it is unchanged (1 %).

**Limits.** What is left on real files is the table's own error. The amplitude of a table is known to about a factor of two on most bodies (A6300: red 0.6 to 0.8 of the table, blue 0.8 falling to 0.3 towards the edge); on the A7 IV the blue is read about three times too strong (`α` = 0.27) and overshoots by 0.4 px at the edge, and the A7 II's outer blue leaves 0.55 px. A body whose table cannot be trusted needs its own flat-field or test-chart measurement (V2).

**Stage-order consequences.** R5b needs `max |shift| + 6` px of context (`lens::mosaic_ca_halo_px`, even, in `Stage::MosaicCa`); tiles reproduce the whole frame bit for bit and do not depend on the thread count (tests). Its cost is one Catmull–Rom pass over the red and blue photosites, below the noise of the render time (A5000, 20 MP, dev-profile build on a shared machine: whole render 27 s with it, 33 s with `--no-ca`). The adaptive ratio demosaic's CA-aware path (`docs/algorithms/01`, section 3.6) is not reached from the chain, because the chain hands it no curves when the lens corrects its CA on the mosaic; the path and its tests stay for a geometry that keeps its CA in R9. The synthetic golden set has neutral CA tables, so R5b has nothing to correct in its files; real-file renders are what it changes.

### Verifying lens corrections (no test shoots)

- **darktable-cli as an oracle** (run as a separate process in CI, never linked or copied; it is GPL): `tools/lens/run_oracle_suite.sh` writes synthetic Sony files with known lens tables (`tools/lens/lensgen`: a flat field, vertical and horizontal lines; the raw data itself is undistorted), runs `darktable-cli` with only the lens module added (embedded metadata, one correction per render) and saves the module's own float input and output (`--dump-pipe lens`; a TIFF render mixes the planes through the camera matrix and smears lateral CA). Callers cut strips with this halo (`docs/09`, `docs/01`) |

The scheduler computes a tile's required input rectangle by walking the stages backwards (`ym_gpu::cpu::tiling::required_input_rect`); mosaic-domain rectangles start on even coordinates. The receptive fields of the demosaic methods are measured by perturbing single photosites (`tests/cpu_demosaic.rs`). Tiled-versus-whole tests (`tests/cpu_tiling.rs`, `cpu::chain`) give a maximum difference of 0 (pointwise stages bit-exact; the others also 0 in practice, 2e-7 for RL beyond its cap), against a limit of 1e-4. The halos of the raw-algorithm stages are checked against the code's declared ones (`Method::halo()`, `CaptureSharpen::halo_px()`, `SharpenPlan::halo_px`) and each is pinned by a tiling test: tiles with exactly that halo equal the whole frame bit for bit.

### GPU tiling

`ym_gpu::tiles::TilePlan::new(width, height, tile_px, stages)` cuts the frame into cores of 1024 or 2048 px (`tiles::TILE_SIZES`; `kernels::raw::recommended_tile_px` picks the largest that fits half the memory budget with two tiles in flight and one storage binding) and gives each tile its `compute` rectangle from `required_input_rect` over the stages (the table above, so the halos are the measured ones, mosaic origins even).

- The kernels run over the whole compute rectangle and mirror at its edge like the CPU reference; only the last kernel is restricted to the core, so the outer ring (one halo wide) is never read back. Tiles are cropped, not blended, and the tiled result equals the whole-frame result bit for bit for the pointwise and bilinear stages (`tests/gpu_spike.rs`, `tests/gpu_pipeline.rs`: 0.0 difference, gate 1e-4).
- Tile rows complete in raster order and `kernels::raw::RowStreamer` hands the encoder a full-width band as soon as the last tile of a row is in.
- The device thread never pre-empts a running job (`ym_gpu::queue`), so an export that must not hold up viewport frames is cut into jobs at Export priority, one per tile row or per tile (`TilePlan::tile_rows`, `TilePlan::tile_range`: same frame and tile numbers, fewer tiles; one `RowCollector` or `RowStreamer` on the full plan collects the pieces). `tests/gpu_pipeline.rs` shows a Viewport job running between the rows of such an export, with pixels equal to the single-job run.
- `GpuContext::warm_up` compiles every kernel at start-up, so the colour chain's large shader does not land on the first viewport frame. `KernelId::ALL` is the order a cold start needs the kernels: the fit view of a mosaic photo (R1 to R5, the binning, the sigma, the denoise, R9, the copy), the view stages (sampler, colour, output sharpening, C13), the full-resolution chain (demosaic, denoise, R7, capture sharpening, diffraction), the export tail's resize, and last the spikes and the probe, which no render uses. `KernelSet { View, Raw, Tail, All }` and `warm_up_set` compile a group at a time.
- A plan whose tiles lack the demosaic's 1 px of halo, or a raw frame whose pattern differs from the parameters, is refused with `GpuError::InvalidInput` instead of rendering seams or a wrong Bayer phase. Row strides are even, so two f16 samples share a 32-bit word and one thread writes both.
- **Image planes are f32 in memory by default** (`docs/17-gpu.md` section 2): `StoragePreference::Auto` resolves to `StorageMode::F32` on every device (an adapter with `SHADER_F16` does not change it), and the f16 modes are reached only through `StoragePreference::Force` for the legacy kernels and their tests. Every parity test passes in all three modes, with every pool buffer NaN-filled first (poison mode, below).

### The GPU path

Every image stage after decoding runs on the wgpu device, in the app and in `ym`, exports included, each behind the device policy with the CPU reference as its twin (contracts in `docs/17-gpu.md`):

- the adaptive ratio demosaic on a `GpuChain` that takes the same `Chain` and `TilePlan` as the CPU;
- the stages after it (the bilateral denoise, R7, Richardson–Lucy, or method A with its false-colour step and coarse colour pass, and the diffraction deconvolution), the raw front (R1, R3, R4, R5, R5b), R9 and the binned fit-view path;
- the view stages (geometry sampler, colour chain C1 to C12 with a persistent table set, output sharpening, C13 with dither) as one device job per frame;
- the export tail (Lanczos-3 resize, strip sharpening, C13 into bands that the CPU encoders pull) and the device-resident handoff between them.

The contracts:

- image planes are f32 in every mode;
- the logical tiles are the CPU's constants (512 px view, 1024 px export) and a compute rectangle above 2.5 Mpixel is split by a rule that depends on the rectangle alone (lavapipe's storage binding is 128 MiB and the adaptive ratio scratch is 48 bytes per pixel), so no tile depends on the device;
- a pixel depends only on its receptive field, with no float atomics, no subgroup operations, fixed-length sums and absolute coordinates, so tiles equal the whole frame bit for bit on the GPU and one machine gives the same bytes in the app and in `ym`;
- pooled buffers are filled with NaN in tests so that a kernel cannot read what an earlier job left;
- a GPU error re-renders the whole photo on the CPU with a note, never one tile; `--require-gpu` fails the photo instead.

Golden hashes pin the CPU reference (`ym render --cpu`) and GPU renders are compared with those pictures in a separate strict job. On the CPU stay the decode and the 1/8-preview estimates, the R5 offsets of the full chain, the methods behind the test-only switch (Menon, LMMSE, bilinear, log-guided), methods B and C of the single-frame denoise, camera-processed files, the histogram counts, the DNG white and the encoders; the encoder is what is left of an export's CPU time. The performance targets below are for the Mac (M0-H4); no GPU speed is claimed.

**Fast-math on Metal.** Metal's compiler runs with fast-math (wgpu-hal sets only the language version and `preserveInvariance` on `MTLCompileOptions`), which re-associates and contracts. Each kernel therefore forms every product, sum and difference that feeds a decision or the output behind the runtime-zero barrier `opaque` (an OR, never an XOR: an XOR applied twice cancels, `docs/17-gpu.md` K8), and every quotient that must match the CPU is corrected from its exact remainder (`div_exact`; `hl_super`'s mean of one or two photosites is a multiplication by the exact reciprocal). The decisions were checked without a Mac by compiling the same sequences of operations with clang `-O3 -ffast-math -ffp-contract=fast -mfma -mrecip` against strict `-O2 -ffp-contract=off`: R1, R3 and R4 with the clip decisions (3 million cases: 349,062 differ without the barrier, 0 with it), the cube root (500,000 cases: correctly rounded in all of them for start errors up to 3e-7), the compensated reduction (20,000 trees of 256 pairs: 12,082 differ without the barrier, 0 with), the lattice sums of `bin`, the 5 × 5 box of the σ plane and the Catmull–Rom sample of R9 (0 differ with the barrier). Other points that came out of the same checks: the luma pass of the diffraction kernel bounds every finite input sample (about 15 times white), so no product can overflow in any evaluation order; the log-guided reconstruction `x * (a / b)` is written `(x * a) / b` behind barriers; the tie vectors of the adaptive ratio kernel are decisions that rounding noise settles, so Metal has its own bound for `edge_knight` (80, twice the Metal measurement). Not modelled: Metal's `sqrt`, `exp2` and `log2` (the cube root's start and the double-float square root's start tolerate a relative error of 1e-6, the Newton steps correct them). The tests carry one bound per case for every adapter (twice the value first measured on lavapipe, `docs/17-gpu.md` section 12), and every bounded test prints its measured value on a line of its own, so the Metal log carries the numbers; a Metal column is added only when a Metal run shows a difference inherent to `f32`.

**Not on the device yet.**

- Menon, LMMSE and bilinear demosaics, methods B and C of the single-frame denoise, and the neural path have no device kernel. A photo that selects one of them through an internal switch runs its raw chain on the CPU.
- The refinement of the noise model (`docs/06-noise.md`) runs on the CPU.
- A Metal-specific compile of the kernels with fast-math off. wgpu 30 has `Features::PASSTHROUGH_SHADERS` with `ShaderInput::Msl` (source compiled with default options, so the source must carry `#pragma METAL fp math_mode(safe)` and `fp contract(off)`, MSL 3.2, macOS 15) and `MetalLib` (a `.metallib` built offline with `xcrun metal -fno-fast-math`). Both need a Mac to build and to test; they are the escape hatch for a kernel that the barriers do not make safe.
- Recording cost structures (`UniformArena`, `BindGroupCache`, `ReadbackRing`) are not built: they are worth building only if the CPU time of recording shows it (`docs/17-gpu.md` section 3). Recording one dispatch (a uniform buffer from the pool, a queue write, a bind group, a compute pass) takes 66 to 67 µs on lavapipe; a chain tile of 248 × 186 records 42 dispatches, which is 1.0 % of its 273 to 279 ms. On Metal the tile takes milliseconds and the share may be several times larger: `what_recording_costs_per_dispatch_and_per_tile_is_measured_for_the_arena_decision` prints the same lines (as GitHub annotations on the runners), and the Mac session (M0-H4) decides from them.
- Kernel compile times and all GPU speeds on Metal are M0-H4 numbers.
- The σ plane is one whole-frame kernel and the longest single step of the reduced group on lavapipe; it is not split further.
- The stages after the demosaic are not split. A demosaic core above `MAX_PHYS_AREA` (a corner tile of a strong lens) is put together on the host and uploaded once more, and the largest binding of the stages after it is the guided filter's six planes, 24 bytes per pixel of the compute rectangle, which fits a 128 MiB binding up to 5.6 Mpixel; on a device with that binding a larger rectangle is refused as too large and the photo renders on the CPU (Metal's binding is 2 GiB).

### The adaptive ratio demosaic in the render

`ym_gpu::chain::GpuChain` steps the very `Chain` and `Prepared` the CPU runs, through the tile stepper `Chain::begin_tile` / `TileRun` (the CPU's own `run_tile` is a loop over it, bit for bit): R1 to R5b, the R4 undo of the balanced entry, the CA curves and the noise model (`Chain::noise_dn`, `cpu::chain::demosaic_inputs`) are the CPU's own code, so the device cannot be given other numbers than the CPU. A demosaic core whose padded plane is above `MAX_PHYS_AREA` (2.5 Mpixel; the scratch is 48 bytes per padded pixel with shadow matching, 120 MB against lavapipe's 128 MiB binding) is cut by a rule that depends on the core rectangle alone (`split_core`: the longer side in halves, recursively), never on the device, so a split core equals the unsplit one bit for bit (tested down to a few hundred pixels). A mosaic below 2 × 2 photosites is a CPU stage. The range of stages that ran on the device is a `StageRange` in the render report. `GpuStages::RAW_CHAIN` is run by every policy that uses the device: `on` and `require` run every stage, and `auto` runs the signed-off stages (`GpuStages::SIGNED_OFF`), which today is every stage (`docs/17-gpu.md` section 1).

**Faults and cancellation.** The policy is per photo: a device error during an export re-renders the whole photo on the CPU with a note (never a photo of both), a viewport tile re-renders that tile on the CPU with a note, and the photo stays on the CPU from then on; `require` fails the render with `RenderError::Gpu` (export error kind `gpu`). A shader that does not compile switches the raw chain off for the process; an out-of-memory or a too-large buffer is tried once more after the buffer pool is trimmed. All device jobs of a render carry the render's cancel token and one priority (Export, Viewport, TileNeural or Thumbnail, never mixed in a render); going to another photo drops the photo left's device jobs that are still queued, and a render cancelled while its job waits returns at once. A full render takes one snapshot of the options (`options()`) when it begins and makes all of its tiles from it, so a device attached part-way cannot put the tiles of one file on two devices. The same holds when the route goes away part-way: an export whose first tiles ran on the device starts again on the CPU instead of finishing there, and a strict policy fails the next photo as well once a shader error has switched the raw chain off for the process (it never renders that photo quietly on the CPU).

### Stages after the demosaic on the device (R6 to R8)

`StageRange::DEMOSAIC_TO_SHARPEN` (`R6..R8`) runs the demosaic and the stages after it (the bilateral denoise, the guided filter and the detail re-injection, or in their place method A, its false-colour step and its coarse colour pass; Richardson–Lucy, or the diffraction deconvolution when the photo has that method) as one device job per tile with one readback; R9 then runs on the CPU on what comes back. Each stage gets the rectangle the CPU stepper cuts for it (`TileRun::need`), so halos are single-sourced; a stage that is an identity for the photo's controls (no iteration, Colour 0 with nothing to re-inject) is not recorded.

- *The noise sigma.* The device reads the photo's half-resolution plane and the gain at each cell's centre (`SigmaHalf`, from `SigmaPlane` and `gain_plane`); a dispatch (`sigma_expand.wgsl`) expands the cells a tile reads with the rule of `full_sigma_map` (cell `(x / 2, y / 2)` clamped to the plane, times its gain), which gives the CPU map's bits for every cell (tested at odd origins and odd frame sizes). The full-resolution map (4 bytes a pixel, 200 MB at 50 MP) is lazy in `FullChain`: it is made the first time a CPU stage runs (`FullChain::cpu_chain`), never on the route `R6..R8` (`FullChain::sigma_map_built`, tested). The pre-denoise copy of R7's `Y_classical` is one luma plane on the device, not a copy of the image.
- *Parity:* the stages after the demosaic inside the chain (R6..R8 against R6..R6, the same device demosaic) 5.2e-6 over 96 cases, and they add nothing to the tie flips of the demosaic (*Chain parity* above). Tiles equal the whole frame bit for bit for every stage and the chain (two tile sizes, every combination of the stage switches). A poisoned device equals a plain one, `LP_NUM_THREADS=1` equals the default, every binding stays under 128 MiB at `MAX_PHYS_AREA`, a split demosaic core changes no bit, and a cancelled tile leaves the pool at its baseline.
- The render asks for `ym_core::pipeline::raw::DEVICE_RANGE` (`R6..R8`) (`raw_route` and the CPU fall-back record of `pipeline/graph.rs`, the report label `R6..R8` in `tests/render_gpu.rs`) wherever the policy runs the raw chain on the device: `On`, `Require`, and `Auto` on a hardware adapter.

### The raw front, R9 and the fit-view path on the device

- *The photo's words.* `kernels::prep::DeviceRaw` puts the raw readout on the device once (two u16 per u32, in one or two row slabs of at most 128 MiB, so a 61 MP plane is one binding and a 70 MP plane two); the cRAW quantisation step is a byte index into a table of at most 256 values when the photo has that few distinct f16 steps, else f16 pairs (exact: a step that is not an f16 value is refused).
- *`prep`* (`prep.wgsl`) is R1 with the −0.05 floor, R3 and R4 in one pass over a rectangle, plus the clip bits (one bit per photosite, one thread per word, no atomics) by the CPU's two rules (`raw >= white - 4 qstep`, else `(raw - black) * inv >= 0.995`).
- *R5* (`highlights.wgsl`) is the CPU's steps: per superpixel the channel values, their correctly rounded cube roots and the clipped flags; the opposed estimate over the clamped 3 × 3 in the CPU's order; the apply pass with the chroma offsets as uniforms (the full chain passes the CPU's `Prepared` offsets as numbers); and for the reduced path the global offsets by the fixed-order reduction of the stage table.
- *R5b* (`mosaic_ca.wgsl`) and *R9* (`lens.wgsl`).
- *Reduced path.* The σ plane from the raw words (`sigma.wgsl`: R1, R4, the 5 × 5 box means in the CPU's order, `sigma_quad`: no host plane), `bin` k × k (`bin.wgsl`: the green mean, red and blue as the lattice of the CPU's `bin_mosaic` with the weights from the host, the vignetting gain at the binned pixel) and the σ that binning leaves, the bilateral denoise and R9 at 1/k. `GpuReduced::run` goes through the frame in slabs of 1024 rows: a first sweep reduces the offsets, a second makes each slab's mosaic, applies R5 and bins it into the output; the slab height changes no bit (tested), and nothing of full resolution is built on the host.
- *The range R1..R9* (`StageRange::RAW_TO_LENS`, `GpuChain::run_tile_front`) runs the whole chain of a tile from the resident words as one device job with one readback. The rectangles are the CPU stepper's (`Stage::input_rect` walked backwards, `FrontShape::plan`, tested to give `required_raw_rect`); the front of a demosaic core that is cut above `MAX_PHYS_AREA` is made again for each part from its own rectangle (a part can start at an odd photosite; with neither R5 nor R5b after R1, R3 and R4 the front makes exactly that rectangle, and with one of them its input is aligned to the superpixel grid by the stage); the CPU's R5 offsets travel as numbers.
- *In the render.* `GpuStages::RAW_FRONT` (in `SIGNED_OFF`) turns it on together with `RAW_CHAIN`: `raw_route` then asks for `FRONT_RANGE` (R1..R9) and the photo's graph holds the `DeviceRaw`, uploaded the first time a tile or a reduced group needs it and counted in `StageRuns::raw_uploads`. A renderer keeps the words of two photos (the one looked at and the one before it, then the most recently used), and an export pins its photo's words while it renders, so parallel exports are never evicted tile by tile. `Job::group(k)` makes the fit view and the thumbnails with `GpuReduced` from the same words (`StageRuns::device_groups`; the host σ plane is not built for them). A device error falls back to the CPU: for a tile as for the demosaic, for a reduced group for that group alone with the note (and the photo's route ends unless the error is about the request's size); `Require` fails the request; a photo whose words cannot be put on the device (budget, a readout above two slabs) runs R6..R8 behind the CPU's front for that request.
- *Parity on lavapipe* (`tests/gpu_{front,lens,reduced,chain}.rs`; the chain numbers are under *Chain parity* above): a lossy file 0 over 1e-4 (largest 2.1e-6) tie-free; frames from 2 × 2 to 40 × 40 within 1.0e-5; a 1024 × 1024 corner tile of a 50 MP frame behind a strong lens with CA on the mosaic: 467 of 3,145,728 over 1e-4, largest 4.3e-3, the demosaic core cut in two; the reduced group against the CPU composition of the stages 9.8e-7 (R5, gain, denoise and R9 together), at 50 MP 7.0e-7 without R9 and 2.0e-5 with it at k = 4 (hard-edged content in the far corner). Tiles equal the whole frame bit for bit (prep, R5, R5b, R9, binning, the group in slabs of 8 to 1 << 20 rows, the chain at two tile sizes). A 70 MP header (9792 × 7168) runs through two slabs (`#[ignore]`d, `a_70_mp_frame_runs_through_two_slabs`: the corner tile and a tile across the slab boundary have the CPU's bits); the 50 MP tests (`a_50_mp_frame_matches_the_cpu_in_default_slabs`, `a_50_mp_frame_corner_tile_runs_the_whole_front_chain_and_is_split`) are `#[ignore]`d too.

### Device foundation

- **Poison mode.** With `GpuConfig::poison` (`YM_GPU_POISON=1`, always on in the test helpers) `BufferPool::acquire` fills the whole size class with `0x7FC07FC0`, a NaN as one f32 and as two f16 (and `COPY_DST` is added to the usage so the fill is an ordinary queue write), so a kernel that reads what it did not write produces NaN instead of passing by luck on a zeroed fresh buffer. Several parity tests measure their error in a way that skips a NaN, so `tests/gpu_device.rs` (`existing_kernels`) is the NaN-proof check: it runs every host wrapper (adaptive ratio, log-guided, diffraction, output sharpening, the colour chain on every configuration of `tests/common/chains.rs`, the raw front end to display), whole and tiled, on a poisoned and on a plain device and requires the same bits and no NaN or infinity. `common::exact::assert_tiles_equal_whole` refuses a non-finite frame, because a frame of NaN equals itself.
- **Health.** An uncaptured wgpu error (a validation error nobody scoped, an out-of-memory) taints the device instead of panicking its thread, a device-lost callback marks it lost, and a readback that does not finish within 30 s taints it too (`GpuConfig::readback_timeout`; on Mesa lavapipe a second `queue.submit` blocks behind a running one, so the timeout covers the wait, not the submit). `Gpu::is_lost()` reports either, and the next allocation, submission or readback of a job fails with `GpuError::DeviceLost`. A driver out-of-memory while creating a buffer is reported as `OutOfBudget`.
- **Shared tokens.** `Gpu::submit_with_token` and `Gpu::run_with_token` take the render's own `CancelToken`: setting it skips the jobs of the render that have not started and is seen by the one that runs.
- **Kernel sets.** Kernels not yet written are registered as placeholders (`KernelId::is_placeholder`, a stub that writes one NaN, skipped by the warm-up) so that their ids, sets and offline checks exist before they do. `tests/shaders_naga.rs` validates every kernel in every mode with `Capabilities::empty()` (the f16 modes add the capability of their own declarations), translates to MSL, SPIR-V and HLSL, and lints the source for the kernel contract (`docs/17-gpu.md` section 6: entry point and workgroup size, at most 8 storage and 1 uniform buffers, 16 KiB of workgroup memory, no subgroups, float atomics, texture sampling, `fma()` or extra directives).

### View kernels

The view stages after the chain have device entry points that take and give `GpuImage`s, so a frame can stay on the device from the sampler to the bands the encoders pull.

1. *Persistent tables* (`kernels/color.rs`, `ChainTables`, one set per device thread, keyed by the device's counters): the ACES 2.0 tables and the 64 × 64 dither table are uploaded once per device, the curve tables (four tables of 1024 `f32`, 16 KB a set; the last 12 sets are kept) once per curve edit, and look cubes are kept in an LRU of 6 entries or 192 MiB keyed by a 128-bit hash of the cube's content. The per-frame uniform (`ChainU`) is 2096 bytes and holds only the scalars and the colour warp's pins (`docs/02` C9b); an unchanged chain costs under 0.2 ms of CPU to prepare and uploads nothing, a curve edit uploads 16 KB, a look change uploads one cube once (counters in `tests/gpu_color.rs`).
2. *Colour stage* (C1 to C12): `PreparedChain::encode_stage` reads a `GpuImage` window and writes a `GpuImage` (f32 planes, with a destination stride and x offset, so a wider destination can take a tile), `encode_rgba8` stops at RGBA8 for the Before view; the host wrappers `render` and `render_tiled` are layers on them, and device to device equals the host wrapper bit for bit (tested).
3. *Encode* (`kernels/encode.rs`): C13 with the blue-noise dither, the letterbox and the outside plane to RGBA8, RGB8 or RGB16 bands (`encode_c13`, `encode_c13_strided`, `encode_host`); the bytes equal the CPU encoder's 8-bit codes (0 of 18,471 differ) and bands equal the whole frame bit for bit.
4. *Output sharpening* reads a window of a `GpuImage`, writes the core, and fuses with C13 and the dither (`PreparedSharpen::encode_rgba8`) or chains to the encode kernel; the two roads are bit-identical (`docs/algorithms/04` section 10).
5. *Sampler* (`kernels/sampler.rs`, CPU port `cpu/sampler.rs`): the eight EXIF orientations, quarter turns, the straighten angle and the crop in one pass with copy, Catmull–Rom or box filtering and an outside plane; positions come from per-column and per-row tables (an integer and an `f64`-split fraction) and exact row intervals for the inside mask, computed on the CPU, so a pixel does not depend on the window it is computed in (tiles equal the whole bit for bit; positions never form an `f32` of the order of 10^4). Against the CPU port the copy road is exact, Catmull–Rom and box are within 5e-6 (measured on lavapipe: 5.96e-7 over 192 cases, 3.6e-7 at both the near and the far corner of an 8658 × 5772 frame; the test bound is 1.2e-6 on software adapters and 5e-6 on hardware), and the outside mask is identical for every orientation, turn, angle and crop.

Every colour, encode, sampler and sharpen pass goes through `PassList` and `ctx.submit`; none calls `queue.submit` or `write_buffer`.

### f16 storage and the 1e-3 gate

The f32 device is the default; this caveat applies to the forced f16 modes only. The balanced mosaic and the demosaiced planes are rounded to f16 (relative step 4.9e-4, absolute 4.9e-4 to 9.8e-4 between 1 and 4), and the gains push saturated or clipped samples to 2 to 4. The 1e-3 gate of the spike chain (normalise, gains, bilinear, fixed matrix, sRGB) is met by the 50 MP scene and by the smooth test scenes (at most 7.9e-4 with f16 storage; 5.4e-4 on the small test frames; 2.4e-7 with f32 storage), but it is data dependent: a frame of full-range, uncorrelated noise on every photosite (an unrealistic worst case, `white_noise_scene` in `tests/gpu_spike.rs`: values up to 1.4 × white, gains 2 and 1.6, a matrix with negative terms, so a dark output is a difference of large f16-rounded terms that the sRGB toe then multiplies by 12.9) reaches 4.8e-3 to 6.1e-3 against the plain f32 reference. Against a reference that rounds to f16 at the same two places (`f16_aware_reference`) the GPU agrees to 1.4e-6 in every storage mode and every scene, so the difference is storage precision, not kernel error; `spike_matches_an_f16_aware_reference_to_rounding_noise` pins it at 2e-5 for at least 99.9 % of the samples. A tight colour gate is judged against the f16-aware reference or on the f32 device. The peak GPU memory of the 50 MP spike run is 0.281 GiB by the pool ledger (0.282 GiB by the driver's allocator report), against a gate of 1.5 GiB.

### Device residency

What a tile, a group and an export leave on the device between two jobs, and the proof that this changes no bit.

- *The tile stays.* `GpuChain::run_tile_device` is `run_tile_front` that does not read the tile back: the range R1..R9 from the resident words ends in a three-plane `GpuImage`, cropped on the device when the last stages were identities and assembled on the device from its parts when the demosaic core was cut above `MAX_PHYS_AREA`, both with the **copy kernel** (`copy.wgsl`, `kernels::copy`), which moves samples and computes on none, so fast-math cannot touch it. The readback of the image has the host tile's bits (`gpu_residency.rs`: four CFA phases, lens and none, whole, corner and inner rectangles, a cut core), and the job is one submission and no readback.
- *The export reads it in place.* `ExportTail::add_tile_device` binds the tile as the sampler's source: the tile of a 1024 px row does not go down to the host (12 MB) and up again; the bands are the ones `add_tile` makes from the host copy, bit for bit (plain and sharpened, 8 and 16 bit, shrunk), and the DNG's device colour stage takes the tile the same way (`colour_device_tile_to_host`). **At most three submissions per tile**: the chain's job, one job that makes the slabs the tile opens (a tile of 1024 rows over slabs of 512 opens two, and they are one job), and the tile's own; the only readbacks of an export are the bands.
- *The reduced group is a series of jobs, in bands.* `GpuReduced` makes the group of the fit view as `RowBands` (`REDUCED_SLAB_ROWS / k` rows of the result each, a buffer of its own per band), the bilateral denoise and R9 working on windows of rows (`RowBands::window`: a band itself when the rows lie in one, else a copy; the bilateral reads two rows beyond its window and the lens stage reads the rows its displacement reaches, `LensTable::source_rect`), the σ binned into bands too, and `ReducedRun` steps through it one slab, band or plane of work at a time, so that **a viewport frame queued behind the group waits for one step and not for the whole group**. The bands put together are the one-piece run's bits (tested); at 50 MP and `k = 2` no buffer of the run is above 22 MiB (the group of 3912 × 2608 in six bands), so a device with a 128 MiB binding runs it. `Job::group_backing` makes it a job per step (`GpuRoute::reduced_resident`; a cancelled render drops the state between steps and the buffers go back to the pool).
- *The caches keep it there.* `Backing { Cpu, Gpu }` in the group and tile caches of `PhotoGraph` (`docs/01`, "Resident caches"): the sampler gathers its window out of the cached pieces (`kernels::copy::encode_gather`), so a fit frame reads back its RGBA8 frame and nothing else, and a 100 % frame over cached tiles uploads next to nothing.

**Measured on Mesa lavapipe** (llvmpipe, LLVM 20.1.2, a loaded machine: times are indications; counts are exact). One job at a time on the device, so what matters for a frame that waits is the longest job: a regular chain job for a 1024 px tile of a 50 MP photo (about 1.1 MP of mosaic with its margins) takes 2.2 s on average and 4.3 s at the longest over 54 tiles (`--release`); the steps of the group at `k = 2` of the same photo take, longest by kind, 1.0 s (offsets, 6 steps), 0.13 s (fold), 1.4 s (bin, 6), **5.9 s (the σ plane, one step)**, 1.4 s (denoise, 6) and 0.75 s (R9, 6): 26 steps and 36 s together. *Submissions and transfers.* A chain tile from the resident words: 1 submission, 42 dispatches, 46 small uploads (11 KB) and no readback for a 248 × 186 tile; tiles handed to the tail on the device: at most 3 submissions per tile, plain 8 bit 6 tiles with 1 readback in all (7 with host copies), sharpened 16 bit 9 tiles with 1 (10), shrunk and sharpened 6 tiles with 1 (7); an export of a 900 × 600 photo in 12 tiles reads back 1 time with the raw front on the device and 13 with the front behind the CPU; the first fit frame of a photo reads back 1 time with a resident group (5 submissions) and 2 with the host caches (6); a 100 % frame over cached tiles uploads 14 KB, with host caches 993 KB. *The 50 MP memory gate* (`--release`, `fifty_megapixels_through_the_chain_and_the_tail_stay_under_two_gib`, 8436 × 5624, 54 tiles of 1024 px, 16 bit, sharpened, through the chain and the tail): the pool ledger peaks at **600 MiB** (the gate is 2048 MiB), is back at **0 MiB** when the run is over, at most 3 submissions per tile and no tile read back. The ledger of the renderer: a photo with its words and a fit group holds 3.2 MB (the 900 × 600 test photo), the tiles of a 100 % view 3.1 MB more, navigating away lets the tiles go and forgetting the photo gives everything back (`ym-core/tests/gpu_residency.rs`).

## Performance targets (Apple M1, 50 MP)

| Path | Target |
|---|---|
| Fit preview after open (classical, 1/4 res) | < 300 ms |
| Colour-only edit, viewport refresh | < 16 ms |
| 1:1 neural tiles visible on a 1440p viewport | < 1.5 s |
| Full neural export, JPEG | < 6 s per photo |
| CPU-only fallback export | < 90 s per photo |

These are targets; measured values are reported at each gate. The raw group of the cold fit preview takes 418 ms of 1111 ms at 24 MP on four shared x86-64 cores on the CPU (`docs/01`); the 300 ms target for it depends on the device path of the raw front. The colour-only target depends on the colour pass, which has a kernel (166 to 197 ms with `--gpu` on lavapipe against about 500 ms on the CPU, `docs/01`).

**CPU reference, measured** (4-core x86-64, `cargo bench -p ym-gpu --bench cpu_stages`, which runs the bilateral denoise and R7 path with the default demosaic). The machine was shared with other jobs (load average 13 to 17 on 4 cores), so wall times are inflated several-fold; CPU seconds are the dependable number. Per stage at 50 MP, CPU seconds: normalise 0.35, vignetting 1.3, gains 0.05, highlights 2.2, demosaic (LMMSE) 9.2 (adaptive ratio 10.0 to 10.8), bilateral 19.4, colour guided filter 9.7, detail 0.9, RL (n = 3) 12.1, lens resample 9.9. The whole chain R1 to R9 (LMMSE, bilateral, guided filter, RL with the Auto values, distortion + CA resample) took 69 CPU-seconds, about 17 s on four idle cores if it scales (measured wall 103 s under that load); with the adaptive ratio demosaic about 2 CPU-s more. Method A, the default denoise, costs 0.5 s per megapixel (wall, 3 threads; `docs/algorithms/05-single-frame-denoise.md` *Measurement*). The CPU-only fallback target (< 90 s per photo) looks met with a wide margin on four cores with the bilateral path; the whole chain with method A is not timed as a whole, and confirming it on an idle machine and on the M1 is part of M0-H4.
