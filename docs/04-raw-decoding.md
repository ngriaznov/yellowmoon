# 04 · ARW decoding

Crate: `ym-raw`. Our own decoder, Apache-2.0. You may read LibRaw, rawler, rawspeed and ExifTool to learn the format; write the code yourself and verify it against them as oracles (`tools/oracle`). Background: `research/notes/sony-arw-formats.md`.

## Output

```rust
pub struct RawImage {
    pub meta: RawMetadata,             // camera, exposure (ISO, shutter, aperture, EC), lens, timestamps, orientation
    pub layout: Layout,                // Bayer { pattern: RGGB.., active_area, crop } | Ycbcr { subsampling }
    pub data: Plane<u16>,              // undithered sensor values, linear after the camera curve
    pub black: [f32; 4], pub white: [f32; 4],   // per CFA position
    pub wb_as_shot: Option<[f32; 4]>,  // from SR2 0x7313 (RGGB) or 0x7303 (GRBG)
    pub qstep: Option<Plane<f16>>,     // quantisation step per pixel (cRAW and ARW6 only)
    pub lens: Option<LensTags>,        // 0x7032 vignetting, 0x7035 CA, 0x7037 distortion
    pub tone_curve: Option<[u16; 4]>,  // 0x7010 knots, for cRAW
    pub preview: Option<JpegRef>,      // embedded full-size JPEG location (for fast thumbnails)
}
```

Never dither. rawler dithers its curve output; that is wrong here, because the quantisation map feeds the denoise network.

In code (`crates/ym-raw`): `ym_raw::metadata::{probe, probe_bytes, probe_source, read_preview}` return `RawMetadata` (everything above except the pixels, plus the strip or tile locations in `RawMetadata::storage` and where each level came from); `ym_raw::decode::{decode, decode_with, decode_bytes, decode_source}` return `RawImage` (`decode_with` takes a `DecodeOptions`, today only the Lossless M/S switches below). `Layout::Bayer` carries `active_area` and `crop` as `Option<Rect>` (`None` = the whole readout, no crop). `lib.rs` re-exports nothing; use the module paths.

Conventions of the decoded image (M0-05, M2-09):

- `data`, `black`, `white` and `qstep` share one scale: the samples as the file stores them after the camera's own curve (14-bit for the 14-bit modes, Lossless L and cRAW; 12-bit for the 12-bit modes). Nothing is shifted, masked or dithered.
- `data` covers the whole readout (`meta.width` x `meta.height`, margins included); `black` and `white` are indexed by CFA raster position. `qstep` has the size of `data`.
- **Lossless M and S** are camera-processed RGB, not a mosaic: `layout` is `Layout::Ycbcr { subsampling }` (the REDUCED path: no demosaic) and `data` holds *interleaved camera RGB*, three samples per pixel. `data.width` is `3 * pixel width` (`RawImage::pixel_width()` gives the width in pixels, `channels()` the 3, `is_reduced()` the flag), `data.height` the rows. `black` and `white` are ordered red, green, green, blue for this layout. The white balance is divided out again, so the data is unbalanced camera RGB like a demosaiced mosaic, and `wb_as_shot` still holds the camera's gains (see Lossless M and S below for the scale).
- `ym_raw::decode::arw1`, `craw`, `ljpeg`, `uncompressed`, `ycbcr` and `arw6` are the decoder modules; they work on a `ByteSource`, so they read tiles with positional reads and decode them on all cores (rayon).

## Container

- ARW is little-endian TIFF. IFD0 holds the 1616 x 1080 preview JPEG (`JPEGInterchangeFormat`) and the EXIF pointer, IFD1 the 160 x 120 thumbnail; the raw image is in a sub-IFD (`SubIFDs`, 0x014A) with `NewSubFileType = 0`. Older files may place it differently; walk all IFDs and pick the one with Sony raw compression and the largest dimensions.
- EXIF sub-IFD and the Sony maker note (0x927C) carry ISO, exposure, lens and the model ID (0xB001). Some maker-note tags (0x9050, 0x94xx) are enciphered with a byte substitution cipher and model-specific layouts; read only what we need (bit depth hints, RAWFileType 0x2029 if useful) and treat failures as "unknown".
- ISO: prefer Sony's maker-note ISO over EXIF `ISOSpeedRatings` (16-bit, saturates at 65535). Map extended ISOs (below base) to base gain for noise purposes. The probe reads, in this order: `SonyISO` from the enciphered maker-note table 0x9416 (byte 4, 16-bit word `v`, ISO = `100 * 2^(16 - v/256)`), else from table 0x9405 when its first stored byte is one of 0x25, 0x3A, 0x76, 0x7E, 0x8B, 0x9A, 0xB3, 0xE1; then EXIF `RecommendedExposureIndex` 0x8832 or `ISOSpeed` 0x8833 (which first depends on `SensitivityType` 0x8830: 2 and 4 prefer the index), both 32-bit; last `ISOSpeedRatings` 0x8827. `RawMetadata::iso_source` records the origin. The byte cipher of the 0x9xxx tables is `c = b^3 mod 249` for `b < 249` (bytes 249 to 255 unchanged); it reproduces LibRaw's substitution table exactly. Bodies whose ISO lives in other tables (0x2010 variants) fall back to the EXIF tags.
- Maker note: an IFD whose value offsets are absolute file offsets. Older bodies put a 12-byte header in front of it (`SONY DSC \0\0\0`, `SONY CAM \0\0\0`, `SONY MOBILE`, `\0\0SONY PIC\0`, or `VHAB     \0` on Hasselblad rebadges). **Modern ARW files have no header**: the IFD starts at the first byte of the value (ExifTool's `MakerNoteSony5`, "used in SR2 and ARW images"; the real ILCE-9 file dumped in github.com/lclevy/sony_raw starts its maker note `63 00 03 10 04 00 10 00`, i.e. 99 entries). A value without a Sony header is read as an IFD when `Make` is `SONY`, or `Hasselblad` with a Lunar, Lusso, Stellar or HV model, and does not start `01 00` (ExifTool's rule). Tag 0xB001 is the model ID, 0xB000 the ARW version bytes (`[3,2,0,0]` is ARW 2.2; `[1,0,0,0]` marks SR2 and is rejected as `NotArw`), 0x2001 the full-size preview: a 32-byte header followed by the JPEG (the layout of the header is undocumented, ExifTool documents the tag for JPEG files, and none of the seven real ARW files seen (A500, A5000, A7M3, A7M4, NEX-5N, NEX-7, ILCE-9) has it: their preview is the IFD0 `JPEGInterchangeFormat`, 1616 x 1080). The probe takes the length from the first header word only when a JPEG end marker (`FF D9`) sits exactly there; otherwise the JPEG runs to the end of the value, as in ExifTool.
- Raw sub-IFD tags (ExifTool `Exif.pm`, "found in Sony ARW images"): 0x7000 `SonyRawFileType` (0 uncompressed 14-bit, 1 uncompressed 12-bit, 2 cRAW, 3 lossless, 4 lossless 2, 6 Compressed RAW 2), 0x7010 tone curve (four 16-bit knots, returned as stored), 0x7032 / 0x7035 / 0x7037 lens tables (signed 16-bit, 17 / 33 / 17 values, returned as stored), 0x7038 `SonyRawImageSize` (width and height of the valid image: becomes `active_area`), 0x74C7 / 0x74C8 crop origin and size (becomes `crop`; the DNG default crop tags are used when these are absent), 0x7310 / 0x7313 repeated levels. Rectangles that do not fit the readout are ignored.
- Which file is an ARW: a TIFF (`II*\0` or `MM\0*`) with a raw directory (CFA photometric with one sample, or YCbCr with three samples and at least 12 bits at compression 7) *and* Sony evidence (`SONY` make, a Sony maker-note header, or Sony 0x70xx tags in the raw IFD). Hasselblad rebadges pass through the maker-note header. `DNGVersion` present, maker-note `FileFormat` = SR2, the models DSC-F828, DSC-V3 and DSC-R1 (SRF and SR2), non-TIFF input and non-Sony raw files are `NotArw`. Four samples per pixel or photometric 32892 is `Arq`. A Sony file whose `SubIFDs` pointer leads nowhere is `Corrupt`; the A100 (raw data behind the `SubIFDs` pointer) is `Unsupported`.
- Preview: `RawMetadata::preview` is the embedded JPEG to show first. The candidates are the maker-note preview, the `JPEGInterchangeFormat` thumbnails and the single-strip 8-bit JPEG images of every directory that start `FF D8 FF` and lie inside the file. A real ARW holds several (the ILCE-7M4 file in drewnoakes/metadata-extractor-images: a 160 x 120 thumbnail in IFD1, the 1616 x 1080 preview in IFD0, and a 7008 x 4672 full-size JPEG of 1.7 MB in a third directory; older bodies have the first two). The choice is the smallest candidate whose long edge, read from its frame header, is at least 1024 px (the 1616 x 1080 preview: the start screen needs a few-megapixel decode, not 33 MP), else the largest candidate. JPEGs coded with a lossless process (start-of-frame SOF3) are never chosen: no viewer can show them.
- Limits: image area at most 120 MP and 65 535 px per side; at most 2048 entries per directory, 64 directories, nesting depth 4, 8 MiB per value, 64 MiB of reads per probe; raw data must lie inside the file and be at least as large as an uncompressed layout needs. All of these are `Corrupt`, never a panic or an unbounded allocation.

### SR2 private data (black, white, white balance)

1. IFD0 tag `DNGPrivateData` (0xC634) holds a 4-byte little-endian offset to the **SR2Private** IFD.
2. SR2Private contains `SR2SubIFDOffset` (0x7200), `SR2SubIFDLength` (0x7201) and `SR2SubIFDKey` (0x7221, 4 bytes LE).
3. Decrypt `length/4` little-endian 32-bit words starting at the offset with Sony's pad cipher: seed four words by iterating `key = key·48828125 + 1` (wrapping u32); fix up word 3 from words 0 and 2; extend to 127 words with the shift-xor recurrence over words p−4, p−2, p−3, p−1; byte-swap the pad words; then for each data word advance the pad (`pad[p] = pad[p+1] ^ pad[p+65]`, indices mod 128) and XOR. Write it from this description and verify against both oracles on every sample.
4. Parse the decrypted bytes as a bare IFD that starts at the first byte of the block (no TIFF header). Value offsets inside it are **absolute file offsets**, so a value sits at `stored offset - SR2SubIFDOffset` inside the block (LibRaw's `parseSonySR2` and rawler's `IFD::new(.., -sony_offset, ..)` agree; checked against LibRaw on synthetic files, M0-04). Tags:
   - `0x7310` BlackLevel (4 values per CFA position), falling back to `0x7300` (older);
   - `0x787F` WhiteLevel (per channel);
   - `0x7313` WB levels in RGGB order, falling back to `0x7303` (GRBG).
5. Typical modern values: black 512 and white 15360 in SR2 (the real ILCE-9, ILCE-7M3 and ILCE-7M4 files; the DNG `WhiteLevel` in the raw IFD of the same files says 16383 or 16380). 12-bit modes are scaled: check the bit depth and that black < white. Implemented in `sr2::level_shift` and `sr2::fit_levels`: Sony writes the levels on a 14-bit scale, so when the largest white level exceeds `2^bits - 1` of the stored samples, every level is shifted right by the smallest number of bits that makes it fit (4095 and 128 for 12-bit data, the same correction LibRaw applies to `linear_max` and rawler to black and white). cRAW is the exception: it decodes to a 14-bit scale whatever its BitsPerSample says (12 in every real cRAW file), so its levels are used as they are (black 512 and white 15360 in the A500, A5000, NEX-5N, NEX-7 and A7 III files, the values LibRaw reports). A file whose black level is not below its white level at every CFA position is `Corrupt`.
6. Newer bodies repeat black level (0x7310), white balance (0x7313, signed 16-bit values) and the DNG `WhiteLevel` (0xC61D) as plain tags in the raw IFD. Order of preference for each of black, white and white balance: SR2, then the raw IFD, then a documented default (black 512 for cRAW and `128 << (bits - 12)` otherwise, white `2^bits - 1`, no default white balance). The two can differ: the real ILCE-9 file has SR2 white 15360 and raw-IFD `WhiteLevel` 16383; SR2 wins. Levels read from the file are shifted down together (`sr2::level_shift`, decided by the white level) when they are on the 14-bit scale and the samples are narrower; a default is already on the samples' scale and is never shifted. `RawMetadata::{black_source, white_source, wb_source}` say which one was used. The values are stored per CFA position in raster order (`CfaPattern::rggb_to_positions` maps Sony's R, G1, G2, B order); `wb_as_shot` keeps the stored scale (green about 1024).

## Decoders by TIFF compression

`DecodeKind` is chosen by `metadata::classify` from compression, bits per sample, photometric interpretation, samples per pixel and the stored byte count: 32766 is `Arw6`; 7 with YCbCr and three samples is `LosslessMS` (chroma subsampling from the `YCbCrSubSampling` tag, else the sampling factors in the first tile's JPEG header, else 4:2:0); 7 with one sample is `LosslessL`; 1 with 12 bits is `Uncompressed12` (16-bit words) and with 14 or 16 bits `Uncompressed14`; 32767 with one byte per pixel (`bytes = width * height`; real cRAW files from the A500, A5000, NEX-5N, NEX-7 and A7 III all say BitsPerSample 12, `SonyRawFileType` 2, so the byte count decides as in LibRaw, and 8 bits counts too) is `Craw`, with two bytes per sample `Uncompressed14`, with 12 bits and `bytes * 8 = width * height * 12` `Uncompressed12` (packed), 12 bits and any other byte count `Arw1` (the Huffman-coded format of the A200 to A390; the real A300 file has 0.98 bytes per pixel, noisy synthetic data needs more), and anything else `Unknown`. The A100 itself (raw data behind the `SubIFDs` pointer) is still `Unsupported`: no sample. For odd bit depths at compression 1 `SonyRawFileType` decides. The metadata keeps `compression` so a decoder can tell packed 12-bit (32767) from 16-bit words (1).

| Compression / layout | Variant | Decode |
|---|---|---|
| 32767, bits 12 | ARW 2 12-bit uncompressed (packed) | Unpack 12-bit little-endian samples row by row: three bytes hold two samples, `b0 | (b1 & 0xF) << 8` and `b1 >> 4 | b2 << 4` (LibRaw's `packed_load_raw` with `load_flags = 80` and its `col ^ 1` swap). Verified against LibRaw and rawler on synthetic files; no real sample. |
| 32767, one byte per pixel | cRAW (lossy) | Block decoder below. |
| 32767, bits 12, other byte count | ARW 1 (A200 to A390, Huffman) | Fixed-code Huffman decoder below. |
| 1 | 14-bit (or 12-bit) uncompressed | Read u16 LE samples; respect `BitsPerSample`. |
| 7, SamplesPerPixel 1, Photometric CFA | Lossless L | Tiled LJPEG-92 below. |
| 7, Photometric YCbCr (6), SamplesPerPixel 3 | Lossless M / S | Reduced path below. |
| 32766 | ARW 6.0 Compressed RAW 2 (lossy wavelet) | Gated, below. |

### cRAW

Each row stores `width` bytes. Every 32 pixels form two interleaved 16-pixel blocks (even columns and odd columns, i.e. same CFA colour). Each block is 128 bits, read LSB-first:

- 11-bit `max`, 11-bit `min`, 4-bit index of the max pixel, 4-bit index of the min pixel;
- 14 × 7-bit deltas for the other pixels: `value = min(2047, (delta << shift) + min)` where `shift = max(0, bitlen(max − min) − 7)`.

Then expand through the camera curve: tag 0x7010 holds 4 knots (each `(v >> 2) & 0xFFF`); with `c0 = 0`, `c5 = 4095`, the curve rises by `2^i` per index step between knot `i` and knot `i + 1` (slopes 1, 2, 4, 8, 16). Index the curve with `value << 1`. All six real cRAW files seen (A500, A5000, A6300, A7 III, NEX-5N, NEX-7) store the knots `8000, 10400, 12900, 14100`, i.e. decoded knots 2000, 2600, 3225 and 3525, so the curve reaches 17204 at the top code (a little above 16383: real frames show 16596).

**Scale.** The curve output is used as it is: it is on the 14-bit scale of the uncompressed modes (black 512, white 15360 from SR2) and is what rawler and LibRaw 0.22.1 (`sony_arw2_load_raw`) return, so `data`, black, white and `qstep` need no conversion for those two oracles. The 12-bit `>> 2` scale (black 128, white 4095) is dcraw's and old LibRaw releases'; neither oracle uses it any more. Measured: all six real cRAW files decode bit-identical to LibRaw's `raw_image`, and within rawler's dither window to rawler (the window is a quarter of the local curve step around the undithered value; the largest observed difference is half a curve step per code, inside the window).

Never dither, and never clamp to 14 bits: values above 16383 are real.

**Quantisation map (`qstep`, M2-03).** Both quantisation stages are known exactly. Per pixel, in output DN:

- the two exact pixels (max and min) were rounded to one code of the 11-bit curve: `qstep` is the larger of the curve distances to the neighbouring codes one below and one above;
- a delta pixel was rounded to a multiple of `2^shift` codes above `min`: `qstep` is the larger of the curve distances to the neighbouring representable codes `2^shift` below and above (inside one curve segment: `2^shift` codes times 2 index steps times the slope, the "step in the 11-bit domain times the local slope"). There is no neighbour below the lowest `2^shift` codes; above code 2047 the curve continues with its last step;
- one bucket is wider: delta 127 is the largest the format can store and `max - min` is only known to be below `128 * 2^shift`, so pixels from `min + 127 * 2^shift` up to the block maximum all decode to it. For a delta-127 pixel `qstep` is widened to `2 * (curve(max) - curve(decoded)) + (curve(max + 1) - curve(max))`.

A true value that the encoder rounded to the nearest representable value lies within `qstep / 2` of the decoded one; an encoder that truncates puts it in `[decoded, decoded + qstep)`. (The delta stage of the real cameras rounds to nearest, ties upwards: in the A7 III file 3,123 delta pixels of the shift-1 blocks decode one code above their block's maximum, every one of them in a block whose `max - min` is odd, which truncation can never produce.) A camera also rounds the 14-bit sensor value to the 11-bit code before the delta stage, so for a delta pixel with a shift above 0 the interval a true value can lie in is `2^shift + 1` codes wide, one code more than the map reports (with shift 0 and for the two exact pixels it is exactly the reported one code); the variance is nevertheless exactly that of one rounding of step `2^shift` (`(4^shift - 1) / 12` for the integer delta stage plus `1 / 12` for the code stage, in code units squared), so `q^2 / 12` is the right noise power and `qstep / 2` the right half-width for the single-stage model of the test encoder. The denoise network uses it as the quantisation noise scale (`q^2 / 12`) and to suppress cRAW's "blondie" stripes within the known intervals. Output is `Plane<f16>` of the size of `data`; every value the format can produce is below 2048 (the widest, the top bucket, spans at most 15 codes) and so exact.

Test encoder and property tests: `ym_raw::testgen::CrawEncoder` (feature `testgen`) is the inverse of the decoder with both rounding modes and any monotonic knots; `crates/ym-raw/tests/craw_qstep.rs` checks the bound above for 400 random mosaics per case (uniform noise, gradients, clipped highlights, spikes, every block spread so all shifts occur) with random curves, with the real camera curve, with the truncating encoder, and through whole synthetic files. The bound only limits `qstep` from below, so the same file also holds a model that reads the 128-bit blocks bit by bit and applies the definition above literally (f64, no tables); `qstep` and the decoded values must equal the model's exactly, on encoder output and on arbitrary bytes.

### ARW 1 (A200 to A390, Huffman)

TIFF compression 32767, 12 bits, and a byte count that fits no other layout (LibRaw's `sony_arw_load_raw`, chosen by the same test). MSB-first bit stream from the start of the strip, no stuffing. The image is coded **column by column from the last column to the first**; within a column the even rows (0, 2, 4, ...) come first, then the odd rows. The file holds `ImageLength + 8` rows (LibRaw and rawler return all of them; we decode them to keep the running sum in step and return `ImageLength` rows). Every sample is `sum += diff` over the whole traversal (it starts at 0 and never resets). `diff` is a JPEG-style difference: a Huffman-coded bit length `n` (0 to 17) and `n` bits, a leading zero bit meaning negative. The Huffman code is fixed (dcraw's table): the bit lengths 17, 16, 15, 14, 13, 12, 11, 10, 9, 8, 7, 6, 5, 4, 3, 0, 2, 1 have code lengths 15, 15, 14, 13, 12, 11, 10, 9, 8, 7, 6, 5, 4, 3, 3, 3, 2, 2, assigned in that order as increasing binary numbers within each length, the first code being all zero bits. A sum outside 0 to 4095 is `Corrupt`. Verified bit-identical to LibRaw on the real A300 file (OpenImageIO-images, 3880 x 2600, black 0, white 3840 on the 12-bit scale) and to LibRaw and rawler on synthetic files. rawler keeps a white level of 15360 for this body; LibRaw and SR2 say 3840.

### Lossless L (tiled LJPEG-92)

- Tiles from `TileWidth`/`TileLength`/`TileOffsets` (512×512 on current bodies; whatever the tags say is accepted up to 16 M samples per tile). Real files carry the strip tags as well (`StripOffsets` = first tile, `StripByteCounts` = all tiles, `RowsPerStrip` = the image height; rawler looks for them); the tile tags win.
- Each tile is a lossless JPEG (ITU T.81 process 14) stream that declares 4 components and half the width and height: each decoded row of 4-component pixels holds two consecutive sensor rows of the 2×2 Bayer quad: component 0 is the sample at `(2j, 2i)`, component 1 at `(2j, 2i+1)`, component 2 at `(2j+1, 2i)`, component 3 at `(2j+1, 2i+1)`. Unpack into two rows of `TileWidth` samples. The real ILCE-7M4 tile (the only Lossless L body we have a file for) declares precision 14, 256 x 256, four 1x1 components, one Huffman table shared by all four (15 symbols, longest code 10 bits), predictor 1, point transform 0, no restart interval; 140 tiles of 205 to 273 kB. Our decode of that file is bit-identical to LibRaw, rawler and libjpeg. The quad order is therefore confirmed on one body (A7 IV), not three.
- Our own LJPEG-92 decoder (`decode::ljpeg`): SOF3, DHT (several tables, codes to 16 bits, fast 10-bit lookup), DRI and RSTn, predictors 1–7, point transform, 2 to 16 bits, 1 to 4 components with any sampling factors (needed for M/S), all prediction rules of T.81 H.1.2.1 (first sample 2^(P-Pt-1), first line of a scan or restart interval predicted from the left, first sample of later lines from above). The `ljpeg` crate is LGPL; not used.
- Edge tiles are decoded whole and cropped on copy. Tiles are decoded in parallel (one task per tile row, one per tile inside it).
- LibRaw quirks found while building the oracle, none of them affecting real Sony files: LibRaw takes any file with exactly four tile offsets for a Sinar 4-shot file; its Sony LJPEG loader is chosen by model name (`ILCE-1`, `ILCE-7*`, `ILCE-9*`), so a synthetic `ILCE-1M2` comes back all zero; and it does not restart prediction after an `RSTn` the way T.81 and libjpeg do when the interval is more than one row and the predictor is two-dimensional (predictor 1 restarts are fine).

### Lossless M and S (reduced path)

- These are camera-processed: white-balanced, demosaiced, chroma-subsampled YCbCr (4:2:0 or 4:2:2), losslessly coded as LJPEG tiles with 3 components. They are not Bayer. Implemented in `decode::ycbcr` (M2-09).
- Tiles (512 x 512, Y sampled 2x2 or 2x1, Cb and Cr 1x1, the stream declares the tile size) are decoded in parallel into full-frame Y, Cb and Cr planes. 4:2:0 uses Sony's variant of the first-column prediction, which LibRaw and rawler both implement (rawler calls it a probably broken Sony encoding): the first luma sample of an MCU row that has a row above is predicted from the first sample of the *previous MCU row* (two rows up), not from the row above; everything else follows T.81 with predictor 1.
- Chroma is upsampled either by replication (LibRaw) or, by default, by co-sited linear interpolation: the chroma sample belongs to the left and upper luma sample, in-between samples are the rounded average of their neighbours, horizontally then vertically; tile borders are not seams because it runs on the full-frame plane. This is the intended behaviour of rawler's `interpolate_yuv`, not what rawler does: it interpolates per tile, leaves the last column of a tile alone, and applies the vertical step to one row in every three (measured on a synthetic 4:2:0 file: rawler's red channel agrees with this decode on rows 1 mod 6 and with replication on rows 5 mod 6), so the two outputs differ and rawler is information only for M/S. The co-sited siting itself is rawler's reading of Sony's format and has not been measured on a real M or S file (none is available here, [HUMAN] with the scale below): if the camera averages each group instead, linear upsampling puts the chroma half a sample off, and `ChromaUpsampling::Replicate` (LibRaw's choice) is the safer setting.
- YCbCr → RGB is the full-range BT.601 inverse used by LibRaw's `ycc2rgb` (single precision, truncation): `R = Y + 1.402 Cr`, `G = Y − 0.34414 Cb − 0.71414 Cr`, `B = Y + 1.772 Cb`, with `Cb` and `Cr` taken relative to 16383, clamped to 0..65535. (rawler uses 1.4, 1.765, 0.343 and 0.711; they are rounder and we have no real file to prefer them.)
- The white balance is then divided out: `v = (v_balanced − pedestal) / gain + pedestal` with the gains `wb_as_shot` (SR2 0x7313, G1 = G2 = 1024) divided by green, and `pedestal` twice the SR2 black level (1024 for the usual 512, which is LibRaw's `black = 1024` and rawler's `black * 2`). The result is unbalanced camera RGB. Without SR2 white-balance data the balanced values are kept and `wb_as_shot` is `None`.
- Levels (red, green, green, blue): `black = pedestal`, `white = pedestal + (17536 − 1024) / gain`. 17536 is LibRaw's `maximum` for these files, "estimated on over-exposed ISO100 frame" in its source; it is the ceiling of the balanced data, and dividing the gains out makes the red and blue ceilings lower than green's. **This scale (the factor 2, the 15-bit range, the ceiling) comes from LibRaw and rawler, not from a measurement of ours: no real Lossless M or S file exists in the test environment.** Check it on the RawDB A7R V "yuv" sets, A9 III, A1 II and RX1R III files once they can be fetched (blocked here); until then treat white as approximate (it only moves the exposure, which is automatic).
- `DecodeOptions { ycbcr: YcbcrOptions { chroma, undo_white_balance } }` selects the behaviours; `Replicate` with `undo_white_balance: false` is exactly LibRaw's pseudo-raw output (tested bit-identical, below).
- Output: `Layout::Ycbcr`, interleaved RGB (see Output above). Camera-RGB mosaics in downstream code must branch on `RawImage::is_reduced()`.
- The pipeline skips highlight reconstruction on the mosaic and the demosaic network; it runs the denoise-only variant of the network if available, else a light classical denoise. The sensor map runs as usual.
- The UI tags these photos REDUCED with the note: "This file was saved in the camera as Lossless M or S. The camera has already processed it, so colour emulation is approximate. Use Lossless L or uncompressed for best results." `yellowmoon info` prints a "Reduced" row and `"reduced": true`, `"subsampling"` and `"supported"` in `raw` of its JSON.
- Detection: a raw IFD with compression 7, photometric YCbCr and three samples (BitsPerSample 12 or more, or absent), not the 8-bit "RGB preview" directory of reduced resolution (a NewSubFileType 1 directory is skipped unless it states 12 bits or more: LibRaw skips exactly `bps == 8 && NewSubFileType == 1`, and nothing says the real M and S files leave their raw directory unflagged).
- LibRaw 0.22.1 reaches its YCbCr loader only for Compression 6 (compression 7 is rewritten to 6 on a path our synthetic tiled files do not take; otherwise it falls back to a generic loader and returns zeros). The oracle therefore decodes a temporary copy with that one compression value changed (`tools/oracle/rawpy_compare.py`, `input_patched`); the tile data is untouched. It reads 4:2:0 and 4:2:2 only.

### ARW 6.0 Compressed RAW 2 (gated)

- A7 V (Compressed, Compressed HQ) and A7R VI (Compressed, HD). Tiled (up to 16 tiles), packetised wavelet codec built on Sony's LLVC (SMPTE RDD 34: reversible 5/3 lifting, variable-length coding) with Sony deviations. A green-mean plane plus residuals; R and B as colour-difference planes; 12-bit codes and a companding curve whose constants are not stored in the file.
- Permissive reference: lightcraft (Rust, MIT/Apache-2.0; 14-bit only). LibRaw master (LGPL/CDDL) as an oracle.
- **Gate:** [HUMAN] M2-H3: email Sony about IP for RDD 34-based decoding. We ship the ARW 6.0 decoder only after a satisfactory answer, or after a legal opinion Mykyta accepts. Until then: detect, and show "ARW 6.0 compressed files from the A7 V and A7R VI aren't supported yet. Lossless files from these cameras work. We're working on it." Build the decoder behind a cargo feature `arw6` that is off in release builds until the gate clears. M0-05 added only the detection and the feature: `decode::arw6` returns `RawError::Unsupported` (the message above) with the feature on or off, and `decode_with_metadata` calls `arw6::decode` under the feature, so a decoder drops in there. lightcraft can be studied when the gate clears; nothing from it is in the tree.
- Quantisation map: derive from the wavelet quantiser per subband if feasible; otherwise a per-tile constant from the bitrate mode. Test 12-bit files once a sample exists (none public as of Oct 2026).

## Lens tags

Raw sub-IFD tags 0x7032 (vignetting), 0x7035 (chromatic aberration), 0x7037 (distortion): up to 16 knots each, as signed 16-bit values preceded by a count (17, 33 and 17 values; the chromatic-aberration table is the count and 32 knots, presumably two channels of 16 back to back; the layout is unverified until a real file is checked; the ILCE-9 file of the lclevy dump stores `32, 512 ×12, 640 ×3, 896 ×2, 768 ×4, 640 ×6, 512 ×2, 384, 256, 128`, where 512 looks like unity, and the same file's 0x7032 and 0x7037 start `16, 0, 32, 128, 288, ...` and `16, 13, 0, -25, -56, ...`, so the first value of each table is the knot count). `LensTable::raw` holds the values exactly as stored, `count()` the leading count and `knots()` the rest. Return them raw; the maths lives in `docs/05-raw-processing.md`. If a tag is missing (older bodies, adapted lenses), lens corrections are skipped for that part and the RAW tab says "No lens data in this file".

## Errors

Every failure returns a typed error with a plain message:

- `Unsupported { camera, variant }`: a known variant we don't decode yet (ARW 6.0 until gated).
- `NotArw`: SRF, SR2, ARQ, or not a TIFF ("This isn't an ARW file. Yellowmoon opens Sony ARW files only."). ARQ gets its own message: "Pixel-shift ARQ files aren't supported. Open the individual ARW frames instead."
- `Corrupt { detail }`: truncated or malformed. Fail that file and keep the session going; never show partially decoded pixels.

## Performance targets

- Metadata probe (no pixels): < 20 ms per file.
- Full decode, 50 MP lossless L on an M1: < 400 ms using all decode threads; uncompressed: < 150 ms (memory-bound).
- Embedded JPEG preview extraction: < 30 ms; used for the start screen's first thumbnails before our own render replaces them.

### Measured (M0-05, not an M1)

`cargo run -p ym-raw --features testgen --release --example decode_bench -- DIR` writes one 8192 x 6144 (50.3 MP) synthetic file per variant with the test encoders, then decodes each from disk (warm page cache) five times with 1, 2 and 4 rayon threads. Machine: 4 vCPU Intel Xeon at 2.8 GHz (Linux VM). Wall time is in milliseconds, best of five with the median in brackets; the CPU seconds of the best run (user plus system, from `/proc/self/stat`) are the number that stays valid when the machine is shared. The table is the review run on a quiet machine (load average about 2 with the benchmark itself running); the implementer's first run, on a machine that was shared with other jobs (load average about 12), gave up to three times these wall times at the same CPU seconds on 4 threads, for example 1013 ms for Lossless L.

| Variant | File MB | 1 thread | 2 threads | 4 threads | CPU s (1 thread) |
|---|---|---|---|---|---|
| uncompressed 14-bit | 100.7 | 94 (100) | 92 (98) | 92 (101) | 0.09 |
| packed 12-bit | 75.5 | 130 (138) | 119 (142) | 113 (159) | 0.13 |
| cRAW with qstep map | 50.3 | 757 (890) | 515 (597) | 367 (393) | 0.75 |
| Lossless L | 61.7 | 951 (963) | 462 (517) | 333 (347) | 0.95 |
| Lossless M/S 4:2:0 (linear chroma, white balance undone) | 69.7 | 3852 (4010) | 1886 (1960) | 1315 (1388) | 3.80 |

- Uncompressed 14-bit decodes in about 92 ms wall here, inside the 150 ms target; it is memory-bound, so threads do not help. The target is for an M1 and this is a different machine.
- Lossless L needs 0.95 CPU seconds per 50 MP, so the 400 ms target needs the tiles spread over at least three cores (0.95 / 0.4 = 2.4); on four vCPUs it takes 333 ms (median 347). Whether an M1 reaches 400 ms is **unverified** until the benchmark runs there [HUMAN]. The decoder has a fast path for the common shape (every component unsampled, a whole number of MCU rows per restart interval); the files the benchmark writes use it, and so do the real files.
- cRAW (0.75 CPU s) includes the qstep map. M/S (3.8 CPU s) is the slowest decoder; it has no target and was not profiled further.
- The synthetic pixels are a gradient with noise, so the sizes of the Lossless L, cRAW and M/S files say nothing about real file sizes.

## Tests

- **Oracle CI (`tools/oracle`, `tools/oracle/ci.sh`):** for every file in the corpus, our decoded `data`, black, white and WB must equal the oracles' values, and any other mismatch fails the build. `oracle --corpus DIR --report FILE` decodes every `*.ARW` with ym-raw and compares it with LibRaw (`raw_image`, undithered, through `tools/oracle/rawpy_compare.py`), with libjpeg for the Lossless L tiles (`libjpeg_dump.py`, a third implementation that handles every predictor and restart interval) and with rawler 0.8 in process (test-only, LGPL, never linked into a shipped crate); `oracle dump FILE --out RAW.bin` writes our decode. Exit code 0 passes, 1 is a mismatch or an unreadable file, 2 means LibRaw could not run, or refused every file that ym-raw decoded (a run in which nothing was compared is not a pass). Per variant: uncompressed, packed 12-bit, ARW 1, cRAW and Lossless L must be identical to LibRaw (LibRaw does not dither); Lossless L must also be identical to libjpeg; rawler dithers cRAW, so for cRAW it must agree within its dither window `base + ((delta * r + 1024) >> 12)`, `r` in 0..2048, and exactly elsewhere. Lossless M and S are compared with LibRaw's pseudo-raw RGB (replicated chroma, white balance left in, see above); rawler is information only there. Cases the oracle itself cannot decode (LibRaw: 4:4:4 M/S, restart intervals of more than one row with a two-dimensional predictor, Lossless L from models other than `ILCE-1`, `ILCE-7*`, `ILCE-9*`; rawler: anything but whole 512 x 512 tiles with predictor 1 and no restarts) are `oracle_error` or `informational` in the report, never a pass or a failure. ARW 6.0 is compared with LibRaw master and lightcraft once the decoder exists. CI commands: `pip install rawpy numpy pylibjpeg-libjpeg`, then `tools/oracle/ci.sh` (`tools/oracle/README.md` has the rest, including the exact cRAW 14-bit convention and the M/S comparison).
- **Results (M0-05).** Synthetic corpus, 48 files from `gen_corpus`: LibRaw identical on 46, `oracle_error` on 2 (4:4:4 M/S, and predictor 4 with two-row restart intervals; both outside what LibRaw reads), mismatches 0; libjpeg identical on all 20 Lossless L files; rawler identical on 21, inside its dither window on the 8 cRAW files, informational on 19 (M/S, partial or non-512 tiles, restarts), mismatches 0. Nine real files (local only, see Corpus): LibRaw identical on all 9, libjpeg identical on the Lossless L file, rawler identical on 3 and inside its dither window on the 6 cRAW files.
- **Synthetic files (M0-04, M0-05, while the corpus is unreachable):** `ym_raw::testgen::ArwBuilder` writes structurally faithful ARW files (IFD0, thumbnail IFD, EXIF, maker note with enciphered ISO table and 0x2001 preview, SR2Private and the encrypted SR2 sub-IFD, raw IFD, pluggable payload). Test-only encoders write every payload: uncompressed 14-bit and 12-bit words, packed 12-bit, ARW 1, cRAW (`CrawEncoder`: tone curve and rounding configurable), Lossless L (own LJPEG encoder: predictors 1 to 7, restart intervals, tile sizes, partial tiles, optimal or skewed Huffman tables) and Lossless M and S (4:2:0, 4:2:2, 4:4:4). `crates/ym-raw/tests/oracle_libraw.rs` (metadata) and `oracle_decode.rs` (pixels) run LibRaw on them and skip when rawpy is missing (`YM_REQUIRE_ORACLE=1` makes that an error). Results from synthetic files do not close the corpus gate.
- **Round trips and properties:** `decode_roundtrip.rs` (every variant, the L quad order, truncated or damaged files are `Corrupt` and never yield partial pixels, ARW 6.0 and unknown layouts are `Unsupported`), `ljpeg_props.rs` and `craw_qstep.rs` (proptest); the decoders' unit tests cover bad Huffman tables, oversize declarations and corrupt headers. Exact round trips: uncompressed, packed 12-bit, ARW 1 and Lossless L for every predictor, restart interval, tile size and table shape; Lossless M and S against the encoder's own planes, and, with the encoder's `co_sited` option (the siting the linear upsampling assumes), a smooth colour ramp through the shipped default path (linear chroma, white balance divided out) to within 2 DN in 4:4:4, 4:2:2 and 4:2:0 on an odd-sized image with partial tiles; no oracle reads that path, since LibRaw replicates chroma and leaves the balance in. `decode_hostile.rs` runs about 3,600 seeded attacks on one small file of every decodable variant (random byte damage, the tags that size buffers set to 0, 1, 31, 4096, 65535, 2^32 - 1 and so on, 120 MP claims behind a 15 kB file, truncation) through `decode_bytes` with a counting allocator: no panic, no attempt over 20 s, peak live heap at most 1.5 GiB (the worst case seen is 228 MiB, a lazily zeroed 120 MP plane), a success is consistent.
- **Corpus:** RawDB (rawdb.dnglab.org, CC0) and raw.pixls.us (CC0 files only, per-file licence check), fetched by `tools/fetch/samples.sh` into `testdata/arw/`. Gaps to fill [HUMAN]: FX2, RX10 V, 12-bit ARW 6.0, A1 Lossless M/S. Until then nine real files from public repositories are used locally, never committed (licences unchecked; sources and commands in `tools/oracle/README.md`): six cRAW (A500, A5000, A6300, A7 III, NEX-5N, NEX-7), one Lossless L (A7 IV), one 14-bit uncompressed (A7 II) and one ARW 1 (A300). They settled three points the synthetic files could not: cRAW is on the 14-bit scale with no `>> 2`, the Lossless L tile layout and quad order, and the extra 8 rows of ARW 1.
- **Fuzzing:** `cargo fuzz` targets in `crates/ym-raw/fuzz` for the TIFF walker, SR2 parser and metadata probe (M0-04) and, since M0-05, `craw` (blocks, tone curve, qstep map), `ljpeg` (headers, tables, restart intervals, every predictor, sampling factors), `ycbcr` (Lossless M and S: the input replaces the tile payload of a valid synthetic file) and `decode_any` (the whole `decode_bytes` path). Properties: no panic, no unbounded allocation (declared dimensions are capped at 120 MP, a tile at 16 M samples, `ljpeg` has a sample budget), typed errors only. One 10-minute run of each new target on the final code (AddressSanitizer, seeds from `gen_seeds` plus the corpus of the shorter runs made while developing, shared 4-vCPU machine): `craw` 433,660 runs (721 per second, coverage 756, features 2,299), `ljpeg` 106,795 (177 per second, 1,083 / 4,160), `ycbcr` 71,740 (119 per second, 4,011 / 8,459), `decode_any` 258,577 (430 per second, 4,355 / 11,096); no crash, timeout or out-of-memory, peak resident memory 376 to 497 MB against the 2,048 MB limit. The corpora are git-ignored. The nightly CI job repeats this for every target (`docs/13-testing.md`).
- **Quantisation map:** `crates/ym-raw/tests/craw_qstep.rs`: encode a known image with our own cRAW encoder (test-only, nearest and floor rounding), decode, and check every true value lies within ±qstep/2 of the decoded value (400 random cases, plus the real camera curve). A pixel at the top bucket (delta 127) can lie anywhere between its reconstruction and the block maximum, so its qstep is widened to cover that (`craw::top_bucket_step`); a test pins it.
