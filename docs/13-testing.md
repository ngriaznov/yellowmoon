## GPU tests without a GPU

GPU tests look for an adapter and skip with a clear message when none exists, unless `YM_REQUIRE_GPU=1` is set. The `gpu-lavapipe` CI job sets it and runs the kernels on Mesa's software Vulkan driver, which checks correctness (not speed). GitHub's Apple-silicon runners do expose a Metal device (a paravirtualised one): `mac-gpu.yml` runs the same suites there with `WGPU_BACKEND=metal` and `YM_REQUIRE_GPU=1`, which checks the WGSL-to-MSL translation, Metal's fast-math and the parity of every kernel on real Metal, but not speed. Speed and the look of the native viewport are checked on a physical Mac before each gate [HUMAN M0-H4], with `tools/dev/mac-gpu-check.sh`.

**As built (M0-07, M1-09 to M1-11).** `crates/ym-gpu/tests/common` opens one device per f16 storage mode the adapter supports (native `f16`, packed `f16`, plain f32; each is a separate device, so every mode is exercised) and skips when `Gpu::start` finds no adapter; with `YM_REQUIRE_GPU=1` that is a panic. A skipped test passes without testing anything (its loops are empty), so the skip is announced loudly: a banner written straight to the process's stderr, which the harness's output capture does not swallow (`eprintln!` from a passing test is captured and would have been invisible), plus a `::warning::` annotation on GitHub Actions; `a_missing_adapter_skips_loudly_or_fails_when_required` runs one GPU test in a child process on a backend that cannot exist (DirectX 12 on Linux and macOS) to prove both halves of the contract. Run them with `WGPU_BACKEND=vulkan YM_REQUIRE_GPU=1 cargo test -p ym-gpu` (about 3 minutes in debug on a loaded 4-core machine, almost all of it compiling, and 20 seconds of test time in release; the 50 MP test is `#[ignore]`, `cargo test -p ym-gpu --release --test gpu_spike -- --ignored --nocapture gpu_spike_50mp`, 43 seconds on lavapipe in release including the CPU reference).

## GPU golden, determinism, faults and the Mac harness

**As built (`docs/17-gpu.md` sections 5, 9, 12 and 15).** The kernel-level parity tests above prove each stage; this section is the level above them: the whole photo through `ym`, the same photo twice, the photo with the device broken, and the machine-readable report a Mac session leaves behind.

### GPU golden: `golden check --device gpu` and `golden device-check`

The hashes of `expected.json` pin the **CPU** reference (the runner renders with `ym render --cpu` and `YELLOWMOON_GPU=off`, so a machine with a graphics card cannot change them). The device is held to the CPU's pictures within gates. `ym render --require-gpu --json` renders a file strictly on the device (no adapter is exit 4 and the runner stops with exit 2 before rendering; a device error fails the file), and the file must also say `"device": "gpu"` in its JSON (`ExportReport.device`, the path the photo took) and carry no note that mentions the graphics card, otherwise it is `FELL BACK` and fails whatever its pixels are. The comparison is the CPU mode's statistic (ΔE00 of the 1/4 downsample: median, 99th percentile, maximum) plus the share of samples of the full-size picture that differ by more than 8 codes of 16 bits. Options, the calibration table and the rationale are in `tools/golden/README.md` ("GPU mode").

| Gate | Plan (proposed) | Default (calibrated) | Worst of 61 files, first run on lavapipe |
|---|---|---|---|
| median ΔE00 | 0.02 | 2.1e-4 | 1.003e-4 |
| 99th percentile | 0.05 | 2.2e-2 | 1.066e-2 |
| maximum | 0.5 | 3.8 | 1.855 (`D6500__ILCE-7SM3__iso400__rggb__12b__packed12`) |
| samples more than 8 codes off | 1e-3 | 7.4e-3 | 3.66e-3 |

The first proposed gates were to be "calibrated on the first lavapipe run"; with them 50 of the 61 files fail, all on the count of samples (6 also on the maximum), because the output sharpening's halo limiter decides on a rank of luma values and a pixel at a hard chart edge takes the other side of a rank when the device's f32 chain and the CPU's f64 chain differ in a last bit (`docs/algorithms/04`; the sharpening kernel alone matches the CPU to 3e-7). The defaults are twice the worst first-run value, as every calibrated bound is: tighter than the proposal for the median and the 99th percentile, looser for the maximum and the count. `--gpu-gates plan` restores the proposed set. Mykyta agreed to these defaults on 2026-10-15 (STATUS question 26: keep the slight deviation; the limiter stays as it is); changing them again needs his agreement.

Where it runs: the `golden-gpu` job of `ci.yml` (ubuntu-24.04, lavapipe, `needs: golden`, so the references are in the cache) checks the ten files of `tools/golden/gpu-subset.txt` on a push and all 61 files on the nightly schedule, against the stored pictures; the Metal job of `mac-gpu.yml` checks the same ten files with `--reference render`, i.e. against a CPU render **of the same run on the same machine**, because the CPU hashes of a Mac differ from those of the Linux machine that wrote `expected.json` by a code. Both then render one of the owner's photos (`testdata/readme-photos/src/A1M01749.ARW`, the `readme-photos` branch in Git LFS, cached by the hash file `tools/fetch/owner-photos.sha256` and verified with `tools/fetch/owner-photos.sh --verify`) with `golden device-check --long-edge 1500`: once on the CPU, once strictly on the device, same gates. The synthetic charts cover clipped highlights, all four CFA phases, cRAW, lossless and camera-processed files; a real 50 MP photo covers what a chart cannot (large gradients, real noise, a real lens). Measured on lavapipe (Mesa 25.2, LLVM 20.1, debug build, 4 shared cores) with `A1M01749.ARW` at a long edge of 1500 px: ΔE00 median 0 (mean 6.5e-5), p99 3.8e-4, maximum 0.028; 94 of 4 500 000 samples (2.09e-5) more than 8 codes off, the largest difference 102 codes; both renders and the comparison took 82 s. The photo sits an order of magnitude inside the chart-calibrated gates on every statistic, so the workflows pass no overrides.

### GPU determinism and fault injection

`crates/ym-core/tests/gpu_determinism.rs` (no feature needed) holds the determinism rules of `docs/17-gpu.md` section 5 against the whole export: the same export is the same bytes every time and on a device of its own (six formats); export, other photo, export (A-B-A) for frames and exports, with the renderer's view caches on the device (`resident_caches`, the default) and on the host, and the pool back at its baseline once both photos are forgotten (a viewed photo keeps its group and tiles resident until then; an export never keeps anything); a cancel part way and then the next export equals the uninterrupted one; viewport jobs injected from the progress callback change nothing; one, two and four exports in flight give the same bytes; and a child process with `LP_NUM_THREADS=1` writes the digests of the same exports, which equal the parent's (Mesa's own thread count must not matter).

`crates/ym-core/tests/gpu_faults.rs` (feature `fault-injection`, run by the `gpu-lavapipe` job) breaks the device under the export, one level above `render_gpu.rs` and `gpu_export.rs`: every fault `YM_GPU_FAULT` knows (`oom`, `shader`, `lost`, `tile@1`, `tile@4`) against JPEG, PNG 16, TIFF 16 and DNG, in both policies, plus `cancel@N`, plus a queue of two photos. In every cell where the policy falls back the file is the CPU export of the same photo bit for bit, the report says `device = cpu` and carries the note, one file and no temporary is left, progress never goes back, and the host ledger and the device's pool are back at their baseline; under `Require` the photo fails with the kind `gpu`, nothing is written, the ledgers are back. A cancel ends the export as cancelled and the next export of the photo is the uninterrupted one. After a `tile@N` the second photo of a queue is made on the device again; after a loss or a shader that does not compile it is the CPU's, bit for bit (`shader` cells use a device whose pipelines are not compiled yet: a pipeline that is cached cannot fail to compile).

*A DNG is two renders.* The raw plane and the preview are separate renders with a fallback each. A fault that fires once (`tile@N`) is spent by the render it hits, so the other would have stayed on the device and the file would have been a mix, with `device = gpu` next to a note that says the CPU did (found by this matrix; `docs/17-gpu.md` section 9 asks for the whole photo on the CPU). `FullImage::fell_back_to_cpu` (typed, set when a render was made again on the CPU) lets `export_photo` keep the file whole: when the raw render fell back, the preview is made on the CPU reference path, and when only the preview fell back, the raw plane is made again on it. `a_dng_after_a_one_shot_device_error_is_the_cpu_export_whole` checks `tile@1` and `tile@4` (the raw render's tiles) and `tile@7` and `tile@10` (the preview's) against the CPU export, byte for byte, and the matrix holds every DNG cell to the same. It does not touch the persistent faults (`oom`, `shader`, `lost`), which close the route for both renders.

### Bounds on hardware, and what a number is allowed to do

A parity bound has two columns, software (lavapipe, the CPU-like rounding) and hardware (Metal). A hardware bound starts as the measured value of the first Metal run, doubled, and is never loosened. Where a Metal run has not printed a number yet, the test keeps the old generous bound and **prints** the value it sees (`ci_note`, written straight to stderr so that it reaches the job log although the harness captures `println!`; the helper also prefixes the line with the test file's name), and the next Metal log tightens it. Values from the first Metal run that are now in the tests: the export tail (`gpu_export.rs`: 16-bit samples more than 1 code off 5.1e-4, more than 8 codes off 1.94e-4, largest difference 1102 codes; JPEG 10 codes, 4.25e-4, 0.9965; the sharpened 8-bit case 4 codes, 7.4e-6 over the floor of 2, 0.9997), `render_sharpen.rs` (more than 10 codes over one), the main case of the denoise kernel (1.32e-6), and Richardson-Lucy (2.38e-6 at 4 iterations, 4.52e-6 at 10). The bright-flat, tile and sequence cases of the denoise and detail kernels, and the tile, beyond-cap and PSF cases of Richardson-Lucy, still have their old bounds and print what they see.

### Device residency

The 50 MP gate (`fifty_megapixels_through_the_chain_and_the_tail_stay_under_two_gib`, `#[ignore]`, run with `--release -- --ignored`): 8436 x 5624, 54 tiles, peak 600 MiB of device memory against 2 GiB, back to 0 afterwards, measured on lavapipe; the Metal job runs it too.

### `ym doctor --bench` and `tools/dev/mac-gpu-check.sh`

`ym doctor --bench FILE.ARW [--repeat N]` (`docs/10-cli.md`) times the render path of one photo on this machine and prints one report (text, or `--json`; the report names no file and no folder): the compile of each kernel set (`view`, `raw`, `tail`; the first launch with an empty shader cache is the slow one), the decode, the views (the fit view in a 1440 x 960 and a retina cell, the first sharp frame at 100 %, a colour-only edit, a thumbnail), full-size JPEG, 16-bit TIFF and 16-bit PNG exports through the queue the application and `ym render` share, the repeat check (the same JPEG `N` times, default 10, whose bytes must be equal), the host and device peaks, and the GPU time of each pass from timestamp queries where the adapter has them (`GpuConfig::timestamps`; `Gpu::take_pass_times`). It follows the graphics policy in force, so `YELLOWMOON_GPU=off` measures the CPU reference with the same command.

`tools/dev/mac-gpu-check.sh [--out FILE.json] [--photo FILE.ARW] [--repeat N] [--with-cpu] [--skip-tests]` is the Mac session of M0-H4 in one command. ### The ML backend on the renderer's device

`ym-ml` with the feature `burn` can run its model on the device the renderer opened: `ym_ml::backends::burn_backend::import_device(&Gpu)` hands the `wgpu` instance, adapter, device and queue of a `ym_gpu::device::Gpu` to burn (`Device::wgpu_options().setup(...)`), so one device holds the kernels and the model. `ym-gpu` requests that device the way cubecl does when its feature `ml` is on (the extra features and limits cubecl asks for). `crates/ym-ml/tests/burn_shared_device.rs` (the `ml-backends` job, lavapipe, `YM_REQUIRE_GPU=1`; on Metal the `ym-gpu` side of the recipe, its feature `ml`, is built and run by `mac-gpu.yml`) checks a tensor operation, a golden demosaic tile through `BurnJdd::with_device` against the PyTorch output within 2e-3, a `ym_gpu::kernels::resize` job on the same device (a flat 0.5 field stays exactly 0.5) and the model again afterwards with the same bytes as before the kernel, so the two do not disturb each other's buffers. Measured on lavapipe: the golden tile differs from PyTorch's by 1.9e-7 (the test bound is 2e-3), the test runs in 1.2 s, and a cold debug build of burn and cubecl takes 33 minutes on the shared 4-core machine, which is why only the `ml-backends` job compiles them.

## Performance logging and the viewport job

The owner's report of 2026-10-16 ("UI in Yellowmoon is sluggish") was diagnosed from the code, on a machine with no Mac: where the time goes needed numbers from the real window. The shell can now produce them.

**Switch.** `src-tauri/src/perf.rs`. On in development builds and, in a release build, when `YM_PERF=1` is in the environment (`YM_PERF=0` turns it off in a development build). Everything goes to the local log (`logs/yellowmoon.log`, and stderr in a development build) with the target `ym::perf`; nothing is sent anywhere (hard rule 7). With it off, each hook is a flag check. A window with nothing in it is not logged, so an app left open on an idle photo does not fill the log.

**What the log says**, every 5 s while the app is in use:

| Line | Meaning |
|---|---|
| `main thread: waits <4 ms a, <8 ms b, <16 ms c, <33 ms d, <100 ms e, slower f; worst N ms` | A watchdog thread posts a closure to the main thread every 4 ms and times how long it waited: how long the page, the menu and the window would have waited for the main thread. Healthy is nearly everything under 4 ms. Written when the window had viewport activity or a wait of 8 ms or more |
| `the main thread stalled` (warn, `lag_ms`) | One wait of 33 ms or more, at the moment it happens |
| `viewport: requests R, rounds N, presented P, cancelled C, tiles cancelled T, request to present p50 X ms p95 Y ms (n K), drawn zero-copy Z uploaded U, set_rect …, ym-frame …, acquire mean … max …, upload mean … max …, pass mean … max …` | The viewport worker. `requests` is what the webview asked for (inputs, patches, cell, Before, mode), `rounds` the renders the worker started, `presented` the frames that reached the sink, `cancelled` the rounds that ended with no frame (before the change of 2026-10-16, `docs/01` §Native viewport, nearly every round during a drag), `tiles cancelled` the sharp-tile passes given up for a newer request (expected). `request to present` is the time from the oldest request a round answers to the moment its frame was presented (a sharp follow-up has none). `acquire` is the native sink waiting for a drawable (a display wait: close to one refresh means the worker waits for the display, `docs/STATUS.md` lists the next step), `upload` the copy of a host frame into the sink's texture, `pass` the sink recording its pass into the drawable, submitting it and presenting. `drawn zero-copy Z uploaded U` (native sink only) counts the frames drawn straight from the core's device (`docs/17` §16: no readback, no upload) and the host frames uploaded first; with the core's device in use nearly every frame is zero-copy, at every zoom (since 2026-10-20 a view magnified above 100 % is a device frame too, cut into bands when it is too big for one binding like any other view). `set_rect` is the `viewport_set_rect` command (main thread; one of 2 ms or more is a warn of its own), `ym-frame` a request of the frame scheme from the handler being called to the response being ready (thread wait plus the work) |

A drag that works shows `presented` close to `rounds` and `cancelled` near 0; one that starves shows `requests` far above `presented` and `cancelled` close to `rounds`. A wait-bound pipeline shows `acquire` near a refresh. A Look-tab burst or a 500-file open that hurts shows up as `main thread` waits above 16 ms and `ym-frame` maxima.

**The viewport job** (`.github/workflows/build.yml`, `macos-15`). The job opens the owner's photos in the debug build with `YM_SMOKE_OPEN`, captures the screen when the native viewport shows a picture, and then (`YM_PERF_SCRIPT=1`, at `YM_PERF_SCRIPT_AT` seconds, 70 in the job) drives the page like a hand: 240 `ctrl+wheel` events (a zoom in about the middle of the cell, 200 in and 40 out), 240 pan wheel events and 60 keyboard moves of the Temperature slider (`shift`+arrow, in blocks of 10 alternating direction), 8 ms apart by a timer (which keeps to it only roughly: the milliseconds each phase really took are in the result). The driver is `SMOKE_PERF_SCRIPT` in `src-tauri/src/app.rs` (debug builds only, like the rest of the smoke run; it looks for `[data-viewport]` and the label "Temperature" and says what it did not find in `missing`). It leaves its result in `window.__ymPerfResult`, which the smoke thread polls with `eval_with_callback` (a script that is evaluated does not wait for promises, so the page's `window.__ymPerf.snapshot()` of `src/perf.ts` must answer at once). The job summary shows every `ym::perf` line, the `smoke: perf script` result and the `smoke: perf page` snapshot. The page's counters need the page to be told to measure: with `YM_PERF` set (not empty, not `0`) the shell registers a plugin with no commands whose initialisation script is `window.__YM_PERF__ = true;` (`perf::page_plugin`, `src-tauri/src/perf.rs`; Tauri runs it in the main frame before the page's own scripts, the window of `tauri.conf.json` included) and `perfRequested` in `src/perf.ts` reads it. A plain debug build does not set it, so the page measures only when asked there with `?perf` or `localStorage.ymPerf`. If the flag does not arrive, the snapshot is `null` and the job says so with a warning (`smoke: perf page null`), still without failing; checked on Linux under Xvfb with the debug app: `YM_PERF=1` gives a snapshot with the api's calls and `store.notify`, no `YM_PERF` gives `null`. **It never fails on the numbers**: thresholds change only with the owner's say (`AGENTS.md`). The job builds the development profile on a shared runner with no trackpad: the counts (presented, cancelled, requests per frame, renders per event) are the evidence, absolute times are not; the WebKit scroll path (the rubber band) cannot be driven from there and stays a manual check (`docs/STATUS.md`, M0-H4). A release-profile run (`cargo build --release -p yellowmoon-app --features custom-protocol`, `YM_PERF=1`) would give honest times; the smoke driver is not in a release build, so the log alone would be read. **What the job checks about the page** (`smoke: the page lets the viewport through`, which fails the job when it says no): the boxes under the middle of the cell are listed by `elementsFromPoint`, which skips what takes no pointer events and ignores masks, so the dark glass interface's aurora (opaque, `pointer-events-none`, kept off the cell by a two-layer CSS mask sized from `--cell-x/y/w/h`) is never in that list. `SMOKE_DESCRIBE_PAGE` therefore also reads the aurora's computed mask and the cell variables, and `page_paints_over_cell` (`src-tauri/src/app.rs`) requires: no box over the cell with a background colour, a background image or a backdrop blur; a mask whose first layer is composited with `exclude` or `xor`; a second layer in pixels at the cell's rectangle (1.5 px of room); and `--cell-x/y/w/h` set. Each problem is printed as `smoke: the page paints over the cell: …`. The same script runs in Chromium in `e2e/viewport.spec.ts`, so a rename of `.ym-aurora` or a change of the mask is caught on Linux before the Mac job. It still reads the page, not the pixels: the `screencapture` PNGs are artefacts and nothing asserts on them.

**Unit tests** (`cargo test -p yellowmoon-app --bin yellowmoon-app`): `perf::tests` (windows, percentiles, the histogram's buckets, the switch), `viewport::tests` (which request stops which render, the launch id, what is cached, the cap of `snapshot_synced`, and a run with the synthetic ARW harness: 200 settings changes 2 ms apart must present more than one frame), `events::tests` (1,000 `render_stats` give at most one send per period and the last value arrives; terminal `photo_progress` states always arrive, in order, for hundreds of photos reported from four threads), `app::tests` (the `ym-frame` answers and their `Cache-Control`; the handler returns at once while another thread holds the store).

### Checking the macOS code on Linux

`src-tauri/src/native.rs` is built for macOS only, so `cargo check` on Linux never sees it. With the target installed (`rustup target add aarch64-apple-darwin`) it type-checks and lints from Linux, but the build scripts of `ring` and `objc2-exception-helper` compile C and Objective-C with the host `cc` and the macOS SDK's headers, which are not there. Nothing is linked in a check, so a stand-in compiler that writes an empty object file is enough:

```sh
cat > /tmp/fakecc.sh <<'EOF'
#!/bin/bash
out=""; prev=""; compile=0
for a in "$@"; do [ "$prev" = "-o" ] && out="$a"; [ "$a" = "-c" ] && compile=1; prev="$a"; done
if [ "$compile" = 1 ] && [ -n "$out" ]; then echo "" | clang --target=arm64-apple-macosx -x c -c - -o "$out"; exit $?; fi
exec clang "$@"
EOF
chmod +x /tmp/fakecc.sh
CC_aarch64_apple_darwin=/tmp/fakecc.sh AR_aarch64_apple_darwin=llvm-ar CARGO_INCREMENTAL=0 \
  cargo clippy -p yellowmoon-app --target aarch64-apple-darwin --all-targets -- -D warnings
rm -rf /absolute/path/to/target/aarch64-apple-darwin   # about 270 MB
```

It proves the Rust compiles and lints, not that the layer draws: the Mac checks are `docs/11` §Native viewport and the `viewport` job.

## Golden images

Four tiers, so CI works for everyone (a fifth source, local-eval, sits outside the golden set; see the last bullet):

- **Synthetic tier (stop-gap):** the generated set above (`tier: "synthetic"` in the manifest; the evaluation scene is `synthetic-eval`, local only). It needs no download, so it is the only golden tier that can run in the environment that wrote this plan, and it runs wherever `tools/fetch/synthetic.sh` does (a few minutes). It is a **stop-gap until the CC0 tier is fetchable**: it tests regressions of our own pipeline on known, reproducible inputs and gives colour and exposure checks against ground truth, but it is not a stand-in for real files, and its references are our own earlier outputs like every golden reference. When the CC0 tier works, the synthetic entries stay as the always-available baseline (and the only source of ground truth for colour); they do not replace the real files. Generation is a pure function of the recipes, the code version and the library versions, so the manifest lists the files and their parameters and **no content hash of the ARW files** (another numpy version may draw other noise): the expected output hash and the reference image belong to the golden runner and its stored references.
- **CC0 tier:** RawDB and raw.pixls.us files with fixed settings. Runs on every push and pull request, including forks.
- **Free-licence tier:** the Play Raw files (CC0, CC BY, CC BY-SA) with attribution in the manifest. Same triggers; fetched from their original URLs or from a public test bucket that keeps the attributions.
- **Evaluation tier:** copyrighted files (Photography Life, Imaging Resource), downloaded by hand to a development machine for visual review and the blind A/B only. Never in CI, never uploaded.
- **Not a tier, but next to them: local-eval.** Nine real Sony files of unclear or restricted licence that `tools/fetch/real-eval.sh` fetches from public GitHub repositories (pinned commits and blob ids) into `testdata/real/` on a development machine: smoke tests that skip without them, the auto-exposure study (`tools/eval`), visual checks. Same rules as the evaluation tier (never committed, never uploaded, the script refuses to run in CI), and no gate and no golden test depends on them. Which files, from where and under what licence: `docs/validation-data.md` (the local-eval tier) and `docs/test-photo-sources.md`.


- `tools/golden/manifest.json` lists files, settings (JSON, same schema as `ym:Settings`) and the expected output hash and a reference image (16-bit PNG, stored outside git with the test data). Each entry also has `tier` (`synthetic`, `synthetic-eval`, and for the real files `cc0`, `free`, `eval`), `id`, `file` (relative to `testdata/`) and, for generated files, `sidecar` (the scene's ground truth), `scene`, `light`, `body`, `model_id`, `iso`, `cfa`, `bits`, `variant`, `group` and `set` (`default`: a plain `synthetic.sh` run writes the file, 61 of them; `full`: only with `--full`, 35; `eval`: only with `--full`, the CIE scene, 18). A runner that takes `set == "default"` therefore finds exactly the files of the default run. The synthetic entries are written by `python3 -m training.synth.make_scenes --write-manifest tools/golden/manifest.json` (one per ARW file, with `settings: {}`, i.e. everything Auto; `expected_hash` and `reference` stay empty on purpose, because the runner keeps its hashes in `tools/golden/expected.json` and its pictures in `testdata/golden/refs/`, see below); a test checks the committed file against the recipes. Entries of other tiers are left alone by that command.
- The runner renders through `ym render --json --settings <manifest entry>`, compares with the reference: ΔE00 per pixel on a 1/4-resolution downsample; reports median, p99 and max.
- When a change is intended, the PR updates the references with a note and (if pixels changed) bumps `pipeline_version`.

**As built (M1-15 golden runner, `tools/golden`).** Commands: `golden check`, `golden update --note "why"`, `golden truth`, `golden synth`; options and exit codes in `tools/golden/README.md`. The decisions:

- *Rendering.* One `ym render --json --quiet --settings <the entry's settings> --format png --bits 16 --colour-space srgb` process per file, in an empty `YELLOWMOON_HOME` (so the user's default look, display rendering and imported looks cannot change a golden render). Not one process for a batch: a photo's automatic exposure and its pooled noise model depend on the other photos of the run (burst grouping by capture time, `docs/01`), so the same file rendered in other company would give other pixels and the hashes would depend on `--filter`. A 16-bit PNG, not a JPEG: no dither and no lossy coding between the pipeline and the comparison. The default synthetic set (61 files at 1248 x 832) takes about 100 s on four cores shared with other jobs (`--jobs 2`).
- *Hashes in git, pictures outside.* `tools/golden/expected.json` (committed) holds the SHA-256 of the decoded 16-bit samples (and size) of every golden picture and a log of explained updates; the PNG carries the application version in its XMP, so the hash is over the pixels and not the file. The pictures themselves are `testdata/golden/refs/<id>.png` (git-ignored, about 280 MB for the default synthetic set; the CI cache). A file whose hash is the expected one is *identical* and needs no stored picture; the picture is read only to measure a change.
- *The gate.* A changed file is compared with its reference picture: ΔE00 (`ym_color::deltae`) per pixel on a 4 x 4 box-filtered (linear light) downsample, reported as median, p99 and maximum. The run fails when the **maximum** exceeds the tolerance (`--tolerance`, 0.5; `--metric p99` holds the 99th percentile against it instead), when a file changed and no reference picture exists to say by how much (`NO REFERENCE`), when the reference is not the picture `expected.json` describes (`STALE REFERENCE`), when `expected.json` has no entry for the file, when the picture changed size, or when `ym` failed. A file that is not on disk is skipped (`--require-all` fails it); a run that checked nothing exits 3. It prints a reminder when pixels moved and `pipeline_version` did not.
- *"Explained."* `golden update --note "why"` renders the selection again, writes the new pictures and hashes, and appends the note, the pipeline version and the largest ΔE00 any picture moved by to the log in `expected.json`. Without a note an update that would change an existing picture prints the pictures and their ΔE00 and writes nothing (exit 1). So the explanation is the committed note and the new hashes; an unexplained change leaves the old hash in git and fails the check. Added files need no note.
- *Sets.* `--set synthetic` (tier `synthetic`, set `default`: what a plain `tools/fetch/synthetic.sh` writes), `synthetic-full`, `synthetic-eval` (local), `cc0`, `tier2` (tier `free`), `tier3` (local, never CI), `all`; `--filter TEXT` narrows by id. The `cc0` and `free` entries come with `tools/fetch/golden.sh` once the hosts are reachable; the runner needs nothing else for them.
- *Platform.* The render is CPU code in f64 and f32 with no fused multiply-add and no thread-dependent reduction (checked: one thread and eleven threads give the same hashes as the run that wrote `expected.json`), so the 16-bit codes do not depend on the machine except through the last bit of a platform `libm` function. That a code moves because of it is an estimate (about 1e-4 per picture), not a measurement: no second platform was available when this was written. If a hash differs only in a few codes on another platform, the check falls back to the reference picture and measures it (ΔE00 of that should be below 0.01); record such a platform in the note of the update. A machine without the reference pictures cannot do that fall back and reports `NO REFERENCE`: keep the CI cache warm (GitHub evicts a cache that nobody has used for seven days, so the `golden` job also runs on the nightly schedule, on the default set). `expected.json` here was written on Linux x86_64. The hashes are those of the `ym` that was built when they were written: any later change to the pipeline moves them and needs `golden update --note` with the change.
- *CI.* The `golden` job of `ci.yml` (ubuntu-24.04, not the moving `ubuntu-latest` label: the render is CPU code that calls the platform libm, and `expected.json` was written on Linux x86_64 with the glibc 2.39 of Ubuntu 24.04) installs the pinned toolchain, generates the synthetic set (`tools/fetch/synthetic.sh --release`), builds `ym` and `golden` (in two `cargo build` calls, not `-p ym-cli -p golden` in one: `golden` switches on `ym-raw`'s test-only `testgen` feature, and one build gives every package the union of the features, so the `ym` under test would carry the test writer that the shipped one does not; `cargo tree -p ym-cli -p golden -e normal -i ym-raw` shows it), restores `testdata/golden/refs` from a cache keyed on `expected.json`, runs `golden check --require-all --write-missing-refs` (`--require-all`: a file that is not on disk fails the run instead of being skipped, so a half generated set cannot pass; identical pictures without a reference file get one, so a green run fills the cache) and `golden truth` (a report with no gate, copied to the job summary), runs the auto-exposure gate (G3, `tools/eval/autoexp.py --gate`) on the same `ym` and the same synthetic set (37 files, one raw variant per scene; machinery only), and uploads the JSON reports. It runs on every push and pull request and on the nightly schedule, so the cache is used at least once a day (GitHub evicts one that nobody has used for seven days); the nightly runs the default set, because `--set synthetic-full` has no entries in `expected.json` yet. The generator's output was byte-identical under numpy 2.2.6 / scipy 1.15.3 / Pillow 11.3.0 and numpy 2.5.4 / scipy 1.18.1 / Pillow 12.3.0 (checked on one scene), so the Python requirements are not pinned beyond colour-science; if a hash differs on a fresh runner with no code change, pin those three first. A release `ym` finds its data folder through `YELLOWMOON_DATA` (the job sets it to the checkout's `data/`). The `dng` job is the same shape for the DNG gates: it builds `dng_validate` once (cached binary, saved right after the build so that a failing gate does not lose it; the job runs on ubuntu-24.04, where `libjxl-dev` is 0.7), then `cargo test --release -p ym-export --test dng_validate`, `cargo test --release -p dngfit` and `tools/dng/run_gates.sh --png`, with `YM_REQUIRE_EXTERNAL_TOOLS=1` so that a missing tool fails instead of skipping.

**End-to-end colour against the ground truth (`golden truth`, first measurement, 2026-10-12).** For each synthetic scene the real `ym` writes a DNG with default settings; the DNG holds the picture after the colour chain up to the look and curve (C1 to C11) as linear AWG4, the last place before the display transform where it can be compared with the ALEXA estimate of the sidecar without a tone curve. Per patch the interior is averaged in linear light, the picture is scaled by 0.18 over the luminance of its 18 % grey patch (the truth is reflectance-referred, a render has its own automatic exposure: one number, so a white-balance error stays in the result) and CIEDE2000 is taken in CIELAB of the AWG4 colours (white = a perfect white of the scene) against `truth.probes[].alexa.awg4`. "Baseline" is Sony camera RGB through the same ARRI matrix with no sensor map (the sidecar's `sony_through_arri`). The sensor-map gate (median at most 0.5 per held-out light, with true lights, no noise) is a different, stricter measurement; this one includes the light estimate (within 200 K of the truth in these scenes), the noise, the demosaic and the exposure scaling. The scenes, noise and lights are synthetic assumptions (`training/synth/README.md`); the number says how well the chain recovers spectral reflectances seen through the published Sony curves, not how it does on real cameras.

## Blind A/B protocol [HUMAN]

- 50 A1 photos covering daylight, shade, tungsten, LED, mixed light, night, skin, foliage, high ISO.
- Each photo exported by Yellowmoon (Neutral look) and by Capture One, Lightroom and DxO with default settings and a matched exposure. Pairs shown in random order and side, on a calibrated P3 display, through a small web page that records choices (`tools/abtest`, written by the agent).
- Raters: Mykyta plus at least two others. Report preference with a binomial confidence interval.
