## GPU tests without a GPU

GitHub-hosted macOS runners may not expose a Metal device. GPU tests look for an adapter and skip with a clear message when none exists, unless `YM_REQUIRE_GPU=1` is set. The `gpu-lavapipe` CI job sets it and runs the kernels on Mesa's software Vulkan driver, which checks correctness (not speed). Metal behaviour and performance are checked on a real Mac before each gate [HUMAN M0-H4] or on a self-hosted Apple silicon runner if Mykyta registers one.

**As built (M0-07, M1-09 to M1-11).** `crates/ym-gpu/tests/common` opens one device per f16 storage mode the adapter supports (native `f16`, packed `f16`, plain f32; each is a separate device, so every mode is exercised) and skips when `Gpu::start` finds no adapter; with `YM_REQUIRE_GPU=1` that is a panic. A skipped test passes without testing anything (its loops are empty), so the skip is announced loudly: a banner written straight to the process's stderr, which the harness's output capture does not swallow (`eprintln!` from a passing test is captured and would have been invisible), plus a `::warning::` annotation on GitHub Actions; `a_missing_adapter_skips_loudly_or_fails_when_required` runs one GPU test in a child process on a backend that cannot exist (DirectX 12 on Linux and macOS) to prove both halves of the contract. Run them with `WGPU_BACKEND=vulkan YM_REQUIRE_GPU=1 cargo test -p ym-gpu` (about 3 minutes in debug on a loaded 4-core machine, almost all of it compiling, and 20 seconds of test time in release; the 50 MP test is `#[ignore]`, `cargo test -p ym-gpu --release --test gpu_spike -- --ignored --nocapture gpu_spike_50mp`, 43 seconds on lavapipe in release including the CPU reference).

## Test data

Never commit raw files or large data. `tools/fetch/` downloads into `testdata/` (git-ignored) and checks SHA-256 against `tools/fetch/manifest.json`. CI caches `testdata/` keyed on the manifest hash. Usage, manifest format, licence rules and exit codes: `tools/fetch/README.md`. Which data backs which gate, where it may be stored and what is reachable from the agent environment: `docs/validation-data.md`.

**Status of the corpus (M0-09).** rawdb.dnglab.org, raw.pixls.us and discuss.pixls.us were blocked where the scripts were written, so `manifest.json` ships with the body list and an empty file list; `samples.sh --refresh` on a machine with open internet fills it. Until then decoder, detection and pipeline tests run on synthetic ARW files from the test-only writer (`ym-raw`, feature `testgen`) with LibRaw (rawpy) and rawler as independent oracles. Results obtained that way are reported as "synthetic only" and do not close a corpus gate.

**The synthetic ARW set (stop-gap).** `tools/fetch/synthetic.sh` generates a deterministic, physically based synthetic set into `testdata/synthetic/` (git-ignored; scenes in `scenes/`, ARW files in `arw/`; files directly in `testdata/synthetic/` are leftovers of an older generator (`ym-raw`'s `gen_corpus` example writes `testdata/oracle-synthetic` now); no test reads them and this script leaves them alone, so they can be deleted; about 37 mosaics and 61 ARW files, under 300 MB, a few minutes; `--full` adds every light under every body, a 6240 x 4160 scene for timing and an evaluation scene with the CIE CES: 88 mosaics, 114 files, about 740 MB; measured on the shared 4-core build machine, the default set takes 2.5 minutes cold). `training/synth` renders scenes (the 190 rawtoaces reflectances in a chart with gradients, a neutral ramp, a zone plate, slanted edges, a blown highlight and a deep shadow) under blackbody 2850 and 3200 K, CIE D 5500, 6500 and 7500 K, FL11, LED-B3, LED-V2 and one mixed light, through the published curves of six bodies (A7R IV, A7 III, A7S III, A6400, RX100 IV, and the A1 with model ID 384 on the A7R IV curves), with a known Poisson-Gaussian noise model and four CFA phases, as raw mosaics with a JSON sidecar of ground truth (the true light and white, the noise model, per patch the ALEXA-estimate reference in AWG4 and LogC4 and the "Sony through ARRI matrix" baseline, a made-up embedded JPEG). `golden synth` writes each mosaic as uncompressed 14-bit, packed 12-bit, cRAW, lossless L and lossless M/S ARW files through `ym_raw::testgen` and checks that decoding gives the mosaic back (exactly, or within `qstep / 2` for cRAW). Details: `training/synth/README.md`. The ground truth was recomputed by code that shares nothing with the generator except the data files (the published curves, the rawtoaces reflectances, ARRI's runtime matrix table) and agrees to the nine digits the sidecars keep on every patch (checked on all 37 default scenes in the review, on four in `training/synth/test_synth.py`, `IndependentRecomputation`); the mosaics hold the stated camera DN and noise (mean within sampling error, variance `a x + b + 1/12`). The set is **synthetic only**: it exercises the decoder, the colour chain and the comparison machinery, and says nothing about real cameras, real tone curves or real noise. The noise parameters and the JPEG rendering are our own assumptions, labelled as such in every sidecar.

Independent readers check the set: LibRaw (rawpy) reproduces the mosaic exactly for every uncompressed, packed 12-bit and lossless L file it reads (LibRaw reads lossless L only for the ILCE-1, 7x and 9x models; the A6400 and RX100 IV files are reported as a model gate), agrees with ym-raw on every cRAW file and on the Lossless M/S pseudo-raw RGB, and ExifTool reads back every metadata field and the embedded preview (`tools/golden/oracle_check.py`, `synthetic.sh --oracle`).

## Golden images

Four tiers, so CI works for everyone (a fifth source, local-eval, sits outside the golden set; see the last bullet):

- **Synthetic tier (stop-gap):** the generated set above (`tier: "synthetic"` in the manifest; the evaluation scene is `synthetic-eval`, local only). It needs no download, so it is the only golden tier that can run in the environment that wrote this plan, and it runs wherever `tools/fetch/synthetic.sh` does (a few minutes). It is a **stop-gap until the CC0 tier is fetchable**: it tests regressions of our own pipeline on known, reproducible inputs and gives colour and exposure checks against ground truth, but it is not a stand-in for real files, and its references are our own earlier outputs like every golden reference. When the CC0 tier works, the synthetic entries stay as the always-available baseline (and the only source of ground truth for colour); they do not replace the real files. Generation is a pure function of the recipes, the code version and the library versions, so the manifest lists the files and their parameters and **no content hash of the ARW files** (another numpy version may draw other noise): the expected output hash and the reference image belong to the golden runner and its stored references.
- **CC0 tier:** RawDB and raw.pixls.us files with fixed settings. Runs on every push and pull request, including forks.
- **Free-licence tier:** the Play Raw files (CC0, CC BY, CC BY-SA) with attribution in the manifest. Same triggers; fetched from their original URLs or from a public test bucket that keeps the attributions.
- **Evaluation tier:** copyrighted files (Photography Life, Imaging Resource), downloaded by hand to a development machine for visual review and the blind A/B only. Never in CI, never uploaded.
- **Not a tier, but next to them: local-eval.** Nine real Sony files of unclear or restricted licence that `tools/fetch/real-eval.sh` fetches from public GitHub repositories (pinned commits and blob ids) into `testdata/real/` on a development machine: smoke tests that skip without them, the auto-exposure study (`tools/eval`), visual checks. Same rules as the evaluation tier (never committed, never uploaded, the script refuses to run in CI), and no gate and no golden test depends on them. Which files, from where and under what licence: `docs/validation-data.md` (the local-eval tier) and `docs/test-photo-sources.md`.


- `tools/golden/manifest.json` lists files, settings (JSON, same schema as `ym:Settings`) and the expected output hash and a reference image (16-bit PNG, stored outside git with the test data). Each entry also has `tier` (`synthetic`, `synthetic-eval`, and for the real files `cc0`, `free`, `eval`), `id`, `file` (relative to `testdata/`) and, for generated files, `sidecar` (the scene's ground truth), `scene`, `light`, `body`, `model_id`, `iso`, `cfa`, `bits`, `variant`, `group` and `set` (`default`: a plain `synthetic.sh` run writes the file, 61 of them; `full`: only with `--full`, 35; `eval`: only with `--full`, the CIE scene, 18). A runner that takes `set == "default"` therefore finds exactly the files of the default run. The synthetic entries are written by `python3 -m training.synth.make_scenes --write-manifest tools/golden/manifest.json` (one per ARW file, with `settings: {}`, i.e. everything Auto; `expected_hash` and `reference` stay empty on purpose, because the runner keeps its hashes in `tools/golden/expected.json` and its pictures in `testdata/golden/refs/`, see below); a test checks the committed file against the recipes. Entries of other tiers are left alone by that command.
- The runner renders through `ym render --json --settings <manifest entry>`, compares with the reference: ΔE00 per pixel on a 1/4-resolution downsample; reports median, p99 and max.
- When a change is intended, the PR updates the references with a note and (if pixels changed) bumps `pipeline_version`.

**As built (M1-15 golden runner, `tools/golden`).** Commands: `golden check`, `golden update --note "why"`, `golden truth`, `golden synth`; options and exit codes in `tools/golden/README.md`. The decisions:

- *Rendering.* One `ym render --json --quiet --settings <the entry's settings> --format png --bits 16 --colour-space srgb` process per file, in an empty `YELLOWMOON_HOME` (so the user's default look, display rendering and imported looks cannot change a golden render). Not one process for a batch: a photo's automatic exposure and its pooled noise model depend on the other photos of the run (burst grouping by capture time, `docs/01`), so the same file rendered in other company would give other pixels and the hashes would depend on `--filter`. A 16-bit PNG, not a JPEG: no dither and no lossy coding between the pipeline and the comparison. The default synthetic set (61 files at 1248 x 832) takes about 100 s on four cores shared with other jobs (`--jobs 2`).
- *Hashes in git, pictures outside.* `tools/golden/expected.json` (committed) holds the SHA-256 of the decoded 16-bit samples (and size) of every golden picture and a log of explained updates; the PNG carries the application version in its XMP, so the hash is over the pixels and not the file. The pictures themselves are `testdata/golden/refs/<id>.png` (git-ignored, about 280 MB for the default synthetic set; the CI cache). A file whose hash is the expected one is *identical* and needs no stored picture; the picture is read only to measure a change.
- *The gate.* A changed file is compared with its reference picture: ΔE00 (`ym_color::deltae`) per pixel on a 4 x 4 box-filtered (linear light) downsample, reported as median, p99 and maximum. The run fails when the **maximum** exceeds the tolerance (`--tolerance`, 0.5; `--metric p99` holds the 99th percentile against it instead), when a file changed and no reference picture exists to say by how much (`NO REFERENCE`), when the reference is not the picture `expected.json` describes (`STALE REFERENCE`), when `expected.json` has no entry for the file, when the picture changed size, or when `ym` failed. A file that is not on disk is skipped (`--require-all` fails it); a run that checked nothing exits 3. It prints a reminder when pixels moved and `pipeline_version` did not.
- *"Explained."* `golden update --note "why"` renders the selection again, writes the new pictures and hashes, and appends the note, the pipeline version and the largest ΔE00 any picture moved by to the log in `expected.json`. Without a note an update that would change an existing picture prints the pictures and their ΔE00 and writes nothing (exit 1). So the explanation is the committed note and the new hashes; an unexplained change leaves the old hash in git and fails the check. Added files need no note.
- *Sets.* `--set synthetic` (tier `synthetic`, set `default`: what a plain `tools/fetch/synthetic.sh` writes), `synthetic-full`, `synthetic-eval` (local), `cc0`, `tier2` (tier `free`), `tier3` (local, never CI), `all`; `--filter TEXT` narrows by id. The `cc0` and `free` entries come with `tools/fetch/golden.sh` once the hosts are reachable; the runner needs nothing else for them.
- *Platform.* The render is CPU code in f64 and f32 with no fused multiply-add and no thread-dependent reduction (checked: one thread and eleven threads give the same hashes as the run that wrote `expected.json`), so the 16-bit codes do not depend on the machine except through the last bit of a platform `libm` function. That a code moves because of it is an estimate (about 1e-4 per picture), not a measurement: no second platform was available when this was written. If a hash differs only in a few codes on another platform, the check falls back to the reference picture and measures it (ΔE00 of that should be below 0.01); record such a platform in the note of the update. A machine without the reference pictures cannot do that fall back and reports `NO REFERENCE`: keep the CI cache warm (GitHub evicts a cache that nobody has used for seven days, so the `golden` job also runs on the nightly schedule, on the default set). `expected.json` here was written on Linux x86_64. The hashes are those of the `ym` that was built when they were written: any later change to the pipeline moves them and needs `golden update --note` with the change.
- *CI.* The `golden` job of `ci.yml` (ubuntu-24.04, not the moving `ubuntu-latest` label: the render is CPU code that calls the platform libm, and `expected.json` was written on Linux x86_64 with the glibc 2.39 of Ubuntu 24.04) installs the pinned toolchain, generates the synthetic set (`tools/fetch/synthetic.sh --release`), builds `ym` and `golden` (in two `cargo build` calls, not `-p ym-cli -p golden` in one: `golden` switches on `ym-raw`'s test-only `testgen` feature, and one build gives every package the union of the features, so the `ym` under test would carry the test writer that the shipped one does not; `cargo tree -p ym-cli -p golden -e normal -i ym-raw` shows it), restores `testdata/golden/refs` from a cache keyed on `expected.json`, runs `golden check --require-all --write-missing-refs` (`--require-all`: a file that is not on disk fails the run instead of being skipped, so a half generated set cannot pass; identical pictures without a reference file get one, so a green run fills the cache) and `golden truth` (a report with no gate, copied to the job summary), runs the auto-exposure gate (G3, `tools/eval/autoexp.py --gate`) on the same `ym` and the same synthetic set (37 files, one raw variant per scene; machinery only), and uploads the JSON reports. It runs on every push and pull request and on the nightly schedule, so the cache is used at least once a day (GitHub evicts one that nobody has used for seven days); the nightly runs the default set, because `--set synthetic-full` has no entries in `expected.json` yet. The generator's output was byte-identical under numpy 2.2.6 / scipy 1.15.3 / Pillow 11.3.0 and numpy 2.5.4 / scipy 1.18.1 / Pillow 12.3.0 (checked on one scene), so the Python requirements are not pinned beyond colour-science; if a hash differs on a fresh runner with no code change, pin those three first. A release `ym` finds its data folder through `YELLOWMOON_DATA` (the job sets it to the checkout's `data/`). The `dng` job is the same shape for the DNG gates: it builds `dng_validate` once (cached binary, saved right after the build so that a failing gate does not lose it; the job runs on ubuntu-24.04, where `libjxl-dev` is 0.7), then `cargo test --release -p ym-export --test dng_validate`, `cargo test --release -p dngfit` and `tools/dng/run_gates.sh --png`, with `YM_REQUIRE_EXTERNAL_TOOLS=1` so that a missing tool fails instead of skipping.

**End-to-end colour against the ground truth (`golden truth`, first measurement, 2026-10-12).** For each synthetic scene the real `ym` writes a DNG with default settings; the DNG holds the picture after the colour chain up to the look and curve (C1 to C11) as linear AWG4, the last place before the display transform where it can be compared with the ALEXA estimate of the sidecar without a tone curve. Per patch the interior is averaged in linear light, the picture is scaled by 0.18 over the luminance of its 18 % grey patch (the truth is reflectance-referred, a render has its own automatic exposure: one number, so a white-balance error stays in the result) and CIEDE2000 is taken in CIELAB of the AWG4 colours (white = a perfect white of the scene) against `truth.probes[].alexa.awg4`. "Baseline" is Sony camera RGB through the same ARRI matrix with no sensor map (the sidecar's `sony_through_arri`). The sensor-map gate (median at most 0.5 per held-out light, with true lights, no noise) is a different, stricter measurement; this one includes the light estimate (within 200 K of the truth in these scenes), the noise, the demosaic and the exposure scaling. The scenes, noise and lights are synthetic assumptions (`training/synth/README.md`); the number says how well the chain recovers spectral reflectances seen through the published Sony curves, not how it does on real cameras.

## Blind A/B protocol [HUMAN]

- 50 A1 photos covering daylight, shade, tungsten, LED, mixed light, night, skin, foliage, high ISO.
- Each photo exported by Yellowmoon (Neutral look) and by Capture One, Lightroom and DxO with default settings and a matched exposure. Pairs shown in random order and side, on a calibrated P3 display, through a small web page that records choices (`tools/abtest`, written by the agent).
- Raters: Mykyta plus at least two others. Report preference with a binomial confidence interval.
