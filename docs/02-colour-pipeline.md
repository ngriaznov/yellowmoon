# 02 · Colour pipeline

Crates: `ym-color` (CPU reference, constants, fitting helpers), `ym-gpu` (WGSL kernels). Data: `data/alexa/`, `data/arri/`, `data/cameras/`.

## Idea in one paragraph

A Sony sensor and an ALEXA sensor see the same scene differently, and how differently depends on the light. We estimate the light in each photo, then map white-balanced Sony RGB to what the ALEXA's sensor would have recorded under that light (the **sensor map**). From there we follow ARRI's published processing: ALEXA white balance at the user's colour temperature, ARRI's colour matrix for that temperature, ARRI Wide Gamut, LogC. Looks and the display transform work on LogC4 exactly as they do for ALEXA footage. Two quantities stay separate on purpose: the **scene light** (estimated) drives the sensor map; the **user's CCT** drives the ALEXA white balance and the ARRI matrix. "3200 K under daylight" therefore looks the way it would on an ALEXA.

## Stage order

Input to this chain is the output of `docs/05-raw-processing.md`: demosaiced, denoised, lens-corrected, scene-linear camera RGB, black-subtracted, white level = 1.0, balanced with the **initial** gains `g0` used for highlight recovery and demosaic.

| # | Stage | Space in → out | Where |
|---|---|---|---|
| C1 | Residual white balance to the scene light | camera RGB (g0-balanced) → camera RGB balanced for the scene light | fused 3×3 |
| C2 | Sensor map for the scene light | balanced Sony RGB → balanced ALEXA native RGB | fused 3×3 |
| C3 | Re-apply ALEXA's own white for the scene light | balanced → ALEXA native (unbalanced) | fused 3×3 |
| C4 | ALEXA white balance at the user's CCT and tint | ALEXA native → ALEXA native, balanced for the user's white | fused 3×3 |
| C5 | ARRI matrix at the user's CCT | ALEXA native → linear AWG3 | fused 3×3 |
| C6 | AWG3 → AWG4, exposure | → linear AWG4, scene-referred | fused 3×3 |
| C7 | Highlight range and low-light toe | linear AWG4 → linear AWG4 | per pixel |
| C8 | LogC4 encode | linear AWG4 → LogC4 | per pixel |
| C9 | Primary grade (contrast, brightness, zones, colour balance, saturation) | LogC4 → LogC4 | per pixel |
| C9b | Colour warp: pins that move chosen colours across the chroma plane | LogC4 → LogC4 | per pixel + pins in the uniform block |
| C10 | Look: CDL, then 3D LUT, blended by intensity | LogC4 → LogC4 (LogC3 looks via exact conversion) | per pixel + f32 LUT storage buffer |
| C11 | Curve | LogC4 → LogC4 | f32 curve tables (storage buffer) |
| C12 | Display transform: ACES 2 (default; the display placement and the white lift come first) or an imported ARRI display LUT | LogC4 → display linear or display code values | per pixel |
| C13 | Display encode | → Display P3 (viewport) or the export colour space | per pixel |

C1–C6 are linear and fuse into **one 3×3 matrix per photo**, recomputed on the CPU when a colour setting changes:

```
M = 2^EV · M_awg3→awg4 · M_arri(CCT_user) · diag(g_user) · diag(w_A(E_scene)) · M_map(scene) · diag(g_res)
```

where every `w`, `g` is normalised so its green component is 1.

## Constants

### LogC4 (ARRI LogC4 specification, 2022)

```
a = (2^18 − 16) / 117.45     = 2231.8263090676883
b = (1023 − 95) / 1023       = 0.9071358748778103
c = 95 / 1023                = 0.09286412512218964
s = 7·ln2·2^(7 − 14c/b) / (a·b) = 0.1135972086105891
t = (2^(14·(−c/b) + 6) − 64) / a = −0.01805699611991131

encode(x) = x ≥ t ? (log2(a·x + 64) − 6) / 14 · b + c : (x − t) / s
decode(E) = E ≥ 0 ? (2^(14·(E − c)/b + 6) − 64) / a : E·s + t
```

Checks: `encode(0.18) = 0.2783958365`, `encode(0) = 0.0928641251`, `decode(1.0) = 469.8` (11.35 stops above 0.18).

### LogC3, EI 800 (ARRI LogC3 VFX document)

```
cut 0.010591  a 5.555556  b 0.052272  c 0.247190  d 0.385537  e 5.367655  f 0.092809
encode(x) = x > cut ? c·log10(a·x + b) + d : e·x + f
decode(t) = t > e·cut + f ? (10^((t − d)/c) − b) / a : (t − f) / e
```

Check: `encode(0.18) = 0.3910068` (= 400/1023 to 1e-8). LogC3 is only used to run LogC3 looks; we always use EI 800.

### ARRI CCT matrices

`data/arri/Alexa_aces_matrix.txt` (ARRI via aces-dev v1.3.1, AMPAS licence) holds camera-native → AP0 matrices at 17 CCTs: 2000, 2100, 2200, 2400, 2600, 2900, 3200, 3500, 3900, 4300, 4700, 5100, 5600, 6500, 7500, 9000, 11000 K. `data/arri/alexa_native_to_awg3_17cct.json` holds the derived native → AWG3 matrices, `inv(AWG3→AP0) · M_AP0(CCT)` with the exact matrix above; every row sums to 1 within 1e-14, as balanced input requires. `ym-color` derives them itself from the `.txt` and tests against the JSON to 1e-12.

**Interpolation:** linear in mired between the **bracketing** pair; clamp CCT to [2000, 11000]. Note: ARRI's `v3_IDT_maker.py` uses `searchsorted` and then pairs index `i` with `i+1`, which extrapolates from the next pair for CCTs between table entries. We use the bracketing pair. Both agree exactly at the 17 table CCTs; test that.

**As built (M1-01).** `ym_color::{consts, gamut, logc, arri, deltae}`.

- *Constants.* `consts` holds the primaries and whites, the normalised primary matrix (`Primaries::rgb_to_xyz`), CAT02 von Kries (`cat02_adaptation`) and the LogC constants; `gamut::matrices()` returns every derived matrix, computed once in f64. Typed linear spaces (`LinearAwg3`, `LinearAwg4`, `LinearAp0`, `LinearRec709`, `LinearDisplayP3`, `LinearRec2020`, `Xyz`) and encoded spaces (`LogC4`, `LogC3Ei800`) are newtypes over `[f64; 3]` with the conversions as methods. The LogC4 constants are stored as literals and checked against their defining formulas in the tests.
- *Checks.* Every printed matrix is reproduced to 5e-11 (the 10-decimal rounding of the f64 values; AWG3 to AP0 to 5e-10); AWG3 to AP0 equals `alexa_native_to_awg3_17cct.json`'s `awg3_to_ap0_cat02` to 1e-12; rows of AWG3/AWG4 to AP0 and of every same-white gamut matrix sum to 1 within 1e-15 (largest 6.7e-16). LogC4 round trip over [−0.02, 400]: ≤ 1e-14 + 1e-12·|x|; LogC3: 5e-13 in the linear domain (the 2.5e-7 step at `cut` only shows in code values; `encode(x)` is above `decode`'s break, so linear values round trip).
- *colour-science 0.4.7.* LogC4 and LogC3 agree to 1e-14; the sRGB transfer to 1e-14; its AWG4 matrices to 1e-9. Its AWG3 matrix is stored to 6 digits and its AP0 to 10, so AWG3 to AP0 and AWG3 to AWG4 differ from ours by up to 6e-7; ours follow the derivation from primaries. OpenColorIO's built-in `ARRI_LOGC4_to_ACES2065-1` (float32, approximate exp/pow, about 2.5e-4 relative) agrees to 2.3e-5 relative and `ARRI_ALEXA-LOGC-EI800-AWG_to_ACES2065-1` to 1.9e-4: OCIO uses ARRI's LogC3 constants at full precision (0.2471896383, …), docs/02 and the VFX document print them rounded to 6 digits, which is what we implement (relative difference ≤ 1e-5 above code value 0.1, up to 7e-4 below linear 1e-3).
- *Table loading.* `ArriTable::builtin()` embeds `data/arri/Alexa_aces_matrix.txt` with `include_str!` (3 KB; the runtime needs neither the data folder nor network, and the AMPAS notice ships with the binary). `ArriTable::parse(text)` reads any file in that format. `native_to_awg3(cct)`, `native_to_awg4(cct)`, `native_to_ap0(cct)`; `bracket(cct)` returns the pair index and the mired weight. Derived matrices agree with the JSON to 5.1e-15; table rows sum to 1 within 5e-15, derived within 5.8e-15; at the 17 table CCTs the interpolation returns the table entry bit for bit.
- *ARRI's pairing, as published.* `getIDTMatrix` in `v3_IDT_maker.py` (aces-dev v1.3.1) does `i = searchsorted(ccts, cct)`; for `i` equal to the last index it returns that row unchanged, otherwise it interpolates the pair `(i, i + 1)` in 1/CCT with a weight that is negative between two entries (an extrapolation backwards from the next pair), and above the last entry it fails. So every CCT from 9000 K to 11000 K gets the 11000 K matrix. `tests/arri.rs` reimplements that behaviour: it agrees with ours at the 17 CCTs and differs between them by up to 6.2e-3 in a matrix coefficient (at 3700 K).

## C1 · Scene light and residual white balance

- The **illuminant estimate** (below) gives the scene light as camera RGB `w_scene` (green = 1) plus class probabilities.
- Raw processing balanced the mosaic with `g0 = 1 / w_scene_initial` (`white_scale / w_scene_initial` for a body with a white scale, see *White scale of stand-in bodies* below). `g_res = w_scene_initial / w_scene` (element-wise). It is identity unless the scene light changed after open (Pick white, a light preset, Re-run).
- **Pick white:** take the 5×5 median of demosaiced camera RGB (before C1, so still balanced with `g0`) at the clicked point; reject if any channel is above 0.9 of clip ("That spot is too bright to use. Pick a grey or white area that isn't blown out."). Undo the initial gains: `w_scene = sample ⊙ w_scene_initial` (element-wise), then normalise to green = 1. Class probabilities stay as estimated.
- **Light presets** (Colour › White balance segment):

| Preset | Scene light for the sensor map | User CCT set to |
|---|---|---|
| Auto | estimate | estimated CCT |
| Day | CIE daylight 5500 K, class daylight | 5500 K |
| Shade | CIE daylight 7500 K, class daylight | 7500 K |
| Tung. | blackbody 3200 K, class tungsten | 3200 K |
| LED | estimated chromaticity, class LED = 1 | estimated CCT |
| Fluor. | estimated chromaticity, class fluorescent = 1 | estimated CCT |

**As built (M1-07), C1.** `ym_color::wb` (`SceneLight`, `EstimatorClasses`, `LightSource`, `picked_scene_white`, `residual_gains`, `median_rgb`) and `ym_color::chain`.

- *Scene light.* `SceneLight { w_scene, classes, confidence, cct_k, duv }`: the camera white (green = 1), the four profile-class probabilities, the confidence, and the CCT and Duv read from the profile's locus (`SceneLight::new`; `from_parts` takes a CCT that is already known). The estimator's six classes fold into the profile's four (`EstimatorClasses::to_profile_classes`): daylight and shade/overcast are daylight, tungsten/halogen is tungsten, fluorescent and LED stay, and the `mixed` mass goes to the class whose reference lights cover the scene CCT (tungsten below 4000 K, daylight from 4000 K, the `E_scene` rule).
- *Presets.* Day, Shade and Tungsten are model lights: the camera white is the profile locus at 5500 K, 7500 K (CIE daylight table) and 3200 K (blackbody table), the CCT is that temperature exactly, Duv 0, class probability 1, confidence 1. LED and Fluorescent keep the estimate's chromaticity, CCT and Duv and put all probability on their class. A preset always replaces the estimate; Pick white (below) replaces the estimate first, so for LED and Fluorescent the "estimated chromaticity" is the picked one while Day, Shade and Tungsten override it. The settings do not record which came last, so the front end should clear `white_pick` when a preset is chosen and set `light_source` to Auto when a white is picked.
- *Pick white.* The sample is the per-channel 5×5 median of g0-balanced camera RGB (`median_rgb`). The mosaic clips at 1.0 per channel before the gains, so channel `c` clips at `1 / w_scene_initial[c]` after `g0` (`white_scale[c] / w_scene_initial[c]` for a body with a white scale); a sample with any channel above 0.9 of that is refused with the message above (`PickWhiteError::TooBright`; a sample taken where a vignetting gain was applied should be divided by that gain first). Added: a channel that is not a number or below 1/1024 of its clip level (ten stops down) is refused with "That spot is too dark to use. Pick a grey or white area that is lit." (`TooDark`), because there is no colour in the noise floor. Bright wins when both apply. The result keeps the class probabilities, takes confidence 1 and reads CCT and Duv from the locus. `g_res` is `w_scene_initial / w_scene` with both normalised to green = 1, exactly `[1, 1, 1]` when they are equal.
- *Pick white and white balance.* A pick changes the scene light, not the user's white (`docs/11` says the core sets the white balance from the pick; it does, through the scene light). `ym-core` should leave `white_balance` Auto after a pick: the Kelvin and tint rows then show the readout of the picked light and the picked sample renders neutral exactly. Moving Kelvin switches to Manual with the sensor map still at the picked scene light.

## C2 · Sensor map

Maps white-balanced Sony RGB to white-balanced emulated ALEV III RGB for the scene light. Exposure-invariant (linear) and white-preserving (`M·[1,1,1]ᵀ = [1,1,1]ᵀ`) by construction.

**Offline fit** (Python in `training/sensor_map/fit.py`; the earlier objective is the one of the published sensor-map result, `research/alexa-ssf/out/sony_profiles.csv` (`fit.fit_map_weighted_rgb`), see step 3):

1. Inputs: the camera profile's spectral curves `S_P`, the ALEXA estimate `S_A` (`data/alexa/alexa_alev3_estimate_380_780_5.json`), the 190 rawtoaces training reflectances (Apache-2.0), and reference light SPDs.
2. Reference lights per class:
   - tungsten: blackbody 2000–4000 K every 250 K;
   - daylight: CIE daylight 4000–11000 K every 500 K;
   - fluorescent: CIE F1–F12;
   - LED: CIE LED-B1…B5, LED-BH1, LED-RGB1, LED-V1, LED-V2.

   SPDs come from the `colour-science` datasets at fit time. Only the fitted coefficients ship (`docs/14-licensing.md`).

**Gate lights (held out of the gate fit):** blackbody 2850 K, CIE daylight 5250 K and 6750 K, CIE FL3.1, FL3.8 and FL3.15, LED-B3, LED-RGB1 and LED-V2. The first three and the FL3 series fall between or outside the fit grid by construction; for the gate run, refit with LED-B3, LED-RGB1 and LED-V2 removed from the LED class. The shipped fit uses all lights. The reference numbers in `research/alexa-ssf/README.md` were measured on lights inside the fit grid, so they are a lower bound, not a target.
3. For each light `E`: Sony responses `c_s[n] = S_P·(E∘R_n)`, ALEXA responses `c_a[n] = S_A·(E∘R_n)`, each divided by its own response to the white (`R = 1`), for the 190 training reflectances `R_n`. Fit the white-preserving 3×3 that minimises the **CIE Lab error after ARRI's matrix**. Let `T_E` be the light's CCT for the ARRI lookup (the generating temperature for blackbody and CIE daylight lights, the Ohno 2013 CCT of the SPD for fluorescent and LED lights), `A(T)` ARRI's native → AP0 matrix interpolated linearly in mired between the bracketing table entries (clamped to 2000–11000 K, see C5), and `Lab(·)` the CIE Lab of an AP0 triple with the ACES white (AP0 → XYZ, white = ACES white). The parameters are the 6 free coefficients `m = (m0 … m5)` of

   `M(m) = [[m0, m1, 1−m0−m1], [m2, m3, 1−m2−m3], [m4, m5, 1−m4−m5]]`

   (rows sum to 1, so `M·[1,1,1]ᵀ = [1,1,1]ᵀ`), and the objective is

   `J(m) = Σₙ ‖ Lab(A(T_E)·M(m)·c_s[n]) − Lab(A(T_E)·c_a[n]) ‖²`   (Euclidean distance in Lab, 190 patches, no weights).

   `J` is minimised by Levenberg–Marquardt with an analytic Jacobian and a Gauss–Newton polish, started from the linear solution of the previous objective (weights `Y_target^(−2/3)`, which approximate `J` and are kept in the code as `fit_map_weighted_rgb`, the objective that reproduces `research/alexa-ssf/out/sony_profiles.csv`). Start, solver and options are fixed, so the fit is deterministic; the coefficients agree to ~1e-13 whatever the start (`python3 -m training.sensor_map.fit --stability`), and the shipped tables are checked to 5e-9 (`build_profiles --check`).

```python
def residuals(m):                       # 190 × 3 Lab differences, flattened
    M = white_preserving(m)             # rows [m0, m1, 1 - m0 - m1], ...
    return (ap0_to_Lab((src @ M.T) @ A.T) - ap0_to_Lab(dst @ A.T)).ravel()    # A = A(T_E)

w = clip(Y_target, 1e-3, None) ** (-2/3)                       # start: weighted RGB least squares
Aw = stack([src[:,0] - src[:,2], src[:,1] - src[:,2]], axis=1) * w[:,None]
for r in range(3):
    m, *_ = lstsq(Aw, (dst[:, r] - src[:, 2]) * w)
    M0[r] = [m[0], m[1], 1 - m[0] - m[1]]
m = levenberg_marquardt(residuals, start=M0[:, :2].ravel(), jac="analytic")    # then Gauss-Newton polish
```

   Decision 2026-10-12 (Mykyta): Lab-optimal objective adopted after the M1-05 gate; LED-V2 remains a reported gate failure.

4. Store per profile: for each class, a list of `(mired, M)` sorted by mired.

**Runtime:** `M_map = Σ_k p_k · M_k(mired_scene)`, where `M_k(mired)` interpolates linearly in mired within class `k` and clamps at the ends. A convex combination of white-preserving matrices is white-preserving.

**Optional upgrade (M1, only if it wins):** a tiny MLP (≤ 5k parameters) from the illuminant estimate's features to the 6 free coefficients. Keep it only if it lowers held-out-light ΔE00 by ≥ 0.05 median against the table blend.

**Gate (M1):** 99 CIE CES samples, 9 test lights not in the fit grid. Per-light ΔE00 median ≤ 0.5, p95 ≤ 1.2, against rendering the same reflectances through `S_A` directly. Reference numbers for the A7R IV profile are in `research/alexa-ssf/README.md` (0.16–0.45 median per light).

## C3–C4 · ALEXA white

`w_A(E) = ∫ S_A(λ) E(λ) dλ`, normalised to green = 1 (5 nm sums, 380–780 nm).

- C3 multiplies by `w_A(E_scene)`. `E_scene` is the SPD of the estimated light: blackbody below 4000 K, CIE daylight from 4000 K (the rawtoaces convention, also used to fit our ALEXA curve). For the LED and fluorescent classes use the precomputed `w_A` of the class's reference lights (in `profile.json`), interpolated in mired and blended by class probability.
- C4 multiplies by `g_user = 1 / w_A(E_user)`, where `E_user` is blackbody or daylight at the user's CCT (same 4000 K rule), then applies tint.
- **Auto white balance** sets `E_user = E_scene`, so C3·C4 is the identity and the scene white lands exactly on neutral. The Kelvin shown is the scene CCT rounded to 50 K; the tint shown is the value that reproduces the scene's distance from the locus.
- **Tint:** `t ∈ [−50, 50]`. Positive is magenta. Multiply the green gain by `2^(−t/100)` (±0.5 stop at the ends). ARRI's tint mapping is unpublished; this is ours. Revisit in M1 against ARRI sample footage, if any is usable (`docs/16`).
- `w_A` for blackbody and daylight on a 10 K grid (1500–25000 K) is **precomputed offline** by the fit scripts into `profile.json` (`alexa_white`), together with the camera locus. The runtime only interpolates these tables, so no CIE datasets (observers, daylight basis) are compiled into the app. The `colorimetry` crate and colour-science are training/test dependencies only.

**As built (M1-07), C3–C4.** `ym_color::wb::{scene_alexa_white, scene_tint, tinted_white, auto_readout, manual_user_gains}`.

- *The scene's tint.* The class model of C3 (`w_A` of a blackbody or CIE daylight at the scene CCT, or the LED and fluorescent lists) has no off-locus component, yet a real photo's light sits off the locus, and the Tint row has to show how far. So `w_A(E_scene)` carries the scene's own tint: the camera white's signed log-chroma distance from the locus, `d = Duv / duv_scale(CCT)` (positive towards magenta), becomes the green gain that would cancel it, `t_scene = −100 d / (√2 ln 2)` (about 102 tint units per log-chroma unit; Duv 0.01 reads a tint of 11 at 5500 K, 16 at 3200 K, 23 at 2500 K), weighted by the daylight plus tungsten probability (the LED and fluorescent class whites already contain their reference lights' distance from the locus) and held in −50…50. `w_A(E_scene) = [g w_r, 1, g w_b]` with `[w_r, 1, w_b]` the class-blended `w_A` of the scene CCT and `g = 2^(−t_scene/100)`. A greener light gives a positive tint (the correction adds magenta), a magenta light a negative one; a preset on the locus gives exactly 0. The Duv is the camera's readout, so it is only as good as `docs/03` says (spiky spectra differ from CIE Duv; between about 3800 K and 4300 K a Duv beyond ±0.002 is not trustworthy, and so is this tint).
- *Auto.* `g_user = 1 / w_A(E_scene)` with that tinted, class-blended `w_A` (not the model at the CCT, `docs/03`), and the C3·C4 product is set to exactly `[1, 1, 1]`. The scene white lands on `2^EV [1, 1, 1]` to 6e-15 (all 11 profiles, every class mix, CCT 1900–12000 K, Duv −0.01…0.007, any initial white; `tests/chain.rs`).
- *Readout.* Kelvin is the scene CCT rounded to 50 K and held in 2000–11000 K. Tint is the value that reproduces the scene's distance from the locus: the gains of `Manual { kelvin, tint }` act on the scene white `w_s = w_A(E_scene)` as `[w_s,r / w_u,r, 2^(−t/100), w_s,b / w_u,b]` (`w_u = w_A` at that Kelvin), the three agree only when the scene sits on the locus, and the tint that comes closest on the green axis is `t = −50 log₂((w_s,r / w_u,r)(w_s,b / w_u,b))`, held in −50…50, computed for the rounded Kelvin that is shown. Consequences, all tested: (1) `Manual` at the shown Kelvin and tint renders the Auto picture times the green gain `2^(−t/100)` (the tint scales green only, so it changes brightness by at most half a stop at ±50 and by 3.5 % at ±5) to 1e-12 for daylight and tungsten scenes whose CCT is a multiple of 50 K; (2) with the Kelvin rounded, the scene's ALEXA white is off neutral by the colour of up to 25 K: at most 1.6 % per channel at 2000 to 2300 K (a kelvin is a bigger step in mired at the warm end), 1.3 % up to 4000 K (the junction included), 0.5 % above (measured every 3 K on all 11 profiles; `tests/wb.rs`); (3) for an LED or fluorescent scene a green gain cannot cancel the red/blue offset of the class white, so the shown pair leaves up to 3.4 % (A7R IV, LED, 2750–6500 K). Applied to the camera white as a green gain, the tint cancels the cast to within 4.1 % of its Duv in a round trip through the locus readout (worst of 11 profiles).
- *Manual.* Kelvin is held in 2000–11000 K and tint in −50…50 (`WhiteBalance::manual` and the chain refuse values outside); `E_user` is the blackbody table below 4000 K and the CIE daylight table from 4000 K, `g_user = [1 / w_r, 2^(−t/100), 1 / w_b]`, and the user's Kelvin picks the ARRI matrix. **The 4000 K rule makes `w_A` step** (red −1.2 %, blue −3.4 % going up, `docs/03`); a Kelvin slider dragged across 4000 K moves the scene white by 1.1 % red, −0.4 % green and 4.4 % blue (A7R IV, daylight scene, about 0.06 stop in blue). The rawtoaces convention is kept as specified; cross-fading the tables over 3500–4500 K would make `w_A` a mixture of two lights that are not on the same locus and was not adopted.
- *Apple Auto nudge (`docs/19` section 5).* With Apple Auto's answer, Auto (light source Auto, white balance Auto, no picked white) moves the user's white by `m = −10 × step` mired (the answer's `white` step, −2…+2; a warmer picture is a negative `m`): `CCT_user = 1e6 / (1e6 / CCT_scene + m)`, held in 1500–25000 K (the white tables; a nudge of 20 mired never reaches either end from a scene the estimator reports). The user's white is the scene's tinted, class-blended white moved along the locus to `CCT_user`, channel by channel `w_A(E_user) = w_A(E_scene) · w_locus(CCT_user) / w_locus(CCT_scene)` (`w_locus` the blackbody/daylight model, 4000 K rule), so it keeps the scene's tint and class mix; `g_user = 1 / w_A(E_user)`, C3·C4 is `w_A(E_scene) / w_A(E_user)` (green exactly 1), and the ARRI matrix takes `CCT_user` held in 2000–11000 K, as for a manual Kelvin. For daylight and tungsten light this is the class-blended white evaluated at `CCT_user` (`docs/19`'s wording), and the nudged chain equals `Manual { CCT_user, 0 }` on the locus to 1e-9. For fluorescent and LED light the class whites are lists of real lights, not ordered in colour and constant beyond their ends, and evaluating them at `CCT_user` moved the white the wrong way or not at all on every shipped profile (LED at 2700 and 4000 K, fluorescent at 2700 K); moving the scene's own white as the locus moves gives every class the same monotonic nudge (decision of this implementation, recorded in `docs/19`). The readout is `auto_readout`'s for the nudged white: Kelvin `CCT_user` rounded to 50 K, and the tint that reproduces it, which is the scene's tint up to the rounding for daylight and tungsten light. `m = 0` takes none of this path: the chain is Auto's bit for bit (all 11 profiles, every class). A light preset, a picked white and a manual white balance get no nudge. `ym_color::wb::{nudged_cct, nudged_alexa_white, nudged_readout}`, `ChainSettings::white_shift_mired`, `ColorEstimates::white_shift_mired`; tests `crates/ym-color/tests/white_nudge.rs` (±10 and ±20 mired move the scene white's R/B in AWG4 and the Kelvin readout the right way, monotonically, for every class, on and off the locus, 2200–10000 K).
  **The tint nudge** (prompt version 2, `docs/19` section 5). Under the same conditions the answer's `tint` step adds `Δt = 5 × step` (−10 … +10, positive magenta) to the scene's own tint, the sum held in −50 … 50; the user's white (moved along the locus first, when there is a warmth nudge too) takes the tint as a manual tint is given to a white, `tinted_white`: red and blue times `2^(−Δt/100)`, green 1 (`ym_color::wb::{nudged_tint, nudged_alexa_white}`, `ChainSettings::tint_shift`, `ColorEstimates::tint_shift`). The readout's tint moves by `Δt` and its Kelvin stays. `Δt = 0` takes none of this path (Auto bit for bit), and a warmth nudge without a tint nudge is the white nudge above unchanged (`crates/ym-color/tests/white_nudge.rs`: a magenta nudge takes green out of the picture, both signs, every class).
- *Direction of a Kelvin setting.* The user's Kelvin is the light the ALEXA is balanced for, as on the camera: a daylight scene set to 3200 K renders **bluer** than Auto, not warmer, and a tungsten scene set to 5500 K renders warmer. For the A7R IV, CIE D 5500 K, 3200 K: AWG4 white `[0.6747, 0.9488, 1.6434]` (blue over red 1.28 stops, green over red 0.49 stops; Auto is `[1, 1, 1]`), equal to the independent spectral simulation of ARRI's balance (ALEXA estimate curves, Planck's law or the CIE D lights of the exporter's fixtures, the 17-CCT matrices) to 3e-9 for a white patch (312 cases: 3 bodies, 13 lights of all four classes, Auto and 8 Kelvin settings; `tests/chain_spectral.rs`). The 24 ColorChecker patches through the sensor map differ from the simulation by the map's error, 0.47 ΔE00 median at worst and 1.4 at most (3 bodies, Auto, 2800/3200/5500 K). docs/15 M1-07 says "warmer"; the maths says cooler (see STATUS, questions).

### Camera RGB ↔ CCT and Duv

For a profile, the fit scripts tabulate camera RGB (green = 1) of blackbody 1500–4000 K and daylight 4000–25000 K every 10 K, as log-chroma `(ln R/G, ln B/G)`, plus the matching CIE xy and the Duv scale, into `profile.json` (`locus`). The camera RGB is in the camera's **raw scale** (the published curves, not normalised per channel; C1), so it is comparable with the as-shot gains, Pick white and the illuminant estimate. Convert `w_scene` to CCT by nearest point on that polyline, with linear interpolation between neighbours. Duv is the signed perpendicular distance, positive towards magenta, rescaled to CIE Duv through the profile's XYZ estimate. Use this for the Kelvin and tint readouts and the light presets.

## C5–C6 · ARRI matrix, AWG4, exposure

- `M_arri(CCT_user)` from the interpolated table above.
- `M_awg3→awg4` from the constants.
- Exposure: `EV = EV_auto + 0` in Auto, or the slider's absolute value in Manual. The slider range is −4…+4 EV absolute; its detent sits at `EV_auto`.

**As built (M1-07), C5–C6.** `ym_color::chain::{FusedChain, ChainSettings, ProfileTables, ChainStages, ClipLevel, ColorEstimates}`.

- `FusedChain::build(tables, &estimate, w_scene_initial, &settings)` returns the 3×3 (`matrix()`), the factors (`stages()`: `g_res`, `sensor_map`, `w_a_scene`, `g_user`, `c3_c4`, `user_cct_k`, ARRI and AWG3→AWG4 matrices, `2^EV`), the resolved scene light, the Kelvin and tint to show (`readout()`: the Auto readout, or the user's values for Manual) and the clip level. `ProfileTables` is the three tables of a profile the chain reads (`profile.sensor_map.classes`, `profile.alexa_white`, `profile.locus`), so `ym-color` does not depend on `ym-profiles`. Order of the scene light: estimate, then Pick white (`ChainSettings::picked_white`, the sample), then the preset. The CCT for the ARRI matrix is the scene CCT in Auto and the user's Kelvin in Manual; `ArriTable` clamps it to 2000–11000 K. The matrix is the product of the formula above, checked stage by stage on random pixels to 1e-13. The exposure must give a usable gain: `FusedChain::build` refuses an EV that is not finite or whose `2^EV` overflows or underflows (`ChainError::InvalidExposure`, beyond about ±1000 stops), and `ColorEstimates::chain` refuses a manual exposure outside −4…+4 (`ExposureSetting::manual`/`validate`, `ChainError::Exposure`); the automatic value is not range-checked (the highlight guard can take it to −4).
- `ColorEstimates { scene, w_scene_initial, ev_auto }` is the colour part of `AutoEstimates`; `.chain(...)` resolves `ExposureSetting::{Auto, Manual { ev }}` against `ev_auto` and `.metering_chain(...)` builds the all-Auto, EV 0 chain that auto exposure meters through (metering happens once at open and on Re-run, so later white-balance edits do not move the exposure).
- *Clip level for C7.* A neutral surface brightens until the first camera channel clips. After C1 it is `[s, s, s]` and channel `c` clips at `s = 1 / w_scene[c]`, so the first clip is at `balanced = min_c 1 / w_scene[c]` (1 for daylight on a Sony sensor, below 1 for a light so red that red clips first). Mapped through the matrix this is `M·[balanced; 3]` (`FusedChain::clip().awg4`; `clip_level(&matrix, w_scene)` for any matrix). C7's highlight range reads it as a luma, `ClipLevel::luma()` (the Rec.709 weights on that triple, the norm the stage applies to every pixel); `ClipLevel::n`, its largest channel, is kept as a diagnostic. In Auto the triple is neutral, `2^EV · balanced` on every channel, so both are `2^EV · balanced`; with a manual white balance the clipped neutral is coloured and the luma is the one C7 compares pixels with.

### Auto exposure

Goal: the exposure the photographer's camera chose, with a safety net for highlights, stable across a burst.

**This is an interim rule (decision of 2026-10-14).** Until the intelligent automatic settings of a later milestone replace it, Auto exposure *is the camera's own exposure*: Yellowmoon meters nothing of its own. A photo processor does not need to rescue a shot; the Exposure slider does that, and an ALEXA has no auto exposure either.

1. Run C1–C6 with EV = 0 on the 1/8-resolution preview. Compute linear luminance `Y` with the AWG4 Y row.
2. Ignore pixels in the clip mask and pixels with `Y` below the 1st or above the 99th percentile.
3. `m = exp(Σ wᵢ ln Yᵢ / Σ wᵢ)`, with a centre weight `wᵢ = exp(−r²/(2·0.35²))` (r = distance from centre over the half-diagonal). `m` is the scene's key. It is reported as a diagnostic and **does not move the exposure**.
4. `EV_auto = clamp(CAMERA_GAIN_EV, −3, +3)` with `CAMERA_GAIN_EV = +1.11 EV`: the same number for every photo.
   `CAMERA_GAIN_EV` is the median gain of the cameras' own JPEG engines (raw level to the level the JPEG renders as middle grey, `log2(0.18 / x)`): +1.11 EV over 12 photos from 9 Sony bodies, std 0.13, range +0.87 … +1.33, no relation to the scene's key (an ideal ISO 12232 camera would be +0.79; Sony places grey higher).
   There is **no exposure-compensation term.** The raw data already holds the photographer's compensation (the camera exposed that much more or less), so with a constant gain it reaches the picture in full, as it does in the camera's JPEG: a scene shot with +1 EV of compensation renders exactly one stop brighter than the same scene without. (The previous rule added half of it, `0.5 · EC`.)
   Why: a camera exposes the scene and then applies a nearly constant gain. Our earlier meter (the geometric mean to 0.18, plus half the compensation) normalised the key a second time, which pulled bright scenes down and pushed dark ones up beyond what the camera did (`EV_auto` against log2 of the JPEG median had a slope of −0.41 EV per EV) and sat 0.23 EV under the cameras' median gain on every file. A shot the camera exposed badly stays badly exposed; that is the point of the rule, and the slider fixes it.
5. Highlight guard: if more than 0.5% of non-clipped pixels would exceed linear 8.0 after exposure, lower `EV_auto` until they don't, but by no more than 1 EV. Level and fraction are unchanged; the guard runs after step 4 and can only lower the exposure. 8.0 is 5.47 stops over middle grey, about the clip of an ALEXA (ALEV III) at EI 180, not at EI 800 (whose clip is 7.64 stops over grey, linear 35.9; C7); it is kept as it is (decision of 2026-10-17, `docs/16`), and on Sony data it has not acted (see the gate status below).
6. Files of the same camera within 2 s of each other and with identical exposure settings share the median `EV_auto` (bursts stay consistent). With a constant gain the median is that constant unless the guard acted on a frame.

The **white lift** (C12 step 1b) is the other automatic estimate made on this preview, right after the exposure and at the exposure the photo renders with; it is not part of the exposure rule and does not move it.

`CAMERA_GAIN_EV` is a starting value, fitted on 12 local files (9 bodies, licences of nine of them unclear) and measured as the gate's own reference, so a pass of the gate on those files says little about other cameras (in-sample). Re-fit it on the golden set (M1-H5) and keep the rule. The intelligent automatic settings (a later milestone) replace step 4, not the rest.

**As built (M1-08).** `ym_color::exposure`: pure functions over plain buffers (`PreviewRgb`: interleaved f32 RGB, the 1/8-resolution preview balanced with `g0`, and an optional clip mask) and small metadata structs; no decoder or GPU dependency. `auto_exposure(&preview, &matrix_ev0)` is steps 1 to 5 (1188×792 pixels, the 1/8 preview of a 61 MP frame: about 0.2 s on a loaded machine; the camera's exposure compensation is not an input), `share_burst_ev(&frames, &ev_auto)` step 6. `CAMERA_GAIN_EV` (+1.11) and `EV_LIMIT` (3) are constants of `ym_color::exposure`; `TARGET_GREY` (0.18) is the reference of the reported key and of the gain. Where the steps are silent:

- *Luminance.* `Y` is the AWG4 `Y` row applied to `M·rgb` (folded into one row vector), raised to a floor of 1e-4 before the logarithm of the reported key so that black and negative pixels (noise after black subtraction) count as very dark rather than missing. A pixel with a non-finite channel counts as masked. A lens-cap frame, a flat frame and an empty preview all get the camera gain.
- *Percentiles* are the linearly interpolated quantiles (numpy's default) of the sorted unmasked luminances; a pixel is kept when `q01 ≤ Y ≤ q99`. The mask is applied first. With a few percent of outliers in one tail the quantile falls inside that tail and nothing is dropped, which is what the spec's "ignore the 1st and 99th percentile" gives. The interpolation is written `a + (b − a)·f`, which returns exactly `a` for equal neighbours: the form `(1 − f)·a + f·b` is an ulp off for some, and on a flat or black frame the 1st percentile then lands above every pixel and the band is empty. If the band is empty anyway (two distinct values and nothing else) every unmasked pixel is metered.
- *Centre weight.* `r` is measured from the pixel centre to the image centre over the half diagonal (`w = 1` at the centre, 0.017 in a corner).
- *Highlight guard.* Over every unmasked pixel (not only those kept by the percentiles, which would remove the highlights it looks for), `Y` after exposure against 8.0. Solved in closed form: the largest EV at which at most `floor(0.005 n)` pixels exceed 8 (from the `(floor(0.005 n) + 1)`-th brightest `Y`), and `EV_auto = max(that, EV_before_guard − 1)` when it is below `EV_before_guard` (the camera gain, +1.11). The result lies in +0.11 … +1.11; it never raises the exposure. `AutoExposure` reports `ev_before_guard` (the former `ev_metered`), `guard_reduction_ev`, `mean_luminance` (the key statistic, a diagnostic) and the pixel counts.
- *No usable pixel* (everything masked, or an empty preview): nothing can be reported and the guard has nothing to look at, so `EV_auto = clamp(CAMERA_GAIN_EV)` too, `metered = false`.
- *Bursts.* A frame joins a group when the previous frame (in time order) with the same camera string and identical settings (shutter, f-number, ISO, exposure compensation; equal to 1e-9 relative) is at most 2 s earlier. Those are consecutive gaps, so a burst of any length is one group; a time-lapse at fixed settings with gaps under 2 s would also be one group. The median of an even group is the mean of the two middle values; a frame without a capture time is alone. Step 6 follows steps 4 and 5, so a frame whose highlight guard lowered its own EV takes the group median (the camera gain, unless more than half of the burst was guarded), which can undo the guard for that frame; the spec orders it this way.
- *The gate* ("within ±0.5 EV of the embedded JPEG, median luminance in linear light, ≥ 80 % of the golden set"): `preview_median_luminance(&preview, &matrix_ev0, ev)` is the median `Y` of our render over every pixel (masked ones included, as the JPEG's median includes them) at an exposure; `jpeg_median_luminance(&rgb8)` the median `Y` of a decoded 8-bit sRGB image (sRGB decoded to linear, Rec.709 luminance; an Adobe RGB preview would be a little off); `exposure_error_ev(ours, reference) = log2(ours / reference)`; `evaluate_gate(&entries, 0.5, 0.8)` gives the pass rate, the outliers worst first (for the M1-H5 review) and the entries it could not use. Decoding the embedded JPEG and reading the files is the caller's job (the tests decode with `zune-jpeg`, a dev-dependency, MIT OR Apache-2.0 OR Zlib).
- **Gate status (M1-08, metric G3, decision 2026-10-13; the interim exposure rule of 2026-10-14): met on the 12 local files (in-sample) and on the synthetic tier (by construction); the 80 % bar still cannot be measured on a golden set.** The gate is `tools/eval/autoexp.py --gate` (`docs/13`, `docs/15`): G3 is `EV_auto` minus the camera engine's gain (`log2(0.18 / x)`, `x` the scene-linear level that the embedded JPEG renders as mid grey, by quantile matching at the JPEG's size), and the gate is met when at least 80 % of the files have |G3| ≤ 0.5 EV. A file that fails to analyse, or whose gain cannot be read, counts as a miss; the exit code is 3 when the gate is not met; the outliers (with the camera's key and DRO setting) are printed and written to `report.md` and `results.json` for the M1-H5 review. It replaces the comparison of median luminance in linear light (G1, which the Rust helpers above still compute) as the gate. `EV_auto` is now the constant +1.11 EV (the camera gain), so G3 is `1.11 − camera gain` per file: it shows how far each camera is from the median of the cameras, nothing more. ## C7 · Highlight range and low-light toe

Two gains that keep the channel ratios of a linear AWG4 pixel: the **highlight range** acts on its luma above a knee, the **low-light toe** on its norm `n = max(R, G, B)` near black. The range comes first. They never act on the same pixels: the range is exactly 1 below +1 stop over middle grey, the toe acts within a few noise floors of black.

**Highlight range** (`rolloff.highlights = r ∈ [0, 1]`, default 1; owner's decisions of 2026-10-17, `docs/16`; the research is `research/arri-highlight-clipping-2026-10-17.md`, proposal P2). An ALEXA (ALEV III) at EI 800 clips 7.64 stops over middle grey; a Sony body at the camera's exposure clips about 3.6 stops over it (3.58 on all 12 local photos at Auto). Below the Sony's clip the chain already holds what an ALEXA exposed for the same grey would record, so the one difference is where the clip lands. The stage maps the Sony's top stop onto the ALEXA's range: nothing changes below a knee one stop under the Sony clip, the Sony clip is placed on a target between where it was recorded (`r = 0`) and the ALEXA's EI 800 clip (`r = 1`), and nothing goes past the ALEXA's clip. `r = 1` is what an ALEXA's own video output does with its clip ("normalized": the sensor clip at 100 % video at every EI); `r = 0` is ARRI's "photometric" conversion (the clip renders where its scene level puts it, today's picture). The default is 1, the clip at white: the owner's choice of 2026-10-17 after a before-and-after at 0, 0.5 and 1. It was 0.5 until then, pending a blind A/B that this choice settled. It replaces the earlier tanh shoulder of C7 (which moved a neutral by at most 0.14 stop at the clip, 2 display codes). It works **alongside the white lift** of C12 step 1b: the range moves the camera's clip, the lift brings a photo's brightest areas to a real white when they sit well under the clip, where the range does nothing (owner's decisions of 2026-10-17: the range was first to replace the lift; after a comparison with 0.1.9 showed photos without clipped highlights darker in their upper tones, the lift stays, `docs/16`).

```
Y    = 0.2126 R + 0.7152 G + 0.0722 B          luma of the linear AWG4 pixel (Rec.709 weights, REC709_LUMA_WEIGHTS)
s    = log2(Y / 0.18)                          stops over middle grey
h_S  = log2(Y_clip / 0.18)                     the Sony clip: Y_clip = ClipLevel::luma(), the clipped neutral after C1-C6
h_A  = log2((1 - 256/65535) · 800 / 4)         the ALEXA (ALEV III) clip at EI 800: 7.638209540303716 stops (linear 35.86)
s_k  = max(1, h_S - 1)                         the knee: one stop under the Sony clip, never under +1 stop
w    = clamp((h_S - s_k - 0.25) / 0.75, 0, 1)  fade: 1 when the clip is 2 stops or more over grey, 0 at 1.25 or less
E    = w · r · max(h_A - h_S, 0)               how far the Sony clip moves, in stops (it lands on T = h_S + E)
u    = (s - s_k) / (h_S - s_k)                 only where E > 0, so h_S - s_k >= 0.25
phi  = u²  (u <= 1),   2u - 1  (u > 1)         C1 at the clip; values R5 rebuilt above the clip keep the clip's slope
s'   = s + E · phi   where s > s_k and E > 0,   s elsewhere
s'   = min(s', h_A)                            the ALEXA's hard clip
gain = 2^(s' - s)                              rgb' = gain · rgb, all three channels
```

`h_A` is ARRI's own formula for the ALEV III clip (the LogC3 VFX document's clipping level and ARRI's ACES input transform for ARRIRAW: grey at `0.01 · 400 / EI` over black, linear up to the 16-bit white; it reproduces ARRI's LogC3 clip code 0.9539 at EI 800). ARRI's data sheets round it to 7.4 stops; the formula is used (decision of 2026-10-17). The target EI is fixed at 800, ARRI's base EI. The knee depth (1 stop), the floor of the knee (+1 stop), the fade and `phi` are taste, not ARRI figures.

- *Properties* (all tested). The gain is exactly 1 for `s <= s_k` (the stage returns the input unchanged, bit for bit: mid grey and everything under +1 stop never move); `s'` is continuous with a continuous slope at the knee and at `u = 1`, and non-decreasing in `s` (slope at least 1 up to the cap, 0 above it); the Sony clip lands on `T = min(h_S + E, h_A)`; the three channels are multiplied by the same number, so a pixel's colour ratios are kept exactly; below the cap every output channel is non-decreasing in each non-negative input channel (a channel times a non-negative, non-decreasing function of a luma with positive weights). At the cap the luma is held at the ALEXA clip with the ratios kept, so there raising one channel lowers the others' output (what a hard clip of the luma does). `r = 0` is the identity below the ALEXA clip.
- *The ALEXA clip on its own.* When `h_S >= h_A` (Exposure about +4 EV over Auto, or more), `E = 0` and the stage is the identity below `h_A` and the ALEXA's hard clip above: the only case where an ALEXA sensor clip acts on recorded data.
- *Exposure.* `Y_clip` is measured after C6, so it includes `2^EV` and `h_S` follows the Exposure slider as an ALEXA's clip follows its EI. With `r = 1` the clip stays on the ALEXA clip at every exposure where the fade is 1, so darkening the photo does not darken a clipped sky (ARRI's "normalized" behaviour). The fade (ours) keeps the map continuous when the clip comes within two stops of grey (Exposure about 1.6 stops under Auto): the expansion falls off to nothing at 1.25 stops (2.3 stops under Auto), where the knee would otherwise reach middle grey.
- *Edge values.* A pixel with a non-finite channel passes through unchanged, as the rest of C7; `Y <= 0` (black, or all channels at or under zero) gets a gain of 1. `E`, `s_k` and `h_S` are computed once per chain on the CPU in f64; a `Y_clip` that is not a positive finite number is refused when the chain is built (`ToneError::InvalidClipLevel`).
- *Where it acts.* C7 is scene-linear, before the LogC4 encode, so everything after it sees the range: the grade, looks, the curve, ACES 2, the DNG's pixels, and **an imported ARRI display LUT and the LogC3-to-Rec.709 looks**, which receive values up to the ALEXA clip (LogC4 0.760, LogC3 EI 800 0.954: the range ARRI made them for) and apply ARRI's own shoulder to them (owner's decision of 2026-10-17; before it, they kept the Sony's recorded highlights). The Before view (the camera's default rendering) does not have it.
- *Display result* (computed; a neutral; ACES 2 with the placement; no look; sRGB codes): at Auto, +1 / +2 / +2.58 / +3.08 / +3.33 / +3.58 (the clip) stops over grey render 158 / 192 / 208 / 220 / 224 / 229 at `r = 0`, 158 / 192 / 208 / 229 / 240 / 248 at `r = 0.5` and 158 / 192 / 208 / 236 / 249 / 254 at `r = 1`, as the chain renders them (`crates/ym-color/tests/tone.rs`; the report's table, section 4, rounds two cells one code the other way).

**Low light** (`rolloff.low_light = r`, default 0.5). `τ = 4r · σ_floor`, where `σ_floor` is the noise model's read noise mapped to linear AWG4 at this exposure. `f(n) = n³ / (n² + τ²)`, which is monotonic, ~n above 3τ and crushes the noise floor smoothly below τ. `r = 0` disables it.

**As built (M1-09; the highlight range 2026-10-17).** `ym_color::tone::ToneParams::new(highlights, low_light, clip_luma, noise_floor)`, `apply(LinearAwg4)`, `apply_rgb(Vec3)`; `ToneParams::range()` is the prepared `HighlightRange { knee_stops, clip_stops, expansion_stops, cap_stops }` (`s_k`, `h_S`, `E`, `h_A`) with `stops(s)` and `gain(luma)`; the constants `HIGHLIGHT_CAP_STOPS` (`h_A`, with `alexa_clip_stops(ei)` the formula), `HIGHLIGHT_KNEE_DEPTH_STOPS` (1), `HIGHLIGHT_KNEE_FLOOR_STOPS` (1) and `HIGHLIGHT_MIN_SPAN_STOPS` (0.25) are in `ym_color::tone`. The pixel is `toe(range(rgb))`: the range's gain on the luma, then the toe's scale `n² / (n² + τ²)` of the gained pixel's norm (for `n <= 0` the toe's scale still applies, so a pixel with `n = 0` and `τ > 0` goes to black); non-finite input passes through. `r_low_light = 0` is the exact identity of the toe. Tests (`crates/ym-color/tests/tone.rs`): the formulas against an independent f64 composition, exact identity below the knee, the slope continuity at the knee and at `u = 1`, `s'` non-decreasing over a grid of amounts × clip levels × noise floors, the clip landing on `T`, the cap, `r = 0` the identity below the cap, the fade at low clip levels, each output channel non-decreasing in its own input below the cap (proptest), and the toe as before.

## C9 · Primary grade (LogC4)

Let `v` be LogC4 RGB. `L = encode(Y_lin)` uses the luminance of the linear values before C8. Grey `g = 0.2784`. One stop in LogC4 is `b/14 = 0.06480` code values; call it `S`.

| Control | Range | Operation |
|---|---|---|
| Contrast `c` | −100…100 | `u = v + (T(L) − L)` on all three channels: the tone curve `T` below, with the slope `k = 2^(0.6·c/100)` at grey, fixed at black, grey and the top code value; then `u`'s chroma, keeping its direction, scaled part of the way (`β = 0.5`) toward the chroma length of `T` on each channel (the colour step below) |
| Brightness `b` | −100…100 | `v += (b/100) · S · bump(L; g, 2.5S)`: a midtone lift that leaves black and white |
| Shadows `s`, Highlights `h`, Black `k`, White `w` | −100…100 | `v += (x/100) · 1.5S · bump(L; centre, 1.5S)` with centres at grey −3, +3, −6, +6 stops |
| Colour balance (shadows, midtones, highlights) | `(a, b)` in the unit disc | `v += 0.03 · (a·e₁ + b·e₂) · zone(L)`, `e₁ = (1, −½, −½)/√1.5`, `e₂ = (0, 1, −1)/√2`; zones centred at −3, 0, +3 stops |
| Saturation `s` | −100…100 | in linear AWG4, `rgb′ = Y + λ·(rgb − Y)`, `rgb = decode(v)` of the pixel at this point of C9 (after the rows above) and `Y` its luminance: `λ = 1 + s/100` for `s < 0`; for `s > 0`, `λ = r′/r` with `r = (Y − min(rgb))/Y`, `r′ = 1 − (1 − r)^F`, `F = 1 + α·s/100`, `α = 1.5`; then encoded to LogC4 again |

`bump(L; μ, σ) = exp(−(L − μ)²/(2σ²))`. All constants are starting values; tune them visually in M3. Apply in the order of the table.

**Auto inputs of this stage** (`docs/19` section 5, table version 2). Contrast, Saturation, Highlights, Shadows and Black are Auto or a manual value, and so are the shadows and highlights colour-balance wheels (a manual point); the midtones wheel stays a point. Auto is 0 (the wheels (0, 0)), the grade above without that row, unless Apple Auto answered for the photo and set that value: then it is the table's value of the answer's step (Highlights −40, −20, 0, +20, +40; the others −30, −15, 0, +15, +30) and, for a wheel, the colour's direction at its strength's radius (0.3, 0.55, 0.8). A value the answer left empty stays 0. The grade takes the values in effect (`ym_core::pipeline::color::grade_params` resolves them against the photo's estimates); nothing in this stage's maths changes.

**Contrast is a tone curve on the luma** (the lead's design of 2026-10-19, `docs/16`; it replaces `v = g + (v − g)·2^(0.6·c/100)`). With black `a = encode(0) = 0.0929`, grey `g`, the top code value `b = 1` (linear 469.8, 11.35 stops over grey; here `b` is not LogC4's constant) and `h_k(t) = k·t / (1 + (k − 1)·t)` (`h(0) = 0`, `h(1) = 1`, slope `k` at 0 and `1/k` at 1, increasing for every `k > 0`):

- `g ≤ x ≤ b`: `T(x) = g + (b − g)·h_k((x − g)/(b − g))`;
- `a ≤ x < g`: `T(x) = g − (g − a)·h_k((g − x)/(g − a))`;
- above `b` and below `a`: the straight line of slope `1/k` through the end, so `T` is defined, continuous, has a continuous slope and is increasing for every `x`.

The change `T(L) − L` is added to all three channels: `u = v + (T(L) − L)`. On the log segment a common offset multiplies `x + 64/a` (`x + 0.029`) by a common gain, which is a common gain in linear light wherever `x` is well above 0.029, so the channel ratios, and with them the hue, are kept while the luma follows `T`. In plain words: the slider has the slope it always had at mid grey (`2^(0.6·c/100)`, so it feels the same there), and instead of stretching the whole range about grey it bends toward black and the brightest code, which stay where they are (more contrast flattens the tones near them, less steepens them). `c = 0` skips the row (bit-exact identity). The rows after Contrast use the original `L`.

**Contrast adds part of the colour a curve on each channel would** (the owner's answer of 2026-10-19, after the first contact sheets: on its own the offset adds no colour, and on his three photos Contrast +60 lowered the mean CIELAB chroma by 5 to 7 % where the old per-channel control raised it by 15 to 21 %; the lead's design, our own maths in the C9 chroma plane). With the chroma of a LogC4 triple `x` in the colour-balance plane, `c_x = (e₁·x, e₂·x)`:

- `p = (T(v_r), T(v_g), T(v_b))`, the same curve `T` on each LogC4 channel; `c_u` and `c_p` the chromas of `u` and `p` (`c_u = c_v`, as `e₁` and `e₂` sum to 0);
- `f = 1 + β·(|c_p|/|c_u| − 1)` with `β = CONTRAST_COLOR = 0.5`, and `f = 1` where `|c_u| < 10⁻⁹` (`CONTRAST_NEUTRAL_CHROMA`): neutrals stay neutral;
- `v′ = u + (f − 1)·(c_u1·e₁ + c_u2·e₂)`: `u`'s chroma scaled by `f`, its direction (the hue in the plane) kept.

The mean of the three channels (the position on the neutral axis) is `u`'s, since `e₁` and `e₂` sum to 0. `T`'s slope lies between `min(k, 1/k)` and `max(k, 1/k)`, so by the mean value theorem on each channel difference `|c_p|/|c_u|` does too, and `f` lies between `1 − β·(1 − min(k, 1/k))` and `1 + β·(max(k, 1/k) − 1)`: 0.83 to 1.26 at the ends of the range. The implementation limits the ratio to that interval, which only guards rounding. `β = 0` is the hue-keeping offset alone, `β = 1` gives `u` the chroma length of the per-channel curve. In plain words: more contrast makes the midtones more colourful, half as much as a curve on each channel would, and takes some colour from the deepest shadows and the brightest tones, where the curve flattens; less contrast does the opposite; black stays black and the hue stays. On the owner's three photos (`ym render --cpu`, JPEG at 1200 px, mean CIELAB chroma) Contrast +60 changes the mean chroma by +5.2, −0.8 and +1.9 % (+30: +2.6, −0.1, +1.0 %; −30: −2.6, −0.3, −0.7 %; −60: −5.3, −1.0, −1.3 %), where the offset alone gave −7.1, −5.3 and −7.7 % at +60 and the 0.4.2 control, a gain about grey on every channel that also moved black, +20.7, +14.5 and +17.1 %. The darkest percent stays where the offset alone put it (L* 0.3, 8.1, 0.4 at +60). For tuning (a temporary build, Contrast +60): `β = 0.75` gives +11.2, +1.5, +6.8 %, `β = 1` +16.9, +3.9, +11.7 % (−60: −15.8, −6.7, −10.6 %).

**Saturation keeps the luminance** (the lead's design of 2026-10-19, confirmed by the owner the same day, `docs/16`; it replaces the subtractive `v = M + (v − M)(1 + s/100)` of 2026-10-13, which pivoted on the brightest channel `M` and made colours denser and darker). The chroma `rgb − Y` is scaled about the luminance `Y`; as the AWG4 `Y` row sums to 1, `Y` does not move. In plain words: more saturation makes colours stronger without making them darker or lighter, less makes them greyer, and −100 is the grey of the same luminance. Below 0 every colour is blended evenly toward that grey. Above 0 the scale depends on how close the darkest channel already is to 0: `r` is 0 for a neutral and 1 when the darkest channel is at 0 (scaling the chroma by `1/r` would take it there), so a muted colour has its chroma scaled by nearly `F`, a strong one by nearly 1, and the darkest channel ends at `Y·(1 − r′) ≥ 0`: no channel is pushed below 0. A pixel with `Y ≤ 0` or a channel at or below 0 is left as it is for `s > 0`. `s = 0` skips the row. The hue (the direction of `rgb − Y`) is kept at every setting. The ASC CDL saturation inside looks (C10, Rec.709 weights) is a standard and does not change, so the Signature look renders as before. `α = SATURATION_BOOST = 1.5` (was 1.0) was measured, at the owner's request of 2026-10-19 ("boost saturation"), so that Saturation +60 raises the mean CIELAB chroma of his three photos by about as much as the old control did: the old +60 raised it by +84.6, +64.9 and +69.3 % (mean +72.9 %); with `α` from 1.2 to 2.0 in steps of 0.1 the new +60 gives a mean of +61.7, +65.9, +69.8, **+73.6** (1.5), +77.2, +80.7, +84.1, +87.3 and +90.4 % (1.0 gave +53.0 %), so 1.5 is the closest (`ym render --cpu`, JPEG at 1200 px, CIELAB of the JPEG, sRGB D65). Unlike the old control the gain is about even across photos (+72.7, +75.1, +73.0 %): strong colours gain less, muted ones more. The constants (`k`'s exponent 0.6, `β = 0.5`, `α = 1.5`) are tunable.

- *Stops are scene-referred.* "Grey ±n stops" is the LogC4 code of `0.18·2^±n` (`grade::logc4_at_stops`), not `g ± n·S`: LogC4 is linear in stops only far above the toe, and `g − 6S` would sit below the code value of black. `S` is used for widths and amplitudes only.
- *Zones.* `zone(L) = bump(L; centre, 1.5 S)` at −3, 0, +3 stops (Gaussian bumps, not a partition of unity: colour balance leaves the extremes alone). Shadows, Highlights, Black and White add `x/100 · 1.5 S · bump(L; centre, 1.5 S)` to all three channels; positive is brighter for all four. Contrast and Saturation are skipped when 0 (the grade is then bit-exactly the identity, and bit-exactly the grade of pipeline 0.4.2 for every other control).
- *Ranges.* Controls clamp to −100…100; a colour-balance vector longer than 1 scales back to the unit circle.
- *"Monotonic".* Per pixel in the control value: Brightness, Shadows, Highlights, Black and White raise every channel (non-decreasing); for a luma between black and the top code value Contrast moves the mean of the three channels, and every channel of a neutral, away from `g` (up above, down below; `h_k(t)` grows with `k` for `0 < t < 1`), and beyond the ends toward the end (the line of slope `1/k`); the colour step scales a coloured pixel's chroma by `f` without moving that mean, so a single channel of a coloured pixel is not promised to follow it; Saturation scales `|rgb − Y|` by a factor that never falls as `s` rises (`Y` and neutral pixels are unchanged; at `s = −100` every channel equals `Y`); Colour balance displaces along a fixed direction by `0.03·r·zone`, so the length grows with the radius. As a tone map on a neutral ramp, one control over its full range keeps the slope above 0.39 (brightness ≥ 0.757, zone controls ≥ 0.393, contrast between `2^−0.6 = 0.66` and `2^0.6 = 1.52`, analytically). **Not guaranteed:** several tonal controls stacked at ±100 can fold the ramp (all four zone controls and Brightness at −100 with Contrast +100: worst slope −0.15 inside the valid code range, −0.68 below black; at +100: −0.10 with Contrast −100). The UI should limit the stack or the grade should be re-fitted (reported in STATUS).
- *Saturation where the spec is silent.* `Y` is taken from the pixel after Contrast, Brightness, the zone controls and Colour balance (decoded to linear AWG4), so Saturation never changes the luminance those controls set; `L` is not used by this row. Below `r = 1e-9` (`SATURATION_SMALL_R`) `λ` is its limit `F`, and that covers `r < 0`: the blue weight of the AWG4 `Y` row is negative, so a blue or violet whose red and green are nearly equal can have every channel above `Y` (linear `(0.02, 0.02, 0.57)` has `Y = 0.0002`). No channel can then reach 0 as the chroma grows, and the formula `r′/r` would exceed `F` without bound as `Y` goes to 0 (by 101 for that blue at `s = 100`); such pixels get the plain factor `F`. `r′` is computed as `−expm1(F·ln(1 − r))`, the same number without the cancellation of `1 − (1 − r)^F` at small `r`. ## C9b · Colour warp

The owner's request of 2026-10-17 (`docs/16`): a chroma warp in the manner of DaVinci Resolve's Color Warper, on the Colour tab. Pins move chosen colours across a chroma plane; colours near a pin follow it smoothly, locked pins hold their colours, and neutrals never move.

**The chroma plane.** For a LogC4 pixel `v`, its chroma is `c = (e1·v, e2·v)` with the colour-balance axes of C9 (`e1 = (1, −½, −½)/√1.5`, red against cyan; `e2 = (0, 1, −1)/√2`, green against blue), and its tone is `L = encode(Y(decode(v)))`, the LogC4 code of its linear luminance (as C11's luma curve). Moving `c` by `d` adds `d1·e1 + d2·e2` to `v`, which leaves the mean of the three channels, and so the pixel's brightness along the neutral axis, unchanged. Pure red sits at 0°, green near 120° and blue near 240° (counter-clockwise from `+e1`). The UI draws the plane out to `|c| = 0.30` (`WARP_PLANE_EXTENT`), which holds the colours of ordinary photos: a red of linear (0.18, 0.009, 0.009) in AWG4 reads `|c| = 0.13`.

**A pin** has a source `s` and a target `t` (points of the plane), a range `ρ`, two tonal weights (Shadows `w_lo`, Highlights `w_hi`, 0…1), a pivot `p` in stops from grey, an exposure `x` in stops, and a lock flag. A locked pin's target is its source and it has no exposure or tonal weights.

For a pixel of chroma `c₀` and tone `L` the warp is a flow, not one jump (the fix of 2026-10-19, below): in `N` small steps every moving pin's Gaussian slides from its source toward its target and the pixel follows it, so a pin reaches as far as its range however long its move.

```
δ_i  = t_i − s_i                                   moving pins
G(d², ρ) = exp(−min(d² / (2ρ²), 80))               every Gaussian, its exponent limited to 80
w_i  = w_lo + (w_hi − w_lo) · smoothstep(P_i − 2S, P_i + 2S, L),   P_i = logc4_at_stops(p_i)
λ    = Π_k (1 − G(|c₀ − l_k|², ρ_k))               locked pins l_k hold their colours
g    = smoothstep(0, 0.02, |c₀|)                   neutrals never move
γ    = g · λ                                       the pixel's own weight, at its original chroma
N    = clamp(⌈1.25 · Σ_i |δ_i| / (ρ_i √e)⌉, 1, 64)  steps, one number for the frame, from the pins
c    = c₀, then for k = 0 … N − 1, τ = k / N:
  m_i  = s_i + τ · γ · w_i · δ_i                   each centre slides by the share of its move this pixel takes
  φ_i  = G(|c − m_i|², ρ_i)                        each moving pin's reach, with the range as set
  c    = c + (γ / N) · Σ (w_i φ_i δ_i) / max(1, Σ φ_i)   overlapping pins share, they do not add up
D    = c − c₀                                      chroma displacement
E    = γ · Σ (w_i G(|c₀ − s_i|², ρ_i) x_i) / max(1, Σ G(|c₀ − s_i|², ρ_i))   exposure in stops, in one step
v'   = v + D1·e1 + D2·e2 + E · S                   S = one stop in LogC4 (0.06480)
```

- *Range is the range* (the owner's report of 2026-10-19, `docs/16`). The first version grew a moving pin's range to `ρ' = max(ρ, |δ|/1.5)` so that one pin could not fold the plane; any drag longer than 1.5 ranges replaced the slider's value by `|δ|/1.5`, so with Range 1 (ρ = 0.01) a drag of 0.1 reached 0.067 and most of a photo's colours (they lie within `|c| ≈ 0.13`) followed. The range is now used as set: a colour three ranges beside or behind the source moves by at most `exp(−4.5)` of the move (exactly that for a move of one step), where the grown range moved it by most of the move.
- *A single pin reaches its target exactly* (where its tonal weight is 1, away from locks and from neutral): the pixel on the source sits on its pin's centre at every step (`φ = 1`, `n = 1`) and moves with it, to rounding. A pixel that takes a share `γ·w < 1` of the move sees the centre slide by that share and lands on `s + γ·w·δ`, as in one step: Shadows at 40 % moves the source's shadows by 40 % of a long move. (Sliding the centres the whole way and slowing the pixel instead, the first draft, left such a pixel behind its centre: a tonal weight of 0.5 moved the source by 7 % of a 0.2 move at range 0.01.) Pins that overlap share their reach, so two pins on one colour take it to their target rather than twice as far.
- *No folding for one pin.* At one tone, away from neutral and locks (`γ = 1`), every pixel follows the same flow, that of one pin moving `w·δ`. Its field `w·δ·φ(c)` has the Lipschitz constant `w|δ| / (ρ√e)` (a Gaussian is steepest one range from its centre), an Euler step `c ↦ c + V(c)/N` is one to one with a positive Jacobian determinant when `Lip(V)/N < 1`, and a chain of one-to-one steps is one to one. The rule for `N` keeps `Lip(V)/N ≤ 0.8` for each pin. The cap of 64 never breaks that for one pin: sources and targets lie within 0.5 of neutral, so `|δ| ≤ 1`, and `ρ ≥ 0.01` give at most `1/(0.01√e) = 60.7`. It can bind for many long, narrow moves at once (their bounds add up), and then the plane can fold; so can locks and the neutral guard (`γ` changes across the plane) in odd arrangements, as before. The plane shows where every pin's colour lands.
- *What a long, narrow move does to the colours on its way.* A one-to-one map that takes `s` to `t` must move what lies between them: the colours ahead of the source on the line of the move, within about a range of it, are pushed ahead of the moving centre and arrive packed just past the target, in their order; the colours just behind the source, in a sliver about `2ρ²/|δ|` long, are stretched along the path. Colours more than two ranges from the line barely move. The stretch is steep (up to about `|δ|² / (2ρ²)`, 5,000 for a move of 1 at range 0.01), so in that sliver the flow magnifies rounding: see the f32 numbers in As built.
- *Steps.* Typical moves take few steps: a move of 0.1 at the default range 2, four such pins 8, a move of 0.2 at range 1 16, the longest move at range 1 the cap (64). A move of up to 1.32 ranges takes one step, which is the old one-step formula (`D = γ·Σ(w φ δ)/n` with `φ` at the sources) bit for bit; so is any warp whose moves add up to no more than that, and the old code never grew a range for a move under 1.5 ranges, so such warps render as they did (the CPU now limits the exponent to 80 as the kernel always did, which changes nothing a render can show). The cost is `N` Gaussians a moving pin a pixel (an `exp` and about twenty other operations, the tonal weight recomputed each step) on top of the one-step exposure: 2 for one default pin and a short drag, 64 × 16 = 1024 at the extreme.
- *Exactness.* No pins, or only locked pins, skip the stage (renders are byte-identical to a version without it). A locked pin's colour does not move at all (`λ = 0` there), at every tone.
- *Ranges.* At most 16 pins (`WARP_MAX_PINS`). Sources and targets are scaled back to `|c| ≤ 0.5`, `ρ` clamps to 0.01…0.25 (default 0.04), the tonal weights to 0…1 (default 1), the pivot to −6…+6 stops (default 0), the exposure to −2…+2 stops (default 0). Defaults leave `w_i = 1`. The constants are `WARP_STEP_SAFETY` (1.25), `WARP_MAX_STEPS` (64) and `WARP_EXP_LIMIT` (80) in `ym_color::warp`, mirrored in `src/components/warpMath.ts` (a test reads the Rust file).
- *Where it runs.* After C9 and before C10, so a look and the curve act on the warped colours, it travels into the DNG with the rest of the LogC4 grade, and Before leaves it out (Before is the camera default; its "after the grade" reading point is C9, before the warp). The kernel is `c9b_warp` in `color.wgsl`, the pins `vec4<f32>` rows of the colour kernel's uniform block filled per frame on the CPU (sources, moves, ranges, tonal weights, pivots, exposures and the number of steps). The draft said a storage buffer; the uniform is simpler and no slower (decision of 2026-10-17, below).

## C10 · Looks

A look is `CDL → LUT`, applied in its own encoding, then blended:

```
in  = v (LogC4)
out = look(in)
v'  = in + k · (out − in)        k = intensity / 100, blended in LogC4
```

- **CDL** (ASC v1.2): `x = max(x·slope + offset, 0)^power` per channel, then saturation with Rec.709 weights (0.2126, 0.7152, 0.0722): `L = w·x; x = L + sat·(x − L)`.
- **3D LUT:** `.cube` (Resolve/Adobe format: `LUT_3D_SIZE`, optional `DOMAIN_MIN/MAX`, optional `LUT_1D_SIZE` shaper, red varies fastest). Tetrahedral interpolation. Inputs are clamped to the domain. Upload as an **f32 storage buffer** (one `vec4<f32>` per node, red varying fastest) and interpolate by hand in the shader (tetrahedral), never with hardware trilinear. Not a texture: a LUT texture stored as rgba16float rounds values in [0.5, 1) by up to 2.4e-4, which alone is more than the 2e-4 parity target between the GPU kernel and the CPU reference. A 65-point cube costs 4.4 MB and a 129-point one 34 MB as f32, which is acceptable for one look at a time. Only image intermediates are f16 (`ym_gpu::kernels::color`, section Precision decision).
- **LogC4 log-to-log looks** (ARRI LogC4 Look Library, our built-ins): apply directly.
- **LogC3 log-to-log looks:** LogC4 → linear AWG4 → AWG3 → LogC3 EI 800 → LUT → linear AWG3 → AWG4 → LogC4. The blend happens in LogC4 after converting back.
- **LogC3-to-Rec.709 looks** (look and rendering baked together) **replace** C12: the chain is C9 → C11 (the curve runs before the look in this case) → LogC4 to LogC3 conversion → LUT → display Rec.709 (gamma 2.4). Intensity blends between our C12 output (from the same C11 output) and the LUT output in display-linear Rec.709. The UI marks these looks "includes display rendering". A DNG of such a look is allowed, approximately (owner's decision of 2026-10-14): ARRI's display rendering has no scene-linear form, so the DNG's pixels are the scene values that ACES 2 (with the display placement, C12) turns into the look's display picture at the chosen intensity, found with the inverse output transform (`Aces2Transform::inverse_ap0_linear`; display white and out-of-gamut values clamp, scene values are limited to the range of the DNG profile), and Adobe's renderer, running the profile fitted to ACES 2, shows approximately that picture (`docs/09`, "What a DNG carries"). The same holds for an imported ARRI display LUT chosen as C12.
- **Built-in looks:** Neutral is the identity. Signature (the default look, owner's decision of 2026-10-14) is parametric (a luma tone curve and CDL saturation in LogC4, optionally hue/saturation curves) and stored as JSON in `data/looks/builtin/`; it is baked into a 65³ LUT at load, so C10 treats it like any LogC4 LUT (`docs/08` Built-in looks).

**As built (M1-10).** `ym_color::{cdl, cube, lut, look}`.

- *CDL.* `x = max(in·slope + offset, 0)^power`, then `L = 0.2126R + 0.7152G + 0.0722B; out = L + sat·(x − L)`. No clamp at 1 (the CDL runs on log codes and look output); OpenColorIO's `CDL_ASC` also clamps at 1 before and after saturation and agrees wherever every intermediate stays in [0, 1]. `Cdl::new` checks the ASC ranges (slope ≥ 0, power > 0, saturation ≥ 0).
- *.cube dialects.* `cube::parse` reads the Adobe/IRIDAS dialect (`TITLE`, `LUT_3D_SIZE` or `LUT_1D_SIZE`, `DOMAIN_MIN/MAX`) and the Resolve dialect (`LUT_1D_INPUT_RANGE`, `LUT_3D_INPUT_RANGE`, a 1D table followed by a 3D table in one file, the 1D table being a shaper). Sizes: 3D 2 to 129, 1D 2 to 65536; at most 256 MiB; comments, blank lines, LF, CRLF, CR, a BOM and case-insensitive keywords are accepted; every number must be finite; every failure is a typed `CubeError` with the line number. Domains: for a lone table, `DOMAIN_*` or the matching `LUT_*_INPUT_RANGE` (they must agree if both are given); with both tables `DOMAIN_*` and `LUT_1D_INPUT_RANGE` belong to the shaper and `LUT_3D_INPUT_RANGE` to the cube. A 1D-only file parses but `parse_lut` refuses it (a look needs a 3D LUT). OpenColorIO reads the same files the same way (`iridas_cube`, `resolve_cube`).
- *Tetrahedral.* `Lut3d::sample` uses the six-tetrahedra split of the fractional position (the same as OpenColorIO's), clamps to the domain (a NaN input counts as the domain minimum), is exact at grid nodes and continuous across cell faces. Against OpenColorIO 2.6 tetrahedral on our own synthetic cubes (`tools/vectors/lut_vectors.py`: identity 9, warp 17, ripple 33, an asymmetric-domain 9, a 2-point extreme cube, a 64-entry shaper plus 9-point cube; 3714 points each including grid nodes, cell diagonals and out-of-domain inputs) the largest difference is 2.1e-7 = 0.0002 code values at 10 bits (OpenColorIO's float32); trilinear would be 1.75e-3 (1.8 code values) on the warp cube, so the gate pins the method.
- *Looks.* `look::LookTransform::{neutral, new, eval_logc4, apply_logc4(v, intensity_pct), eval_display_rec709}`, `blend_logc4`, `blend_display_linear(own, look, intensity_pct)` (both in the same linear primaries; convert the look output with `LinearRec709::to_display_p3` / `to_rec2020` first), `rec709_gamma24_decode` (negative LUT output clamps to 0). 0 % returns the input and 100 % the look output exactly. CDL and LUT run in the look's own encoding (a LogC3 look applies its CDL to LogC3 codes). Inputs above the LUT domain clamp (LogC3 code value 1.0 is linear 55, so LogC4 highlights above that hold the LUT's top value in a LogC3 look).
- *Parametric looks.* `look::ParametricLook::from_json` reads the schema documented at the top of `crates/ym-color/src/look.rs` (`yellowmoon.parametric-look/1`: `cdl`, `hue_vs_sat`, `hue_vs_hue`, `luma_vs_sat`, all optional, evaluated in LogC4, chroma and hue measured along the C9 axes `e1`, `e2`, Rec.709 luma preserved) and `bake(65)` samples it on a 65³ cube (33³ until 2026-10-19). The example in `tests/data/looks/` bakes with a maximum error of 3.2e-3 LogC4 code values at 65 points (at 33 points: median 1.1e-4, maximum 7.7e-3, the most saturated reds next to the blue floor; 3.7e-3 where all channels are above black).

## C11 · Curve

Applied in LogC4 after the look and before the display transform, so it travels into DNG export and behaves the same under every display transform. Four monotone cubic splines (Fritsch–Carlson) on [0,1]: luma (applied as `v += curve(L) − L`) and R, G, B (per channel). Baked into four 1024-entry tables, uploaded as **f32 storage buffers** and looked up by hand with linear interpolation in the shader, not as 1D textures (an f16 texture would round the values in [0.5, 1) by up to 2.4e-4, more than the 2e-4 parity target). The histogram in the Curve tab is of LogC4 values. Numbers in the UI show code values × 255, rounded.

**As built (M1-09).** `ym_color::curve::{Curve, CurveSet, BakedCurves}`. Fritsch–Carlson tangents (mean of the neighbouring secants, zero at extrema and flat segments, one-sided at the ends, then the `α² + β² ≤ 9` limiter); 2 to 16 control points, `x` strictly increasing, all in [0, 1]; invalid input is a typed `CurveError`. The spline is C1 and never overshoots the data of a segment. Between 0 and the first point and between the last point and 1 it holds the end value. The 1024-entry table (`CurveTable`, sampled at `i/1023`, linear interpolation; worst deviation from the exact spline 5.9e-7) continues with slope 1 outside [0, 1] (`eval_extended`: `x + table[0]` below 0, `x − 1 + table[1023]` above 1), so the map stays monotone for LogC4 values beyond the unit range; the shader's `curve_eval` applies the same extension explicitly. The luma curve uses `L = encode(Y(decode(v)))` of the pixel entering C11 and is applied before the R, G, B curves.

## C12 · Display transform

### ACES 2 (default)

Port the ACES 2.0 output transform (aces-output, Apache-2.0) to Rust (CPU reference) and WGSL.

1. LogC4 → linear AWG4 → AP0 (AWG4 → XYZ, CAT02 D65 → ACES white, XYZ → AP0; compute the matrix in `ym-color`).
1a. **Placement.** Multiply the AP0 triple by `2^k` with `k = DISPLAY_PLACEMENT_EV = +0.85` (`ym_color::display`; a constant of the look, not a control, and not a measurement). `aces2_input_matrix()` is `2^k · awg4_to_ap0`: the CPU chain uses it and the GPU kernel's `AWG4_TO_AP0` constant is written from it, so both apply the same numbers. It sits after the look and the curve, so a look still sees mid grey at LogC4 0.2784 (the placement is after C10 and C11), and before the ACES 2 transform. Through the Neutral look it puts scene 0.18 at display-linear 0.1893 (OpenColorIO's ACES 2.0 SDR value for `0.18 · 2^0.85` is 0.189253; sRGB code 120.4, 50.0 % video at gamma 2.4) instead of 0.1000 (code 89, 38.3 %): +0.92 EV of display light for +0.85 EV of scene light, about where a camera JPEG puts mid grey (ISO 12232: 0.18, code 118; ours is 2.4 codes higher).
   It applies to the ACES 2 path only. An imported ARRI display LUT and the LogC3-to-Rec.709 looks keep ARRI's own brightness: with such a look the intensity blend (C10) runs between our C12 (placed) and the look's LUT (not placed), so its Intensity slider also changes the brightness, by up to 0.85 EV (accepted). A DNG carries the placement in `BaselineExposure` (`docs/09`).
   Why: ACES 2 SDR is a cinema rendering, which puts scene 0.18 at 10 nits, 0.85 EV under a camera JPEG. Yellowmoon is a photo processor, not a video tool: "we can do brighter than the reference LUT" (owner, 2026-10-14). What it does to highlights, measured on the 12 local files (2000 px sRGB renders, largest channel, before = the previous pipeline: metered exposure, no placement; after = the camera gain and the placement): pixels at or above code 220 were 0.001 % on average (at most 0.015 %) and are 0.16 % on average (at most 1.16 %, A7 II; A1M01739 0.44 %, A1M01749 0.28 %, all others 0.05 % or less); pixels at or above code 250 are 0.000 % before and after on all 12 (on the A1 photos the 99th percentile luma code goes from 148, 172 and 151 to 171, 217 and 195; the camera JPEGs' are 182, 242 and 215, and 49 and 33 % of their pixels on two of the three scenes are at or above code 220, so there is room). Median luma code (8-bit, 0.2126 R′ + 0.7152 G′ + 0.0722 B′): 77 … 118 before, 91 … 177 after. The three A1 photos against the owner's reference exports and the camera JPEGs (median luma code, now / owner export / camera JPEG, previous in brackets): A1M01749 143 / 143 / 137 (94), A1M01739 177 / 192 / 195 (118), A1M01454 127 / 115 / 112 (103), that is +0.00, −0.26 and +0.31 EV against the owner's exports in linear light.
1b. **White lift** (owner's decision of 2026-10-14, task D-02; `white_offset_ev`, the Automatic card's White row). A per-photo scene-linear gain `2^(A · smoothstep((s − 1) / span))` on the luma of the decoded C11 output (`s` the stops over middle grey), applied to linear AWG4 **before the placement** and ACES 2: exactly 1 up to +1 stop over mid grey (mid grey and everything below it are untouched), ratio-preserving, per channel monotone, ACES 2 path only (an imported ARRI display LUT and a LogC3-to-Rec.709 look keep ARRI's highlights). `A` and the anchor are sized per photo from the 1/8 preview when it is opened; the DNG carries it in its pixels. The full text, the estimator, the constants and the numbers are in the section *White lift (C12 step 1b)* below.
2. ACES 2 output transform with: peak luminance 100 nits, SDR, white D65, and limiting primaries:

| Output | Limiting primaries | Encoding |
|---|---|---|
| Viewport | P3-D65 | Display P3 (sRGB transfer) |
| sRGB export | Rec.709 | sRGB transfer |
| Display P3 export | P3-D65 | sRGB transfer |
| Rec.2020 export | P3-D65 | Rec.2020 primaries, BT.1886 (gamma 2.4) |

3. Gamut compression is part of ACES 2; out-of-gamut values from C8 are handled there.

Reference values: generate test vectors offline with OpenColorIO ≥ 2.4 (BSD-3), which ships ACES 2 built-in transforms. Commit the vectors (a few hundred RGB triplets per output) under `crates/ym-color/tests/data/`. Gate: ≤ 1 code value at 10 bits against the vectors. The vectors test the transform itself and do not include the placement (step 1a): the chain tests build the AP0 triple with `aces2_input_matrix()`, and the chain-level OpenColorIO vectors (`display_ocio_vectors.rs`, `gpu_color_vectors.rs`) feed a fused matrix of `2^-k` so that the placement cancels.

**CPU reference (M1-11), as built.** `ym_color::aces2` (`Aces2Output::{Viewport, Srgb, DisplayP3, Rec2020}`, `Aces2Transform::new(output)`, `transform_ap0`, `transform_ap0_linear`; attribution and commit hashes at the top of the module).

- *Source.* The transform's maths lives in the ACES project's **aces-core** repository (`lib/Lib.Academy.*.ctl`); aces-output only holds the per-display presets that call it. The port follows the CTL and was cross-checked against OpenColorIO's C++ implementation.
- *Vectors.* `tools/vectors/aces2_vectors.py` writes `crates/ym-color/tests/data/aces2/{viewport,srgb,display_p3,rec2020}.json` (898 AP0 inputs per output: neutrals from −8 to +12 stops, gamut primaries and secondaries at five exposures, a chromaticity wheel, AP0 primaries, edge cases, seeded random in-gamut, out-of-gamut, near-black and very bright values) with OpenColorIO 2.6.0's float32 output. Every output is the built-in `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-<REC709 or P3-D65>_2.0` followed by a `DISPLAY - CIE-XYZ-D65_to_<sRGB, DisplayP3 or REC.1886-REC.2020>` built-in. The studio config has display/view pairs for sRGB (`sRGB - Display` / `ACES 2.0 - SDR 100 nits (Rec.709)`) and Display P3 (`Display P3 - Display` / `ACES 2.0 - SDR 100 nits (P3 D65)`); the script checks they equal the built-in chain exactly. It has no Rec.1886 Rec.2020 display, so the Rec.2020 export is the P3-limited built-in plus the Rec.1886 Rec.2020 display built-in, which is how the config builds its own pairs.
- *Numerics.* f64 with the reference's iteration tolerances unchanged (the CTL and OpenColorIO run in float32). The tables agree with OpenColorIO's float32 tables to 1e-5 relative. Gate result: at most 0.03 code values at 10 bits over the vectors and 0.05 over random sweeps of 1.9 million samples per output.
- *Reference glitch.* In float32 the reference returns NaN (black) in a thin band of scene luminance near 128 × white with a little chroma, where the tone-scaled lightness reaches the display maximum. The port guards that case and returns white; an f32 WGSL port needs the same guards (see the module notes).
- *Rec.2020 overshoot.* P3 red lies just outside Rec.2020, so saturated cyan converts to a blue up to 1.00121 in linear light (1.0005 encoded, half a 10-bit code value). The reference leaves it unclamped; `transform_ap0` clamps to [0, 1], `transform_ap0_unclamped` keeps the reference value.
- *The inverse (2026-10-14, for the DNG of a look with its own display rendering).* `Aces2Transform::inverse_ap0_linear` is the port of the reference's `outputTransform_inv` (`aces2/inverse.rs`: the inverse tone scale, the inverse chroma compression with the inverse toe, and the gamut compression run backwards along the same compression vector, in two passes above the analytical threshold; the geometry is `compress_gamut_with`, shared with the forward transform through the reference's `invert` flag). Display values are cleaned first (not a number is 0, outside `0..=peak` clamps), so the result is always finite; near display white it grows (display 0.99 is scene 58.6, 1.0 is the roof, 128), and the caller limits it. Gate (`tests/aces2_inverse.rs`, vectors `tests/data/aces2/srgb_inverse.json` from OpenColorIO 2.6's built-in transform run in the inverse direction, `tools/vectors/aces2_inverse_vectors.py`): in-range vectors (display up to 0.9, 1,016 of the 1,242) agree to a relative 1.3e-4 (the neutral ramp 5.0e-5; display 0.99 gives 58.559 against OpenColorIO's 58.562); display to scene to display returns the display value to 5.5e-10 over the same 1,016 colours (the CTL's two-pass inverse is exact to f64 rounding here), scene to display to scene to 2.2e-14 relative over 193 colours.

### White lift (C12 step 1b)

Owner's decision of 2026-10-14 (`docs/16`; task D-02 of `research/dynamic-vs-lut-2026-10-14.md`, section 2, stage 2). A per-photo, scene-linear gain on the tones above +1 stop over middle grey, so that the brightest tones of a photo can reach a real white. Mid grey and everything below +1 stop are untouched. It is an *automatic* setting: its amount is sized from the photo's own highlights when the photo is opened, shown in the Automatic card (`White`) and offset with `white_offset_ev` (Light › White › Offset, `ym render --white-offset`).

**Why.** ACES 2 SDR is a cinema rendering with a flat shoulder: 1.4 scene stops above the placed middle grey lift the display by about 0.4 stop, so a photo whose highlights sit two or three stops over grey ends at light grey. Measured on the 12 local photos at +0.85 EV with no lift, the 99.5th percentile of the display luma code is 147 to 218 against 161 to 247 in the cameras' JPEGs; the placement of step 1a closes part of the gap and not the missing white. The C9 Highlights and White sliders are the wrong tool (to reach the same picture they would need 61 to 84 and 31 to 42 on the six photos that need it, and they change 40 to 83 % of the pixels). The clip level is a constant +3.58 stops over grey on all 12 photos (green clips first), so the clip does not tell one photo from another (the C7 highlight range moves it the same way for every photo); what varies from photo to photo is the distribution of the highlights, and that is what sizes the lift.

**The stage** (`ym_color::exposure::white::WhiteLift`; the CPU reference, `display/transform.rs`, the WGSL `white_lift_gain` in `color.wgsl`):

```
Y    = 0.2126 R + 0.7152 G + 0.0722 B           luma of the decoded C11 output, linear AWG4
s    = log2(Y / 0.18)                           stops over middle grey
t    = clamp((s - 1) / span, 0, 1)              span = max(anchor - 1, 0.25)
gain = 2^(A * t^2 (3 - 2t))                     smoothstep
rgb' = gain * rgb                               all three channels
```

`A` is the amount in stops and `anchor` the stops over grey at which the lift is complete: the **two scalars** of a photo (`AutoEstimates::white`). The stage sits after C11 (so a look still sees mid grey at LogC4 0.2784), in front of the placement of step 1a and ACES 2, **on the ACES 2 path only**. Properties, all tested (`crates/ym-color/tests/white_lift.rs`): the gain is exactly 1 up to +1 stop (so mid grey lands on the same display value, bit for bit, and nothing below +1 stop moves, to far better than 1e-9 in scene-linear); it never decreases with the luma and never exceeds `2^A`; the three channels are multiplied by the same number, so the colour ratios of a pixel are kept exactly; every output channel is non-decreasing in each input channel (a product of a channel and a non-negative, non-decreasing function of the luma); `A = 0` is the exact identity (`WhiteLift::NONE`, the same bits as no stage). *The luma has the Rec.709 weights and not the AWG4 `Y` row*: the `Y` row has a slightly negative blue weight (-0.036), and a gain driven by it makes a saturated blue's own output fall when its blue channel rises (slope -0.31 at `[0.46, 0.49, 2.67]`); with positive weights the property is exact. A neutral value is its own luma either way (both rows sum to 1), which is all the estimator measures.

**ARRI's own rendering.** An imported ARRI display LUT and a look that includes its own display rendering (LogC3 to Rec.709) keep ARRI's highlights: the chain ignores the lift for a display LUT (`ColorChain::white_lift()` is then the identity), and for a display-baked look the blend of C12 runs between *our* C12 (placed and lifted) and the look's LUT (neither), like the placement, so at 100 % the picture has no lift and at 0 % it is our C12 with it.

**With the highlight range** (2026-10-17). C7's range acts first, on the scene side; the lift acts on the C11 output. The estimator meters the preview after the range at its default, so the range's work is counted: a photo whose highlights reach the camera's clip has them taken towards white by the range already and gets a smaller lift, or none; a photo whose brightest areas sit well under the clip (a sky two stops over grey) is untouched by the range and gets the lift it had in 0.1.9. Where both act on a pixel the gains multiply, and ACES 2 holds the result at white. Measured on the 12 local photos at Auto (`ym render --cpu`, default look): `A` runs from 0 to 0.98 stops and 4 photos get none, two because the range already takes their highlights to display codes 240 and 247 (A1M01739, ILCE-7M2) and two because they are not high-key (ILCE-7M3, NEX-5N); A1M01749's 90th percentile of the display luma code is 224.9 with the lift and 203.7 without it (225 in 0.1.9, which had the lift and the old shoulder). The estimator's reference neutral axis uses `ToneParams::IDENTITY` (the range's cap at 7.64 stops would bend it), and the estimator's own tests were rebuilt with the range at its default.

**The DNG carries it** (owner's rule: the DNG carries every change except sharpening, `docs/09`). The lift is a scene-linear gain, so it is baked into the DNG's AWG4 pixels after the look and curve and before the fitted profile (`ColorChain::apply_dng_pixel` is C11 decoded and lifted): the DNG's pixels through ACES 2 with the placement (`BaselineExposure`) are the app's picture with the lift in it, to 1e-5 of display light (`crates/ym-core/tests/white_lift.rs`; `crates/ym-color/tests/white_lift.rs` to 1e-12).

**The two scalars** (`ym_color::exposure::white::estimate_white`, a pure CPU function of the 1/8 preview, called by `AutoEstimates::compute_with_look` after the exposure). The preview is the one the exposure is metered on (balanced with `g0`, vignetting gain applied), taken through the all-Auto chain at the photo's exposure and C7 at its defaults (the highlight range at 1 and the toe at 0.5, whatever the photo's own Range settings):

1. `L` is the stops over grey of the luma of every pixel. `P` is the 99.5th percentile of `L` (the brightest half percent of the photo) and `B` the 99.5th percentile of a box-blurred copy of `L` (radius `0.007 · width` preview pixels, 8 for a 1188-pixel preview; edges average the part of the window inside the frame): `B` is the level of the photo's highlight *areas*, a few small speculars do not move it. Clipped blocks count like any other pixel (a clipped sky is a white to lift); a non-finite pixel counts as the darkest.
2. `P` and `B` are carried through the **reference look**, the Signature look (`data/looks/builtin/signature.json`, read by `SessionEnv::load`; no look is the identity), on the neutral axis: the lift acts on the C11 output, so what it has to add is what the look has not already given. `anchor` is `B` after the look; the amount is sized for `P` after the look.
3. `d` is the display luma code (0 to 255, ACES 2 with the placement, sRGB) a neutral tone at `P` has through the reference rendering, and `high_key = clamp((B_before_look - 1) / 1.5, 0, 1)` says how high-key the photo is. The target code is `d + high_key · max(235 - d, 0)`. **The ramp reads `B` before the look**: the look lifts the shoulder by itself (the Signature look by about half a stop above +1 stop), and counting that in the ramp as well would make the lift grow twice for the same photo.
4. `A` is the smallest amount that takes the display code of `P` to the target (a bisection on the neutral axis through the real chain: `ColorChain::apply_pixel`), held to 0 … 2 stops; a photo whose highlights are not above +1 stop gets 0.

The estimator never sees the user's settings (light, exposure, grade, look, curve): it runs once per open with the photo's automatic exposure, like the other automatic estimates, so no slider moves it, and "Re-run" recomputes it. The user's offset is added afterwards: `amount = clamp(A + white_offset_ev, 0, 3)`, so offset 0 is the automatic amount, a negative offset of `A` (or more) gives no lift at all, and a low-key photo can be given one by hand. **No burst rule:** the estimate is a function of the photo's own preview, so the app and `ym` give the same two numbers for any set of photos; it is made at the photo's own exposure and is not re-made when a burst median replaces the exposure (with the constant camera gain that happens only to a frame the highlight guard lowered, by at most one stop, and the highlight guard acted on none of the 12 photos). **Deterministic:** single-threaded, f64 sums in a fixed order and order statistics (`select_nth`): the same preview gives the same bits whatever the thread count of the decoder or the machine's core count (`tests/white_lift.rs::the_estimate_is_the_same_whatever_the_decode_threads`). Cost: 100 ms (median of five, dev profile) for the 1188 x 792 preview of a 61 MP frame, the per-pixel pass, the blur and two order statistics (`cargo test -p ym-color --test white_lift -- --ignored --nocapture timing`); the whole open of a photo, decode included, takes 0.2 to 0.5 s on the 12 local photos.

**Re-tuned with the Signature look in place** (the prototype's target code 235 and ramp 1 … 2.5 stops are unchanged; what changed is where they are read). The research prototype sized the lift against the bare ACES 2 picture (amounts 0, 0.13 to 0.31, 0.77 to 1.15 stops at +0.85 EV). ### Imported ARRI display LUT

If the user chose "ARRI's display rendering" in the wizard or preferences, C12 is the imported display `.cube` (for example LogC4 → Rec.709 gamma 2.4, or → P3). LogC4 display LUTs apply to the LogC4 output of C11 directly; LogC3 display LUTs (the older package, including the classic Rec.709) apply after converting LogC4 → linear AWG4 → AWG3 → LogC3 EI 800. For the viewport, decode the LUT's output transfer (gamma 2.4 for Rec.709) to display-linear, convert primaries to P3, and encode with the sRGB transfer. For export, convert to the chosen colour space the same way.

## C13 · Display encode

sRGB transfer for sRGB and Display P3, BT.1886 inverse (gamma 2.4) for Rec.2020. Dither 8-bit outputs with a fixed blue-noise texture (seeded, deterministic). Embed the matching ICC profile on export (`docs/09-export.md`).

**As built (M1-10).** `ym_color::encode`. sRGB (IEC 61966-2-1, thresholds 0.0031308 and 0.04045) for sRGB and Display P3, the pure `x^(1/2.4)` for Rec.2020; both odd-symmetric below zero, clamped to [0, 1] before quantising (`OutputSpace::encode_clamped`). `quantize(v, bits)` rounds to nearest (8, 10 or 16 bits; a NaN is 0). *Dither (8-bit only):* a 64 × 64 void-and-cluster rank texture (Gaussian σ = 1.5 on a torus, seed `0x59454c4c4f574d4f`, integer weights and lowest-index tie-breaks; generated by `encode::blue_noise::generate`, embedded as a table so no platform's `exp` can change it, fingerprint `0x993fccd5c6db3aa9` checked in the tests). The threshold at absolute output pixel `(x, y)` is `(rank[y mod 64][x mod 64] + 0.5)/4096`; the code is `floor(v·255 + threshold)`; all three channels share the threshold (achromatic noise). Over one tile the thresholds are the 4096 evenly spaced values in (0, 1), so a constant input averages to its exact value (measured error 0 over 1021 levels) and the result is never more than one code from `v·255`. Spectrum: power at radial frequencies 1 to 5 is 1e-4 of the power at 16 to 33 (white noise would be 1). A change to the table changes every dithered export (bump `pipeline_version`).

**As built (C7 to C13 chain).** `ym_color::display` (`ColorChain`, `ChainParams`, `DisplayTransform`, `OutputTarget`, `Frame`): the CPU reference of everything per pixel after the fused C1–C6 matrix, which the CPU fallback runs and every GPU kernel is parity-tested against.

- *Order.* `M · x` (supplied as a 3×3) → C7 → C8 → C9 (with `L` from the linear values entering C8) → C10 → C11 → C12 → C13. A LogC3-to-Rec.709 look is classified when the chain is built: C10 is skipped, the curve runs first, and C12 evaluates both our display transform and the look's LUT from the same C11 output and blends them in display-linear (`blend_display_linear`, in the output's primaries, so the look's Rec.709 is converted first). At intensity 0 the result is our C12 bit for bit, at 100 it is the look's. Neutral, an identity look and an intensity of 0 skip C10 and are exact identities. `ColorChain::trace(rgb)` returns every stage's value for debugging kernel parity stage by stage.
- *Entry points.* `apply_pixel` (code values in [0, 1], f64), `apply_to_display_linear` (C1–C12, the picture an exporter resizes in linear light before `encode`, `encode_u8` or `encode_u16`), `apply_logc4_pixel` and `apply_dng_pixel` (stop after C11, decode to linear AWG4; with a look that includes display rendering at an intensity above 0, or an imported display LUT, the scene-linear AWG4 triple that ACES 2 turns into the chain's display-linear sRGB picture, `dng_inverts_display()`, limited to `DNG_SCENE_LIMIT / 2^DISPLAY_PLACEMENT_EV`), `apply_before_pixel`, and band-parallel buffer renders over planar or interleaved f32 (`render_encoded_f32`, `render_display_linear_f32`, `render_dng_linear_awg4_f32`, `render_u8`, `render_u16`, `encode_display_linear_u8/u16`). The planar layout is `ym_gpu::cpu::RgbImage`'s. Threads are `std::thread::scope` workers over row bands (no `rayon` in `ym-color`'s manifest); output is bit-identical for any thread count, and 8-bit dither uses absolute pixel coordinates (`origin`), so tiles agree with the whole image. NaN camera samples count as 0, infinities are limited to ±1e30.
- *Imported ARRI display LUT.* `ArriDisplayLut { lut: Arc<Lut>, input: LogC4 | LogC3Ei800, output: DisplayLutOutput }`, as C12 above: LogC4 input directly, LogC3 after the exact conversion; the output codes are decoded with the LUT's transfer, converted by a 3×3 to the output's primaries (a colour outside the output gamut is clipped by C13, not gamut-mapped) and encoded by C13. `DisplayLutOutput::from_target("rec709-g24")` reads the importer's target slug: primaries from `709`/`srgb`, `p3`, `2020`; transfer from `gNN`/`gammaNN`/`srgb`. Decisions: with no gamma in the slug Rec.709 and Rec.2020 are gamma 2.4 and P3-D65 is gamma 2.6; HLG, PQ and DCI-white targets are refused (`UnsupportedTarget`). Verify the real package names when they are fingerprinted (M3-H2).
- *C13 transfer.* The chain encodes display-linear with `encode` (IEC 61966-2-1, break at 0.0031308) as specified. The ACES 2 port's own `transform_ap0` ends with the reference's continuous "moncurve" (slope 12.9232, break at 0.0030399); the two differ by at most 9.8e-6 near linear 0.00304 (0.0025 of an 8-bit code, 0.64 of a 16-bit code). The Rec.2020 output (a pure power law) is unaffected. A WGSL port follows C13 (IEC).
- *Before view.* The photo as the camera would render it by default, outside the stages above: see *The Before view* below. Until 0.1.3 it was the LogC4 signal at C8 shown as code values (`docs/11` said "the LogC4 signal before look and display transform"); `BeforePoint::CameraLog` (the output of C8) and `BeforePoint::AfterGrade` (C9) remain in `ym_color::display` for tests and diagnostics, and the app no longer uses them.
- *Speed (`tests/display_perf.rs`, one 4-vCPU machine shared with other builds, load average 22–30, so wall times are inflated; CPU time per pixel is the stable figure).* Full chain with ACES 2, camera RGB to dithered 8-bit: 1.05 µs of CPU per pixel with zero grade, Neutral look and identity curves, 1.27 µs with grade, a 33³ look and curves; the DNG stop (C1–C11) is 0.48 µs. Projected on four free cores: about 3.6 and 2.9 Mpx/s, a 24 MP frame in 7 to 8 s. Preparing a chain takes 17 to 40 ms the first time (ACES 2 tables), then under 1 ms.

## The Before view

The owner's request (2026-10-16): "The 'before' button shows LOG file, which doesn't make much sense. Can we show basic RAW processing instead, without ARRI transformation, edits to color, light, etc, but with demosaicing? Sort of default look, as Sony would produce it by default so users can see what changes Yellowmoon introduced." The Before view therefore shows the photo as the camera would render it by default. It uses the raw stages R1 to R9 of the final picture except R3, the lens vignetting correction, which the camera's own picture leaves out (the owner's decision of 2026-10-16, `docs/16`): demosaic, denoise, the distortion and chromatic-aberration corrections, the decode switches, crop and orientation are as for the final picture. Then only constants and facts of the file:

```text
camera RGB (the mosaic x g0, as it enters the chain)
  --M_before--> linear Rec.709          M_before = M_xyz_to_rec709 . inv(CM_n) . diag(gs / g0) . 2^CAMERA_GAIN_EV
  --camera tone curve, per channel--> display-linear Rec.709
  --from_linear_rec709--> the output primaries --C13--> code values
```

- *As-shot white balance* `gs = [R/G, 1, B/G]`: the gains stored in the file, on the body's own raw scale (no white scale, `docs/03`), not our estimate. A file without usable gains keeps `g0` itself (the identity balance). `g0` is divided out because the raw stages already multiplied the mosaic by it, so the result does not depend on it.
- *Body colour matrix* `CM`: the D65 colour matrix of the body (XYZ to camera RGB), numbers from the bodies' published D65 colour matrices (`data/cameras/color-matrices.json`, `docs/14` rule 8), found by the file's Sony model ID when the file has one, otherwise by its Model string (an ID that is not listed gives the A7R IV entry even when the Model string names a listed body: the ID wins, as in `docs/03`); a body that is not listed, a Make other than Sony and the two bodies left out (ILCE-7M5 and ILCE-7RM6: none published) use the A7R IV entry, as the profile registry falls back to the A7R IV profile. Two entries borrow their numbers by the owner's decision of 2026-10-16 and say so in a `note`: the A1 II (ILCE-1M2, ID 400) takes the A1's numbers, because it has the A1's sensor (the published numbers for the two are the same), and the A3000 (ILCE-3000, ID 302, which Sony writes for the A3500 too) takes the generic E-mount matrix, the numbers the published tables give any E-mount body without an entry of its own (the NEX-5N's; the A6000, A5000 and A5100 carry them too), on the same evidence as those three. The numbers belong to the ID the camera writes, so each entry's ID is the one Sony publishes for that body (the first draft had eight IDs of other bodies, so that a real NEX-6, NEX-5T, A7S or A6500 file got the A7R IV entry and an A7, A7R or A6000 file got a neighbour's numbers; fixed 2026-10-16). `CM_n` has its rows scaled so that D65 white maps to camera `[1, 1, 1]`, so the as-shot white comes out exactly neutral (R = G = B).
- *Camera gain* `CAMERA_GAIN_EV` (+1.11 EV, *Auto exposure* above): the same constant as the final picture's exposure, so middle grey 0.18 sits where the camera's own JPEG puts it.
- *Camera tone curve*, per channel in linear Rec.709, the same on every body: `y = min(1, k t / (t + s))`, `t = max(x, 0)^n`, `n = 1.6558`, `sigma = 0.4569` (`s = sigma^n = 0.273358`), white 2.5 (`y = 1` from `x = 2.5`), `k = (white^n + s) / white^n = 1.059955`. Middle grey 0.18 lands on display-linear 0.18675, sRGB code 119.7 of 255 (the median of the 12 embedded JPEGs at that level is 119.8); the slope there is 1.36 in log-log, about 52 codes a stop; the neutral raw clip (2.16) lands on code 253. A negative linear value is clamped to 0 per channel, as in the JPEGs, and the curve is applied in Rec.709 primaries (what the JPEG engine does) before the conversion to the output's primaries, which keeps the picture inside the sRGB gamut. The constants are in `ym_color::camera_default`; `data/cameras/camera-default-tone.json` carries them, a 28-point golden table and the fit summary, and a test pins the file to the code.
- *What is not in it:* no sensor map (the ALEXA emulation), look, grade, curves, display transform (ACES 2 or an ARRI LUT), highlight range (C7), display placement or output sharpening, **no lens vignetting correction (R3)**, and no user setting reaches it: exposure, white balance, look, tone, colour, curves and the RAW tab's Range do not (the fused matrix is not used at all), and neither do the Detail controls that sit in the raw group, noise reduction and capture sharpening, which the Before view reads at Auto whatever they say (the owner's decision of 2026-10-16, which keeps the earlier reading; `PhotoSource::for_before_view`). The decode switches and the lens corrections do change it, as they change the raw (a switch that moves pixels, such as the distortion correction, moves them in the Before view too; the lens switch also decides whether the file's vignetting table exists for the final picture, and the Before view never applies it), and so do crop and orientation (geometry is applied as for the final picture).
- *Where.* CPU reference: `ColorChain::apply_before_pixel` (`BeforePoint::CameraDefault`, the default; `ChainParams::camera_default` is the per-photo `CameraDefault`, `CameraDefault::neutral()` when a caller does not know the body); the pixel readout (`sample_pixel`) and every buffer render of `View::Before` follow it. `ym-core` builds the `CameraDefault` per photo in `color_plan` (`camera_default_of`: the table by model ID, the as-shot gains from the raw, `g0` from the estimates) and puts it in the grade key, so a frame of the Before view is never served for another body or white. The colour kernel (`Stop::Before`, `lk.w = 2`) computes the same: the 3x3 and the curve constants are in the uniform block (`cam0` to `cam2`, `camt`; 1056 bytes since this change, 992 before), the Rec.709 to output matrix is the one the display-baked look uses (`look_m*`), and the result is already C13-encoded. The histogram is of the final picture and does not change.
- *The raw front without R3 (2026-10-16).* `PhotoSource::for_before_view` sets `before_view` (and puts Detail at Auto); `Job::params` turns that into `RawParams::vignetting = false` when the photo has a vignetting table to apply (`has_vignetting_profile`: a mosaic file, a usable 0x7032 table, the lens switch on); `RawPlan::without_vignetting` is then the plan (levels, lens maps, crop and clip answer are the final picture's; only the profile is left out), and the `FullChain`, the device's reduced front (`reduced_params` has no vignette table, so the prep kernel skips R3) and the tiles are built from it. The flag is part of `RawParams::key`, so every cache of the raw group (`groups`, `tiles`, the display and frame caches) keeps the Before view's entries apart from the final picture's and nothing made without R3 is ever served for a picture that has it; the graph keeps one plan and one prepared chain for each of the two, so flipping back and forth prepares neither again; the sigma plane is shared (it is made before the gain). The hue differs from Sony's by 4.5 degrees at the median (1.3 to 9.9), which a per-channel curve cannot fix; the JPEG's chroma over ours is 0.94 at the median (0.78 to 1.17), so no separate saturation factor is used. In the deep toe (-4.5 to -3.5 stops) the JPEGs are 2 to 3 codes brighter than the curve. Several bodies share one published matrix (sensor siblings; fourteen groups of two to five bodies in the table, 37 of the 44 bodies), which is right where the sensor is the same and unverified where it is not; the A1 II and the A3000 are two of those by decision, not by publication.

## Illuminant estimate

Input: the 1/8-resolution preview of black-subtracted camera RGB **before** any white balance, with clipped pixels masked, plus metadata.

Output: `w_scene` (camera RGB of the light, green = 1); class probabilities over {daylight, shade/overcast, tungsten/halogen, fluorescent, LED, mixed}; a confidence value.

**Baseline (M1):**

1. Log-chroma histogram `u = ln(G/R)`, `v = ln(G/B)`, 64×64 bins, weighted by `√Y`, as in FFCC (Barron & Tsai 2017, Apache-2.0 reference code).
2. FFCC-style filter, trained per camera profile family, gives the chromaticity. Train on (a) synthetic scenes: random rawtoaces and CES reflectances under the reference lights, rendered through `S_P` with noise, and (b) Cube++ (CC BY 4.0) converted to each profile through its own camera matrices.
3. A small classifier (logistic regression or a 2-layer MLP) on histogram moments, the FFCC output, scene brightness `Bv = log2(N²/t) − log2(ISO/100)`, and the camera's as-shot white balance (tag 0x7313) predicts the class.
4. Prior: the camera's as-shot white balance, converted to a chromaticity, enters as a Gaussian prior on `(u, v)` with σ = 0.05. Sony's own auto white balance is good; we refine it.

Which estimator wins (FFCC, C5 or DMCC style) is decided in M1 by the gate (no test shoots in V1): median angular error ≤ 2° on held-out synthetic scenes and ≤ 3° on the Cube++ test split converted to each profile, reported (not gated) on NUS-8's Sony A57 subset (evaluation only), and the sensor-map gate still met with estimated lights.

**As built (M1-06).** `ym_color::illum` (`IlluminantModel`, `RawPreview`, `ShotInfo`, `IlluminantEstimate`) reads `data/models/illum/<profile-id>.json` (`IlluminantModel::load_for_profile(data_dir, profile_id)`); `training/illum/` is the training code and the numerical reference (the Rust agrees with it to 1e-9 on `crates/ym-color/tests/data/illum/`); `data/models/illum/MODEL_CARD.md` has every number below for all 11 profiles. One model per profile (not per family), each 13 k parameters.

- *Input contract.* The preview is **raw**: black-subtracted camera RGB at about 1/8 of the sensor resolution, white level 1.0 for every channel, **no white balance applied** (not the `g0`-balanced data of the chain), with a byte mask of the blocks that contain a clipped sample. For a stand-in body with a white scale (`docs/03`) the caller multiplies red and blue by it first, so the estimator reads the profile's raw scale it was trained on (the clip level of that preview is then the scale, not 1.0; the mask, not a level, decides what is clipped). The camera's channel balance is what makes the output usable: `w_scene` is in the **published raw scale** of the profile's curves (`fit.sony_curves_raw`, clipped at zero, not peak-normalised: the same scale as the profile `locus` after the C1 fix), and it is compared with the as-shot gains (tag 0x7313 as multipliers `[gR, gG, gB]`; `ShotInfo::as_shot_uv` takes `(ln gR/gG, ln gB/gG)`). The estimator, the locus and the as-shot gains all live in that scale; `chain.rs` is scale-free.
- *Histogram.* Two channels of 64 × 64 bins of 0.0625 in `(u, v)`, the window centred on the profile's light locus (1500 to 25000 K) so that the saturated surfaces of every light fit: the pixels (weight `sqrt(Y)`, `Y = 0.25 R + 0.5 G + 0.25 B`) and the 3 × 3 masked local absolute deviation (the edges, as in FFCC; weight `sqrt(Y)` of the edge triple). Bilinear splatting instead of FFCC's rounding; a pixel is counted when all channels are finite and above 1/1024 (edges: 1/4096), clipped blocks are masked. Previews are subsampled with the stride `isqrt(pixels / 16384)`, so a preview of fewer than 65 536 pixels is histogrammed whole and the 1080 × 720 preview of a 50 MP frame uses every 6th pixel in both directions (21 600 pixels).
- *Filter and Gaussian.* `Z = sum_c IFFT(FFT(X_c) FFT(F_c)) + B` (circular convolution, own radix-2 FFT), softmax, and the mean and covariance of the softmax map in log-chroma plus a learned variance floor. FFCC's toroidal (von Mises) mean was not needed: the window leaves a margin on every side and the bias suppresses the rest. Trained with the FFCC losses (softmax cross-entropy and Gaussian negative log-likelihood, here for both the histogram-only and the fused estimate, plus an L1-like error) and the FFCC regularisers (total variation and L2 on filter and bias).
- *As-shot prior.* A Gaussian with sigma 0.05 on `(u, v)` multiplied into the estimate (precision-weighted mean), not added to the logits: with a wrong preset white balance the prior is the same fixed Gaussian, there is no robust fallback. Without an as-shot value (or with unusable gains) the estimate is the histogram's alone.
- *Output.* `w_scene = [exp(-u), 1, exp(-v)]`; six class probabilities from a 25 → 24 → 6 `tanh` head on the histogram moments, the estimate, the as-shot value and `Bv` (`ShotInfo::bv`); a confidence that is a logistic regression on the same features and three more (Mahalanobis distance of the histogram estimate from the as-shot value, the log variances of the two Gaussians), fitted on validation scenes with held-out lights to be the probability of an error under 2 degrees. A preview without a usable pixel (everything clipped, dark or non-finite) returns the as-shot white, or the camera's D55 if there is none, with confidence 0 and the class frequencies (`fallback = true`). `IlluminantEstimate::scene_light(&locus)` is `SceneLight::from_estimate` (the six classes fold into the profile's four there).
- *Training data.* Synthetic only, all splits by light **and** by reflectance (details and licences in the model card): scenes of soft-edged colour cells with shading, texture, highlights, grey patches and mixed lighting, rendered through the profile's raw curves with Poisson-Gaussian noise and clipping; the rawtoaces 190 patches split 132 / 20 / 38 (train / validation / test) plus smooth random spectra and convex mixes; CIE D series, blackbody, FL1-FL12, FL3.1-FL3.15, LED-B1..V2 (CC BY-SA, HUMAN M1-H4 still open) and generated near-white LED and fluorescent spectra, with held-out temperature bands, held-out CIE lamps and disjoint seed streams; the nine gate lights are held out. **CES 99 is evaluation only**, deviating from the sentence in the Baseline list above that trains on it. The simulated as-shot white balance and the class and brightness priors are assumptions (no camera data in V1).

Results (`data/models/illum/MODEL_CARD.md` has all of them for all 11 profiles; angular error in degrees, median / p90 / worst):

- *Gate, held-out synthetic scenes* (3000 scenes per profile: held-out lights and held-out reflectance patches). Median with the as-shot prior 1.22 to 1.30 over the 11 profiles (all pass; the gate figure, because the estimator ships with the prior); histogram only 1.79 to 1.98 (all under 2, but see the review below: the histogram-only median sits within sampling noise of the 2-degree line for some bodies); on the 99 CES (evaluation only) 1.23 to 1.33 with the prior and 1.67 to 1.90 without. A7R IV: 1.23 / 4.93 / 22.1 with the prior, 1.93 / 6.53 / 42.9 histogram only.
- *Against simpler estimators* (A7R IV, same scenes): grey world 3.76 / 8.63 / 40.0, white patch 4.75 / 11.01 / 26.8, shades of grey 4.48 / 10.33 / 27.9, grey edge 4.29 / 9.67 / 27.3; the simulated as-shot white balance alone 1.54 / 6.46 / 26.0; grey world fused with the same as-shot prior 1.55 / 6.30 / 24.1. FFCC without the prior halves the error of every histogram baseline; with the prior it beats the as-shot value alone by 20 % in the median and 24 % at p90 (the as-shot error model is an assumption: no camera data in V1). Dropping the edge channel costs 0.14 degrees in the median and 0.4 at p90 (earlier recipe, same scenes); training on the 132 patches without perturbed and mixed reflectances gave 4 degrees on unseen patches instead of 2: a model memorises its patches, so the training mix is broader than the held-out one.
- *Classes* (A7R IV, with prior): accuracy 62.7 % over six classes, 72.4 % over the four profile classes (mixed excluded). Warm LED and tungsten, and LED and fluorescent, have the same chroma and are separated only by small distances from the locus and by `Bv`; the confusion matrix is in the model card. Confidence: AUC 0.749, Brier 0.174 against 0.215 for a constant.
- *Stand-in cost* (the A7R IV model on scenes rendered through the other ten bodies' curves): median 1.18 to 1.64 with the prior, 1.92 to 2.89 histogram only.
- *The sensor-map gate with estimated lights* (`training/illum/gate_estimated.py`, A7R IV, 200 scenes per gate light, the M1-05 tables): **not met**, and not meetable as worded. Estimated end to end every one of the nine lights is over (worst median 3.042, worst p95 19.827, against 0.5 and 1.2): the white-balance error of any estimate is a colour cast, about 1.2 to 1.9 dE00 per degree of median angular error, so 0.5 would need the white right to about 0.3 degrees. With the white known and only the estimator's classes, mired and CCT in play ("map only"), the median changes by -0.02 to +0.15 dE00 (worst median 0.740, LED-V2, the accepted M1-05 failure) and the p95 rises by 0.19 to 0.69, which puts 9 of the nine lights over the gate (LED-V2 by median as before, the others by the p95 limit of 1.2, which the known-light fit met with margins of 0.03 to 0.61). Reported, not loosened. Proposal for Mykyta (decision pending): keep the M1-05 gate as the sensor-map gate (known light), gate the estimator by the angular error alone, and state the estimated-light check as the map-only increase over the known-light numbers (for example at most +0.2 dE00 in the median and +0.7 in the p95), because the white-balance cast is the estimator's error and not the map's.
- *Cube++ (gate <= 3 degrees) and NUS-8 Sony (report only): not run.* `zenodo.org` and the NUS-8 host are unreachable from the build environment. `tools/fetch/cubepp.sh` (SHA-256 pins empty until someone runs `--accept-new` with access) and `training/illum/eval_cubepp.py` (conversion to each profile through the source body's colour matrix and a least-squares XYZ to camera 3 x 3, tested on a mock layout only) are ready; the layout assumptions are unverified.
- *Real photographs.* `training/illum/smoke_real.py` runs the models on the nine ARW files in `testdata/real/files` (unrecorded provenance, no ground truth): the histogram-only estimate lies within 0.4 to 6.0 (median 3.0; grey world 0.2 to 9.4, median 4.0) degrees of the camera's own white balance. A gross-failure check, not an accuracy number.
- *Speed.* One estimate of the 1080 x 720 preview of a 50 MP frame (21 600 pixels histogrammed, stride 6): 3.6 ms on the shared 4-core build machine (load average 3 to 10), of which the histograms take 3.0 ms; the FFTs, the fit and the head take under 1 ms (`cargo test --release -p ym-color --test illum -- --ignored --nocapture timing`).
- *Decision for `docs/16`* ("Illuminant estimator: FFCC, C5 or DMCC style"): **FFCC**. It wins every held-out comparison above against the grey-world family and against the as-shot value alone, passes the synthetic gate on all profiles, and costs 13 k parameters and about 4 ms per photo. C5 and DMCC need a multi-camera real dataset that V1 cannot get; neither was built.

**Review of M1-06 (independent, same day).** What was checked, what was fixed, what is left open.

- *Reference and port.* A numpy implementation written from this section alone (not from `training/illum/`) agrees with the reference `training/illum/model.py` to 1.6e-13 on all 11 shipped models (histograms, filter, both Gaussians, class head, confidence); the Rust estimator agrees with the reference to 2.8e-13 on all 11 (`every_shipped_model_matches_the_python_reference`; the first version compared the A7R IV model only). Regenerating the vectors gives byte-identical files.
- *Gate figures on fresh scenes.* Re-drawn test sets (other dataset seeds, same held-out lights and patches, 3000 scenes): with the as-shot prior 1.23 to 1.29 on all 11 bodies (the gate figure; it rests on the assumed as-shot error model), histogram only 1.72 to 1.98 on ten bodies and **1.98 and 2.08 on the A7R II**, and 2.18 on the A7R IV's validation scenes (other held-out lights). The histogram-only "all pass" above is therefore within sampling noise (about 0.03 degrees for the median of 3000 scenes) of the 2-degree line for the bodies at the top of the range; only the with-prior figure is a comfortable pass.
- *Independent scenes.* The 37 chart scenes of `training/synth` (another generator: ColorChecker-style chart of the 190 patches, mosaics through the same curves, ISO 100 to 12800, all four CFA phases, 12 and 14 bit; previews binned 8 x 8 from the mosaic like the Rust preview) read 0.22 degrees median histogram only (grey world 1.64, the camera's as-shot white 0.67), mixed lighting 3.5. That confirms the preview contract (black level, CFA, raw scale) end to end. The classes there: daylight 21 of 21 and tungsten 6 of 7 right; the fluorescent scene and all 7 LED scenes were not recognised (called daylight or mixed), as the low LED and fluorescent recall above says.
- *Real files with real `Bv`.* `smoke_real.py` now passes `Bv` from the EXIF. Four of the nine files read 14.3 to 14.6, outside the synthetic range (-2 to 13, daylight mean 9.3): the brightness prior of the scenes is about five stops low for sunlit scenes, because `Bv` here is EV at ISO 100 (sunny 16 is 15). On those files the head extrapolates the right way (daylight 0.89 to 0.98 with the true `Bv`, 0.52 to 0.81 without it), so nothing is wrong, but the prior should be redrawn at the next retraining.
- *A wrong preset white balance.* With the specified single Gaussian (sigma 0.05) the estimate follows a preset that has nothing to do with the light: on the A7R IV's test scenes with such a preset (11 %, assumed) the median error is 5.9 degrees with the prior and 1.9 without it, p90 15.5 against 5.9. `training/illum/robust_prior_study.py` applies a two-component prior to the shipped filters without retraining (`(1 - eps) N(sigma 0.05) + eps N(sigma_b)`, `eps` and `sigma_b` picked on the validation scenes: 0.1 and 0.2): A7R IV median 1.23 to 1.21, p90 4.93 to 4.16, p95 8.45 to 6.33, preset scenes 5.9 to 3.1, good automatic white balance 0.85 to 0.87, worst case 22 to 33 (the histogram's own outliers are no longer capped by the prior); the A7 III model gives the same picture (p90 5.03 to 4.24, p95 8.54 to 6.23). This keeps the specified Gaussian as the main component and changes only its tails, but it alters the shipped fusion (and the inputs of the class and confidence heads, trained on the single Gaussian), so it was **not** applied: a decision for Mykyta and the orchestrator, then a retrain of the heads and a new report.
- *The proposed estimated-light thresholds* (at most +0.2 dE00 in the median and +0.7 in the p95 over the known-light numbers) sit just above the worst values measured (+0.153 and +0.693). They describe this model; they are not an independent criterion. The sensor-map gate "with estimated lights" was re-run (40 scenes per light): the same picture (end to end worst median 2.9, worst p95 17.0, all nine lights over; map only worst median 0.73, p95 1.68).
- *Hardening, all with tests (`tests/illum_robust.rs`).* `ShotInfo::bv` returns `None` for settings whose value overflows (was infinite); `estimate_from_histograms` checks the shape of the histograms it is given and returns `IllumError::InvalidHistograms` (was a slice panic) and ignores a non-finite as-shot value or `Bv`; `histogram::compute` refuses a specification with fewer than two bins (was an underflow). Hostile previews (NaN, infinities, negative and enormous values, 0 x 0 to 300 x 200 pixels) with absurd gains and exposure settings give finite, normalised output.
- *Not changed.* The model file's SHA-256 covers the tensors only (the scalars `pad_variance`, `prior_sigma`, `temperature`, the window and `default_uv` are not covered); as-shot gains whose log-chroma is far outside the histogram window are still used, with a low confidence; the `scenes.py` docstring says the simulated as-shot error has a median of about 2 degrees where the measured value is 1.5 (editing it would change the training-source hash stamped in the models).
