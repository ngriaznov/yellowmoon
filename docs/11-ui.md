# 11 · User interface

Reference: `design/mockups/` (open `index.html`; the pages run offline), `design/screenshots/` (every state at 2880×1800), `design/tokens.css` / `tokens.json`. The mockups are the source of truth for layout, copy and states. This spec covers behaviour, data wiring and anything the mockups don't show.

Style: "bold grid, white". Figtree throughout. 3 px black rules divide the window into cells. Each tool tab has a flat colour that fills its tab, its title block, its slider fills and any changed value box. Controls are square and boxed (2 px borders). The photo fills its cell edge to edge. Yellow (#FFC20E) is the brand colour: the moon mark, the start screen, the Look tab, progress fills.

## Window

- Tauri window, `titleBarStyle: Overlay`, hidden title. The traffic lights sit over the folder cell; keep 84 px of left padding there.
- Minimum size 1180 × 760. Default 1440 × 900.
- Light appearance only in V1 (the dark variant in `research` is not shipped).

### Component library notes (M3-01)

The components live in `src/components/` and are exported from `src/components/index.ts`. `components.html` (run `npm run dev`, open `/components.html`) shows every component in every state; `/components.html?replica=photos&tab=light` (also `start`, `export`, `wizard`) rebuilds a mockup screen from them, and `e2e/components.spec.ts` compares each with the mockup pixel by pixel. Decisions taken where the mockups and the table above differ or are silent:

- **Tab bar:** the separators are 3 px, as in `photos.html` (the table said 2 px).
- **Wheel:** 92 px across including the 2 px border, 88 px inside it (the table's 88). The puck travels inside the rim, so a point of length 1 sits 7 px in.
- **AUTO in a card header** is a 26 px toggle button (`AutoToggle`: ink while automatic, pressing it restores Auto); the AUTO and EDITED tags on the Automatic rows are the 22 px `Tag`.
- **Tags** the mockups do not draw: ON takes the tab colour, REDUCED the peach error colour, `done` is ink like READY, `active` (a running file's "45%") is yellow like DEVELOPING. A `sm` size (14 px) exists for the CAN'T OPEN tag on a 60 × 40 thumbnail.
- **Slider patches:** `onChange(value, final)`. While the thumb is dragged it fires at most once per animation frame with `final = false`, then once with `final = true` on release; keys, typed values, Reset and double click fire once with `final = true`. The same contract holds for `Wheel` and `CurvePlot`. A control keeps showing its own value until the controlled value catches up (or one second passes), so a slow reply never makes the thumb jump back.
- **Reset** on an automatic value (Exposure, Kelvin, Tint, Sharpen, Noise reduction) must go back to Auto, not to the number Auto resolves to: pass `onReset`.
- **Wheel keys:** arrows nudge the puck (Shift ×10), Home, Delete or Backspace centre it; exposed as a slider whose value is the strength, with the strength and hue in `aria-valuetext`.
- **Curve:** a press adds a point on the curve at that x, a drag moves it, dragging an inner point more than 14 px off the plot deletes it. The two end points move up and down only and cannot be deleted. They are drawn only while the plot is hovered, focused or the point is selected, so a resting plot looks like the mockup. Keys: Tab through the points, arrows move one code value (Shift ×10), Delete removes, Return on the plot adds a point in the widest gap. Input and Output show the dragged point, else the position under the pointer, else the selected point, else the middle.
- **Focus:** every interactive element gets the global 3 px ring with a 2 px offset, including tabs and segments (the focused cell is lifted so its neighbours do not paint over the ring). The slider draws its own ring because its native input is transparent.
- **Photo cell:** `PhotoCell` carries `data-viewport` and reports `{ x, y, width, height, scale }` through `onRect` on mount, on ResizeObserver callbacks and on window resize. With `native` it draws no `<img>` and is transparent (a native layer draws behind it); with a `frame` (the fallback viewport's picture of the whole cell) it draws that picture at its own size, one picture pixel to one device pixel, on paper; otherwise the photo is an `<img>` letterboxed on paper. The Photos screen chooses from `viewport_info` (see "Wiring to the shell" below); the component's own default for `native` is `isTauri()`.
- **Base line height** is `normal`, as in the mockups (the skeleton's 1.4 made every row a few pixels taller).
- **Added beyond the table** because the mockups use them everywhere: `Button`, `LinkButton`, `KeyHint`, `ProgressBar`, `TitleBlock`, `Field`, `Rows`, `InfoRow`, `AutoRow`, `SwitchRow`, `SearchField`, `Histogram`, `DevelopList`, `WheelGroup`, and the hooks `useTabShortcuts` (⌘1–⌘6), `useWindowDrop` (whole-window drops, with Tauri's real paths inside the app), `useFrameEmitter` and `usePointerDrag`.

### Screen notes (M3-05 to M3-08)

Start, Photos, the six tabs, Crop and Pick white are built in `src/screens/`, on a store (`src/state/store.ts`) that mirrors the core and is the only code that calls `Api`. Decisions taken where this spec or the mockups were silent:

- **Store.** Plain TypeScript with `subscribe`, tested without React; `context.tsx` provides it. Events (`photo_progress`, `thumbnail_ready`, `render_stats`) are applied in batches of about two frames, so 500 photos developing do not draw 2000 times. A status event that arrives before the session snapshot (the core emits while `open_paths` is still answering) is kept and applied when the session arrives.
- **Patches.** `store.update(patch, final)` sends one patch at a time per photo. While one is in flight, later drag patches fold into one waiting patch, so a slow core is never flooded and the last value always arrives. Fields that need no resolving (look, contrast, light preset, wheels, curve, switches, crop, …) show at once; Auto fields wait for the core's reply. A failed patch shows the error and asks the core for the settings again.
- **Auto semantics.** A value equal to what Automatic resolves to *is* Automatic: typing +0.30 into Exposure, or dropping the slider on its detent, sends `{ exposure: { kind: "auto" } }` (the same for Kelvin/Tint together, Sharpening and Noise reduction). Reset on a row of an Auto field sets only that value (and collapses to Auto when it matches); the card's Reset and the AUTO button send Auto. The AUTO button of the Exposure card says whether *exposure* is automatic, not Contrast or Brightness. White balance counts as automatic only when `white_balance` is Auto, `light_source` is Auto and no white was picked.
- **Output sharpening (the Output row of the Sharpening card; owner's decision of 2026-10-13, not in the mockup).** `design/mockups/photos-detail.html` has two rows in the Sharpening card; the third, **Output**, is added by that decision (`docs/16`) and the mockups are left as they were. The row is the standard slider: 0 to 200 %, step 5, the detent and Reset at **100 %**, the value shown as `100%` (`formats.percent`), no unit word, no AUTO tag. It is a plain number: moving it sends `{ output_sharpening: n }`, its own Reset and a double click send `{ output_sharpening: 100 }`, not Auto (`DevelopSettings.output_sharpening`, `docs/01`). Amount and Radius above it are the capture sharpening and stay exactly as they were (Auto, Richardson–Lucy). The card's Reset puts the whole card back: `{ sharpen: Auto, output_sharpening: 100 }` (like the Colour balance card, which resets its wheels and Saturation together). The viewport, the filmstrip thumbnails and the Look tiles show the sharpened picture as the slider moves, and the exports are made with it; the Before view, the histogram and the pixel readout do not (`docs/01`). Undo and redo take it like any field (one step per drag). There is nothing on the Export screen and no switch: 0 is off. The e2e screenshot of the Detail tab (`photos-detail`) therefore differs from the mockup's by the extra row; its budget in `e2e/helpers/compare.ts` is 2 % (measured 1.06 %). "Apply to" copies the look and its intensity only (`docs/01`), so the amount stays with the photo unless Copy settings and Paste move it (below: they take every setting but the crop, the orientation and the Pick white point, the output sharpening included; until the owner's request of 2026-10-16 the app had no copy-and-paste of other settings).
- **White lift (the Light tab's White card and the Automatic card's White row; owner's decision of 2026-10-14, not in the mockup, `docs/02` C12 step 1b, `docs/16`).** The lift is an automatic setting: a per-photo scene-linear gain on the tones above +1 stop over middle grey, sized from the photo's own highlights when it is opened, that gives a high-key photo a real white (0 for a low-key one). **Automatic card:** a row **White** between Exposure and White balance, value `+0.77 EV` (the lift in effect, `values.white_ev`, `formats.ev` and " EV") or `None` when it is 0, the AUTO tag while the offset is 0 and EDITED otherwise, the arrow opening Light (accessible name `White +0.77 EV, Auto. Open Light`). **Light tab:** a second card, **White**, between Exposure and High dynamic range, with the AUTO button (accessible name "Auto white": ink while `white_offset_ev` is 0, pressing it sends `{ white_offset_ev: 0 }`), the card's Reset (the same patch) and one slider, **Offset**: −3 to +3 stops in steps of 0.05, the detent and Reset at 0 (the automatic amount), shown as signed stops with `formats.ev` and no unit word (`0.00`, `+0.30`, `−0.50`). It is a plain number, not Auto: moving it sends `{ white_offset_ev: n }` and shows at once (the Automatic card's row follows with the core's reply: `values.white_ev` is the automatic amount plus the offset, never below 0, so an offset of minus the automatic amount, or lower, reads `None` and gives the render of no lift). The row is called Offset because the Light tab already has a **White** slider in High dynamic range (the C9 control, −100 to 100); the two are different settings and the card is named White after the Automatic card's row, as the owner called it. Re-run on the Automatic card puts the offset back to 0 with exposure, white balance and noise. Undo and redo take it like any field (one step per drag). The lift acts only with the built-in ACES 2 display rendering; with an imported ARRI display LUT or a look with its own display rendering the slider still moves but nothing changes in the picture (ARRI's highlights). Tests: `src/screens/WhiteCard.test.tsx` (the card, the row, the AUTO semantics, Re-run, undo), `src/repo.node.test.ts` (the Light blurb), `e2e/` screenshots (the Light and Look tabs differ from the mockup by the new card and row; their budgets are in `e2e/helpers/compare.ts`).
- **Tone card (the Look tab's third card; owner's decision of 2026-10-13, not in the mockup, `docs/16`).** `design/mockups/photos-look.html` has two cards on the Look tab; the third, **Tone**, sits directly under the Look card and has three rows in this order: **Temperature**, **Contrast**, **Saturation**. They are the *same settings* as Colour › White balance › Kelvin, Light › Exposure › Contrast and Colour › Colour balance › Saturation (`white_balance`, `contrast`, `saturation`; no new `DevelopSettings` field). Both copies are built from the same code (`src/screens/tools/controls.tsx`: `KelvinSlider`, `ContrastSlider`, `SaturationSlider`), read the resolved value and send the same patch through `store.update`, so moving one moves the other, and undo, redo and Reset take them like any field (one undo step per drag). Contrast and Saturation: −100…100, step 1, default and Reset 0, read as `formats.signed`. **Temperature is the Kelvin control, unchanged:** 2000–11000 K in steps of 50, the detent and the box showing the photo's Auto Kelvin (`5450 K`), the row's own Reset sends the Auto Kelvin with the current tint and the light preset and picked white cleared (that is Auto while the tint is Auto), dropping on the Auto value sends `white_balance: auto`, and moving it on an Auto white balance makes it Manual at that Kelvin with the Auto tint, as a patch with only `kelvin` does. **Tint stays on the Colour tab only**, and nothing is removed from Light or Colour. The card header has the AUTO button and, after a Pick white, the EDITED tag, exactly as the White balance card (`whiteBalanceState`: automatic only when `white_balance` is Auto, `light_source` is Auto and no white was picked); as on the Exposure card, the button speaks for the temperature only (accessible name "Auto temperature"), not for Contrast or Saturation. The card's Reset sends `{ white_balance: auto, light_source: auto, white_pick: null, contrast: 0, saturation: 0 }` (the tint goes with the white balance, as with the White balance card's Reset). The labels differ between the tabs (Temperature here, Kelvin on Colour) because the person looking at the Look tab has not met the word Kelvin; the value box reads `5450 K` on both. Saturation is subtractive (`docs/02` C9): more makes colours denser and darker, less makes them paler. Tests: `src/screens/ToneCard.test.tsx` (sync both ways, undo and redo, Auto semantics, Reset) and `e2e/tone.spec.ts`. None of the mockup's screenshots shows the card: in every Look state it lies below the visible part of the panel (even with the search `film` leaving two tiles), so the three Look comparisons are unchanged (0.15 %, 0.24 % and 0.39 %) and need no budget.
- **Light presets.** `light_source` is sent as it is; while White balance is Auto the core resolves a kelvin for the preset (the mock: Day 5500, Shade 7500, Tung. 3200, LED 4800, Fluor. 4100) and the Kelvin box shows it as a change.
- **Undo and redo** are per photo, in memory, 100 steps. An entry holds only the fields one change touched (before and after, as two patches), so changes made by "Apply to" on other photos never get in the way. A whole drag, or a whole crop session, is one step. ⌘Z waits for patches in flight. "Re-run" is a step. A paste is one step in the history of each photo it changed (the core says which fields changed, `paste_settings`), so ⌘Z on a photo takes that photo's paste back and no other.
- **Look tab sections (owner's decision of 2026-10-16, not in the mockup, `docs/08` §Look model).** The owner wrote: "We somehow need to resolve the fact that there could be LUTs and ALF in the looks, maybe via UI to display section. Also make sure that second import does not duplicate looks." (The second sentence is `docs/08` §One look, one entry.) `design/mockups/photos.html` has one group for everything imported, **ARRI looks · imported**. With ARRI's five Look Files downloads and the person's own files the list can hold about 600 tiles, and the same title ("Film") in several libraries with no way to tell them apart. ### Shell notes (M3-02, M3-03, M3-04, M3-13)

The Rust side of the interface is `src-tauri` (package `yellowmoon-app`). It is thin: `src/api.rs` has one method per command and no Tauri types, `src/commands.rs` wraps each in a `#[tauri::command]` that runs it on a blocking thread, and everything that crosses the bridge is a type of `src/wire.rs`.

**IPC (M3-02).**
- *Typed bridge.* `specta` + `tauri-specta` generate `src/api/bindings.ts` from the commands and events. `wire.rs` mirrors the core's serde types (the core's types do not derive `specta::Type`) and converts through serde (`wire::convert`); `core_types_convert_without_loss` checks that nothing is lost on the way. The drift check is `cargo test -p yellowmoon-app --bin yellowmoon-app bindings`: it regenerates the file in memory and fails when the committed one differs; `YM_UPDATE_BINDINGS=1` on the same command rewrites the file. Two more tests tie the bridge to the frontend: `field_names_match_the_typescript_contract` and `variants_match_the_typescript_contract` compare every interface and every tagged union of `src/api/types.ts` with the generated types (so `types.ts` stays the hand-written contract, with `export interface` blocks). The TypeScript side is checked by the compiler: `tauriApi` calls the generated `commands` of `src/api/bindings.ts` instead of `invoke("…")`, and `src/api/contract.ts` makes `tsc -b` fail when a payload of `types.ts` and the generated one disagree in the direction it flows, when an event of `ApiEvents` is not a generated event (or the other way round), or when an `Api` method and its command differ in arguments or answer. `every_command_and_event_of_the_frontend_is_in_the_bindings` counted the `invoke("…")` calls of `src/api.ts`; there are none now (it fails with "found 0 commands"), so the test has to shrink to its event half, `every_event_of_the_frontend_is_in_the_bindings`: the commands are `tsc`'s job, and `src/api.test.ts` compares the wire names and argument keys of every method with `bindings.ts`.
- *Errors* are `AppError { scope, message }` (`ErrorScope` of `types.ts`), thrown by the generated functions (`ErrorHandlingMode::Throw`), so a rejected `invoke` is what `isAppError` expects.
- *Differences from `types.ts`*, for whoever wires `api.ts` to the bindings: `SettingsPatch` is the core's patch, a little more generous than `Partial<DevelopSettings>` (nested `decode`, `rolloff`, `color_balance` and `curve` objects and a manual `white_balance`, `sharpen` or `noise_reduction` may leave parts out; `crop: null` and `white_pick: null` clear); `AutoOr<M>` is one enum per setting (`ExposureSetting`, …) with the same JSON; numbers are `number` (the Rust `Num` newtype, because specta would write `number | null` for an `f64`); unit commands return `null`; `MatchKind` has no `forced` variant (only the CLI's `--profile` makes one).
- *Additions* (not in `docs/01`'s original table, not in `types.ts`'s first version; `docs/01` lists them now): commands `viewport_info()` (`native` or `fallback`), `export_busy()`, `restart_app()` and `thumbnails()`; events `export_busy { busy }`, `settings_changed { photo_id }` (sent after a `viewport_input` Pick white click set the photo's `white_pick`; ask `get_settings` again) and `viewport_frame { seq, width, height, sharp, url }` (fallback viewport only; an empty `url` with a size of 0 × 0 means "no picture": remove the image).
- *Events.* `photo_progress`, `thumbnail_ready` (`{ id, url }`: the address of a PNG of at most 240 px that the shell serves on the `ym-frame` scheme, `docs/01` IPC), `render_stats` (after every viewport frame, with the frame's `zoom_percent` and the Fit zoom `fit_percent`), `export_progress`, `looks_changed`, `looks_import_progress` (the copy stage only), `download_found`, `menu_action`, `error` and `update_state` are registered. The shell sends `update_state` never: the updater runs in the webview (`updater.ts` with `tauri-plugin-updater`; `docs/12`), and `capabilities/default.json` allows `updater:default` only. "Update ready" waits for the export queue: the webview knows the run it started, and `export_busy` (command and event) says whether a queue is busy, also after a reload. The restart itself is the app's own command, `restart_app`, not the process plugin's `relaunch` (its permission is not granted and the plugin is not loaded): Tauri's restart cannot be vetoed by the exit handler (`ExitRequestApi::prevent_exit` is ignored for it, so "An export is still running…" would never be asked and the exit would cancel the export and delete its file), so the shell refuses it where it starts, while an export is queued or running (scope `export`, "An export is still running. Restart after it finishes."; the update stays ready and the cell enables when `export_busy` says the queue is idle), and once a restart has begun `export_start` is refused. Tests: `AppApi::begin_restart` against a real export in `src-tauri/src/api/tests.rs`, the updater's reaction in `src/updater.test.ts`.

**Session (M3-03).** `open_paths` takes the dropped or chosen paths (a folder is read one level deep; non-ARW files are ignored; "No ARW files in what you dropped." is an `open` error when nothing is an ARW file). `open_dialog` and `choose_folder` / `choose_look_files` use the system dialogs from Rust (`tauri-plugin-dialog`), starting in the folder remembered in the preferences; the webview does not use the dialog plugin, so `dialog:default` is not in the capabilities. The window accepts drops of files and folders (`dragDropEnabled`; the webview reads the real paths from `onDragDropEvent`). Closing the session (⌘W; the webview asks first when an export runs) stops development and renders but not exports. Quitting with an export running asks "An export is still running…" (Stop the export and quit / Keep exporting), then cancels the queue and deletes the partial file; the close button of the window asks the same question before the window goes (answering "Keep exporting" after the window was gone would leave an app with no window to show the export in). `export_start` does not wait for the session to finish developing and is not refused for photos outside the job: a burst's shared exposure and the pooled noise model depend on other photos, so the core queues the job and each photo's turn waits until the photos *it* depends on (its burst, its noise pool) have their estimates, then reads them (`docs/01` Session, "App/CLI parity for early exports"); `ym render`, which waits for the whole session, and the app write the same bytes, and neither thumbnails, prefetching nor viewport work are waited for. Only photos of the job's scope that have no estimates at all yet are refused: "One photo is still being developed. Wait until it is ready, then export again." / "Some photos are still being developed. Wait until they are ready, then export again." A thumbnail is made once per photo when it is developed; applying a look, changing the Intensity or the crop or the quarter turn of a photo makes a new one (collected for 300 ms, rendered behind the viewport).

**Viewport (M0-06, M3-04).** The webview reports the photo cell with `viewport_set_rect` (CSS pixels of the window; also on resize), the pointer with `viewport_input`, `viewport_set_mode`, `set_before` and `sample_pixel`. The shell keeps the core's `ViewportState` for the current photo and asks the core for a frame (RGBA8, Display P3, the cell's size in device pixels, letterbox in paper) whenever the state, the photo or its settings change. A newer request does not cancel the frame being drawn: that frame finishes and is shown, and the next round starts at once from the newest state (only the pass that makes sharp tiles gives way to a request, and a request that makes the frame wrong, another photo or another cell size, stops the frame too; `docs/01` §Native viewport). When the zoom needs full-resolution tiles that are not ready, a coarse frame goes out at once, the tiles are made at tile priority, and the sharp frame follows (`viewport_frame.sharp`). A new photo goes back to Fit and Before off; a zoom, pan or Before that was still waiting for the photo it was meant for is dropped, the cell's rectangle is kept. Nothing is drawn before the webview's first `viewport_set_rect` (a cell with an area: the controller's initial 1 × 1 cell is not one). A photo that is still developing is drawn as soon as it is ready; one that failed to develop, or is gone, takes the picture away (`viewport_frame` with an empty `url` on the fallback, the hidden layer on the native viewport) instead of leaving the previous photo in the cell. `viewport_set_rect` is a synchronous command (the main thread takes the webview's messages in order; every `async` command runs on a worker thread of its own, and two rectangles of a window being resized that overtook each other would leave the photo at the wrong size). Pick white: a `viewport_input` of kind `pick_white` converts the click through the straightening, the turn and the lens maps to the `white_pick` space (`Renderer::pick_point_at`), sets it with `update_settings` and sends `settings_changed`; a click on the paper does nothing. In the app the click must go to the shell this way and not be converted in the webview: only the core knows the lens crop, the straighten angle and the quarter turn that lie between a point of the cell and the `white_pick` space (the browser mock has no such thing and takes the point of the shown picture). `sample_pixel` fails with a `viewport` error on the paper. `histogram` runs as a thumbnail-priority job, behind the viewport frames it is asked for after.
- *Native (macOS only, `src/native.rs`).* A plain `NSView` is added behind every sibling in the window's content view (below the webview); wgpu makes the `CAMetalLayer` for it and draws each frame as one full-screen triangle sampling the frame texture. The surface is `Bgra8Unorm` with `SurfaceColorSpace::DisplayP3` (wgpu 30 sets the layer's colour space, macOS converts for the display); without that colour space the sink refuses to start. The view follows `viewport_set_rect` (flipped from AppKit's bottom-left origin). It starts hidden, the first frame drawn shows it, and taking the picture away (no photo, a photo that failed) hides it again, so a cell reported while there is no picture does not bring a stale one back. A surface that has no texture to give yet is asked again a few times (a frame is not asked for twice) before the frame is given up on with an error. Needs `transparent: true` and `macOSPrivateApi` (both set in `tauri.conf.json`), the photo cell transparent (`PhotoCell` with `native`) and nothing under it painting either: `PhotoView` sets `data-native-viewport` on the root element (not `data-viewport`, which marks the cell itself) while it shows, which makes the root, body, `#root` and the Photos screen transparent (`screens.css`), and the sink makes the window itself opaque paper (`PAPER_SRGB`, equal to `--paper`; `src/styles/native-viewport.node.test.ts` checks both). It cannot run on Linux; it is type-checked with `cargo check --target aarch64-apple-darwin -p yellowmoon-app`.
- *Fallback (everywhere, `src/viewport.rs`).* Each frame becomes an RGB PNG with the Display P3 ICC profile, kept (the last three) in a `FrameStore` and served at `ym-frame://localhost/<launch>/frame-<seq>.png` (`http://ym-frame.localhost/…` on Windows; `<launch>` is the app's start time in hex milliseconds and a count, `docs/01` IPC); the `viewport_frame` event says when a new one is there and where. The webview shows it as an `<img>` over the cell (CSP `img-src` allows the scheme). It is what Linux development builds and the tests use, and the M0-06 fallback candidate if the Metal layer fails the checklist. ### Wiring to the shell (M3-02, M3-03, M3-04, frontend side)

How the screens use what the shell offers (the shell's side is "Shell notes" above). Decisions where the specs were silent:

- **Commands and types.** `tauriApi` (`src/api.ts`) calls the generated `commands`; a unit command resolves with nothing. `types.ts` stays the contract the screens use and `contract.ts` compares it with the generated file (a type-level check, no run-time code). The CLI is `ym`: the command line preview, the Preferences hint, the mock and every test say `ym render …`. The dev page `components.html` still reproduces the mockup's `yellowmoon render …` text on purpose.
- **Viewport backend.** The store asks `viewport_info()` when it connects and keeps `viewportBackend`: `native`, `fallback`, or `null` (the API has no viewport: the browser mock). The Photos screen draws accordingly: `native` leaves the photo cell transparent and draws nothing in it; `fallback` shows the latest `viewport_frame` (an `<img>` of `ym-frame://…` the size of the cell in device pixels, drawn at that size from the cell's corner, on a paper cell) and takes it away on an empty `url` or when the photo is not ready (the "Still developing." and "This file can't be opened." notes cover the cell); `null` draws the mock's picture. A frame smaller than 16 px a side is no picture: the shell draws a 1 × 1 frame for a cell the webview has not yet placed. An older frame never replaces a newer one, and never brings back a picture that was taken away: the shell numbers a frame before it encodes it and sends the news that the picture is gone from another thread, so a frame can arrive after the clear that was numbered later (the store keeps the newest number heard, clears included). The cell reports its rectangle on mount, on resize and on layout change (`viewport_set_rect`, CSS pixels; `PhotoCell`, ResizeObserver) in every mode, and when the display scale changes (the window dragged to a display of another scale: the cell keeps its size in CSS pixels, not every web view sends `resize` for it, so `PhotoCell` also listens to the media query for the current scale).
- **Input.** Double click is `viewport_input toggle_zoom`, ⌘ or Ctrl and the wheel is `zoom` about the pointer, the wheel and a drag pan once zoomed, ⌥ over the cell reads `sample_pixel` in CSS pixels of the cell (on the paper there is nothing to read and the readout goes), and Pick white is above. The store mirrors the zoom the core is asked for: a double click flips Fit and 100 %, a wheel zoom multiplies the mirror by the same factor at once (from the Fit zoom; capped at 800 %; at or below Fit it is Fit). The header's percentage and the drag to pan follow the mirror; a menu choice (50 %, 100 %, 200 %) sends exact values. The **Fit zoom** is the core's: `render_stats.fit_percent` (and `zoom_percent`) come from the same `ViewportState` the frame was drawn with, so they count the lens crop, the straighten angle, the crop and the quarter turn (`fitZoomOf`). The screen's own figure (`fitZoomPercent`: the cell's device pixels over the final picture's, from the photo's size and its settings) is used only until a frame has reported, and by the mock, which sends `null`; the store drops the zoom figures of the last frame when another photo opens, since the new photo may have another Fit zoom. A new photo goes to Fit with Before off in the mirror, as in the core. How the wheel, the pinch and a drag are collected and sent is in *Photos input and desktop feel* below; since M3-18 the mirror moves once per frame, when a zoom is closed, and not once per wheel event.
- **A fixed zoom at or below the Fit zoom is Fit.** The core draws Fit for it (`ViewportState::zoom` clamps to the Fit zoom, `is_fit` compares with the Fit zoom to 0.01 %), and the screen says the same: on a big display Fit is 62 % for a 24 MP photo, so the menu's "50 %" is Fit, the header reads "Fit 62%", the picture is letterboxed, a drag does not pan, a click on the paper is ignored by Pick white, and ⌘+ goes from Fit straight to 100 % (`showsWhole`, `zoomStep(mode, delta, fit)`: steps at or below the Fit zoom are skipped, so a key press always does something; Z and a double click give Fit again where 100 % is no more than the Fit zoom). ⌘+ and ⌘− step from where the photo is, not from the start of the list: a wheel zoom leaves the zoom anywhere (137 %), and Zoom In then goes to 200 % and Zoom Out to 100 %. The Fit zoom used for these decisions is not rounded (`fitZoomExact`); the header rounds it for display.
- **The pixel readout** asks the core for one reading at a time and, when the last one comes back, for the place the pointer is at then (a reading takes the core a moment, and the last place must not be lost); a reading that comes back after ⌥ was released is not shown.
- **Events.** `thumbnail_ready` fills the filmstrip, `photo_progress` the Start list and the filmstrip's states, `render_stats` the header, `export_progress` the Export panel (the sequence of docs/01 is tested), `settings_changed` makes the store read a photo's settings again (it skips a photo it has not asked about, and the one whose Pick white it is waiting for), `looks_changed` reloads looks, display LUTs and preferences. The Look tab's tiles ask `look_thumbnail` while they are in view (*Look tiles* below). After a reload of the webview the core does not announce the thumbnails again, so the store asks `thumbnails()` once it has the session back and gets the address of every picture the shell holds.
- **Updates and exports.** The update cell is disabled while the webview's own run is going or the core says an export is busy (`export_busy`, the event, and the command once at connect and again at the click: "Update ready" asks the core at the click and does not restart if an export has begun unheard; the restart itself is the shell's `restart_app` command, which asks again and refuses while an export is queued or running, because a restart Tauri makes cannot be vetoed by the exit handler. The webview takes that refusal (an `AppError` of scope `export`) as "not now": the update stays ready and the cell enables when the export is done).
- **Window.** The header (and the wizard's) has `data-tauri-drag-region`; the folder cell has `deep`, so its text drags too, and buttons never do.
- **About** adds the Independent JPEG Group's sentence to the Adobe notice and the trademark line.
- **Checking it for real.** Playwright drives the mock. `npm run e2e:shell` (`e2e/real/shell-smoke.mjs`; Linux, Xvfb, a built `dist/` and `target/debug/yellowmoon-app`) runs the built frontend inside the real shell: the debug app loads `devUrl`, the script serves `dist/` there with a driver added to `index.html`, drops a folder of ARW files on the window as Tauri's own drag-and-drop event, and checks the Start list, the frames on the `ym-frame` scheme, the thumbnails, a double click, ⌥, a settings change, Pick white, an export to a temporary folder with `export_busy`, a file that is not a raw file, and closing the session. The ARW files are read in place and nothing is written next to them. 35 checks on the nine real files of `testdata/real` on 2026-10-12; the same on the 48 synthetic files. Review of 2026-10-13 added the geometry checks, which need a point off the middle of the photo (the middle of the cell is the middle of the photo whatever is wrong): Pick white lands where the click was on a letterboxed photo, on a photo turned 90°, on a cropped one and on one turned and cropped (the pick is compared with the point worked out independently, within 0.01), a ⌘ wheel zoom keeps the pixel under the pointer, and a drag moves the picture with the pointer (the pixel that was under the start of the drag is under its end, exactly, at 100 %). `YM_SMOKE_SCALE=2` runs the app at a device scale of 2 (`GDK_SCALE`, a larger Xvfb screen), where the frame is twice the cell and a CSS pixel is two device pixels; `YM_SMOKE_ONLY=geometry` runs just the failure-path folder and its Pick white checks. A drop sent before the Start screen has registered its listener is lost, as it would be for a person who drops that fast, so the runner sends the drop again until the screen reacts. 39 of 39 checks pass at scale 1 and at scale 2 on the nine real files.

### Photos input and desktop feel (M3-16 to M3-19, frontend side)

The owner on 2026-10-16: "UI in Yellowmoon is sluggish. I can select UI text, when I pan photo with two fingers on trackpad - all app moves." The cause was in the page, which behaved like a web page: the two-finger pan was not the photo's (the wheel handler was a React `onWheel`, which React registers as passive, so it could not cancel the default action, and WebKit then rubber-banded the whole window), text could be selected by dragging, and every wheel event, every pointer move and every store tick did work. The decisions that fix it (`docs/15` M3-16 to M3-19; the measuring is in the last item):

- **Wheel.** `usePhotoGestures` (`src/components/usePhotoGestures.ts`, used by `PhotoCell` through its `gestures` prop) adds a native `wheel` listener with `{ passive: false }` to the photo cell and calls `preventDefault()` on **every** wheel event over the cell, at Fit, zoomed, in Crop and in Pick white: the gesture is the photo's first, and only then does the handler decide whether to act. ⌘ or ctrl with the wheel zooms about the pointer by `exp(−deltaY / 100)` (ctrl too, because Chromium and some mice send a pinch as ctrl+wheel); the wheel alone pans by the distance the fingers moved when the photo is larger than the cell (`!store.showsWholePhoto()`); at Fit, in Crop and in Pick white it does nothing. There is **no** wheel listener on `document` or `window`: a non-passive one there makes WebKit's scrolling thread ask the busy web process before each scroll step over the whole window, the tool panel included. A cell without `gestures` (the dev page) leaves the wheel to the page.
- **Pinch.** WebKit sends a trackpad pinch as `gesturestart`, `gesturechange` and `gestureend` with a `scale` since the start, not as ctrl+wheel. The cell zooms about the fingers by `scale / previous scale` and cancels all three. `installDesktopFeel` (`src/desktopFeel.ts`, called from `main.tsx`) cancels the same three events on `window`, so a pinch anywhere else never reaches the browser's own zoom. WKWebView has magnification off, so this is a guard, not the only protection. Whether WKWebView delivers the events at all is a check on a Mac.
- **Nothing else scrolls or bounces.** `html`, `body` and `#root` are `overflow: hidden` with `overscroll-behavior: none` (every screen is a fixed grid whose own boxes scroll), the photo cell is `overscroll-behavior: none`, and every box that scrolls on its own (`.ym-tools__scroll`, `.ym-dialog__body`, `.ym-menu__list`, `.ym-wizard__main`, `.ym-develop-list`, `.ym-step-rail`, `.ym-filmstrip__scroll`) is `overscroll-behavior: contain`: it keeps its own end stop and never hands the rest of a gesture to the page. The filmstrip is a row: `overflow-y: hidden`, it scrolls along and never up and down. `src/styles/desktop.node.test.ts` fails when a rule sets `overflow` to `auto` or `scroll` on a selector that is not in that list, so a new scroller cannot forget it. `overscroll-behavior` needs WebKit 16 (macOS 13, or 12 with Safari updated). On macOS 12 without a Safari update the page may still bounce over the header and the filmstrip; if the Mac check shows it, the same `preventDefault` goes on those two boxes (and still not on `document`). The dev page (`components.html`) scrolls as a whole and says so in `dev.css`.
- **Coalescing.** Wheel, pinch and drag input goes through `store.queueViewportInput` into a `ViewportInputQueue` (`src/state/viewportInputQueue.ts`): pans add up, zooms about the same point (within a pixel) multiply, a different kind or a moved anchor closes the entry so the order is kept, one `requestAnimationFrame` sends what has been collected, and only one `viewport_input` is in flight (later frames merge into one waiting message). A burst of 100 wheel events is one command. `flushViewportInput` sends at once: when a drag ends (pointer up), and before a click-type input (a double click, Pick white) and before a zoom mode chosen from the menu or a key, so these land after the wheel input that came before them (`viewport_input` is answered on a pool of threads, so two commands can overtake each other: this is why there is only one in flight). `setCurrent` and `closeSession` drop what has not been sent. A refusal is reported once (the error bar) and drops what was waiting. The zoom mirror follows once per closed zoom, so once per frame. `store.viewportInput` is the same input sent now, in order (tests, double click, Pick white).
- **Text selection.** `html` is `user-select: none` (and `-webkit-user-select`, `-webkit-touch-callout: none`) with `cursor: default`. Selectable again, with the prefixed property WebKit needs: fields (`input`, `textarea`, `contenteditable`, with the I-beam), the command line and its example, the folder an export goes to, the template problem, the CLI path hint in Preferences, the About text, the error bar's text, the wizard's errors (the Downloads-folder problem and the failed import), the drop zone's notice ("No ARW files in what you dropped."), the Start screen's error line (only the one with `role="alert"`: the same note class also styles static notes, which stay unselectable), the reason over a photo that can't be opened, the file names and notes of the queues, the Look import wizard's file names and explanations, the `.cube` dialog's file names and reasons, and the Info rows of the RAW tab. The photo chip, the camera line, headings, tags and buttons stay unselectable (selecting there fights the pan and the double click). `img` and `a` are `-webkit-user-drag: none`. The CSS test names every selectable class and checks that the markup still uses it.
- **Context menu.** `installDesktopFeel` cancels `contextmenu` unless the target is editable (a field, `contenteditable`) or selectable text (the nearest ancestor with a `user-select` that is not `auto` says `text`), so WebKit's page menu (Reload, Back) never opens over the app, and Copy and Paste still do where they make sense. The right-click Inspect Element is gone with it; in a debug build the web inspector opens with ⌥⌘I.
- **Cursor.** A button is an arrow, as in a Mac app (`button { cursor: default }`, and every component rule that said `pointer` now says `default`). Only link-styled buttons (`LinkButton`, `ResetLink`) and real links keep the pointing hand; the CSS test lists them. A disabled control keeps the arrow; a field the I-beam; the slider, the wheel, the curve and the crop frame their own cursors.
- **What redraws.** The Photos screen no longer follows `render_stats`, the zoom or the export run: the zoom button (`ZoomMenu`), the status text (`StatusText`) and the Export cell (`ExportCellContainer`) read them themselves, and the screen reads the settings of every photo, the export options and the preferences only while the Export panel is open. The tool tabs and `PhotoView` are `memo` with stable callbacks, so a frame, a wheel zoom or an export tile redraws one button or one span. `export_progress` is applied with the other batched events (`later`, 32 ms). The Look tab reads only the number of photos and picks from the session. Pick white's `letterboxed` is a selector that returns a boolean, and only while it is on.
- **Histogram.** The Light and Curve tabs call `store.watchHistogram()` (ref-counted; Light also asks for the middle readout, which the store keeps as `middleReadout`). It asks once at once, then after `render_stats` at most every 200 ms (a throttle, not a debounce: the plot follows a drag, five times a second, and updates once after the last frame), and nothing while nobody watches. Before, every presented frame made a `histogram` and a `sample_pixel` request that the next frame had to wait for. The plot lags a drag by up to 200 ms.
- **Look tiles.** One `IntersectionObserver` for the whole Look tab (`createTileWatch`); each tile has an `inView` flag that goes both ways. Only the tiles in view ask for a picture when the photo's other settings change, and 400 ms after they stop changing (`THUMBNAIL_SETTLE_MS`; before it was 250). A tile that leaves keeps its picture and asks again when it is back, if the settings changed meanwhile. `LazyLookTile` is `memo` with one `onSelect(id)` for the grid, so a tick of the status line redraws no tile and choosing a look redraws two. `store.lookThumbnail` lets two requests run at once (`LOOK_THUMBNAIL_CONCURRENCY`; the core has one foreground worker and a job is never taken off it, so the next frame of the viewport waits behind at most one tile), newest first, in order within a group asked for together. A request that has not started when the photo's settings change (a new key) or the person moves to another photo is dropped and rejects with `Superseded` (`isSuperseded`): `useLookThumbnail` does not count it as a failure, spend a retry on it or ask again. Sections that are folded draw no tiles and observe nothing.
- **Small things.** `PhotoCell` reads the cell's place from the last report (the observer, the window resize, the display scale) on a pointer move or a wheel event and not from `getBoundingClientRect` each time; a cell with no size yet is measured. The updater tells its listeners when the percentage changes, not at each chunk of the download.
- **Measuring (M3-20, frontend side).** `src/perf.ts` is off unless the page was opened with `?perf` (or `?perf=1`; `?perf=0` says no and wins), the shell set `window.__YM_PERF__ = true` before the page ran (it does when the app is started with `YM_PERF`, which is how the Mac viewport job turns it on: it can add no address and fill no storage), or `localStorage.ymPerf` is set; off, it records nothing, `getApi()` returns the plain api and `perfCount` is an empty function. On, it counts late animation frames (more than 24 ms after the one before), the renders of `Photos`, `LookTab` and `LazyLookTile`, the store's notifications (`store.notify`), the events the api delivers (`event.<name>`) and the calls and round trips of every command, and `window.__ymPerf.snapshot()` returns one JSON object (`reset()` starts again). A React development build with `StrictMode` renders twice, so count in a production build or in the tests. Nothing is sent anywhere: it stays in the page.

Checks that need a Mac (`docs/STATUS.md`, M0-H4): the two-finger pan at Fit and zoomed, over the header, the filmstrip, the panel's end stops, a dialog and the zoom menu moves only the intended content; a pinch over the photo zooms it about the fingers and nothing zooms the page; ⌘ and ctrl with the scroll zoom the photo; the panel's momentum scroll works and its end stop bounces inside the panel only; nothing selects by drag, ⌘A, double click on the photo or triple click in the header, and the command line, the CLI path in Preferences, error text and About do.
