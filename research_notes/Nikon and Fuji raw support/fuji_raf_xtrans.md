# Fujifilm RAF decoding and X-Trans demosaicing for an Apache-2.0 raw processor (state: 11 November 2026)

Provenance labels used below:

- **[doc]** stated by the cited page, fetched 2026-11-11.
- **[measured]** read by me on 2026-11-11 from the first bytes / header blocks of CC0 sample files on raw.pixls.us with HTTP range requests and a throw-away parser (no third-party decoder code used). The URL cited is the sample file.

## 1. RAF container structure, CFA header, Fuji IFD, black level and WB

### Takeaway
RAF is a big-endian fixed header with three (offset, length) pairs (JPEG, "CFA header" tag block, CFA data block); on every modern body sampled the CFA data block is itself a little-endian TIFF whose only IFD0 entry points to a private "FujiIFD" (0xf000) holding dimensions, bit depth, strip offset, black level, WB and lens-correction curves. All of it was verifiable directly on CC0 samples, so a clean-room parser is straightforward; the traps are per-mode geometry changes and where white balance lives.

### Cited Findings

**File header (all [measured], identical layout on X-Pro1 2012 through X100VI 2024)**
- Bytes 0–15 are ASCII `FUJIFILMCCD-RAW ` (trailing space); bytes 16–19 are a format version `0201`; bytes 20–27 a camera ID string (e.g. `FF179502` for X-T5, `FA189501` for GFX100 II, `FF116501` for X-Pro1); bytes 28–59 the NUL-padded model name; bytes 60–63 a firmware string (e.g. `0100`). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- At byte 84 there are six big-endian u32: JPEG offset, JPEG length, CFA-header offset, CFA-header length, CFA offset, CFA length. JPEG offset was 148 in all 27 files inspected and the bytes there start `FF D8 FF E1 … Exif` (a full JPEG with EXIF and the Fuji makernote). Example X-T5 lossy: (148, 3847648, 3847948, 22260, 3870208, 24170096). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)
- Big-endian u32 at byte 108 is the compression mode: observed 0, 2 and 3 on the three X-H2 files whose names say Uncompressed, Lossless-Compressed and Compressed. This matches ExifTool's `RAFHeader` index 108 `RAFCompression`: "0 = Uncompressed, 2 = Lossless, 3 = Lossy", and index 60 `FirmwareVersion`. — [X-H2 lossy sample](https://raw.pixls.us/data/Fujifilm/X-H2/Fuji-X-H2-Compressed-Raw.RAF); [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- The u32 at byte 112 repeats the CFA length (e.g. 0x01701c60 = 24124512 on the X-H2 lossy file). [measured] — [X-H2 lossy sample](https://raw.pixls.us/data/Fujifilm/X-H2/Fuji-X-H2-Compressed-Raw.RAF)

**CFA header ("RAF" tag block; big-endian)**
- Layout [measured]: u32 entry count, then entries of u16 tag, u16 length, payload. X-T5 has 16 entries: 0x0100, 0x0110, 0x0111, 0x0112, 0x0113, 0x0115, 0x0117, 0x0118, 0x0119, 0x0130, 0x0131, 0x0141, 0x9650, 0x9651, 0xc000, 0xca00. X-Pro1 has 10: 0x0100, 0x0110, 0x0111, 0x0112, 0x0113, 0x0130, 0x0131, 0x0141, 0x9650, 0xc000. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF)
- ExifTool names [doc]: 0x0100 RawImageFullSize ("includes borders"), 0x0110 RawImageCropTopLeft ("top margin first, then left margin"), 0x0111 RawImageCroppedSize, 0x0115 RawImageAspectRatio, 0x0117 RawZoomActive, 0x0118 RawZoomTopLeft, 0x0119 RawZoomSize, 0x0121 RawImageSize, 0x0130 FujiLayout, 0x0131 XTransLayout, 0x2000–0x2410 WB_GRGBLevels per preset (Auto, Daylight, Cloudy, fluorescents, Tungsten, Flash), 0x2ff0 WB_GRGBLevels, 0x9200 RelativeExposure, 0x9650 RawExposureBias, 0xc000 RAFData. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- **0xc000 is not the pixel data.** On X-T5 it is a 21,984-byte blob inside the CFA header; ExifTool calls it `RAFData` and documents only width/height fields in it. The pixel data is in the separate CFA block located by the file header. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF); [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- Values [measured]: X-T5 0x0100 = (5196, 7872) height-then-width; 0x0110 = (21, 12); 0x0111 = (5152, 7728); 0x0115 = (2, 3). X-Pro1 0x0100 = (3288, 5120), crop (12, 28), cropped (3264, 4896). GFX100 II 0x0100 = (8754, 11808), crop (7, 8), cropped (8736, 11648). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- 0x0130 FujiLayout [measured]: bytes `0c 0c 0c 0c` on every X-Trans file inspected, `0a 0b 09 08` on GFX100 II (Bayer). 0x0131 is absent on GFX100 II. — [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF), [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)
- 0x0131 XTransLayout [measured]: 36 bytes with values 0/1/2. X-T5, X-Pro1 and X-Pro2 (compressed) all give `1 0 2 1 2 0 / 2 1 1 0 1 1 / 0 1 1 2 1 1 / 1 2 0 1 0 2 / 0 1 1 2 1 1 / 2 1 1 0 1 1`: twenty 1s, eight 0s, eight 2s, i.e. 1 = green (20 of 36), 0 and 2 = red/blue (8 each). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)
- dcraw reads tag 0x131 into its 6x6 table in reverse byte order (index `35-c`) and masks each byte with 3; it reads 0x2ff0 as four u16 WB multipliers with an index swap (`c ^ 1`, i.e. stored G,R,G,B). [src-read; dcraw 9.28, 2018] — [dcraw.c mirror](https://raw.githubusercontent.com/ncruces/dcraw/master/dcraw.c)
- **Tag 0x2ff0 was not present in the CFA header of any of the eight files I parsed** (X-T5 x3, X-Pro1, X-Pro2 x2, GFX100 II x2). In those files WB is in the FujiIFD (below). [measured] — [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF), [X-Pro2 sample](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3050.RAF)
- 0x9650 RawExposureBias [measured]: two u16 that read as a signed rational: (65464, 100) = −0.72 EV on X-T5, X-Pro1 and X-Pro2; (65364, 100) = −1.72 EV on the GFX100 II files. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)

**CFA block = TIFF with FujiIFD**
- [measured] On X-Pro1, X-Pro2, X-T5 and GFX100 II the CFA block begins `49 49 2A 00 08 00 00 00` (little-endian TIFF). IFD0 has one entry, tag 0xf000 (type 13 = IFD) pointing to the FujiIFD. So the TIFF-style IFD is not only on "newer" bodies: it is already there on the 2012 X-Pro1. — [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF)
- ExifTool FujiIFD names [doc]: 0xf001 RawImageFullWidth, 0xf002 RawImageFullHeight, 0xf003 BitsPerSample, 0xf007 StripOffsets, 0xf008 StripByteCounts, 0xf00a BlackLevel, 0xf00b GeometricDistortionParams, 0xf00c WB_GRBLevelsStandard, 0xf00d WB_GRBLevelsAuto, 0xf00e WB_GRBLevels, 0xf00f ChromaticAberrationParams, 0xf010 VignettingParams. ExifTool says the FujiIFD is "found in RAF images from some models". — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- [measured] Tags actually present: X-Pro1/X-Pro2 0xf001–0xf010; X-T5 adds 0xf011–0xf014; GFX100 II adds 0xf015 and a tag 0x0008. 0xf004–0xf006, 0xf009 and 0xf011+ are not named by ExifTool. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- [measured] StripOffsets (0xf007) was 2048 in every file, relative to the start of the CFA block (the TIFF base), not to the file. StripByteCounts = CFA length − 2048. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)
- [measured] BlackLevel (0xf00a) has **36 values on X-Trans** (one per 6x6 position; all 1020 on X-T5, all 1022 on X-Pro2, all 255 on the 12-bit X-Pro1) and **4 values on Bayer** (1024 on a 14-bit GFX100 II file, 4096 on a 16-bit one). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF), [GFX100 II 14-bit](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0264.RAF), [GFX100 II 16-bit](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- [measured] WB on X-T5: 0xf00e (WB_GRBLevels) = (302, 625, 497) and 0xf00d (Auto) = (302, 625, 497), three u32 in G, R, B order; 0xf00c (Standard) has 8 values (302, 390, 810, 17, 302, 658, 473, 21), which looks like two (G, R, B, illuminant-code) sets. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)

**Makernote (in the embedded JPEG's EXIF)**
- ExifTool lists the rendering-relevant makernote tags: 0x1400 DynamicRange, 0x1401 FilmMode, 0x1402 DynamicRangeSetting, 0x1403 DevelopmentDynamicRange, 0x104d CropMode (1 = "Full-frame on GFX", 2 = Sports Finder Mode, 4 = Electronic Shutter 1.25x Crop, 8 = Digital Tele-Conv), 0x1051 CropFlag, 0x1052 CropTopLeft, 0x1053 CropSize. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)

### Inferences
- A V1 parser needs only: header (model, compression, three offset pairs), CFA-header tags 0x0100/0x0110/0x0111/0x0130/0x0131/0x9650, and FujiIFD 0xf001–0xf003, 0xf007, 0xf008, 0xf00a, 0xf00e. Everything else can be ignored at first.
- Because 0x2ff0 was missing in all sampled files, a decoder should take WB from FujiIFD 0xf00e and treat 0x2ff0 (and the 0x2000–0x2410 preset set) as a fallback for files that lack the FujiIFD. Which bodies, if any, carry only 0x2ff0 was not established (likely pre-X-series FinePix files, which V1 would exclude anyway).
- "1 = green" in 0x0131 follows from the counts; which of 0/2 is red is not derivable from counts alone. dcraw's reversed read suggests the on-disk order is not simply top-left-first, so the mapping must be confirmed against an oracle render or the embedded JPEG on a colour target, per mode.
- The makernote is reachable only by parsing the embedded JPEG's EXIF, so the RAF path needs a JPEG APP1 walker in addition to the TIFF reader the ARW decoder already has.

### Gaps
- No official Fujifilm specification of RAF exists that I could find; everything above is reverse-engineered or measured.
- Meaning of FujiIFD 0xf004–0xf006, 0xf009, 0xf011–0xf015 and CFA-header 0x0112, 0x0113, 0x0141, 0x9651, 0xca00 is not documented by ExifTool. (0xca00 starts with the ASCII string `X-T5_0100`, so it looks like a model/firmware record.)
- White level is not in any tag found; from memory other decoders use per-camera tables. Not verified.
- The libopenraw wiki page on RAF exists but a search result describes it as saying "apparently no compression is applied", i.e. outdated; I did not fetch it. — [libopenraw Fuji RAF](https://wiki.freedesktop.org/libopenraw/Fuji_RAF)

## 2. Compression variants, the Fuji codec, licences and patents

### Takeaway
There are three payload kinds (uncompressed in two packings, lossless, lossy) and the two compressed kinds share one block-structured codec with a 16-byte stream header. Every implementation found (LibRaw, rawspeed, rawler) descends from Alexey Danilchenko's 2016 code and is LGPL-2.1 (LibRaw also CDDL-1.0); no permissive implementation and no permissive written specification was found, so Yellowmoon needs a documented clean-room process for this codec and it is the main legal and schedule risk in RAF support.

### Cited Findings

**Uncompressed**
- [measured] X-Pro1 (BitsPerSample 12): strip size 25,251,840 bytes = 3288 x 5120 x 1.5, i.e. 12-bit packed. — [X-Pro1 sample](https://raw.pixls.us/data/Fujifilm/X-Pro1/DSCF2131.RAF)
- [measured] X-Pro2 (14-bit): 49,674,240 = 4032 x 6160 x 2; X-T5 (14-bit): 81,805,824 = 5196 x 7872 x 2; GFX100 II (14-bit): 206,734,464 = 8754 x 11808 x 2. These are 16-bit containers. First bytes on X-Pro2 (`2f 06 9a 04 …`) and GFX100 II (`31 04 49 04 …`, about 1073 against a black level of 1024) read as little-endian u16. — [X-Pro2 uncompressed](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3050.RAF), [X-T5 uncompressed](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0023.RAF), [GFX100 II uncompressed](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0264.RAF)
- [measured] **Geometry changes with compression mode on the same body.** X-Pro2 uncompressed: full size (4032, 6160), crop origin (16, 16), and the 0x0131 pattern starts `2 1 1 0 1 1 …`; X-Pro2 lossless: full size (4038, 6048), crop origin (21, 16), pattern starts `1 0 2 1 2 0 …`. Cropped size is (4000, 6000) in both. — [X-Pro2 uncompressed](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3050.RAF), [X-Pro2 lossless](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3051.RAF)

**Compressed stream header (lossless and lossy)**
- [measured] The strip begins with 16 big-endian bytes. X-T5 lossless: `49 53 01 10 0e 14 4c 21 00 1e c0 03 00 0b 03 62`; X-T5 lossy: identical except byte 2 = `00`. Read as: u16 signature 0x4953; u8 = 1 lossless / 0 lossy; u8 raw type 0x10 on X-Trans and 0x00 on GFX100 II (Bayer); u8 bits (14, or 16 on a GFX 16-bit file); u16 height 5196; u16 width rounded up to a block multiple 8448; u16 width 7872; u16 block size 768; u8 blocks per row 11; u16 total lines 866 (= 5196 / 6). X-Pro2 lossless: 8 blocks of 768, 673 lines. GFX100 II lossy: 16 blocks, 1459 lines. — [X-T5 lossless](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0021.RAF), [X-T5 lossy](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [X-Pro2 lossless](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3051.RAF), [GFX100 II lossy](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- LibRaw's decoder reads the same fields and validates them: signature against a constant, raw type 16 = X-Trans / 0 = Bayer, bits must be 12, 14 or 16, block size must be a fixed value. A table of per-block sizes follows the header; in lossy files a table of per-line quantisation bases follows that. Lossless uses one main quantisation table, lossy adds three more with a per-line base. Decoding keeps several line buffers per colour, adaptive "gradient" statistics that choose how many bits to read, and a code made of a run of zero bits followed by a value. [src-read summary; no code copied] — [LibRaw fuji_compressed.cpp](https://raw.githubusercontent.com/LibRaw/LibRaw/master/src/decoders/fuji_compressed.cpp)
- A LibRaw forum answer (older) stated the same byte: "1 for lossless compression (supported) and 0 for unsupported lossy". — [LibRaw forum](https://libraw.org/node/2619)

**Which bodies have which mode (from sample headers, [measured])**
- Lossy mode (value 3) is present on X-T4 (firmware 0100), X-S20, X-H2, X-H2S, X-T5, X100VI and GFX100 II samples. X-Pro2 and X-T3 samples exist only as 0 and 2. — [X-T4 lossy sample](https://raw.pixls.us/data/Fujifilm/X-T4/DSCF0268.RAF), [X-S20](https://raw.pixls.us/data/Fujifilm/X-S20/DSCF2529.RAF), [X-H2S](https://raw.pixls.us/data/Fujifilm/X-H2S/IMG-20221005-0667.raf), [X100VI](https://raw.pixls.us/data/Fujifilm/X100VI/DSCF0076.RAF)
- File sizes on X-T5 (40 MP): uncompressed 82 MB, lossless 41 MB, lossy 27 MB. — [raw.pixls.us X-T5 directory](https://raw.pixls.us/data/Fujifilm/X-T5/)

**Patents**
- A search for Fujifilm patents on the RAF compression scheme found none; it surfaced only US 9,516,197 (Pixspan, lossless compression of CFA raw data, Bayer-oriented), which is not Fujifilm's. — [US9516197 on Google Patents](https://patents.google.com/patent/US9516197)

### Inferences
- CDDL-1.0 is file-level copyleft: a file derived from LibRaw's CDDL code would have to stay CDDL in source form. That fails the "Apache-2.0 source" goal just as the ASF policy forbids Category B source in releases. Taking LibRaw under its CDDL option therefore does not let Yellowmoon port the decoder into an Apache-2.0 crate; at most a CDDL-licensed separate binary could be linked, which the project's own rule 1 does not contemplate. This is my reading of the policy text, not legal advice.
- The Yellowmoon rule ("may read to understand a format, then write your own implementation") covers the container and the stream header, which are facts. The entropy coder and adaptive tables are more algorithm than format; a defensible process is two-step: one pass writes a prose specification (bit layout, table construction rules, update rules), a separate pass implements only from that prose, with LibRaw/rawler run as a CI oracle for bit-exact comparison on raw.pixls.us samples. Lossless output is bit-exact by definition, and lossy decoding is deterministic, so oracle equality is a complete test.
- The August 2026 rawspeed PR is evidence that an LLM-assisted *port* of LGPL code is how others did it; that is exactly what Yellowmoon must not do.
- No patent search here amounts to freedom-to-operate. The codec has shipped in LGPL libraries since 2016 and in commercial converters without any reported assertion that I found, which lowers but does not remove the risk.

### Gaps
- The 2020 "Fabian" write-up of the lossless algorithm: I could not locate its URL or its licence. If it is an independent prose description it would be the best clean-room input. Needs a manual look at the pixls.us thread.
- Under what terms Danilchenko first published his code (before LibRaw integration) was not found. The only licence statements located are the LGPL-2.1/CDDL-1.0 header in LibRaw and LGPL in rawspeed/rawler. FastRawViewer and fujirumors pages from 2016 exist but were not fetched. — [FastRawViewer note](https://www.fastrawviewer.com/node/245), [fujirumors 2016](https://www.fujirumors.com/libraw-fujifilm-x-pro2-compressed-raw-support-completed/)
- No Fujifilm-published description of the codec was found.
- Whether rawspeed PR #985 has been merged since August 2026 was not checked.
- No proper patent database search (Fujifilm assignee, RAW coding) was done; the X-Trans CFA layout itself is patented by Fujifilm as far as I recall, but I did not verify numbers or expiry, and a CFA patent does not obviously read on software that demosaics the data.

## 3. Which bodies are X-Trans, which are Bayer, bit depth, sensor makers, exclusions, PDAF

### Takeaway
All X-Trans generations share one 6x6 layout (the pattern bytes are identical from X-Pro1 to X-T5), so demosaic code is body-independent once the phase offset is read per file; GFX and the X-A/X-T100/X-T200 lines are Bayer and could ride the existing Bayer pipeline once RAF decoding exists. Sensor part numbers and sharing with Sony bodies rest on 2018-era secondary reporting only.

### Cited Findings

### Inferences
- Shared silicon with Sony bodies does not give shared colour: the CFA dyes (and on X-Trans the layout) are Fujifilm's, so the Weta/rawtoaces Sony spectral curves that the V1 data rule relies on do not transfer to Fuji bodies, even if the GFX100 and Sony A7R IV class sensors share a pixel design. Fuji support needs its own published spectral data or a matrix-based fallback; that is a V1 data-rule question for the owner, separate from decoding.
- A sensible V1 Fuji scope is: X-Trans I–5 APS-C bodies plus Bayer GFX and X-A/X-T100/X-T200; exclude everything with a non-square-grid legacy layout (Super CCD, EXR, SR families) and 2/3-inch compacts.
- PDAF handling for X-Trans is best treated as a known limitation in V1 (document it) rather than solved.

### Gaps
- I did not find a single authoritative table mapping every body to CFA/bit depth. From memory, not verified this session: all GFX bodies (50S, 50R, 50S II, 100, 100S, 100 II, 100S II, 100RF) are Bayer; X-A1…X-A7, X-A10/X-A20, X-T100, X-T200, XF10 and X half are Bayer; X70 uses the APS-C X-Trans II sensor (the Wikipedia extract placed it ambiguously); X-Trans I/II are 12-bit (measured only for X-Pro1) and III onwards 14-bit; GFX 50 series is 14-bit and 100 MP bodies offer 16-bit.

- Details of Super CCD / EXR / SR raw layouts were not researched (out of scope for V1); only their existence in the sample archive and dcraw's special path were confirmed.
- Exact PDAF row/pixel positions per X-Trans generation are not documented in any source found.

## 4. X-Trans demosaicing: algorithms, licences, learned methods, training data

### Takeaway
The standard classical method (Markesteijn 1-pass/3-pass) originates in dcraw, where it sits outside the "RESTRICTED" block and is therefore under dcraw's "free for all uses" terms, but Yellowmoon's own rule lists dcraw as do-not-copy, so it would still need a clean reimplementation or an owner decision. For a learned demosaicer the path is clear: Gharbi et al.'s code is MIT and has an X-Trans variant, training mosaics can be synthesised from RGB, and RawNIND supplies 677 real X-Trans raws but under CC BY-SA 4.0 with GPL-3/CC-BY-4.0 weights.

### Cited Findings

**Pattern**
- X-Trans is a 6x6 repeating layout against Bayer's 2x2; every row and column contains R, G and B within six pixels; the design is meant to remove the need for an optical low-pass filter. — [Wikipedia: Fujifilm X-Trans sensor](https://en.wikipedia.org/wiki/Fujifilm_X-Trans_sensor)
- [measured] Per 6x6 tile: 20 green, 8 of one chroma colour and 8 of the other (55.6% / 22.2% / 22.2%, against Bayer's 50/25/25). The tile contains 2x2 solid green blocks (e.g. rows 2–3, columns 2–3 of the stored pattern). — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF)
- [measured] The pattern's phase relative to the raw origin differs between files of the same camera (X-Pro2 compressed vs uncompressed), so it must be read per file, then shifted by the crop origin. — [X-Pro2 uncompressed](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3050.RAF), [X-Pro2 lossless](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3051.RAF)

**Markesteijn**
- dcraw 9.28 contains `xtrans_interpolate(int passes)` under the comment "Frank Markesteijn's algorithm for Fuji X-Trans sensors"; it works in 512-pixel tiles and uses a CIELab conversion. It is at line ~4647; the block marked "RESTRICTED code starts here / ends here" spans lines 3046–3748 (Foveon). [src-read] — [dcraw.c mirror](https://raw.githubusercontent.com/ncruces/dcraw/master/dcraw.c)
- dcraw's licence header: "No license is required to download and use dcraw.c. However, to lawfully redistribute dcraw, you must either (a) offer … full source code for all executable files containing RESTRICTED functions, (b) distribute this code under the GPL Version 2 or later, (c) remove all RESTRICTED functions … or (d) purchase a license from the author. The functions that process Foveon images have been RESTRICTED since Revision 1.237. All other code remains free for all uses." (Revision 1.478, 2018/06/01.) — [dcraw.c mirror](https://raw.githubusercontent.com/ncruces/dcraw/master/dcraw.c)
- darktable, dcraw, UFRaw and RawTherapee are all reported to use Markesteijn's algorithm; RawTherapee's documentation says "concerning X-Trans cameras, 3-pass (Markesteijn) is generally the best method". — [xtransdemosaicking blog](https://xtransdemosaicking.blogspot.com), [RawPedia: Demosaicing](https://rawpedia.rawtherapee.com/Demosaicing)

**Learned demosaicers**
- Gharbi, Chaurasia, Paris, Durand, "Deep Joint Demosaicking and Denoising" (SIGGRAPH Asia 2016): both the PyTorch repo and the older Caffe repo are MIT ("Copyright (c) 2016 Michael Gharbi"). — [demosaicnet LICENSE](https://raw.githubusercontent.com/mgharbi/demosaicnet/master/LICENSE), [demosaicnet_caffe LICENSE.md](https://raw.githubusercontent.com/mgharbi/demosaicnet_caffe/master/LICENSE.md)
- The Caffe repo documents an X-Trans model: "For results on the Xtrans mosaick" with `--model pretrained_models/xtrans`, and says there are three pretrained models (bayer, bayer_noise, xtrans). The repo is marked outdated in favour of the PyTorch one, whose README says the noise-aware model is not implemented there. The training set is offered via a download script / dataset page. — [demosaicnet_caffe](https://github.com/mgharbi/demosaicnet_caffe), [demosaicnet](https://github.com/mgharbi/demosaicnet)
- The project page says the training set was built by "mining community photographs for difficult patches". — [demosaicnet project page](https://groups.csail.mit.edu/graphics/demosaicnet/)
- An IPOL article (2019) reviews neural demosaicking for both Bayer and X-Trans and notes that for X-Trans the input is not downsampled, so the architecture differs from the Bayer version (which packs 2x2 into channels). — [IPOL 2019 article 274](https://www.ipol.im/pub/art/2019/274/article.pdf)
- X-veon (posted 20 Feb 2026): neural X-Trans demosaic running in the browser on WebGPU, ONNX weights in the repo, trained on about 2000 of the author's own images with a **simulated CFA** and noise augmentation, 20–30 hours on an M4 Pro; a batch-norm-free variant reached 47.31 dB PSNR; under a minute for 24 MP on an M1 Pro; artefacts remain around night street lamps; **no licence at posting** ("I'll pick the most permissive one"). — [pixls.us X-veon thread](https://discuss.pixls.us/t/x-veon-a-better-demosaic-for-x-trans-100-less-worms/56196)
- neural-demosaic by Danylo Kelvich (12 Jun 2026): "a small neural network", checkpoint about 630 KB in float32, trained on 70 raw images in 15 minutes on a MacBook, about 0.6 s for a 40 MP image, claimed to "quickly outperform Markesteijn (the OpenCL implementation from darktable)" on the author's data, shown by a comparison image without metrics; licence not stated in the post. — [pixls.us fast neural demosaic thread](https://discuss.pixls.us/t/fast-neural-demosaic-for-x-trans/58588)

**RawNIND**
- Paper: Brummer and De Vleeschouwer, "Learning Joint Denoising, Demosaicing, and Compression from the Raw Natural Image Noise Dataset", arXiv 2501.08924 (v2, 20 Jun 2025); it proposes one model on raw Bayer data and one on linear RGB "for better generalization across sensors". — [arXiv 2501.08924](https://arxiv.org/abs/2501.08924)
- Dataset record (UCLouvain Dataverse, doi:10.14428/DVN/DEQCIM, version 1, released 2025-01-15): licence field **CC-BY-SA-4.0**; 2,845 files of which 1,784 ARW, **677 RAF**, 298 CR2, 60 NEF, 15 CRW, 6 DNG; 2,164 filenames start with `Bayer_` and 678 with `X-Trans_` (e.g. `X-Trans_banana_GT_ISO200_…raf`, `X-Trans_banana_ISO6400_…raf`: clean ground truth plus noisy ISO series per scene). — [Dataverse API record](https://dataverse.uclouvain.be/api/datasets/:persistentId/?persistentId=doi:10.14428/DVN/DEQCIM)
- Code repo `trougnouf/rawnind_jddc` is GPL-3; README: "The weights are dual licensed GPL3 + CC-BY-4.0". — [rawnind_jddc README](https://raw.githubusercontent.com/trougnouf/rawnind_jddc/main/README.md), [rawnind_jddc LICENSE](https://raw.githubusercontent.com/trougnouf/rawnind_jddc/main/LICENSE)
- The predecessor NIND dataset is hosted on Wikimedia Commons and "most images are taken with a Fujifilm X-T1 and XF18-55mm". — [Wikimedia Commons: Natural Image Noise Dataset](https://commons.wikimedia.org/wiki/Natural_Image_Noise_Dataset)

### Inferences
- Synthesising X-Trans mosaics from linear RGB is established practice: Gharbi's X-Trans model and X-veon both train on simulated CFAs. Mechanically it is a 6x6 mask applied to a clean linear image, plus a noise model. So Yellowmoon's existing Bayer training set (clean linear RGB targets) can be re-mosaiced to X-Trans with no new captures, which fits the V1 "no own measurements" rule. The real-data question is only validation and noise realism.
- Architecture consequence: the usual Bayer trick (pack 2x2 into 4 half-resolution channels) does not carry over. Options are full-resolution input with a 36-phase position encoding or colour-mask channels (the IPOL observation), or a 6x6 pixel-unshuffle into 36 channels at 1/6 resolution. A single CFA-conditioned network (mask as input) could serve both Bayer and X-Trans; I found no permissively licensed, published pattern-agnostic model to cite, so that is a design option, not a finding.
- Licence fit: Gharbi code and weights (MIT) are usable. RawNIND data is CC BY-SA 4.0: training on it is a question of whether weights are a derivative "adaptation" (unsettled); the conservative reading for an Apache-2.0 project that commits weights is to use RawNIND X-Trans frames for validation/metrics only, or to get the owner's decision. The RawNIND pretrained weights' CC-BY-4.0 option is compatible with shipping alongside Apache-2.0 code with attribution, but those models target Bayer and linear-RGB inputs, not X-Trans mosaics.
- Markesteijn under dcraw's terms looks permissive ("free for all uses"), but (a) it is an informal licence, not an SPDX one, (b) AGENTS.md names dcraw explicitly as never-copy. Independent reimplementation from a prose description, or skipping classical Markesteijn entirely in favour of a learned demosaicer plus a simple bilinear CPU reference, both stay inside the rules.
- Two 2026 hobby projects reaching "better than Markesteijn" with tiny models (630 KB; 15 minutes of training) suggest the quality bar for a small learned X-Trans demosaicer is reachable; both claims are self-reported and visual only.

### Gaps
- Markesteijn's own statement of terms (outside dcraw) was not found; nor whether LibRaw/RawTherapee/darktable versions add LGPL/GPL-only modifications (they are in GPL/LGPL trees and are off-limits either way).
- The Gharbi dataset's licence/terms were not found (the photos were mined from online "community photographs", so redistribution rights are doubtful). Whether the pretrained `xtrans` Caffe weights are still downloadable was not checked. The paper's X-Trans PSNR numbers against Markesteijn were not retrieved (the IPOL PDF exceeded the fetch limit).
- Current licences of `naorunaoru/x-veon` and `danylo-kelvich/neural-demosaic` repos were not checked at the repositories.
- Which camera(s) shot the 677 RawNIND RAFs (probably X-T1, by analogy with NIND) is not confirmed; if all are 16 MP X-Trans II, they do not cover 26/40 MP sensors' noise.
- Academic non-learned X-Trans methods and "linear filter" approaches were not surveyed with sources. A search hit points to an NSF-archived paper on X-Trans demosaicking that I did not read. — [NSF PAR 10342459](https://par.nsf.gov/servlets/purl/10342459)
- No open-licence (CC0/CC BY) dataset of X-Trans raws with ground truth was found other than raw.pixls.us singles (CC0, no ground truth) and RawNIND (CC BY-SA).

## 5. How Apple, Adobe, Capture One, Iridient and open-source tools treat X-Trans; quality bar

### Takeaway
"Worms" and smeared fine colour detail in Adobe's default X-Trans demosaic are the reference failure users know; Adobe's ML "Enhance Details" largely fixed it at a speed cost, and Capture One/Iridient are regarded as roughly equal to it. Apple's system RAW engine now lists every current Fuji body with no compression footnote, which matters for a macOS app because it sets the baseline users get for free.

### Cited Findings
- Apple's "Digital camera RAW formats supported by iOS 26, iPadOS 26, macOS Tahoe 26 and visionOS 26", stated current as of September 2026, lists Fujifilm GFX 100, 100 II, 100RF, 100S, 100S II, 50R, 50S, 50S II; X-A1/A2/A3/A5/A7/A10/A20; X-E1…X-E5; X-H1, X-H2, X-H2S; X-M1, X-M5; X-Pro1/2/3; X-S10, X-S20; X-T1…X-T5, X-T10/20/30/30 II/30 III, X-T50, X-T100, X-T200; X100F/S/T/V/VI; X20, X30, X70, XF1, XF10, XQ1, XQ2; FinePix F600EXR, HS20EXR, S2Pro, S3Pro, S5Pro, SL1000, X100. The page defines footnotes such as "Lossless RAW format only" and "Lossless compressed format only", and none is attached to a Fujifilm entry. — [Apple Support 122870](https://support.apple.com/en-us/122870)
- Contrast: an Apple Communities thread from 2024 says "The latest versions of macOS, iOS and iPadOS still do not support compressed Fujifilm RAW photos (.RAF). Uncompressed .RAF files are supported." — [Apple Communities 255613945](https://discussions.apple.com/thread/255613945)
- Apple adds cameras per OS release and does not back-port to older systems; users can check local support in System Information > Software > Raw Support. — [Apple Communities 254378697](https://discussions.apple.com/thread/254378697)
- Adobe: before 2019, Lightroom's RAF rendering showed worm-like artefacts once sharpening passed a threshold, "no such things" on Canon/Nikon/Sony; a reviewer said Enhance Details "resolves all the issues for X-Trans, no more smearing in fine details, no more edge artifacts and wormy artifacts", but that it is slow and not recommended for batches. — [Fujirumors: Enhance Details tested](https://www.fujirumors.com/lightroom-enhanced-details-for-fujifilm-x-trans-files-tested-fuji-users-beware-wormy-artifacts-fixed), [The Phoblographer, Feb 2019](https://www.thephoblographer.com/2019/02/13/adobe-figures-out-how-to-handle-x-trans-raw-files-its-about-time/)
- Comparisons: one tester found Capture One and Lightroom-with-Enhance "pretty close … quite subjective"; another that Enhance "does a better job than X-Transformer, but you should still use X-Transformer if you have an older and slower GPU"; Iridient results "very close to Capture One". — [Thomas Fitzgerald, Mar 2019](https://blog.thomasfitzgeraldphotography.com/blog/2019/3/do-you-still-need-to-use-x-transformer), [Thomas Fitzgerald, Jul 2025](https://blog.thomasfitzgeraldphotography.com/blog/2025/7/the-best-way-to-process-fujifilm-x-trans-files-in-lightroom-in-2025)
- Users still file Adobe reports like "why does my Fuji raw X-T30 file look like a painting when viewed at 400%". — [Adobe Community bug report](https://community.adobe.com/bug-reports-711/why-does-my-fuji-raw-x-t30-file-look-like-a-painting-when-viewed-at-400-657349)
- Open source: darktable and RawTherapee use Markesteijn (3-pass recommended in RawTherapee); the X-veon author's pitch is "100% less worms" and that DxO PureRAW over-filters. — [RawPedia: Demosaicing](https://rawpedia.rawtherapee.com/Demosaicing), [pixls.us X-veon thread](https://discuss.pixls.us/t/x-veon-a-better-demosaic-for-x-trans-100-less-worms/56196)
- darktable is "camera-agnostic": it does not act on Fuji-specific crop, dynamic-range or film-simulation metadata by default, which is why Fuji raws can look underexposed there. — [onecameraonelens.com, Feb 2023](https://onecameraonelens.com/2023/02/18/fujifilm-raw-files-and-why-they-can-look-underexposed-in-darktable/)

### Inferences
- The acceptance bar for Yellowmoon's X-Trans output, in user terms: no worm/maze texture in foliage and fine texture after normal sharpening, no "watercolour" smearing of low-contrast colour detail, no false-colour fringes on high-contrast edges, and no visible 6-pixel periodicity in flat areas. Matching Markesteijn 3-pass is the open-source baseline; matching Adobe Enhance / Capture One is what Fuji users compare against.
- Apple's list having no Fuji footnote in 2026, against the 2024 forum statement, implies Apple added compressed RAF decoding between those dates; I did not find a release note saying so, and the absence of a footnote is not a positive statement.
- CIRAWFilter could serve as an additional macOS-only visual reference, but not as a CI oracle (not available on Linux runners) and never as part of the product path (rule 6: one Rust core).

### Gaps
- Adobe's own description of Enhance / Raw Details (ML model, claimed resolution gain, DNG output, Bayer and X-Trans coverage) could not be fetched: the helpx page returned HTTP 403. Not cited.
- Nothing from Apple documents how Core Image demosaics X-Trans or its quality; no developer documentation on X-Trans in CIRAWFilter was found.
- Capture One and Iridient algorithms are proprietary and undocumented; only reviewer impressions exist. No quantitative, independent 2025–2026 comparison across converters was found.

## 6. Fuji rendering metadata: film simulation, dynamic range, lens corrections

### Takeaway
DR200/DR400 files are deliberately underexposed by one or two stops and a converter must compensate using `DevelopmentDynamicRange` (makernote 0x1403) and/or `RawExposureBias` (RAF 0x9650); the tags are named by ExifTool but their semantics are community knowledge. Lens corrections are stored as sampled radial curves in FujiIFD 0xf00b/0xf00f/0xf010 and have been reverse-engineered by darktable, with no official description.

### Cited Findings
- DR modes: Fujifilm's DR200/DR400 reduce exposure by one or two stops and raise the tone curve to compensate; a converter that ignores this shows the raw one or two stops dark. — [pixls.us X-T2 underexposed thread](https://discuss.pixls.us/t/fujifilm-x-t2-raw-underexposed-in-darktable-at-iso-400-and-higher/13581), [jmpeltier.com 2018](https://www.jmpeltier.com/2018/07/01/fujifilm-dynamic-range-settings/)
- Tags [doc]: makernote 0x1400 DynamicRange (1 = Standard, 3 = Wide), 0x1402 DynamicRangeSetting (0 = Auto, 1 = Manual, 0x100 = Standard (100%), 0x200 = Wide1 (230%), 0x201 = Wide2 (400%), 0x8000 = Film Simulation), 0x1403 DevelopmentDynamicRange (no notes); RAF 0x9650 RawExposureBias, 0x9200 RelativeExposure. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- Example values from a forum post: a DR400 frame shows "Development Dynamic Range: 400" and "Raw Exposure Bias: -2.7"; a DR100 frame shows −0.7. — [pixls.us X-T1 default processing thread](https://discuss.pixls.us/t/need-help-figuring-out-x-t1-default-dt-processing/32136/9)
- [measured] The DR100-looking baseline is confirmed: X-T5, X-Pro1 and X-Pro2 samples all have RawExposureBias = −0.72 EV; the GFX100 II samples have −1.72 EV. — [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- darktable handles this through a Lua script (`fujifilm_auto_settings`) that reads Development Dynamic Range and applies a +1 or +2 EV style; darktable issue 7705 proposes folding the DR shift into exposure-bias compensation. — [bastibe.de darktable posts](https://bastibe.de/tag-darktable.html), [darktable issue 7705](https://github.com/darktable-org/darktable/issues/7705)
- Film simulation: makernote 0x1401 FilmMode with enumerated values, e.g. 0x0 = F0/Standard (Provia), 0x600 = Classic Chrome, 0x800 = Classic Negative, 0xb00 = Reala ACE. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- Lens corrections: FujiIFD 0xf00b GeometricDistortionParams, 0xf00f ChromaticAberrationParams, 0xf010 VignettingParams. An ExifTool forum thread reports GeometricDistortionParams "contains 23, 35 or 43 rational64s values" described as "curves of lens distortions" with radius-versus-correction pairs. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html), [ExifTool forum msg 46583](https://exiftool.org/forum/index.php?msg=46583)
- [measured] Counts (type 10 = signed rational): X-Pro1 and X-Pro2: distortion 23, CA 31, vignetting 23. X-T5 and GFX100 II: distortion 19, CA 29, vignetting 19. — [X-Pro2 sample](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3051.RAF), [X-T5 sample](https://raw.pixls.us/data/Fujifilm/X-T5/DSCF0022.RAF), [GFX100 II sample](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- darktable's lens correction module has an "embedded metadata" method; a user notes "you have to reverse engineer the metadata embedded in the raw files and figure out the formula being used". Corrections are present when the camera recognises the lens; adapted third-party lenses may have none. — [pixls.us embedded metadata lens correction](https://discuss.pixls.us/t/embedded-metadata-lens-correction/49649), [pixls.us focal length thread](https://discuss.pixls.us/t/lens-correcting-not-detecting-correct-focal-length-and-aperture/47301)

### Inferences
- Counts fit "1 header + N knots + N values per curve": 23 = 1 + 11 + 11 and 19 = 1 + 9 + 9 for distortion and vignetting; 31 = 1 + 10 + 10 + 10 and 29 = 1 + 9 + 9 + 9 + 1 or similar for CA (two channels, red and blue). This is my arithmetic guess; the exact layout must be confirmed against darktable's behaviour as an oracle before relying on it.
- Compensation rule a V1 could adopt: exposure gain = −(RawExposureBias − baseline), where the baseline is about −0.7 EV, or equivalently log2(DevelopmentDynamicRange / 100) stops. The two agree in the forum example (−2.7 vs −0.7 = 2 stops for DR400). Since Yellowmoon renders through its own ALEV-style pipeline, only the exposure offset matters; the highlight shoulder Fuji applies in camera is irrelevant.
- The GFX100 II samples at −1.72 EV are probably DR200 shots (one stop below the −0.72 baseline); unverified without reading their makernote.
- Film-simulation tags are useful to Yellowmoon only as metadata display; the product's look is its own.

### Gaps
- The ExifTool forum was down ("server can't handle the load") when fetched, so the lens-parameter layout is from a search snippet only. The darktable implementation (GPL) was not read.
- Whether RawExposureBias also includes the user's exposure-compensation dial or highlight-tone settings is not established; the −0.72 baseline's meaning is undocumented.
- `D Range Priority` modes and their tags were not researched.
- Units and normalisation of the lens curves (radius relative to image circle or half-diagonal; percent vs ratio) are unknown here.

## 8. Implementation effort and pitfalls

### Takeaway
Container parsing and uncompressed decode are small (days) and fully testable from CC0 samples; the compressed codec and X-Trans demosaic (including a CPU reference, GPU kernel and a retrained model) are the two large items, and colour profiles for Fuji bodies are a separate blocker under the V1 data rule. This section is mostly inference.

### Cited Findings
- Decoder maintenance elsewhere is a single-maintainer bottleneck: "RawSpeed, rawler, and libopenraw all share a single-maintainer bottleneck" (kmilos, Aug 2026); lossy RAF sat unsupported in rawspeed/darktable from the X-T4 era until at least Aug 2026. — [pixls.us "For Fuji cameras users"](https://discuss.pixls.us/t/for-fuji-cameras-users/60257)
- Even with decoding done, LibRaw's X-T5 input colour profile was reported inaccurate in 2023, i.e. per-body colour data lags decoding. — [pixls.us thread 38811](https://discuss.pixls.us/t/any-existing-work-on-fuji-raf-lossy-compression-decoding/38811)
- Pitfalls confirmed on samples: different raw size, crop origin and CFA phase between compression modes of one camera (X-Pro2); 36 vs 4 black levels; 12-bit packed vs 16-bit little-endian containers inside a big-endian file; bit depth varying per file on GFX (14/16); strip offset relative to the TIFF base; WB only in the FujiIFD. — [X-Pro2 uncompressed](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3050.RAF), [X-Pro2 lossless](https://raw.pixls.us/data/Fujifilm/X-Pro2/_DSF3051.RAF), [GFX100 II 16-bit](https://raw.pixls.us/data/Fujifilm/GFX100%20II/_DSF0265.RAF)
- Makernote crop modes exist (GFX "full-frame" 35 mm crop, sports finder, 1.25x electronic-shutter crop, digital teleconverter), so the active area is not always the 0x0110/0x0111 rectangle. — [ExifTool FujiFilm tags](https://exiftool.org/TagNames/FujiFilm.html)
- PDAF-related artefacts exist on both X-Trans (purple grid in flare) and GFX100 (banding). — [PetaPixel 2017](https://petapixel.com/2017/02/23/fuji-cameras-produce-strange-purple-flaregrid-artifact/), [Fujirumors GFX100 PDAF banding](https://www.fujirumors.com/fujifilm-gfx100-phase-detection-pixel-banding-and-pixel-shift-multishot-solution)

### Inferences (effort relative to the existing Bayer-only, TIFF-based ARW decoder; my estimates, not sourced)
- Container + CFA header + FujiIFD + JPEG/EXIF makernote walk: small, roughly 0.3x of the ARW container work, because the TIFF reader is reusable.
- Uncompressed payloads (12-bit packed, 16-bit LE): small; pure bit unpacking with oracle tests.
- Lossless + lossy Fuji codec: the largest decode item, comparable to or larger than Sony's compressed ARW paths. One codec covers both modes (lossy adds per-line quantisation tables and a dequantise step). Clean-room discipline roughly doubles the calendar time compared with a port. Must be bit-exact against LibRaw/rawler in CI; parallel per-block decode is natural because blocks are independent strips (11 on X-T5, 16 on GFX100 II).
- X-Trans demosaic: new CPU reference (f64), new GPU kernel with parity test, new or retrained model, new golden images. The Bayer learned demosaic/denoise models do not apply to X-Trans mosaics. Training data can be re-mosaiced from the existing clean RGB set; the noise model needs Fuji parameters (public noise priors only, per the V1 rule).
- Bayer Fuji bodies (GFX, X-A) reuse the existing demosaic and models once decoded, so "GFX first" is the cheapest way to ship some RAF support: container + uncompressed + codec, no X-Trans work.
- Colour: no Fuji bodies are in the Weta/rawtoaces Sony set that V1 relies on, so RAF support needs either published Fuji spectral sensitivities (not researched here) or a matrix fallback, which changes the product's "spectral emulation" claim for those bodies. This needs an owner decision and is likely the real gating item, not the decoder.
- Per-camera tables still needed and not in the file: white level, any per-body crop quirks, colour matrices.
- Determinism: lossy RAF decode is integer and deterministic, so rule 8 is satisfiable; a learned X-Trans demosaicer must keep the same CPU/GPU parity discipline as the Bayer one.

### Gaps
- No implementer post-mortem with time figures for writing a RAF decoder was found; effort numbers above are my judgement.
- Decode speed targets (e.g. LibRaw/rawler throughput on 40 MP lossless) were not measured.
- Pixel-shift multi-shot RAFs, HEIF/JPEG-only modes, in-camera crop/"digital teleconverter" RAFs, and X-Trans files from the 2/3-inch compacts were not examined.
- Availability of published spectral sensitivity data for any Fujifilm body was not researched (belongs to the colour workstream).
